- ai설명
    
    **프로젝트로서의 방향은 적합해. 다만 기존 설계 그대로라면 “스캐너 여러 개를 연결하고, 샌드박스에서 실행하고, 사례를 모았다”는 결과에 머물 위험이 있어.** 부족한 것은 기능의 수가 아니라, **무엇을 취약점으로 판정할지, 무엇을 자체 기여로 삼을지, 그 효과를 어떻게 검증할지**에 대한 기준이야.
    
    수정안의 중심은 다음으로 잡는 것을 추천해.
    
    > **MCP·Skills의 위험 후보를 발굴하고, 특정 버전·권한·실행 조건에서 실제 보안 경계 위반이 발생하는지 검증하며, 원인과 수정 효과까지 추적하는 연구용 프레임워크.**
    > 
    
    중요한 것은 **취약점 발굴을 계속 핵심 목표로 두되, 도구 개발은 발굴과 검증을 지원하도록 설계하는 것**이야. 아래의 규모와 기능은 제안하는 설계 기준이지, 이미 달성한 성능이나 발견할 취약점 수를 의미하지 않아.

    # 1. 기존 프로젝트 평가
    
    ## 종합 판단: 방향은 유지하고, 핵심 기여와 판정 구조를 수정해야 한다
    
    | 평가 항목 | 기존 설계의 장점 | 부족한 부분 | 보완 방향 |
    | --- | --- | --- | --- |
    | **문제 선정** | 실제 취약점 발굴과 검증을 연결한다 | ‘수상한 행동’과 ‘취약점’의 구분이 충분히 구체적이지 않다 | 공격자 권한·보안 계약·실행 증거를 함께 판정 |
    | **차별성** | 기존 스캐너를 활용해 개발 범위를 줄인다 | 실행 테스트 자체도 이미 존재한다 | 버전·정책·실행 증거·패치 결과를 연결하는 검증 방식으로 구체화 |
    | **범위** | MCP와 Skills의 연결을 다룬다 | 여러 언어·호스트·공격 유형을 동시에 지원하려 한다 | 공통 수집은 넓게, 동적 검증은 제한된 환경부터 |
    | **발굴 방식** | 실제 공개 프로젝트를 조사한다 | 스캐너 경고에 의존하면 기존 미탐을 그대로 놓친다 | 경고 기반 조사와 독립적인 코드·변경 조사를 병행 |
    | **실행 검증** | 실제 파일·네트워크·프로세스 동작을 본다 | 환경 차단 때문에 취약점이 가려지거나, 정상 기능을 취약점으로 오인할 수 있다 | 실험실 보호 정책과 검증 대상의 정책을 분리 |
    | **공급망 분석** | 패키지와 버전을 기록한다 | 단순 실행 테스트에 치우쳐 공급망 요소가 약하다 | 실제 배포물·참조 파일·의존성·업데이트를 증거에 연결 |
    | **평가** | 정밀도·재현율·대조군을 고려한다 | 정답의 독립성, 표본 편향, 검증 실패 처리 방식이 부족하다 | 독립 정답 판정, 그룹 단위 분리, 판단 보류율 공개 |
    | **역할 분담** | 네 명의 담당 영역이 있다 | 한 명에게 실행 환경·검증·평가가 몰릴 수 있다 | 실행 인프라와 판정·평가를 분리 |
    | **성과 관리** | CVE 개수에만 의존하지 않는다 | 도구가 동작하기만 해도 성공한 것처럼 보일 여지가 있다 | 구현 완료와 연구 기여를 별도로 평가 |
    
    특히 **“기존 도구는 정적 분석만 하므로 우리는 동적 분석을 한다”는 차별화 주장은 사용하면 안 돼.** Cisco MCP Scanner는 설명과 구현의 불일치 및 파일 간 데이터 흐름을 분석하고, Promptfoo는 MCP 직접 호출 테스트와 에이전트 경유 테스트를 모두 제공해. 자체 기여는 그보다 구체적으로 정의해야 해. [GitHub](https://github.com/cisco-ai-defense/mcp-scanner)

    # 2. 수정된 프로젝트의 정체성
    
    ## 프로젝트명
    
    ### **MCP·Skills 공급망의 보안 경계 위반 검증 및 취약점 발굴 프레임워크**
    
    ### 프로젝트가 답할 핵심 질문
    
    > **“이 패키지가 위험해 보이는가?”가 아니라, “어떤 구성과 입력에서 어떤 보안 경계가 실제로 깨지며, 그 원인이 어느 구성요소에 있는가?”**
    > 
    
    주 사용자는 일반 소비자보다 **취약점 연구자, 보안 검토자, MCP·Skills 유지보수자**로 잡는 편이 좋아. 처음부터 누구나 파일을 올려 안전 점수를 받는 서비스까지 만들 필요는 없어.
    
    ### 자체 기여는 세 가지로 고정한다
    
    **첫째, 실행 증거 기반 검증.**
    
    경고를 실제 실행과 연결하고, 위반 확인·미재현·판단 불가를 구분한다.
    
    **둘째, 구성과 변경에 대한 추적.**
    
    발견 결과를 특정 패키지·참조 파일·의존성·도구 설명·호스트 설정에 연결하고, 수정 전후에 재검증한다.
    
    **셋째, 독립적인 실증 분석.**
    
    기존 도구가 놓친 문제, 잘못 경고한 문제, 검증할 수 없었던 문제를 원인별로 분석한다.
    
    이 조합이 학술적으로 새로운지는 별도의 선행연구 비교로 확인해야 해. **‘세계 최초’를 전제로 하지 않아도 보안 프로젝트는 성립하지만, 기존 도구에 없는 기능이라고 주장하려면 직접 비교가 필요해.**
    
    ### 연구 질문과 검증 방법
    
    | 연구 질문 | 검증 방법 |
    | --- | --- |
    | **RQ1. 실행 증거를 추가하면 위험 후보를 더 정확하게 판별할 수 있는가?** | 기존 스캐너, 수동 검토, 자체 검증을 같은 사례에서 비교 |
    | **RQ2. 스캐너가 경고하지 않은 영역에서 반복되는 실패 유형을 확인할 수 있는가?** | 무경고 대상의 독립 검토와 재현 |
    | **RQ3. 수정·업데이트가 기존의 보안 판정을 어떻게 바꾸는가?** | 동일한 시험을 변경 전후에 실행하고 정상 작업도 비교 |

    # 3. 범위: 넓게 수집하되, 깊게 검증하는 대상은 제한한다
    
    ## 필수 지원 범위
    
    | 구분 | 핵심 범위 |
    | --- | --- |
    | **운영 환경** | Linux 기반의 격리된 연구 환경 |
    | **MCP** | 공개 소스, 로컬 `stdio` 방식, Python 구현을 우선 대상으로 선정 |
    | **Skills** | `SKILL.md`, 참조 문서, Python·셸 스크립트를 포함한 패키지 |
    | **에이전트** | 설정을 고정한 평가용 호스트 한 종류 |
    | **주요 위반 유형** | 파일 접근, 데이터 전송, 제한된 실행 권한의 위반 |
    | **공급망 요소** | 패키지 버전, 배포물, 참조 파일, 직접 관련 의존성, 업데이트 |
    | **결과물 형태** | CLI, 기계 판독 가능한 결과, HTML 보고서, 재현 테스트 |
    
    기존 스캐너가 지원하는 JavaScript·TypeScript 등의 정적 분석 결과도 수집할 수 있지만, **그것이 자체 실행 검증까지 지원한다는 뜻은 아니야.** 언어별·실행 방식별 지원 상태를 따로 표시해야 해.
    
    Skills는 지시문 하나만이 아니라 실행 스크립트와 필요할 때 읽는 참조 문서를 포함할 수 있어. 따라서 분석 단위를 `SKILL.md` 단독이 아니라 **패키지와 실제로 로드된 파일 집합**으로 잡는 것이 타당해. [Agent Skills](https://agentskills.io/specification)
    
    ## 확장 항목
    
    JavaScript·TypeScript 실행 어댑터, 두 번째 에이전트 호스트, 원격 MCP의 인증·인가 검증, 모델 간 비교는 확장으로 둔다.
    
    반면 다음은 제외하는 게 좋아.
    
    **범용 악성코드 분석기, 자체 하이퍼바이저, 모든 언어의 데이터 흐름 분석기, 무인 공격 에이전트, 모든 SaaS의 권한 감사, 모델 자체의 백도어 탐지.**
    
    이들은 각각 별도 프로젝트가 될 만큼 범위가 커. **이번 프로젝트의 깊이는 지원 대상의 수보다 재현과 판정의 정확성에서 확보한다.**

    # 4. 가장 중요한 보완: ‘취약점’의 판정 기준
    
    ## 4.1. 공격자 모델을 분리한다
    
    기존 안에서는 공격자가 무엇을 통제하는지가 다소 섞여 있었어. 다음처럼 분리해야 해.
    
    | 모델 | 공격자가 통제하는 것 | 조사할 문제 |
    | --- | --- | --- |
    | **T1. 외부 입력 공격자** | 문서, 도구 응답, 도구에 전달되는 입력 | 낮은 신뢰의 입력이 허용되지 않은 동작으로 이어지는가 |
    | **T2. 결함이 있는 정상 구현** | 공격자는 입력만 통제하고 서버 코드는 통제하지 않음 | 구현의 검증 실패로 제한된 접근 범위를 벗어나는가 |
    | **T3. 악성 공급자·업데이트** | 스킬이나 MCP 패키지의 일부 또는 전체 | 승인된 목적과 다르게 숨은 데이터 접근·전송·실행을 하는가 |
    | **T4. 과도한 배포 권한** | 공격자는 환경을 변경하지 않지만 넓은 권한을 악용 | 특정 호스트 구성에서 위험이 성립하는가 |
    
    T3에서 공격자가 이미 임의 코드를 배포하고 사용자가 그것을 실행했다면, **코드가 실행됐다는 사실만으로 MCP 프로토콜 취약점을 발견한 것은 아니야.** 악성 패키지의 행동을 발견한 것인지, 호스트의 승인·격리 경계를 우회한 것인지 구분해야 해.
    
    ## 4.2. 보안 정책의 근거를 기록한다
    
    판정에 사용하는 정책은 세 종류로 구분한다.
    
    **제품이 약속한 경계:** 문서·설정·API 계약에서 제한한다고 명시한 범위.
    
    **사용자가 정한 경계:** 해당 배포 환경의 접근·전송 정책.
    
    **연구용 가정:** 실험을 위해 연구자가 정의한 제한.
    
    연구용 가정을 위반했다고 해서 바로 제품 취약점으로 보고하면 안 돼.
    
    예를 들어 연구자가 임의로 “셸 실행 금지”라고 설정한 뒤 원래 셸 실행이 목적인 스킬을 실행하고 취약하다고 판정하면 잘못된 평가야.
    
    또한 **패키지가 주장한 권한을 실제 권한으로 신뢰하면 안 돼.** Agent Skills의 `allowed-tools`는 구현별 지원이 다른 실험적 필드이고, MCP 명세도 신뢰할 수 없는 서버의 도구 어노테이션을 신뢰하지 말라고 설명해. [Agent Skills](https://agentskills.io/specification)
    
    따라서 정책은 분석 대상이 작성한 파일에서 자동 확정하지 않고, **연구자가 검토한 별도 파일**로 관리한다.
    
    ## 4.3. 판정은 두 축으로 저장한다
    
    하나의 `SAFE / UNSAFE` 값으로 끝내지 않는다.
    
    | 분류 축 | 가능한 값 |
    | --- | --- |
    | **문제의 종류** | 구현 취약점, 악성 행동, 환경 의존 위험, 정책 위반, 단순 위험 기능, 미확인 |
    | **검증 상태** | 위반 확인, 해당 조건에서 미재현, 판단 보류, 실행 실패, 미지원 |
    
    심각도와 증거 수준도 별도야. **잠재 피해가 크지만 증거가 부족한 경우**, **실제로 재현됐지만 영향이 제한적인 경우**를 구분해야 한다.

    # 5. 실제 취약점 발굴 경로를 세 개로 만든다
    
    ## 경로 A: 기존 스캐너 경고에서 출발
    
    기존 도구의 경고를 정규화하고, 중복을 원인 단위로 묶는다. 연구자는 공격자 입력, 보안 정책, 재현 가능성을 확인해 검증 시나리오를 작성한다.
    
    여기서 스캐너는 **후보 생성기**이지 정답 판정기가 아니야. Cisco Skill Scanner도 탐지의 불완전성과 사람 검토의 필요성을 명시하고 있어. [GitHub](https://github.com/cisco-ai-defense/skill-scanner)
    
    ## 경로 B: 경고가 없는 대상의 독립 조사
    
    무경고 대상 중 일부를 선정해 코드와 구성을 검토한다.
    
    확인할 것은 예를 들어 **실제 입력 검증 지점, 허용 경계의 강제 여부, 참조 파일에서 실행 코드로 이어지는 경로, 도구 설명에 드러나지 않은 부수 동작**이야.
    
    **이 경로가 없으면 프로젝트는 기존 스캐너의 경고를 검증할 수는 있어도, 기존 미탐을 체계적으로 조사하기는 어렵다.**
    
    ## 경로 C: 공급망 변경에서 출발
    
    동일 패키지의 변경 전후를 비교해 다음과 같은 변화에서 조사 후보를 만든다.
    
    **실행 진입점 추가, 참조 스크립트 변경, 새 의존성, 외부 요청 대상 변경, 도구 설명·입력 스키마 변경, 권한 설정 변경.**
    
    변경이 있다는 사실 자체는 취약점이 아니야. 변경을 조사 우선순위로 사용하고, 실제 보안 영향은 재현으로 판단한다.
    
    세 경로에서 발견한 후보는 같은 검증 체계로 합친다. 동일한 원인이 여러 경로에서 발견돼도 취약점 수는 중복 계산하지 않는다.
    
    ---
    
    # 6. 시스템 구조와 자체 개발 범위
    
    전체 흐름은 다음과 같다.
    
    **수집·스냅샷 → 스캐닝·독립 조사 → 후보 관리 → 시나리오 승인 → 격리 실행 → 증거 판정 → 원인 분석 → 수정·변경 재검증**
    
    ## 6.1. 모듈별 설계
    
    | 모듈 | 구현할 기능 | 완료 기준 |
    | --- | --- | --- |
    | **수집·스냅샷** | 소스·배포물·파일·의존성의 버전과 해시 기록 | 어떤 대상을 검사했는지 다시 식별 가능 |
    | **스캐너 어댑터** | 도구 버전·옵션·원본 결과 보존, 결과 정규화 | 오류·미지원·무경고가 구분됨 |
    | **구성 관계 분석** | 스킬→참조 파일→스크립트→도구 관계 기록 | 선언된 관계와 실제 관측 관계가 구분됨 |
    | **후보 관리** | 경고·수동 발견·변경 후보를 원인별로 관리 | 하나의 문제에 여러 증거를 연결 가능 |
    | **시나리오 실행기** | 환경 초기화, 직접 호출, 에이전트 실행 | 같은 조건을 반복 실행 가능 |
    | **관측·판정기** | 파일·네트워크·프로세스 증거와 정책 대조 | 위반·미재현·판단 불가를 구분 |
    | **변경·패치 검증** | 변경 전후 동일 시험과 정상 작업 비교 | 위험 차단과 기능 유지 여부를 함께 확인 |
    | **평가·보고** | 비교 실험, 한계 표시, 사례 보고서 생성 | 다른 연구자가 근거를 검토 가능 |
    
    MCP 연결 자체는 공식 SDK를 활용하고, 프로토콜 클라이언트를 처음부터 새로 구현하지 않는 편이 좋아. 공식 Python SDK는 서버와 클라이언트 구현을 제공해. [GitHub](https://github.com/modelcontextprotocol/python-sdk)
    
    기본 구현은 **Python 제어 프로그램, SQLite 메타데이터, 파일 기반 증거 저장소, JSON 결과, 정적 HTML 보고서**로 충분해. 분산 시스템이나 대규모 웹 서비스는 필요하지 않아.
    
    ## 6.2. 구성 관계에는 근거 종류를 붙인다
    
    다음 세 가지를 혼합하면 안 돼.
    
    **선언:** 문서에 이 파일을 사용한다고 적혀 있음.
    
    **정적 추론:** 코드 분석상 해당 함수를 호출할 수 있음.
    
    **실행 관측:** 특정 실행에서 실제 호출이 발생함.
    
    예를 들어 보고서에 다음처럼 표시한다.
    
    > 스킬이 스크립트를 참조함: 선언 확인
    > 
    > 
    > 스크립트가 외부 요청 함수를 호출할 수 있음: 정적 추론
    > 
    > 이번 실행에서 요청이 발생함: 관측 확인
    > 
    
    이렇게 해야 **가능한 경로를 실제 발생한 공격 경로처럼 표현하는 오류**를 줄일 수 있어.

    # 7. 검증 엔진: 이번 프로젝트의 기술적 중심
    
    ## 7.1. 실험실 보호 정책과 대상 정책을 분리한다
    
    이 부분은 기존 안에서 가장 크게 보완해야 해.
    
    **실험실 보호 정책**은 연구자의 PC·계정·실제 인터넷을 보호한다.
    
    **검증 대상 정책**은 조사 중인 프로그램이 지켜야 하는 파일·데이터·실행 범위를 뜻한다.
    
    예를 들어 데이터 유출을 검사하면서 모든 네트워크 요청을 먼저 차단하면, 프로그램이 잘못된 요청을 하려 했는지는 볼 수 있어도 실제 전송이 되는지는 확인하기 어려워.
    
    따라서 다음처럼 구성한다.
    
    > 실제 인터넷 전송은 차단한다.
    > 
    > 
    > 대신 격리된 내부망에 ‘정책상 허용되지 않은 수신처’를 모의 서버로 만든다.
    > 
    > 합성 데이터가 그 서버에 도착하는지 확인한다.
    > 
    
    파일 접근도 마찬가지야. 프로그램이 접근을 제한한다고 약속한 범위 밖에 **합성 파일**을 두되, 운영체제가 먼저 무조건 차단해서 구현 결함이 가려지지 않도록 시험 환경을 설계한다.
    
    **이것은 실제 고객 데이터를 유출하는 실험이 아니라, 격리된 환경에서 경계 위반을 검증하는 방식**이야.
    
    ## 7.2. 두 가지 실행 모드
    
    ### 직접 호출 모드
    
    MCP 도구나 스크립트를 승인된 입력으로 실행한다.
    
    목적은 **LLM과 무관하게 구현의 문제가 존재하는지** 확인하는 것이다. 정상값과 경계 조건을 포함한 테스트는 만들되, 무제한 공격 입력 생성기는 만들지 않는다.
    
    ### 에이전트 경유 모드
    
    고정된 호스트가 실제로 스킬과 도구 설명을 읽고 작업을 수행하도록 한다.
    
    목적은 **해당 문제가 에이전트의 실행 경로에서도 발생하는지** 확인하는 것이다. 로드한 파일, 도구 목록, 승인 설정, 모델 식별자, 입력, 도구 호출을 기록한다.
    
    Promptfoo도 직접 MCP 테스트와 에이전트 테스트를 구분한다. 따라서 두 모드를 제공하는 것 자체가 새 기여는 아니며, **이번 프로젝트의 기여는 실제 구성·정책·부수 동작·패치 결과를 연결하는 검증에 둬야 해.** [Promptfoo](https://www.promptfoo.dev/docs/red-team/mcp-security-testing/)
    
    ## 7.3. 관측은 세 종류로 제한한다
    
    | 관측 대상 | 수집할 정보 | 주의할 점 |
    | --- | --- | --- |
    | **파일** | 접근 대상, 작업 종류, 성공 여부, 변경 결과 | 열기 시도와 실제 읽기를 구분 |
    | **네트워크** | 목적지, 요청, 모의 수신 서버의 수신 결과 | 연결 시도와 실제 데이터 전달을 구분 |
    | **프로세스** | 실행 파일, 부모·자식 관계, 인자, 결과 | 셸이 실행됐다는 사실만으로 취약점 판정 금지 |
    
    대상 프로그램이 직접 출력한 로그만 믿지 않고, **대상 프로세스가 수정할 수 없는 관측 경로**를 사용한다.
    
    직접 만든 커널 계측 도구는 핵심 범위에서 제외하고, 기존 관측 수단을 연결한다. 관측에 실패하거나 지원하지 않는 동작이면 판단 보류로 남긴다.
    
    ## 7.4. 합성 식별값으로 실제 이동을 확인한다
    
    보호 대상 데이터에는 실행마다 다른 식별값을 넣는다. 이 값은 공격 입력이나 스킬 설명에는 넣지 않고, 보호 자원에만 배치한다.
    
    그러면 모의 수신 서버에 같은 값이 도착했을 때 **단순한 전송 주장보다 강한 증거**를 얻을 수 있어.
    
    다만 정확한 식별값 비교는 요약·변환·암호화된 데이터 이동을 모두 잡는 범용 데이터 흐름 분석이 아니야. **어떤 변환을 검증할 수 있는지 명시하고, 나머지는 미확인으로 남긴다.**
    
    ## 7.5. 대조 실험을 필수화한다
    
    문제를 확인한 사례는 가능한 범위에서 다음 조건을 비교한다.
    
    | 조건 | 확인할 내용 |
    | --- | --- |
    | **정상 입력** | 원래 업무가 정상적으로 수행되는가 |
    | **문제 입력** | 주장한 경계 위반이 실제로 발생하는가 |
    | **문제 요소 제거** | 의심한 요소를 제거하면 현상이 사라지는가 |
    | **수정 버전** | 위반은 차단되고 정상 작업은 유지되는가 |
    
    여러 파일이 동시에 바뀌었다면 “업데이트가 원인”까지는 말할 수 있어도, 특정 한 줄이 원인이라고 바로 단정하면 안 돼. 원인 분리가 가능한 추가 시험을 수행하거나 남은 불확실성을 기록한다.

    # 8. 공통 데이터 형식부터 정한다
    
    4명이 병렬로 구현하려면 기능보다 먼저 **모듈 사이의 입력·출력 형식**이 맞아야 해.
    
    | 데이터 | 필수 정보 |
    | --- | --- |
    | **ArtifactManifest** | 대상 ID, 출처, 커밋·배포물 해시, 파일 목록, 관련 의존성, 수집 조건 |
    | **ScanRun** | 스캐너 버전, 옵션, 대상 ID, 지원 범위, 상태, 원본 결과 |
    | **Candidate** | 발견 경로, 주장하는 문제, 관련 위치, 정책 경계, 근거 |
    | **Scenario** | 공격자 통제 범위, 대상·정책 참조, 실행 모드, 합성 자원, 판정 조건 |
    | **ExecutionRun** | 환경·시나리오 해시, 호스트 설정, 실행 결과, 관측 상태 |
    | **EvidenceEvent** | 실행 ID, 순서, 프로세스·도구 호출 관계, 행동, 자원, 결과, 관측 출처 |
    | **Verdict** | 문제 유형, 검증 상태, 근거, 사전 조건, 미확인 사항, 검토자 |
    | **ChangeReport** | 변경 전후 대상, 변경 내용, 영향받는 시험, 재검증 결과 |
    
    해시가 일치한다는 것은 동일한 자료를 식별하는 근거이지, 자료가 안전하거나 선의로 만들어졌다는 뜻은 아니야.
    
    ## 시나리오 정의 예시
    
    아래는 **자체 프레임워크에서 구현할 설정 형식의 예시**야. 기존 제품의 설정 파일이 아니며, 참조값은 미리 등록된 로컬 자원 ID다.
    
    ```
    schema_version: "0.1"
    case_id: "CASE-001"
    
    artifact_ref: "artifact-a"
    policy_ref: "policy-workspace-only"
    
    attacker_control:
      surface: "tool_input"
      can_modify_server_code: false
    
    execution:
      mode: "direct_mcp"
      adapter: "stdio-python"
      scenario_ref: "scenario-001"
      safety_profile: "isolated-mock-network"
    
    fixtures:
      workspace_ref: "workspace-001"
      protected_data_ref: "protected-data-001"
      receiver_ref: "receiver-001"
    
    oracles:
      - type: "canary_received"
        canary_ref: "protected-data-001"
        receiver_ref: "receiver-001"
    
    controls:
      benign_scenario_ref: "scenario-control-001"
      comparison_artifact_ref: "artifact-b"
    ```
    
    이 파일에 임의 셸 명령을 직접 넣어 무조건 실행하는 방식은 피한다. 실행은 승인된 어댑터와 검토된 시나리오를 통해 수행한다.
    
    또한 **평가 정답은 이 파일과 분리**한다. 분석기가 읽는 입력 안에 “이것은 취약 사례”라는 라벨이 있으면 평가가 오염돼.

    # 9. 분석 시스템 자체의 보안
    
    불신 패키지를 다루는 프로젝트에서는 분석 시스템도 공격 대상이야.
    
    ## 실행 구역을 분리한다
    
    **제어 구역**은 대상 목록, 정책, 모델 연결, 결과 관리를 담당한다. 불신 패키지의 코드나 설치 스크립트를 실행하지 않는다.
    
    **실험 구역**은 폐기 가능한 VM 안에서 패키지 설치·빌드·실행을 수행한다. 개인 계정, 운영 토큰, 홈 디렉터리, 호스트 관리 소켓을 연결하지 않는다.
    
    **증거 구역**은 실행 결과를 받아 보관한다. 대상 프로그램이 증거를 덮어쓰거나 판정을 수정할 수 없어야 한다.
    
    스캐닝도 안전한 읽기 작업이라고 가정하면 안 돼. Snyk Agent Scan은 도구 설명을 가져오기 위해 로컬 MCP 명령을 실행하거나 원격 서버에 접속할 수 있다고 명시한다. **설치·빌드·서버 시작·동적 정보 수집을 모두 실행 단계로 취급해야 해.** [GitHub](https://github.com/snyk/agent-scan)
    
    ## 필수 통제
    
    수집한 압축파일·문서는 크기와 경로를 제한해 처리하고, 외부 참조를 자동으로 따라가 실행하지 않는다. 대상이 제공한 설정으로 분석 정책이나 스캐너 옵션을 바꾸지 못하게 한다.
    
    모델 연결의 자격증명은 실험 대상에 제공하지 않는다. 분석용 LLM을 쓰더라도 그 응답을 그대로 실행하거나 최종 판정으로 사용하지 않는다.
    
    보고서에는 원문을 안전하게 표시하고 비밀정보를 마스킹한다. **악성 HTML이나 프롬프트가 보고서·후속 분석 단계에서 다시 실행되거나 지시로 취급되지 않게 한다.**
    
    이 방향은 MCP 공식 지침의 명시적 실행 동의, 최소 권한, 파일·네트워크 제한 권고와도 일치해. [Model Context Protocol](https://modelcontextprotocol.io/specification/draft/basic/security_best_practices)

    # 10. 평가 설계: ‘잘 작동하는 데모’를 넘어서는 부분
    
    ## 10.1. 기본 정답은 자체 판정기와 독립적으로 만든다
    
    가장 주의할 오류는 다음이야.
    
    > 자체 판정기가 위반이라고 출력했으니 정답을 위반으로 정하고, 같은 판정기로 정확도를 계산한다.
    > 
    
    이건 검증이 아니라 순환이야.
    
    정답은 **코드 검토, 공개된 수정 근거, 독립 재현, 보안 계약 확인**을 종합해 작성한다. 두 사람이 독립 검토하고, 불일치는 다른 구성원이 검토한다. 끝내 결론이 나지 않는 것은 정답 평가셋에서 분리하되 조사 결과에는 남긴다.
    
    ## 10.2. 데이터 규모는 ‘파일 수’보다 ‘독립 사례 수’를 기준으로 한다
    
    다음은 제안하는 확보 목표야.
    
    | 데이터층 | 목표 | 용도 |
    | --- | --- | --- |
    | **수집·기본 분석** | MCP·Skills 합계 약 200개 대상 | 조사 기반과 후보 확보 |
    | **독립 심층 검토** | 약 40개 대상 | 경고·무경고 대상을 모두 포함 |
    | **정답 평가** | 약 50개 독립 사례군 | 위반·정상·수정 조건의 비교 |
    | **핵심 검증 유형** | 파일·전송·실행의 3개 경계 | 각 유형의 판정과 한계 확인 |
    
    여기서 **사례군**은 같은 원인에서 나온 취약 버전·수정 버전·입력 변형을 한 묶음으로 본다는 뜻이야. 변형 20개를 만들었다고 독립 취약점 20개가 되는 것은 아니야.
    
    평가 사례는 공개된 실제 문제, 직접 제작한 통제 사례, 독립 조사 사례를 구분한다. 확보한 사례가 적으면 숫자를 맞추기 위해 유사 사례를 복제하지 않고, 평가 범위를 제한한다.
    
    ## 10.3. 개발과 최종 평가를 분리한다
    
    사례군 단위로 개발용·조정용·최종 평가용을 분리한다. 예를 들어 50개를 확보했다면 25·10·15개로 나눌 수 있어.
    
    동일 패키지의 포크, 동일 원인의 다른 버전, 거의 같은 합성 변형은 같은 그룹에 둔다. 최종 평가의 결과를 본 뒤 규칙을 수정했다면, 그 자료는 더 이상 독립적인 최종 평가 자료가 아니야.
    
    정답이 있는 사례와 정상 대조를 함께 사용하는 방식은 OWASP Benchmark와 같은 평가 접근을 참고할 수 있지만, **직접 만든 평가셋의 결과를 실제 생태계 전체 성능으로 일반화해서는 안 돼.** [OWASP Foundation](https://owasp.org/www-project-benchmark/)
    
    ## 10.4. 비교 실험을 세 개로 분리한다
    
    ### 실험 A: 위험 후보의 판별
    
    같은 후보 집합에 대해 **기존 스캐너 결과, 수동 검토 결과, 자체 검증 결과**를 비교한다.
    
    자체 엔진이 추가 실행 정보와 연구자가 작성한 시나리오를 사용했다면 이를 명시한다. 더 많은 정보를 사용하고도 “동일 조건에서 스캐너보다 우수하다”고 표현하면 안 돼.
    
    ### 실험 B: 미탐과 탐지 확장
    
    무경고 대상의 독립 조사에서 확인한 반복 유형을 바탕으로 확장 규칙을 만든다. 그 규칙을 만들 때 보지 않은 사례에서 평가한다.
    
    검증 엔진만으로는 기존 스캐너가 후보로 제시하지 않은 문제를 자동으로 찾아낸다고 주장할 수 없어. **후보 생성의 개선과 후보 검증의 개선을 따로 측정한다.**
    
    ### 실험 C: 변경·패치 검증
    
    동일한 환경과 시험을 변경 전후에 실행한다. 위반 여부와 정상 작업 유지 여부를 함께 비교한다.
    
    변경된 파일만 다시 검사하는 최적화는 선택 기능으로 둔다. 영향 분석이 불확실하면 전체 관련 시험을 다시 수행하도록 하고, 선택 검증이 놓친 회귀도 보고한다.
    
    ## 10.5. 반드시 함께 보고할 지표
    
    | 지표 | 의미 |
    | --- | --- |
    | **정밀도** | 위반이라고 확정한 것 중 실제 위반으로 판정된 비율 |
    | **재현율** | 정답이 있는 위반 사례 중 최종적으로 확인한 비율 |
    | **판정 가능 비율** | 지원 대상 중 충분한 근거로 결론을 내린 비율 |
    | **판단 보류율** | 증거 부족·조건 불명확으로 확정하지 못한 비율 |
    | **실행 실패율** | 설치·초기화·관측 실패로 시험을 완료하지 못한 비율 |
    | **검토 작업량** | 사람이 검토한 후보 수와 필요한 작업량 |
    | **정상 업무 성공률** | 위험 차단 또는 패치 후 원래 업무가 수행되는 비율 |
    | **재현 안정성** | 같은 조건의 반복 실행에서 동일한 결과가 나온 정도 |
    
    **판단 보류나 실행 실패를 삭제한 뒤 정확도만 높게 보여주면 안 돼.** 확정한 결과의 정확도와 전체 대상 중 얼마나 판단했는지를 같이 보여줘야 해.
    
    실제 공개 저장소에는 아직 모르는 취약점이 있을 수 있으므로, 그 집합에 대한 전체 재현율은 계산하지 않는다.
    
    에이전트 경유 시험은 공격 성공률만 보지 않고 정상 업무 수행도 함께 평가해야 해. AgentDojo 역시 공격이 없는 상황에서도 작업 수행 실패가 발생한다는 점을 다루며, 정상 작업과 보안을 함께 평가한다. [arXiv](https://arxiv.org/abs/2406.13352)
    
    ## 10.6. 자동화가 절약한 작업을 과장하지 않는다
    
    시나리오를 사람이 만드는 데 든 작업, 초기 환경 구성, 실패 원인 분석까지 기록한다.
    
    “실행 버튼을 누른 뒤 결과가 빨리 나온다”는 것과 “전체 검토 비용이 줄었다”는 것은 달라. 네 명 안에서 검토 효율을 비교한다면 사례 난이도와 순서를 균형 있게 배정하고, 결과는 **소규모 내부 실험**으로 표현한다.

    # 11. 4명 역할과 구현 단위
    
    역할은 다음처럼 수정하는 편이 균형이 좋아.
    
    | 담당 | 주 책임 | 공동 책임 |
    | --- | --- | --- |
    | **A — 수집·정적 분석·변경 분석** | 스냅샷, 스캐너 어댑터, 결과 정규화, 구성 관계, 변경 후보 생성 | 반복 실패 유형의 탐지 규칙 개선 |
    | **B — 실행 환경·MCP 연구** | 격리 환경, 직접 호출 어댑터, 프로세스·파일·네트워크 관측 | MCP 취약점 조사와 재현 |
    | **C — Skills·에이전트 연구** | 스킬 로딩, 참조 파일 추적, 평가용 호스트, 에이전트 경유 실행 | Skills 조사와 재현 |
    | **D — 판정·데이터셋·평가** | 정책·시나리오 형식, 판정 엔진, 정답 관리, 비교 실험, 보고서 | 독립 검토와 패치 검증 |
    
    B가 격리 환경과 관측을 담당하고, D가 그 증거를 해석하는 판정과 평가를 담당하도록 분리한다.
    
    취약점 발굴은 B·C만 하는 일이 아니야. A는 변경·정적 분석에서 후보를 만들고, D는 오탐·미탐 검토에서 새로운 문제를 발견할 수 있어. **각자는 자기 모듈과 연결되는 발굴 경로를 가진다.**
    
    ## 구현 순서는 기능 의존성으로 정한다
    
    | 작업 묶음 | 산출물 | 통과 조건 |
    | --- | --- | --- |
    | **판정 계약** | 위협 모델, 문제 분류, 정책 형식 | 정상 기능과 취약점을 구분할 수 있음 |
    | **공통 데이터 계약** | Manifest·Scenario·Evidence·Verdict 스키마 | 모듈 간 샘플 데이터가 호환됨 |
    | **실험실 검증** | 격리 환경과 관측 테스트 | 실제 자원에 접근하지 않고 합성 자원의 동작을 관측함 |
    | **직접 재현** | 세 경계의 기본 시나리오와 정상 대조 | 위반·미재현·실행 실패를 구분함 |
    | **에이전트 연결** | 고정된 호스트와 기록 체계 | 정상 작업이 가능하고 실제 호출을 추적함 |
    | **실제 조사** | 경고·무경고·변경 기반 사례 | 독립 검토와 재현 근거가 존재함 |
    | **개선·최종 평가** | 확장 규칙, 비교 실험, 한계 보고 | 평가 자료와 개발 자료가 분리됨 |
    
    특히 **실험실과 판정 체계가 검증되기 전에는 대량으로 불신 패키지를 실행하지 않는다.**

    # 12. 최종 결과물과 완료 기준
    
    ## 결과물 1: 연구용 분석·검증 도구
    
    스냅샷 생성, 기존 도구 실행, 후보 관리, 승인된 시나리오 실행, 증거 저장, 패치 비교가 가능한 CLI를 제공한다.
    
    HTML 보고서에는 **문제 근거, 실행 경로, 적용 정책, 변경 전후 비교, 미확인 사항**이 보여야 한다. 보기 좋은 점수판보다 연구자가 검토할 수 있는 근거가 중요해.
    
    ## 결과물 2: 재현 가능한 사례 묶음
    
    각 사례에 대상 식별자, 환경, 정책, 시험 조건, 증거, 정상 대조, 수정 검증을 포함한다.
    
    공개가 제한된 코드나 미공개 취약점은 그대로 배포하지 않고, 허용되는 메타데이터와 안전한 대체 사례로 구분한다.
    
    ## 결과물 3: 취약점·실패 유형 보고서
    
    신규 취약점, 악성 행동, 알려진 취약점 재현, 환경 의존 위험, 스캐너 미탐·오탐을 별도 집계한다.
    
    새로운 문제는 유지보수자의 비공개 보고 절차를 우선 사용한다. GitHub는 활성화된 저장소의 비공개 취약점 보고를 지원하며, 그렇지 않으면 저장소의 보안 정책이나 연락 경로를 따르도록 안내한다. [GitHub Docs](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability)
    
    ## 결과물 4: 비교 평가와 개선 기여
    
    기존 도구의 어떤 실패를 확인했는지, 자체 검증이 무엇을 더 확인했는지, 개선이 적용되지 않는 조건은 무엇인지 제시한다.
    
    추가 탐지 규칙이나 수정 패치를 상위 프로젝트에 제안할 수 있지만, 병합이나 CVE 발급은 팀이 통제할 수 없으므로 필수 완료 조건으로 삼지 않는다.

    # 13. 결과가 기대와 다를 때의 대응도 설계에 넣는다
    
    | 확인된 상황 | 대응 |
    | --- | --- |
    | **신규 취약점이 발견되지 않음** | 독립적으로 확인한 실패 유형·검증 한계·패치 재현 결과를 평가. 단순 수집만 남았다면 연구 성과가 약하다고 인정 |
    | **기존 도구가 대부분 잘 탐지함** | 탐지기를 복제하지 말고 검증 작업·근거 수집의 개선 가능성을 조사 |
    | **시나리오 작성이 너무 수작업임** | 반복 유형을 템플릿화하고, 자동화 범위를 명시. 범용 자동 검증이라고 주장하지 않음 |
    | **실행 환경 구성 실패가 많음** | 지원 대상을 줄이고 실패율을 공개. 성공한 대상만 골라 전체 성능처럼 표현하지 않음 |
    | **LLM 결과 변동이 큼** | 직접 호출 결과와 에이전트 결과를 분리하고 반복 조건을 고정 |
    | **합성 사례에서만 개선됨** | 합성 조건에서의 효과로 제한. 실제 프로젝트 일반화 주장을 하지 않음 |
    | **변경 분석이 너무 복잡함** | 영향받는 시험의 추천으로 기능을 제한하고 자동 안전 판정은 하지 않음 |
    
    **이 프로젝트의 성공은 “반드시 취약점이 나온다”가 아니라, 발견한 문제를 믿을 수 있게 설명하고, 발견하지 못한 경우에도 무엇을 검사했고 무엇이 남았는지를 증명할 수 있는가에 달려 있어.**
    
    최종적으로는 다음 세 문장에 근거를 붙여 답할 수 있으면 돼.
    
    > **우리는 어떤 MCP·Skills 구성에서 어떤 보안 경계가 깨지는지 확인했다.**
    > 
    > 
    > **그 판단은 스캐너의 경고가 아니라 재현 가능한 실행 증거와 독립 검토로 뒷받침된다.**
    > 
    > **수정 후에는 해당 위반이 차단되는지와 정상 업무가 유지되는지까지 검증했다.**
    > 
    
    이렇게 보완하면 **스캐너 연동 프로젝트를 넘어, 취약점 발굴·실행 검증·공급망 변경 분석·평가 방법이 연결된 보안 연구 프로젝트**가 된다.
