# 01. 외부 AI 워크플로 구성요소의 실사용과 도입 근거

조사 기준일: 2026-09-20  
질문: 사람들이 GitHub·레지스트리·커뮤니티의 Skill·MCP·플러그인·워크플로를 실제로 가져다 사용하는가?

## 1. 결론과 판단 범위

**외부 AI 구성요소의 재사용은 실제 현상이다.** 특히 Skills를 프로젝트에 복사한 흔적과 MCP 배포물의 다운로드는 서로 다른 자료에서 확인된다. 업무용 워크플로 운영도 확인된다. 다만 이 사실만으로 네 가지 구성요소의 이용자가 모두 많다거나, 사용자들이 보안 검토 때문에 곤란을 겪거나, 새로운 플랫폼에 비용을 지불할 것이라고 결론 낼 수는 없다.

| 구분 | 이번 조사로 확인한 것 | 아직 확인하지 못한 것 |
|---|---|---|
| Skill | 공개 레지스트리에서 개인·프로젝트 저장소로 이어지는 재사용 흔적, CLI 설치 관련 업체 보고 | 실제 실행 빈도, 고유 활성 사용자 수, 한국 소규모 팀의 도입률 |
| MCP | npm·PyPI 다운로드를 이용한 연구, Docker 배포 통계, 업무 도입 사례 | 설치 후 도구별 호출 수, 다운로드의 고유 사용자 환산, 외부·사내 개발 서버의 전체 비율 |
| 플러그인·커뮤니티 노드 | 설치·검증·배포 경로와 권한 모델이 공식 문서에 존재 | 전체 사용자 중 외부 제작 플러그인 이용 비율과 지속 사용률 |
| 워크플로 | 실제 기업 운영과 JSON 등 가져오기·내보내기 기능 | 운영 워크플로 중 외부 템플릿을 그대로 가져온 비율 |

따라서 “외부 요소를 검사할 대상 자체가 없다”는 가설은 기각할 수 있다. “우리 대상 사용자에게 반복적인 보안 검토 수요가 있다”는 가설은 현장 확인이 남아 있다.

## 2. 무엇을 실사용으로 셀 것인가

아래 항목은 같은 분모를 갖지 않는다. 합산해 시장 규모처럼 제시하지 않는다.

| 관찰 단위 | 직접 알 수 있는 것 | 알 수 없는 것 |
|---|---|---|
| 공개 저장소·등록 항목 수 | 공급되는 구성요소의 존재 | 설치·실행·고유 사용자 |
| stars·forks | 관심이나 저장소 복제 | 업무 채택·안전성·유료 수요 |
| 패키지 다운로드·컨테이너 pull | 배포물 요청 | 재설치·CI·캐시 영향을 제거한 사람 수 |
| 프로젝트 내부의 파일·설정 | 그 프로젝트에 구성요소가 편입된 흔적 | 활성화 여부, 실제 호출, 사용 의도 |
| 내용·경로·이력 기반 재사용 연결 | 원본과 도입본 사이의 관계를 추정할 근거 | 모든 복제·개명·큰 수정의 완전한 추적 |
| 운영 로그의 호출·활성 사용자 | 특정 서비스 내 실행과 사용 빈도 | 생태계 전체 대표성 |
| 인터뷰·고객 사례 | 실제 업무 맥락과 당사자 설명 | 독립 검증, 인과효과, 모집단 비율 |

이 프로젝트의 수요 검증에는 단순 설치 수보다 **“사용자가 외부에서 가져온 구성을 자기 환경에 붙이고, 이후 변경을 검토한 사례”**가 더 직접적이다. 그것이 플랫폼이 개입할 순간이기 때문이다.

## 3. MCP: 배포물 사용 신호는 충분하지만 호출 통계는 아니다

### 3.1 AISI 연구의 근거와 한계

AISI 연구는 2024년 11월~2026년 2월의 공개 생태계를 대상으로 177,436개 도구 정의를 분석하고 npm·PyPI 다운로드를 사용량의 대리 지표로 사용했다. 개발·IT 관련 도구가 도구 수의 67%, 해당 서버가 다운로드의 90%를 차지한다고 보고했다. 도구의 세부 사용량 배분에는 서버 설치를 그 서버의 도구 사용으로 대응시키는 가정이 들어간다. 이는 도구 호출 로그를 측정한 것이 아니다. [R01: 논문 원문](https://arxiv.org/html/2603.23802v1)

방법론상 공개 저장소와 식별 가능한 패키지에 의존하며, 반복 다운로드·캐시·사내 배포의 영향을 제거한 고유 사용자 통계가 아니다. 다운로드가 일부 인기 서버에 집중되므로 전체 도구가 고르게 사용된다고 해석할 수도 없다. 연구는 실제 사용에 가까운 신호를 제공하지만 전체 AI 에이전트 시장의 인구조사는 아니다. [R01](https://arxiv.org/html/2603.23802v1)

**프로젝트 해석:** 초기 고객을 “모든 AI 사용자”로 잡기보다 개발용 에이전트에 외부 도구를 붙이는 사람부터 검증하는 것이 자료와 잘 맞는다. 반대로 이 연구로 우리 플랫폼의 예상 사용자 수를 계산하는 것은 부적절하다.

### 3.2 Docker의 배포 통계

Docker는 2025-07-01 발표에서 MCP Catalog의 pull이 100만 회를 넘었다고 보고했다. 배포 시스템을 운영하는 업체의 수치라는 점에서는 의미가 있지만, 반복 pull·자동화가 포함될 수 있고 독립 감사된 사용자 수는 아니다. 또한 이 수치는 **그 발표 시점의 누적 배포 신호**이며 2026년 현재 사용량을 나타내지 않는다. [R04: Docker 발표](https://www.docker.com/blog/docker-mcp-catalog-secure-way-to-discover-and-run-mcp-servers/)

**프로젝트 해석:** MCP 서버를 재사용 가능한 배포물로 소비하는 경로가 실제로 존재한다. 동시에 이미 검증·유통을 담당하는 플랫폼이 있다는 뜻이므로, 수요 근거와 경쟁 근거로 함께 읽어야 한다.

### 3.3 업무 운영 사례

Stacklok은 익명 Fortune 500 금융회사 사례에서 100개 이상의 MCP 서버와 매주 접근하는 직원 500명 이상을 보고한다. 공식 upstream registry와 자체 서버를 함께 다루는 운영 구조도 설명한다. 다운로드보다 업무 사용에 가까운 지표지만, 고객명이 공개되지 않은 공급업체 사례이고 독립 로그를 확인하지 않았다. 생산성 향상에 대한 설명을 우리의 인과효과나 소규모 팀의 수요로 옮겨 쓰지 않는다. [R05: Stacklok 사례, PDF 3·6·7쪽](https://stacklok.com/wp-content/uploads/2026/01/Stacklok-Fortune-500-FSI_FINAL.pdf)

**프로젝트 해석:** “발견 → 내부 검토 → 허용 목록 → 사용”이라는 운영 경로는 현실적이다. 하지만 대기업의 중앙 거버넌스 필요가 학생·소규모 개발팀에도 같은 규모로 존재하는지는 따로 조사해야 한다.

## 4. Skills: 등록 수보다 프로젝트로 이동한 흔적이 중요하다

### 4.1 저장소 재사용 연구

2026년 7월 공개된 *From Registry to Repository* v2는 skills.sh의 18,463개 스킬과 5,876개 GitHub 저장소의 개인 사용 스킬 23,199개를 조사했다. 이름과 내용 유사도 등을 이용해 3,709개 재사용 연결을 복원했으며, 도입 후 수정되지 않은 비율을 53%로 보고한다. 자료는 스킬 내용 3월 4일, 저장소 이력 5월 4일까지의 스냅샷이다. [R03: 논문 방법·결과](https://arxiv.org/html/2607.00911v2)

이 연결은 사람의 모든 설치 행동을 기록한 로그가 아니다. 크게 수정하거나 이름을 바꾼 복제본을 놓칠 수 있고 레지스트리→개인 저장소 방향을 가정한다. 반대로 파일이 존재한다고 실행한 사실까지 확인되는 것도 아니다. 그 한계를 감안해도 공개 스킬을 자기 프로젝트에 편입하는 행위의 근거로는 단순 stars보다 직접적이다. [R03](https://arxiv.org/html/2607.00911v2)

**프로젝트 해석:** 검토 단위는 중앙 원본 하나로 끝나지 않는다. 원본, 복사된 로컬 파일, 로컬 수정본 사이의 관계가 필요하다. 스캔 결과가 원본에만 붙어 있다면 사용자가 실제로 가진 파일에 그대로 적용할 수 있는지 확인해야 한다. 이 요구가 현재 도구에서 얼마나 해결되는지는 02·04 문서에서 별도로 검토한다.

### 4.2 Vercel의 설치 관련 수치

Vercel은 2026-02-20 Skills Night 글에서 스킬 69,000개 이상과 “2 million skill CLI installs”를 보고했다. 여기서 200만을 고유 사용자 수나 개별 스킬의 실제 실행 횟수로 바꾸지 않는다. 기사만으로 중복 제거·기간·설치 이벤트의 세부 집계 정의가 충분히 제공되지 않는다. [R02: Vercel 발표](https://vercel.com/blog/skills-night-69000-ways-agents-are-getting-smarter)

현재 Skills CLI의 공식 README는 익명 텔레메트리와 비활성화 옵션을 설명한다. 수집에서 빠지는 설치가 있을 수 있다는 의미이지, 이를 근거로 미관측 사용자 수를 추산할 수 있다는 의미는 아니다. 현재 코드가 과거 수치와 정확히 같은 집계 방식이라는 가정도 하지 않는다. [R42: 확인한 커밋의 텔레메트리 설명](https://github.com/vercel-labs/skills/blob/7407f3893ad4dceab546ac002c3ef806e4000c73/README.md)

### 4.3 외부 배포와 내부 수정의 두 경로

| 경로 | 사용자가 확보하는 것 | 보안 검토 시 확인할 대상 |
|---|---|---|
| 공식 배포본 설치 | 게시자의 배포 파일·서명·보고서 | 현재 파일이 그 배포본과 일치하는지 |
| Git URL에서 가져오기 | 특정 저장소·경로의 파일 | 이동 가능한 branch/tag와 실제 커밋의 관계 |
| 복사·붙여넣기 | 내용만 남은 로컬 파일 | 출처 복원 가능성, 복사 후 변경 여부 |
| 팀이 수정해 공유 | 내부 목적에 맞춘 파생본 | upstream 결과의 적용 범위와 내부 검토 책임 |

위 표는 자료에서 도출한 **검토 모델**이며 각 경로의 점유율을 측정한 결과가 아니다. 원본이 같아도 실행 호스트·권한·수정 내용이 다르면 검토 대상도 달라질 수 있다.

## 5. 플러그인·워크플로: 유통과 업무 운영을 구분해야 한다

### 5.1 n8n의 업무 사용과 재사용 경로

n8n의 Trendyol 사례는 활성 사용자 1,000명 이상, 운영 워크플로 700개, 3개월간 약 50만 실행을 보고한다. 사내 프로젝트별 권한·자격 증명 분리와 중앙 관리도 설명한다. 업체가 고객을 소개한 자료이며 원시 로그를 확인하지 않았다. 특히 이 수치에는 자체 제작 워크플로가 포함되므로 **외부 템플릿 도입 수치로 사용할 수 없다.** [R06: Trendyol 사례](https://n8n.io/case-studies/trendyol/)

n8n은 공식 문서에서 워크플로의 JSON 가져오기·내보내기와 노드 복사 경로를 제공한다. 현재 문서에는 관련 참조를 함께 옮기는 패키지 기능도 Preview로 소개된다. 따라서 “워크플로 파일을 재사용할 수 있다”는 것은 확인된다. 그 기능이 있는 사실과 실제 외부 템플릿 사용률은 별개다. [R15: 현재 경로의 공식 원문](https://github.com/n8n-io/n8n-docs/blob/main/docs/build/manage-workflows/export-and-import.md)

커뮤니티 노드는 별도의 실행 코드 계층이다. n8n의 공식 위험 안내는 노드의 시스템·워크플로 데이터 접근과 업데이트 영향을 설명하고, 검증된 일부 노드를 별도로 구분한다. 이는 공식 플랫폼 안에서도 “외부 코드 선택과 도입”이라는 경계가 있음을 보여 준다. [R14: 공식 위험 안내](https://github.com/n8n-io/n8n-docs/blob/main/docs/integrations/community-nodes/risks.md)

### 5.2 Dify 플러그인의 위치

Dify는 플러그인 manifest에 버전·작성자·런타임·요청 권한을 선언하는 형식을 제공한다. 자체 호스팅 환경에서는 Marketplace 밖의 플러그인도 신뢰할 공개키를 등록해 서명을 검증하는 경로를 문서화한다. 공식 배포만 가능한 폐쇄 구조라고 볼 수 없다. [R16: manifest](https://github.com/langgenius/dify-docs/blob/main/en/develop-plugin/features-and-specs/plugin-types/plugin-info-by-manifest.mdx), [R17: 제3자 서명](https://github.com/langgenius/dify-docs/blob/main/en/develop-plugin/publishing/standards/third-party-signature-verification.mdx)

이번 조사에서 확인한 위 문서는 **지원되는 기능과 공급 경로**의 증거다. Dify 사용자 중 커뮤니티 플러그인을 실제로 쓰는 비율이나, 보안 문제 때문에 도입을 포기한 비율의 증거로 쓰지 않는다. 관련 사용자 조사 없이 이 영역을 핵심 고객군으로 확정하기에는 근거가 부족하다.

### 5.3 네 종류를 동일하게 세면 안 되는 이유

하나의 플러그인 안에 Skill과 MCP 설정이 포함될 수 있고, 워크플로 하나가 여러 노드·외부 API를 호출할 수 있다. 같은 구성을 “플러그인 1개 + 스킬 3개 + 도구 10개”로 중복 집계하면 시장 규모가 부풀려진다. 프로젝트에서는 **도입 결정 1건**과 **그 결정에 포함된 구성요소 목록**을 나누어 기록하는 것이 적절하다.

## 6. 자료가 지지하지 않는 주장

| 주장 | 왜 현재 근거로는 부족한가 |
|---|---|
| 수십만 개가 등록되어 있으므로 수십만 명이 사용한다. | 공급량과 사용자 수는 다른 단위다. |
| n8n을 운영하는 회사는 대부분 커뮤니티 워크플로를 가져온다. | 업무 실행 사례는 제작 출처의 비율을 측정하지 않는다. |
| MCP 사용이 늘었으므로 보안 검토 플랫폼의 구매 수요도 늘었다. | 위험 인식·검토 비용·구매 의사는 별도 변수다. |
| 중앙 레지스트리를 이용하므로 도입 대상은 모두 검증됐다. | 게시·서명·소유 인증·보안 검사는 다른 보장이다. |
| 스킬이 수정되지 않았으므로 안전하게 유지됐다. | 미수정은 보안 속성이 아니다. 원격 의존성·호스트 환경도 달라질 수 있다. |

이 반론을 반영해도 “외부 구성요소의 도입이 실제로 존재한다”는 결론은 유지된다. 줄어드는 것은 **규모와 구매 수요에 대한 확신**이다.

## 7. 우리 프로젝트의 초기 대상 제안

**우선 후보:** 외부 Skill·MCP를 함께 사용하는 개발자 및 소규모 팀. 공개 재사용 근거가 있고, 로컬 구성과 Git 이력을 확보하기 쉬워 검토 과업을 명확하게 만들 수 있다.

**다음 후보:** n8n·Dify 운영팀. 워크플로·플러그인·자격 증명 관계가 중요하지만, 별도 권한 모델과 운영 API를 다뤄야 한다. 첫 구현에 동시에 넣으면 동일한 검증 기준을 유지하기 어렵다.

**초기 대상에서 보류할 것:** 모든 일반 사용자, 모든 에이전트 호스트, 모든 기업 규제 요건을 동시에 만족하는 범용 인증 플랫폼. 이번 자료는 그런 범위의 수요나 실현 가능성을 입증하지 않는다.

## 8. 추가로 수집할 실사용 증거 — 아직 수행하지 않은 조사안

문헌으로 확인할 수 없는 “우리 팀이 해결할 문제”는 짧은 현장 조사로 좁혀야 한다. 아래 인원·기준은 운영 가능한 예시이며 통계적 대표 표본을 뜻하지 않는다.

### 8.1 초기 인터뷰

8~12명의 후보 사용자를 대상으로 최근 실제 도입 사례 하나를 따라간다. 개발자만 모집한 경우 n8n 비개발 사용자 전체로 일반화하지 않는다. 기업 담당자에게는 팀 정책과 개인 사용을 구분해 질문한다.

1. 가장 최근 외부에서 가져온 구성은 무엇이며 어디서 발견했는가?
2. 실제 프로젝트에 넣은 파일·설정·커밋 중 비밀정보를 제거하고 보여 줄 수 있는 것은 무엇인가?
3. 설치만 했는가, 최근에도 실행했는가? 실행 여부를 어떤 자료로 확인할 수 있는가?
4. 이후 업데이트나 로컬 수정을 했는가? 누가 승인했는가?
5. 출처·권한을 확인할 때 사용한 기존 도구와 최종 결정은 무엇이었는가?
6. 사용을 포기했거나 검토를 생략한 최근 사례가 있는가?

“이런 보안 플랫폼이 있으면 쓰겠는가”를 먼저 묻지 않는다. 아이디어 호감보다 실제 행동과 검토 증거를 수집한다. 비밀키·사내 데이터·전체 대화 로그는 수집 대상에서 제외하고 필요한 메타데이터만 받는다.

### 8.2 관찰 기록 단위

| 필드 | 의미 |
|---|---|
| 익명 사용자·팀 ID | 같은 사람의 반복 사례를 독립 사용자로 세지 않기 위해 사용 |
| 도입 사건 ID·날짜 | 구성요소 수와 도입 횟수 분리 |
| 구성 유형·호스트·목적 | 특정 호스트의 결과를 전체 생태계로 확대하지 않기 위한 구분 |
| 원본 위치·고정 버전·로컬 수정 여부 | 외부 유입과 파생 관계 확인 |
| 실제 사용 증거 수준 | 설치 / 설정 등록 / 실행 로그 확인 / 인터뷰 진술 |
| 검토자·기존 도구·결정 | 보안 검토가 발생한 지점 확인 |
| 시간·막힌 이유·재검토 계기 | 문제의 반복성과 비용 확인 |

### 8.3 진행·축소 기준

반복 도입·변경 사례와 검토 공백이 여러 사용자에게서 확인되면 02·05 문서의 과업 평가로 넘어간다. 대부분 공식 패키지만 쓰고 현재 조직 도구로 곧바로 승인할 수 있다면, 외부 유통 플랫폼보다 팀 내부의 변경 검토에 범위를 좁힐 수 있다. 사용 자체가 드물다면 그 사용자군을 첫 대상으로 삼지 않는다.

이 기준은 “문제를 반드시 발견하기 위한 조사”를 피하기 위한 것이다. **수요가 약하다는 결과도 유효한 프로젝트 판단 근거**로 남긴다.

## 9. 계획서에 사용할 수 있는 진술

> 공개 연구는 Skills의 프로젝트 내 재사용과 MCP 배포물의 이용 신호를 보여 준다. 따라서 외부 AI 워크플로 구성요소의 도입은 실제 검토 대상이다. 본 프로젝트는 그중 개발용 Skill·MCP 구성의 도입·변경 검토에 초점을 맞추며, 대상 사용자의 검토 부담과 기존 도구 대비 추가 가치는 별도 평가한다.
