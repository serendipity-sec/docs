왜 n8n 자동화를 보안 검토해야 하나

n8n은 여러 앱을 연결해 일을 자동으로 처리하는 도구입니다. 워크플로우는 한 가지 일을 수행하도록 연결한 단계들의 실행 절차이고, 각각의 단계를 노드라고 부릅니다. AI가 연결된 경우 모델의 판단이 이후 어떤 도구가 호출되고 어떤 값이 전달될지에 영향을 줄 수 있습니다. [n8n 기본 개념]

도구는 연결된 계정의 권한으로 동작합니다

요청을 보낸 사람의 권한과 자동화에 연결된 서비스 계정의 권한은 다를 수 있습니다. 워크플로우는 두 권한 사이에서 요청자의 신원, 데이터의 소유자, 허용된 수신처를 확인해야 합니다.

업데이트가 데이터의 길을 바꿉니다

새 도구, 바뀐 연결, 느슨해진 확인 조건은 각각 작은 변경일 수 있습니다. 그 변경이 기존 데이터나 권한과 결합하면 이전에는 닿지 않던 자료나 동작에 닿을 수 있습니다. 평소 쓰는 입력은 여전히 정상적으로 처리될 수도 있습니다.

  2. 조건·AI가 다음 단계 결정외부 내용이 어느 판단에 영향을 주나
  3. 연결된 도구 호출누구의 권한으로 무엇에 접근하나

FlowDelta의 설계 이 업무의 정책을 기준으로, 이 변경이 어느 금지 효과를 새로 만들었나? 변경 경로에 맞춰 시험과 필요한 관측을 고르고, 같은 조건의 실행 증거에 정책을 적용해 원본 변경과 버전별 판정을 연결합니다.

그래프, 변경 비교, 제한된 전후 실행은 기존 도구에도 있습니다. 팀이 검증할 차이는 같은 시간과 시험 횟수에서 변경 경로와 지식 검색으로 시험을 고르면, 고정된 시험 순서나 단순 텍스트 검색보다 보안 회귀를 더 많이 확인하는가입니다. [비교군·평가 계획]

검사 엔진의 아키텍처

검사는 비교 조건 고정 → 변경 분석 → 시험 선택 → 실행과 관측 → 정책 판정 → 보고 순서로 이어집니다. 각 단계는 다음 단계가 검증할 수 있는 자료를 넘깁니다. 아래 구성도를 누르면 각 단계의 입력과 출력을 볼 수 있습니다.

  1. 입력비교 조건 고정전후 버전과 업무·정책
  2. A변경과 영향 분석바뀐 경로와 위치
  3. B시나리오 검색·계획시험과 필요한 근거
  4. C검사 실행·관측전후 실행과 증거
  5. 판정관측을 정책과 대조위반·차단·판단 불가
  6. 보고버전별 결과 정리검토용 보고서와 포털

지식 저장소는 B에 시나리오 카드를 제공합니다. 실행 환경은 C의 계획을 소비하고, 판정기는 독립 관측과 고정 정책을 받습니다.

입력 · 어떤 조건에서 비교할지 정한다
입력

n8n의 전후 워크플로우 파일, 업무 목표, 보안 정책, 환경과 초기 데이터.

설계

파일과 참조를 검증하고 노드·연결·설정을 같은 형태로 정리합니다. 워크플로우 변경에 집중하는 현재 경로는 정책, 의존성, 모델 설정을 고정하고 두 실행에 같은 초기 데이터를 각각 복제합니다.

출력

비교할 스냅샷과 원본 참조, 동일한 입력을 확인하기 위한 해시.

예를 들어 업무 목표는 정상 완료의 기준을 정하고, 정책은 보호할 자원·허용 주체·동작·예외를 정합니다. 스냅샷은 특정 버전의 입력을 다시 찾을 수 있는 기록입니다. [고정 입력 계약]

A · 바뀐 부분이 어디에 영향을 줄지 찾는다
입력

정규화된 전후 워크플로우, 노드 의미와 명시된 정책 연결.

설계

노드와 관계를 그래프로 표현합니다. 실행 순서와 데이터가 이동하는 경로를 따라가며 변경된 설정·연결의 영향 범위를 좁힙니다. 지원되는 정책의 대상 노드와 연결되면 그 정책도 함께 표시합니다.

출력

analysis.json에 변경 위치, 가능한 영향 경로, 지원 제한을 기록합니다.

전체 설계는 모델이 읽는 지시, 권한, 하위 구성요소까지 관계에 포함하는 방향입니다. 현재 경로의 증거 수준은 지원 범위에서 추론한 정적 가능성입니다. [A 분석 계약]

B · 정책과 변경 경로에 맞는 시험을 고른다
입력

A의 분석, 업무·정책, 시나리오 카드, 실행기가 지원하는 검사 목록.

설계

사례와 규칙을 출처·적용 조건·필요한 증거가 있는 카드로 저장합니다. 변경 경로와 관련성이 높은 카드를 검색해 정상 업무와 보안 확인에 필요한 시험을 고릅니다. RAG는 검색한 근거를 모델에 함께 주어 시험 후보를 선택하도록 돕는 방식입니다.

출력

plan.json과 검색 근거. 검사 종류, 입력·범위, 수집할 자료와 제한을 명시합니다.

모델이 제안한 계획은 등록된 시험과 허용 범위에 맞는지 검사합니다. 증거가 필요한 필수 시험은 그대로 유지하고, 검색·모델·계획의 버전을 남깁니다. [B 검색과 계획] [공유 검색·모델 선택]

C · 등록된 검사로 전후의 기록을 모은다
입력

B의 계획과 기준 입력, 승인된 템플릿과 실행 환경.

설계

정적 검사는 파일에서 경고를 찾습니다. 동적 검사는 지원하는 전후 버전을 같은 조건의 별도 환경에서 구동하고 응답·서비스 이벤트·전후 상태를 수집합니다. 정상 업무 입력으로 기대한 업무 동작도 확인합니다.

출력

정적 경고 또는 실행 기록과 원본 증거. 실행·수집·정리 상태를 각각 남깁니다.

등록된 실행기는 격리 환경과 합성 데이터에 연결합니다. 지원과 실행 완료 상태를 기록해 관측 가능한 범위를 알 수 있게 합니다. [통합 실행 경로] [정적 검사 계약]

판정 · 실제로 일어난 동작이 규칙에 어긋나는지 확인한다
입력

사전에 정한 보안 정책, 신뢰할 수 있는 요청 주체, 자원 상태와 독립 기록.

설계

같은 실행의 기록인지, 누가 어떤 자원에 어떤 효과를 일으켰는지, 증거가 충분한지 확인합니다. 프로그램이 재현 가능한 규칙을 적용해 실행별 보안 결과를 정합니다.

출력

시험에서 관측된 위반·차단·미관측·판단 불가와 판정 근거.

등록 주문 조회의 판정은 실행 결과와 짝을 이루는 별도 보고서에 저장합니다. 정상 업무의 완료, 실행기 상태, 정책 위반을 각각 확인할 수 있습니다. [독립 판정 계약]

보고 · 어떤 버전에 무엇이 확인됐는지 보여준다
입력

같은 정책과 시험으로 얻은 전후 판정, 변경 위치와 근거.

설계

새로 관측된 위반, 양쪽에서 관측된 기존 문제, 수정 후 시험 결과를 연결합니다. 사용자는 사례별 정상 업무, 관측한 효과, 시험하지 못했거나 판단할 수 없었던 범위도 확인합니다.

출력

검토용 버전 비교와 정제된 공개 결과. 원본 실행 자료는 내부에서 추적합니다.

공개 화면은 열람을 담당합니다. 관리자가 등록하거나 검사를 요청하는 흐름을 기획했고, 현재 결과 앱의 계약은 검사 환경에서 공개 형태로 정제한 결과를 받도록 구성되어 있습니다.

시스템 설계에서 실행을 담당하는 프로그램과 결과를 보여 주는 웹 서비스는 분리됩니다. 결과 화면에는 필요한 공개 정보만 넘기며, 팀은 검사 요청을 대기열로 처리하는 방향을 정했습니다. [서비스 회의] [결과 앱 계약]

고정된 정책이 허용하는 업무와 금지하는 효과를 먼저 정합니다. 시험에서는 신뢰할 수 있는 요청 주체, 실제로 동작이 닿은 자원, 서비스 기록을 같은 실행에 연결합니다. 관측 범위와 필요한 증거가 충족됐는지도 확인합니다. [판정 프로토콜]

위반 관측

독립 기록으로 해당 정책이 금지한 효과를 확인했습니다.

차단 관측

보호 조건이 금지 동작을 명시적으로 거절했고, 해당 기록이 확인됐습니다.

위반 미관측

정해진 시험과 관측을 마쳤고, 검사 범위에서 금지 효과가 확인되지 않았습니다.

판단 불가

실행이나 수집이 불완전하거나 필요한 기록을 해당 요청에 연결할 수 없습니다.

같은 조건의 두 결과를 비교

이전 시험에서는 차단되거나 완전한 관측에서 위반이 없었고, 변경 후 위반이 관측되면 그 시험에서 새로 확인한 보안 회귀입니다. 양쪽에서 같은 위반이 관측되면 기존 문제로 구분합니다. 여러 변경이 같이 들어갔다면 처음에는 그 변경 묶음의 효과로 기록합니다.

수정 뒤에는 정상 업무도 다시 확인

같은 시험에서 금지 효과가 사라졌는지와 정상 업무가 계속 되는지를 각각 검사합니다. 시험하지 못한 경로는 보고서의 검사 범위에 그대로 표시합니다. [비교와 재검증]

연구 사례로 따라가는 검증 흐름

팀이 선정한 공개 워크플로우 n8n-claw의 기억 삭제 변경을 보면, 변경 위치를 찾는 일과 효과를 확인하는 일의 역할이 드러납니다.

추가된 삭제 기능과 소유권의 경계

  1. 업무와 정책. 기억 삭제는 업무에 필요한 기능입니다. 연구 정책에서는 일반 사용자가 본인 기억만 삭제할 수 있고, 지정된 관리자의 권한은 별도로 정의합니다.
  2. 업데이트의 변화. 기억 삭제 도구가 에이전트에 연결됐습니다. 팀은 삭제 단계에서 요청자와 대상의 소유자를 확인하는 조건이 빠진 버전을 분석했습니다.
  3. 독립 관측. 팀이 선택한 도구를 합성 환경에서 재생했을 때 타인의 가상 기억이 사라졌습니다. 소유자 검사 등을 추가한 보완 버전에서는 같은 타인 삭제가 차단됐습니다.

이 결과는 선택한 도구 코드와 합성 수신부에서 확인했습니다. 전체 n8n과 실제 모델을 거친 경로의 실행 가능성은 별도 검증 대상입니다. 팀이 조사한 고정 버전의 공개 정적 도구 5개는 이 취약 버전과 보완 버전을 구분하지 못했습니다. [사례 근거] [비교 기록]
