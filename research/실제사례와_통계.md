# 실제 보안 사고 사례와 통계

조사일 2026-09-17 · 발표자료·제안서 보강용

> 제안서 v2에는 사례가 Acronis와 Cline **2건**뿐이다. 조사해보니 훨씬 많고,
> 그중 **postmark-mcp 사건은 이 프로젝트의 문제의식 그 자체**다.
> 발표에서 이 한 건만 제대로 이야기해도 "왜 이게 문제인가"가 설명된다.

## 1. ★ 대표 사례 — postmark-mcp 백도어 (2025년 9월)

**발표에서 이 한 건에 시간을 쓰세요.** 나머지는 목록으로 넘기면 됩니다.

### 무슨 일이 있었나

파리의 한 소프트웨어 엔지니어가 **실명과 정상 프로젝트가 가득한 GitHub 프로필**로,
Postmark(이메일 발송 서비스)의 공식 MCP 서버 코드를 그대로 복사해 npm에 `postmark-mcp`로 게시했다.

| 버전 | 내용 |
|---|---|
| **v1.0.0 ~ v1.0.15** | **전부 깨끗했다.** Postmark 공식 GitHub 코드의 정확한 복사본. 15개 버전 동안 정상 동작 |
| **v1.0.16** | **코드 231번째 줄에 BCC 한 줄 추가.** 이 패키지로 보낸 모든 이메일이 `phan@giftshop.club`으로 복사됨 |

- 주간 다운로드 약 **1,500회**
- 유출된 것: **청구서, 비밀번호 재설정 메일, 내부 커뮤니케이션**
- Koi Security가 2025년 9월 발견. **최초로 실제 확인된 악성 MCP 서버 공급망 사고**

### 왜 이게 우리 프로젝트의 핵심인가

```
v1.0.15  →  v1.0.16
깨끗함        한 줄 추가
              + BCC: phan@giftshop.club
```

- **15개 버전이 깨끗했다.** 즉 "이 패키지는 검토했고 문제없다"는 판단이 **이미 내려진 상태**였다.
- 한 줄 추가로 그 판단이 뒤집혔다. **승인은 한 순간이었지만 신뢰는 지속되지 않았다.**
- 이게 OWASP **AST07 Update Drift**이고, MCP 용어로는 **rug pull**이다.
- 정적 스캐너가 "BCC 필드 추가"를 규칙 위반으로 잡을까? 이메일 도구에 BCC는 정상 기능이다.
  하지만 **버전 간 capability diff**로 보면 즉시 드러난다 — **v1.0.15에 없던 외부 주소가 v1.0.16에 생겼다.**

> 발표 문안 예시:
> "이 패키지는 15개 버전 동안 완전히 깨끗했습니다. 개발자는 실명을 썼고 GitHub 프로필도 정상이었습니다.
> 16번째 버전에서 코드 한 줄이 추가됐습니다. 이메일에 BCC를 거는 줄이었고, 수신자는 공격자였습니다.
> 저희가 만들려는 건 바로 이 한 줄을 사람에게 보여 주는 도구입니다."

## 3. 규모 통계

### 유통 규모

| 지표 | 값 |
|---|---|
| 공개 스킬 | 69,000개 이상 (skills.sh, 2026-02) · 67,453개 버전 (ClawHub 데이터셋) |
| ClawHub 마켓 성장 | ClawHavoc 공개 시점 2,857개 → 이후 **10,700개 이상** |
| MCP 서버 (공식 레지스트리) | **9,652개** |
| MCP 서버-버전 레코드 | **28,959개** — 서버 수의 **약 3배** |
| MCP SDK 다운로드 | 월 약 5억 회 (2026-07) |
| 기업 도입 | 소프트웨어 조직 **41%**가 프로덕션 운영 |

> **28,959 / 9,652 = 약 3.0.** 서버 하나가 평균 세 번 넘게 갱신됐다는 뜻이고,
> 갱신마다 postmark-mcp 같은 순간이 생긴다. **이 비율 하나가 우리 주제의 근거다.**

### 악성 비율

| 조사 | 결과 |
|---|---|
| Bitdefender | 한 마켓플레이스에서 검사한 스킬의 **약 17%**가 숨겨진 악성 코드 포함 |
| ClawHavoc (Antiy) | 악성 패키지 **1,184개**, 발행 계정 12개 |
| Acronis TRU | 악성 스킬 **575개 이상**, 계정 13개 |
| Snyk | 확인된 악성 스킬의 **91%**가 전통적 멀웨어 패턴 + 프롬프트 인젝션을 **결합**해 양쪽 방어를 동시에 무력화 |

### 방어의 한계

| 조사 | 결과 |
|---|---|
| SkillCloak (홍콩과기대) | 패킹 기법이 스캐너를 **90% 이상** 통과 |
| Trail of Bits | ClawHub·Cisco·skills.sh 탐지기 우회. **4건 중 3건이 1시간 미만**에 개발 |
| 스캐너 불일치 (67,453건) | 지목된 스킬의 **81.9%는 단일 스캐너만** 탐지 · 세 스캐너 일치는 **0.69%** |
| CSA 연구 노트 제목 | "AI Agent Skill Scanners: **Bypassed Across the Board**" |

## 4. 탈취 대상 — 무엇이 실제로 털렸나

추상적으로 "위험하다"고 하지 말고 이 목록을 보여 주면 됩니다.

| 사건 | 페이로드 | 탈취 대상 |
|---|---|---|
| ClawHavoc | **Atomic macOS Stealer (AMOS)** | macOS 키체인 인증정보, 브라우저 데이터, 암호화폐 지갑, **텔레그램 세션**, SSH 키 |
| Oura MCP | **StealC** | 개발자 인증정보, 비밀번호, API 키, 암호화폐 지갑 |
| postmark-mcp | 자체 BCC | **청구서, 비밀번호 재설정 메일, 내부 커뮤니케이션** |
| ClawHub 전반 | 소셜 엔지니어링 후 명령 실행 | 거래소 API 키, 지갑 개인키, SSH 인증정보, 브라우저 비밀번호 |

공통점: **개발자 PC의 인증정보**가 표적이다. 학생 개발팀도 정확히 같은 표적이다.

## 5. 발표자료에 어떻게 넣을 것인가

현재 08번 슬라이드("왜 지침도 공급망 보안 대상인가")에 Acronis·Cline 2건만 있습니다.
이걸 **두 장으로 나누기를** 권합니다.

### 슬라이드 08 — 대표 사례 한 건 (신규)

> 제목: **15개 버전이 깨끗했고, 16번째에서 한 줄이 추가됐다**

왼쪽에 버전 타임라인 도식, 오른쪽에 세 줄:

- `v1.0.0 ~ v1.0.15` — Postmark 공식 코드의 정확한 복사본. 15개 버전 동안 정상
- `v1.0.16` — 코드 231행에 BCC 한 줄. 모든 이메일이 `phan@giftshop.club`으로
- 주간 1,500 다운로드 · 청구서·비밀번호 재설정 메일·내부 문서 유출

하단 강조:
> 개발자는 실명을 썼고 GitHub 프로필도 정상이었다.
> 문제는 "누가 만들었나"가 아니라 **"승인 이후에 무엇이 바뀌었나"** 였다.

### 슬라이드 09 — 사건과 통계 (기존 08 확장)

위 2장 타임라인에서 6~7건만 고르고, 3장 통계에서 4개 숫자만 뽑습니다.

추천 조합:
- 사건: postmark-mcp · ClawHavoc(1,184개) · Oura MCP(StealC) · mcp-remote(437,000) · nginx-ui(2,600) · Cline
- 숫자: **28,959 / 9,652** (버전이 서버의 3배) · **17%** (Bitdefender) · **81.9%** (단일 스캐너) · **90%+** (SkillCloak 우회)

> 각 숫자 옆에 "해석의 한계"를 한 줄씩 붙이세요. 지금 발표자료의 동향 표가 그렇게 돼 있고,
> 그게 이 발표자료의 가장 좋은 점입니다. 사례 표에도 같은 규율을 적용하면 됩니다.

## 6. 인용할 때 주의할 것

- **사건 유형을 섞지 말 것.** 악성 구성요소 유포(ClawHavoc), 정상 제품의 취약점(nginx-ui CVE),
  배포 계정 침해(Cline), 스쿼팅 후 백도어(postmark-mcp)는 **서로 다른 사건 유형**이다.
  합쳐서 "AI 공급망 사고 N건"으로 부풀리면 안 된다.
- **다운로드 수 ≠ 피해자 수.** 437,000은 영향 가능 환경 수이지 실제 피해자가 아니다.
- **17%는 한 마켓플레이스의 표본**이다. 전체 스킬의 악성 비율이 아니다.
- **우리 도구가 이 사고들을 막았을 것이라고 주장하지 말 것.** postmark-mcp는 capability diff로
  **보여 줄 수 있었을** 유형이고, 그것도 사용자가 재검토를 했을 때의 이야기다.
  nginx-ui CVE나 Cline 계정 침해는 우리 범위 밖이다.
