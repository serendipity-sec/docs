# FlowDelta의 10주 실행 계획과 논문 평가 명세

개정 기준: 4명·8~10주의 초기 계획, 2026년 10월 9일 통합 설계. 연구 평가를 우선하는 재사용 가능한 오픈소스 코어를 목표로 한다. [입력·데이터 기준](input-and-data.md), [4인 역할·산출물·검토 기준](team-roles.md)과 함께 사용한다. 숫자는 확보·성능 실적이 아닌 계획이다. 주차는 착수일 기준 상대 주차다. 8주까지 시제품과 핵심 비교 결과를 확보하고, 9~10주에 확장 실험·오류 분석·논문 초안을 완성한다.

## 시간과 자원 가정

기술 책임은 팀장·A·B·C로 구체화했다. 실제 이름 배정·주당 가용 시간·예산은 아직 확정하지 않았다. 과거의 매일 10시간·주 7일 가정으로 계산한 투입량을 확정 자원으로 사용하지 않는다. 첫 파일럿에서 사례당 작성·실행·라벨링·초기화·검토 시간을 측정하고 가능한 독립 계열 수를 정한다. 주차표는 순서와 초기 목표이며 완료를 보장하는 일정이 아니다. 아래 완료 기준을 충족하는지로 진행을 판단한다.

일반 개발 PC 외에 Linux 실행 VM과 증거 저장 공간이 필요하다. API 모델을 사용할 경우 자체 학습 GPU는 필수가 아니다. 동시 실행 수는 CPU·메모리·모델 rate limit과 관측기의 안정성을 측정한 뒤 설정한다. 불신 패키지 실행과 연구자 개발 환경을 분리한다.

## 네 명의 모듈 책임

**팀장·A·B·C 네 명 모두 핵심 기능을 구현한다.** A 분석 → B 계획 → C 실행·관측 → 팀장 증거 검증·판정으로 나눈다. 이름은 적지 않는다. 역할별 4개 작업 묶음, 입출력·완료 기준·디렉터리 제안·첫 제출물은 [역할 상세 문서](team-roles.md)에 있다.

| 담당 | 주 구현 책임 | 산출물 | 교차 검토 |
|---|---|---|---|
| A | 입력, n8n 의미, 그래프·변경·영향, 필수 항목, 정적 비교군 | Snapshot·ComparisonCase·Graph·ChangeSet·VerificationObligation 정의 | C의 의미 대조, B·팀장의 소비 계약 |
| B | 카드·검색·가설·계획·검사, 검색 비교군·집계 | ScenarioCard·Hypothesis·TestPlan, 정책 근거표·집계 코드 | A 경로·조건, C 실행 형식, 팀장 판정 요구 |
| C | 환경·서비스·전후 실행·독립 관측·초기화·반복 | ExecutionRun·EvidenceEvent·상태·관측기/초기화·비용 기록 | 팀장 증거 적격성, A 실제 의미 |
| 팀장 | 증거 검사·정책/업무 assertion·항목 장부·전후 비교·보고 | Finding·업무 결과·미확인 목록·JSON/Markdown 보고서 | B 정책·상태, C 증거, A 변경 근거 |

공통 ID·CLI 골격은 A가 준비하고 각자 자기 객체 스키마·명령을 구현한다. 데이터는 B의 업무·정책 근거 → A의 원본·변환·계열 관리 → C의 상태·실행·관측 → 팀장의 assertion·판정 명세로 나눈다. 정답은 사례별 초안 작성자 1명, 각자 먼저 판단하는 검토자 2명, 불일치 조정자 1명을 둔다. 제작 참여 이력을 공개하고 외부 맹검으로 주장하지 않으며 최종 정답을 검색·튜닝에 사용하지 않는다.

B가 공통 지표를 집계하고 A는 계열·분모, C는 원시 비용, 팀장은 판정 상태·통계 해석을 확인한다. 팀장은 평가 동결·주요 통합을 조정하되 모든 작은 수정에 추가 승인을 요구하지 않는다. 네 명 모두 코드·검증·사용 안내와 자기 논문 부분을 작성한다. 구현 시간의 비율은 가용 시간과 파일럿 측정 전에는 고정하지 않는다.

G0에서 같은 사례의 입력·분석·수동 plan·합성 증거·기대 판정 표본을 공유해 네 명이 병행한다. G1 정상 업무 한 건 → G2 두 업무의 전후 연결 → G3 검색·계획 자동화 → G4 파일럿·동결 → G5 평가·재현·공개 준비로 통합한다. 아래 72시간 목표와 주차표는 이 관문을 달성하기 위한 초기 순서다.

## 먼저 통과할 완료 기준

| 순서 | 할 일 | 완료를 확인할 산출물 |
|---|---|---|
| 1 | 실제 업무 후보와 가장 가까운 기존 도구 확인 | 원본·변경 이력·정책/상태 자료 목록, 중복 기능과 추가 검증 질문 |
| 2 | 후보에 맞춰 n8n 지원 동작 확정 | node/typeVersion/operation별 계약, 정상 입력에서 실제 n8n과의 일치·불일치 기록 |
| 3 | 비교 입력과 필수 검증 항목 확정 | TaskContract·ComparisonCase·VerificationObligation 및 미실행/미지원/관측 실패 처리 |
| 4 | 서로 다른 두 업무 사례에서 전체 흐름 연결 | 전후 분석 → 독립 증거 → 정상 업무 결과 → 초기화 확인 |
| 5 | 비용·변동성·수작업 측정 | 사례·반복·토큰·시간·라벨링 비용, 실제 가능한 평가 규모 |
| 6 | 평가 동결과 재사용 검증 | 계열 분할·설정 해시, 비교 실험, 다른 팀원의 새 입력 연결과 재현 기록 |

이 순서는 날짜가 지나면 자동으로 완료되는 계획이 아니다. 데이터 출처를 확인하기 전에 지원 동작 수나 평가 건수를 확정하지 않는다.

## 첫 72시간의 초기 목표

첫날에는 [공개 후보 14550·18499와 τ 자료](input-and-data.md)를 검토해 업무·노드 동작·정책 출처·정상 완료 조건을 정리한다. P1·P2의 지원 형식, 통제 표면, TaskContract·ComparisonCase·검증 항목과 기존 공통 객체의 필드를 합의한다. 정상 workflow 1개, 위험 변경 1개, 정상 변경 1개를 손으로 먼저 정의한다. 지원 n8n 버전·노드 버전·모델·컨테이너 digest와 기존 실험의 재사용 범위를 기록한다.

둘째 날에는 도구 호출을 고정한 상태에서 모의 문서 조회·내부 전송·외부 역할 수신·문서 변경을 실행한다. 정상, 위반, 대상 통제 차단, 관측기 고장을 각각 구분한다. 합성 canary를 공격 입력에 넣지 않아야 한다.

셋째 날에는 작은 변경 그래프에서 카드 5~10개를 검색하고, 하나의 구조화 시험 계획을 실행기까지 전달한다. 사람 작성 plan으로 전체 흐름을 먼저 확인하고 자동 생성으로 교체한다. 이 시점의 결과를 탐지 성능으로 발표하지 않는다.

## 우선순위와 범위 조정

필수 P0는 n8n 어댑터, 정책 P1·P2, 변경·경로 분석, 시나리오 검색·시험 계획, 독립 효과 관측, 전후 비교, 정상 업무 검증, 정답 데이터·baseline·보고서다.

P1은 제한된 승인 계약, 두 번째 모델 일부 실험, 실제 권한 수집기 1종, 지식 카드 웹, 검색 순위 개선이다. P2는 LangGraph 전면 어댑터·재개 분석, 다양한 프레임워크 지원, 선택적 재분석 최적화, 사용자 계정·공개 서비스다.

| 문제가 생긴 시점 | 조정 |
|---|---|
| 2주에 기존 방법과 차별화할 사례를 확보하지 못함 | 논문 주장을 확대하지 않고 변경 벤치마크·시험 추천의 문제로 좁힘 |

## 지원 동작의 작은 계약

기존 설계의 12개 후보는 Manual Trigger, Webhook, Edit Fields, If, 단순 Merge, HTTP 조회, HTTP 전송·수정, AI Agent, Chat Model 연결, 고정 Execute Sub-workflow, Call n8n Workflow Tool, 구조화된 승인 wrapper다. 마지막 wrapper는 프로젝트의 시험 어댑터일 수 있으므로 n8n의 모든 native HITL 동작을 지원한다고 표시하지 않는다.

공개 후보에는 Google Sheets·Telegram·Slack·메모리·Code 등이 있어 이 12개와 일치하지 않는다. 원본 의미와 구현 비용을 확인해 필요한 계약을 선택한다. 12개는 고정 할당량이 아니다. 노드 유형 하나가 모든 동작·버전·배치 의미를 지원한다는 뜻은 아니다. 각 계약에는 지원 파라미터, 필드 매핑, source·sink, 외부 효과, 오류 동작, 버전, 테스트 fixture를 적는다. Merge는 지원한 병합 방식만, 표현식은 상수·필드 참조·제한된 문자열 결합·단순 비교부터 다룬다. item linking·동적 URL·임의 Code node를 완전히 해석한다고 주장하지 않는다. 특히 sub-node 표현식의 첫 item 참조, 배치 입력, 오류 출력, 재시도, 고정/동적 하위 참조를 계약별로 확인한다. 지원하지 못한 경로는 입력 전체에서 차지하는 비율과 함께 보고한다.

## 데이터셋 설계

초기 규모 가정은 독립적인 workflow 계열 30개와 각 계열의 변경 비교쌍 4개다. 확보 실적이나 필수 최소 수가 아니며, 위 완료 기준 5의 파일럿 후 최종 평가 전에 확정한다. 위험 변경 2개와 정상 변경 2개를 만들면 120쌍이며, 위험 60·정상 60쌍이다. 별도로 누락 의존성·동적 참조·권한 미확인·관측 실패 등을 포함한 unknown 20개를 구성한다.

독립 계열은 이름만 바꾼 예제가 아니다. 데이터 이동·분기·하위 호출·도구 노출·권한·승인 위치가 다른 구현 패턴으로 구성한다. 자료는 공개 원본·실제 변경 이력, 공개 업무 기반 통제 평가, 동의받은 운영자 사례로 구분한다. 실제 이력/연구자 변형이라는 변경 출처와 원본 유지/설정 대체/동작 변환이라는 이식 수준도 별도 집계한다. 운영자 사례는 아직 확보하지 않았다. 업무 요청 수·workflow 계열 수·비교쌍 수·실행 수를 따로 센다. τ의 114개 요청을 한 workflow에 넣어도 workflow 114개가 되지 않는다.

| 분할 | workflow 계열 | 변경 쌍 | unknown 사례 |
|---|---:|---:|---:|
| 개발 | 15 | 60 | 10 |
| 검증 | 5 | 20 | 4 |
| 최종 평가 | 10 | 40 | 6 |
| 합계 | 30 | 120 | 20 |

가능하면 공개 프로젝트의 실제 변경 10쌍을 추가 심층 사례로 확보한다. 10쌍은 필수 충족 실적이 아니며, 적격한 사례만 사용한다. 실제 원본에 팀이 위험 변경을 삽입했다면 실제 취약 이력으로 분류하지 않는다. 공개 workflow 약 50개를 추가로 정적 분석해 node·path coverage와 수동 계약 부담을 평가할 수 있지만, 이 집합 전체가 안전 또는 취약하다고 라벨링하지 않는다.

정상 변경에는 화면 좌표 이동만 넣지 않는다. 참조를 보존한 이름 변경, 허용된 수신자 변경, 불필요한 민감 필드 제거, 권한 축소, 동등한 분기 재구성, 하위 함수 분리, 정당한 재승인 등을 포함한다. 위험이 있는 원본의 무해 변경은 새 회귀가 없더라도 기존 위험이 유지되는 별도 사례다.

## 정답과 데이터 누수 관리

정답은 정책·공격자 통제 범위·코드 또는 구성의 의미·독립 실행 증거로 작성한다. 분석기의 경고나 생성 모델의 판단을 그대로 정답으로 쓰지 않는다. 두 명이 독립 검토하고 불일치는 제3자가 조정한다. 판단이 어려운 사례는 그 상태를 유지한다.

같은 원본, fork, 템플릿 파생물, 같은 원인의 수정본과 공격 변형은 한 계열로 묶는다. 최종 평가셋의 결과를 보고 규칙·검색 순위·프롬프트를 바꾸면 그 자료는 개발 데이터가 되며 별도 새 평가가 필요하다.

RAG에는 두 평가 모드를 둔다.

* 알려진 취약점 적용성: 정확한 공개 공지 검색을 허용하고 제품·버전·조건을 맞추는 능력을 평가한다.
* 보지 않은 변경·조합 일반화: 최종 계열의 구체적 코드·정답·공격 payload·패치 해설을 KB에서 제외한다. 일반 공격 원리 카드는 사용할 수 있다. 별도의 공격 원리 보류 실험을 한다면 그 원리 카드도 제외한다.

시나리오 지식 corpus와 평가 corpus의 해시·별칭·출처·근접 중복을 점검한다. private knowledge에도 최종 정답이나 oracle 소스를 넣지 않는다. 공개 모델의 사전학습 누수는 완전히 배제할 수 없으므로 한계로 보고한다.

## 연구 질문과 비교군

우선 연구 질문은 **환경·하위 의존성·정책의 의미를 포함했을 때 부모 구성만 보는 방법의 누락을 줄이고 실제 회귀를 확인할 수 있는가**다. 추가 질문은 **같은 시험 예산에서 변경과 그래프 조건을 사용하는 검색·시험 선택이 확인된 회귀 수를 높이는가**다. RAG는 이 추가 질문에서 기여를 분리한다. 조건 검사로 잘못된 적용을 줄이는지도 측정한다.

| 비교군 | 사용 정보 | 측정 목적 |
|---|---|---|
| B0 노드·설정 규칙 | 전체 정적 구성 | 단순 스캐닝 수준의 후보 탐지 |
| B1 전체 재분석 후 결과 비교 | 양쪽 전체 그래프·동일 정책 | 동일 의미 모델의 기준 구현, 최적화와 의미 비교; 독립 정답은 아님 |
| B2 일반 RAG | 텍스트 diff와 동일 KB·LLM·예산 | 그래프 조건이 없는 검색과 비교 |
| B3 그래프 조건과 고정 시나리오 | 전체 구조·정책·정해진 카드, LLM 검색 없음 | RAG 추가 가치와 지식 검색 비용 |
| B4 제안 방법 | 변경·영향 그래프·조건·혼합 검색·LLM | 종단 간 방법 |
| B5 고정 회귀 시험 | 같은 등록 시나리오와 대상, 변경별 검색·우선순위 없음 | 기존 회귀 시험을 모두 수행하는 방식의 예산 효율 |

외부 도구 비교에는 [n8n-ai-agent-security-lab](https://github.com/0xCD4/n8n-ai-agent-security-lab)을 가장 가까운 비교 대상으로 추가한다. 문서상 정적·변경 기능과 제한된 rehearsal을 구분해 공통 범위를 고정한다. 실행하지 않은 성능은 NOT_RUN이다. FlowGuard·n8n Audit은 공통 정적 규칙만, OWASP 하네스·Promptfoo는 공통 동적 시나리오만 비교한다. 도구가 입력을 지원하지 않거나 환경에서 실행하지 못했다면 미탐이 아니라 UNSUPPORTED 또는 NOT_RUN이다. 공개 기능 설명에 해당 기능이 없다는 이유로 실제 성능을 0점으로 쓰지 않는다.

기능 제거 실험은 B4에서 변경 정보 제거, 환경 제거, 하위 의존성 제거, 지시 영향 제거, 검색 제거를 각각 수행한다. 검색 실험에서는 generator·victim 모델, KB snapshot, 시험 generator·oracle, 최대 토큰·시도·시간을 맞춘다. 검색 방식 외에 생성기나 관측기가 다르면 RAG만의 효과로 해석하지 않는다. 환경 정보가 추가된 비교는 추가 입력의 비용·수동 작업량도 함께 보고한다. 같은 코드를 두 번 검사하는 방식과 비교하지 않으면 변경 분석의 가치를 설명할 수 없다.

선택적 재분석을 구현할 때만 성능 주장을 추가한다. 같은 의미 모델의 전체 분석과 판정·근거 집합을 대조하고, 불일치가 있으면 원인을 해결하거나 최적화의 한계를 보고한다.

## 실행량과 비용 계획

아래 반복 3회·실행량은 비용 계산용 예시이며, 반복 수와 통계 계획은 파일럿 후 평가 동결 전에 결정한다. 기본 재현 실험 예시는 변경 40쌍 × 이전·이후 2버전 × 정상·공격 2조건 × 3회 × 모델 1종 = 480 episodes다. 확인된 위험 중 20쌍의 수정본을 정상·공격 2조건으로 3회 검증하면 120 episodes가 추가된다. 여기서 40쌍은 최종 평가 40쌍과 자동으로 같은 집합이라는 뜻이 아니며, 실제 평가에서 분할·용도를 지정한다. 최종셋에 포함된 실행은 freeze 후에만 수행한다.

별도의 예산 효율 실험은 최종셋의 위험 변경 20쌍에서 B2·B3·B4·B5의 4개 방법 × 2버전 × 버전당 최대 10회 공격 시도를 적용하면 상한 1,600 episodes다. 위험 여부의 정답은 방법에 제공하지 않는다. B5는 공통 시험을 실행할 수 있는 OWASP 하네스 또는 Promptfoo로 구성하며, 호환성 때문에 자체 실행기를 사용하면 그 차이를 공개한다. B0·B1은 정적 분석 비교군으로 유지한다. 정상 변경의 오탐은 앞선 고정 평가에서 별도로 측정한다. 정상 업무 대조는 대상이 같으면 동일 조건의 공통 실행을 참조할 수 있으며, 같은 실행을 독립 표본처럼 여러 번 세지 않는다. 방법별 중복 실행과 재사용 규칙을 로그에 기록한다.

이 두 실험은 고정 시험의 재현성과 검색·생성의 효율을 각각 보는 것이다. 에피소드 하나의 내부 도구 호출 수가 다를 수 있어 에피소드뿐 아니라 총 모델 토큰, 도구 호출, 벽시계 시간, 인프라 비용을 함께 제한한다. 실패한 시도도 예산에 포함한다.

첫 20~30개 pilot에서 에피소드별 토큰·지연·비용을 측정한다. 총 비용은 다음처럼 추정한다.

`모델 비용 = 입력 토큰 합계 × 입력 단가 + 출력 토큰 합계 × 출력 단가 + 임베딩·재정렬 비용`

단가의 단위는 제공자의 실제 청구 단위에 맞춰 환산한다. 예를 들어 2,000 episodes의 평균 모델 비용이 각각 0.03·0.10·0.30달러라면 합계는 60·200·600달러다. 이 값은 민감도 분석용 가정이며 현재 제공자의 가격 견적이 아니다. 실행 VM·저장·반복 실험 비용은 별도다. 파일럿 후 팀 지출상한과 실행 예산을 정하고, 초과 예상 시 사례 품질과 대조군을 유지하면서 반복·확장 범위를 줄인다.

## 측정할 지표

| 단계 | 지표 | 분모와 해석 |
|---|---|---|
| 추출 | 지원 노드·동작·필드·위험 경로 coverage | 전체 입력 대비 지원 비율, 수동 계약 비율 별도 |
| 검색 | Recall@5, nDCG@5, 적용 가능한 카드 비율 | 사람이 관련성을 라벨링한 질의 집합 |
| 생성 | 유효 계획 비율, 조건 모순 비율, 근거 없는 인용 비율 | 생성된 모든 계획, 거부된 계획 포함 |
| 후보 발견 | Precision·Recall·정상 변경 FPR | 정답이 있는 변경 쌍, 위험과 정상의 분모 공개 |
| 실행 | oracle 판정 정확도, 실행 실패율, 관측 불완전 비율 | 모든 계획·실행, 성공한 실행만 선택하지 않음 |
| 최종 확인 | unique confirmed regressions@budget | 같은 예산에서 독립 정답 회귀 중 확인한 수 |
| 회귀 비교 | 공격 성공률 차이와 효과 크기 | 이전·이후의 실제 시도수 및 대응 조건 |
| 기능 보존 | 정상 업무 성공률, 수정 후 성공률 | 공격 없는 정상 업무, 전부 차단한 구성을 감점 |
| 비용 | 확인 1건당 비용, 시간, 검토 시간 | 시나리오 작성·초기화·실패 처리 시간 포함 |
| 신뢰성 | UNKNOWN·abstention·미실행 비율 | 높은 정확도와 낮은 판정 coverage를 함께 표시 |

정적 후보 precision과 실행 확인 precision을 혼합하지 않는다. UNKNOWN을 true positive로 세지 않으며, 판단 가능한 사례만의 수치와 전체 사례에서 확정 결론을 내린 비율을 함께 낸다. 실제 공개 저장소 집합은 모든 취약점의 정답을 알 수 없으므로 전체 recall을 계산하지 않는다.

예산 효율의 주 지표는 정해진 예산 내 확인한 회귀 수다. 고정 시험 결과와 생성·탐색 결과를 구분한다. 동일 원인·동일 계열의 payload 변형을 여러 신규 취약점으로 세지 않는다.

통계는 workflow 계열을 재표집 단위로 한 bootstrap 신뢰구간 등을 사용한다. 120쌍을 120개의 완전히 독립적인 제품처럼 취급하지 않는다. 단일 사례의 반복 결과에는 성공 횟수와 시도 수를 같이 제시하고, 구버전 0회 성공을 안전 증명으로 해석하지 않는다. 작은 표본에서 유의성이 없으면 그 한계를 그대로 쓴다. 예를 들어 최종셋 정상 변경 20개에서 오탐 0개라도 독립 시행을 가정한 단측 95% 오탐률 상한은 약 13.9%다(1−0.05^(1/20)). 계열 내 상관이 있으면 독립 가정도 낙관적이다. 같은 사례 3회 반복은 독립 업무 3개가 아니며, 매회 20% 확률인 현상을 3회 모두 놓칠 확률도 51.2%다(0.8^3). 목표와 관측 결과·불확실성을 구분한다.

## 사전 성공 목표와 완료 조건

아래 수치는 검증셋에서 조정할 수 있는 초기 목표다. 최종 평가 후 기준을 낮춰 달성으로 보고하지 않는다.

| 목표 | 초기 기준 |
|---|---|
| 후보 탐지 | 지원 범위의 정밀도 85% 이상, 재현율 80% 이상을 도전 목표로 설정 |
| 정상 변경 | 정상 변경 FPR 10% 이하 목표, UNKNOWN 비율 별도 |
| 검색 | 독립 라벨 질의에서 Recall@5 80% 이상 목표 |
| 종단 간 효율 | B2 대비 같은 예산의 확인 회귀 수 증가 여부 측정. 효과 크기는 결과로 보고 |
| 증거 연결 | 확정 finding 모두에 source·변경·시험·독립 증거 링크 존재 |
| 미확인 처리 | 관측 실패·미지원·미실행을 통과로 처리하는 계약 오류 0건 |
| 속도 | 명시한 장비·100노드 이하 지원 입력에서 정적 compare P95 30초 목표. 모델 실행 시간 별도 |

프로젝트 구현 완료에는 다음이 필요하다: 설치 가능한 코어, 버전 고정 재현 환경, P1·P2 전체 경로, 데이터셋과 라벨 근거, 최소 정적·동적 baseline, 수정 후 정상 업무 검증, 실패·UNKNOWN 보고, 다른 팀원의 clean-machine 재실행과 지원 범위의 새 사례를 코어 수정 없이 연결한 기록. 설치·입력 작성·수동 환경 정의에 든 시간과 미지원 이유를 남긴다. P3를 추가했다면 그 지원 범위와 별도 평가를 명시한다.

연구 완료에는 비교 실험이 어떤 가설을 지지하거나 지지하지 않는지, 수동 입력·추가 정보·비용의 차이가 무엇인지 설명해야 한다. 수치가 목표에 못 미쳐도 원인과 한계가 있는 완성된 연구가 될 수 있다. 단순 UI 완성이나 경고 수 증가만으로 연구 기여를 입증한 것은 아니다.

## 논문과 공개 아티팩트

가제는 “FlowDelta: Change-Aware Scenario Retrieval and Differential Validation for AI Workflow Security”로 둔다. 제목의 기능들은 제안 내용이며 구현 전에 완성 성과처럼 초록에 쓰지 않는다.

논문은 문제·동기, 위협 모델과 정책, 보안 그래프와 변경 의미, 조건 기반 검색·시험 생성, 실행 판정, 변경 벤치마크, 비교·기능 제거 실험, 사례 연구, 한계 순으로 작성한다. 2주차부터 서론·위협 모델을 쓰고, 6주차에 평가 계획을 고정하며, 8주차에 결과를 넣는다.

공개 후보 아티팩트에는 소스·lock·digest, 스키마·지원 계약, 재배포 가능한 workflow와 카드, 출처·라이선스, 라벨 근거, baseline 설정, 실행 명령, 원시 결과와 집계 스크립트, 실패 사례, 재현 가이드를 포함한다. 미공개 취약점·사내 데이터는 별도 취급하고 공개 저장소에 자동 업로드하지 않는다.

8~10주 동안은 재현 가능한 논문 초안을 목표로 한다. 구체적인 학회·저널 선택과 투고일은 결과의 깊이·모집 일정·공개 정책을 확인한 뒤 정한다. 최상위 학회 채택이나 신규 CVE 수를 일정의 성공 기준으로 두지 않는다.
