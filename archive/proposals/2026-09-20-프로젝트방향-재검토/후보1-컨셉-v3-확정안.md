# 후보 1 컨셉 v3 (확정안) — 규칙을 아는 검사기

작성 2026-09-21 · 김민우 · **A 방향("만든 것으로 승부") 확정. 이제 조사 그만, 설계 시작.**

> v1: 발견→수정 흐름 (기존 도구에도 있음 — A 실험이 부정)
> v2: "AI는 규칙을 모른다" (논지는 맞으나 임팩트 약함)
> **v3: 스캐너는 코드 패턴만 본다. 우리는 "누가 무엇에 접근해도 되는가"라는 규칙을 알고 검사한다.**

이번엔 근거가 다 있다. 실험 5개(A 도구비교·B 논문·C 생성앱·D 교수님앱·표본10개)로 검증 끝.
더 조사하지 않는다. 여기서부터는 만든다.

---

## 1. 한 문장 · 한 대비

**한 문장**: "일반 스캐너는 코드에서 위험한 *패턴*을 찾는다. 우리 도구는 이 서비스의 *접근 규칙*을 알고, 그 규칙이 실제로 지켜지는지 요청을 보내서 확인한다."

**한 대비** (이게 발표의 심장):

| | 일반 스캐너 (Semgrep 등) | 우리 |
|---|---|---|
| 보는 것 | 코드 패턴 (XSS·SQLi 문법) | 사용자·자원 관계 (누가 누구 것을) |
| 아는 것 | 코드 안에 있는 것 | **사람이 선언한 규칙** |
| 실측 결과 | 4개 앱에서 경고 **1,109건** | 같은 앱에서 접근통제 결함 **0건 놓침** |

> **우리가 이미 확인한 사실이다.** hunminword(교수님)에서 Semgrep 0건, 표본 4개에서 1,109건 중 접근통제 0건.
> "스캐너가 못 보는 걸 우리가 본다"는 주장이 아니라 **측정된 결과**다.

---

## 2. 왜 스캐너가 원리적으로 못 하나 (발표 핵심 논리)

"우리 도구가 더 좋다"가 아니라 **"이건 스캐너로는 불가능한 종류의 문제다"** 로 간다. 훨씬 강하다.

```
스캐너의 입력 = 코드만
"이 API에 인증이 있어야 한다" 는 규칙은 코드에 없다 → 사람 머릿속에 있다
→ 어떤 스캐너도 없는 정보는 못 쓴다 (도구 성능 문제가 아니라 정보 부재)

우리의 입력 = 코드 + 사람이 선언한 규칙
→ "예약은 작성자만 수정" 을 알기 때문에, A로 B의 예약을 수정 요청해서 확인할 수 있다
```

이 논리를 **교수님 코드로 실증했다** — direction.txt는 인코딩까지 꼼꼼히 지시했는데 접근 규칙만 없었다.
부실해서가 아니라 **당연해서 안 적혔다** (논문 Hidden security rules 55%).

## 3. 결과물 — 엔진 1 + 두 얼굴

```
                    ┌─────────────────────────┐
                    │      규칙 검사 엔진        │  ← 핵심. 팀 공용
                    │  규칙 → 테스트 생성 →     │
                    │  A/B 계정 실제 요청 →    │
                    │  위반 판정 + 근거        │
                    └───────────┬─────────────┘
              ┌─────────────────┴─────────────────┐
        ┌─────▼──────┐                      ┌──────▼───────┐
        │  웹 얼굴     │                      │  CI 얼굴      │
        │  등록→규칙   │                      │  PR에서 자동  │
        │  선언→검사   │                      │  실행→차단    │
        │  →결과→수정  │                      │  →수정 코멘트 │
        │  발표·시연용 │                      │  실용·배포용  │
        └────────────┘                      └──────────────┘
```

**엔진이 진짜 결과물.** 웹은 발표·시연을 위한 얼굴, CI는 "진짜 쓸 것 같다"를 위한 얼굴.
같은 엔진을 두 군데 물리는 게 기술 기여이자 4명 분업의 축.

## 4. 발표 시연 — 3막 (임팩트 축 3개를 순서대로)

| 막 | 장면 | 임팩트 축 | 상태 |
|---|---|---|---|
| **1막 · 문제** | 데모 앱에 Semgrep 실행 → 경고 쏟아짐 → 근데 "남의 예약 삭제" 항목은 없음 → 초록불 | **스캐너 대비** | ✅ 근거 있음 (1,109 vs 0) |
| **2막 · 우리** | 규칙 선언("예약은 작성자만") → 우리 엔진 실행 → **브라우저에서 A가 B 예약 삭제 성공** → 빨간불 | **실제 삭제 장면** | ✅ C 실험에서 재현됨 |
| **3막 · 닫기** | 수정 프롬프트 → AI에 붙여넣기 → 재검사 초록 → **규칙 파일을 넣고 새 기능 추가 → 처음부터 안전** | **AI에게 되먹임** | ⚠️ ④ 미검증 → 아래 |

**세 축을 다 쓴다.** 1막이 "왜 필요한가"(스캐너 한계), 2막이 "우와"(눈앞 삭제), 3막이 "그래서 뭐"(재발 방지).
2막이 클라이맥스. 1막 없으면 "그냥 검사기"로 보이고, 3막 없으면 "한 번 고치고 끝".

## 5. 지금 남은 단 하나의 미검증 — ④ AI 되먹임

3막의 마지막(규칙 파일 넣고 새 기능 → 안전)만 아직 실측 안 했다. 이것만 확인하면 컨셉 전체가 근거로 닫힌다.
**우리가 만든 앱(vibe-app-baseline)으로 하면 된다 — 남의 코드 안 건드린다.**

실험: 같은 기능 요구를 로컬 AI에게 두 번 시킨다.
- (가) 규칙 파일 없이 "예약 시간 변경 기능 추가" → 소유권 검사 들어가나?
- (나) `CLAUDE.md`에 "예약은 작성자만" 넣고 같은 요구 → 이번엔 들어가나?
- (나)가 (가)보다 안전하면 3막 성립. 논문 §7이 이미 54→25/210으로 실측한 효과의 우리 버전.

→ 코덱스 지시는 [코덱스-지시-AI되먹임.md](코덱스-지시-AI되먹임.md)

## 6. 첫 학기 범위 (엄격하게)

| 만든다 | 안 만든다 |
|---|---|
| 규칙 검사 엔진 (규칙→테스트→A/B 요청→판정) | 범용 취약점 스캐너 (Semgrep 붙임) |
| 규칙 3종: 소유권 · 인증 필요 · 관리자 전용 | XSS·SQLi·CSRF 자체 탐지 |
| 웹 얼굴 (등록·규칙선언·결과·수정) | 자동 패치 적용 (프롬프트·패치 제안만) |
| CI 얼굴 (GitHub Action, PR 코멘트) | 실서비스 URL 스캔 (저장소/컨테이너만) |
| 지원: **Express/FastAPI + SQLite/Postgres**, 명시적 REST API | Supabase RLS 앱 (서버 정책이 코드 밖) — 후속 |
| 수정 프롬프트 + `CLAUDE.md` 규칙 조각 출력 | 다른 프레임워크 |

**주의(표본조사에서 배운 것)**: Supabase 앱은 RLS가 코드 밖(DB)에 있어 정적으로 안 보인다.
→ 첫 학기는 **인가를 코드에서 하는 앱**(Express/FastAPI)만. 이게 검사도 쉽고 시연도 명확.
