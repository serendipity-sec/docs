## 안건별 논의 내용

### 1. MCP 조사 발표 (박용준)

발표 PPT는 간결하게 두고 설명을 자세히 하는 방향이다. 목차는 추가할 예정이다.

**구조와 동작**

- 호스트(Claude, Codex 같은 애플리케이션)와 LLM이 연결된다.
- 호스트가 클라이언트 A/B를 통해 MCP 서버와 리소스에 접근한다.
- 도구 목록 조회 → 호스트의 승인·정책 판단 → 서버 호출 → 성공 응답 또는 JSON 오류 응답 순서로 동작한다.
- 요청·응답 예시는 실제 MCP README를 인용해 보강할 예정이다.

**7월 28일경 프로토콜 개정**

- 세션을 유지하는 stateful 방식에서 stateless 방식으로 바뀌었다고 한다.
- 커넥션 풀, 서버 부하 분산 문제가 개선됐다.
- 새 구조의 적용 여부가 구현마다 달라 생기는 문제가 있을 수 있다는 의견이 나왔다. 이는 MCP 단일 주제로 갈 경우 추가로 검토하기로 했다.

**공개 취약점 사례**

- Atlassian MCP의 전역 인증 처리 문제 (보안 뉴스에서도 다룸)
- DNS 리바인딩, SDK의 DNS 리바인딩
- Kubernetes MCP 인자 주입 (자원 이름이 kubectl 옵션으로 해석됨)
- Git MCP 저장소 경계 오해
- Inspector 인증 누락과 XSS
- 원격 인증 URL 처리, DoS 등

SDK 취약점이 MCP와 어떻게 연결되는지는 "MCP 구성에 쓰는 개발 키트이기 때문"으로 이해했으나 확신은 없다고 했다.

**검사 도구 현황**

- "동적"이라는 말이 런타임 관찰과 샌드박스 실행을 혼용하는 논문들이 있다.
- 대표 동적 분석 도구로 Cisco MCP Scanner가 자주 언급된다. 독립형 CLI 또는 REST API 서버 형태로 쓰며, 스타 약 1.1K, 최근까지 커밋이 올라오고 있다.
- 하이브리드 도구 중에는 언어(JS/TS, Python)와 취약군이 제한되고, 인증 우회·정보 노출 등은 범위 밖인 경우가 있다.
- 전반적으로 커버 범위가 좁고, 검사기 경고와 실제 피해가 일치하지 않는 문제가 있다.

**현황 평가**: 프로토콜은 성숙해졌으나 생태계 전체가 안전하다고 보긴 어렵다. 실제 위험은 사양보다 서버 구현, 호스트 승인 방식, 토큰 설계, 패키지 출처, 외부 API 권한에서 결정된다. 도구가 기대보다 발전하지 않은 이유는 논문 2~3편을 깊게 읽으며 확인해 보자는 의견이 나왔다.

### 2. 스킬 조사 발표 (장준서)

녹취 누락으로 세부 내용은 미기재다. 발표 중 평균 점수 자료(그래프)의 출처를 확인하는 질문이 있었다. 기존 도구가 스킬은 적당히 검사하고 있고, MCP는 상대적으로 부실하다는 평가가 나왔다.

양유상은 두 가지를 요청했다.

- 용준·준서 발표에 스킬/MCP 폴더 구조나 내부 문서 예시 스크린샷을 한 장씩 넣을 것 (GitHub 저장소 하나를 열어 보여주면 됨)
- 무료 스킬 스캐너 3종으로 공개 MCP 서버 모음이나 악성 판정 데이터셋을 직접 돌려볼 것

### 3. 에이전트 프레임워크 조사 발표 (김민우)

- MCP는 "무엇을 할 수 있는지", 스킬은 "무엇을 할지"이고, 프레임워크는 둘을 결합해 실행 순서·권한·루프를 정하는 것이다. 예로 LangChain을 들었다.
- 프레임워크 단의 탐지는 스킬과 MCP가 결합될 때 생기는 권한, 데이터 흐름, 원치 않는 능력(capability)을 본다. 예: 민감 파일 읽기 + 외부 전송 → 유출, 자격 증명 접근 + 외부 API 호출 → 탈취.
- 설정(config)에서 capability를 추출해 그래프로 분석하는 방식이 많다. 앞서 들었던 세미나 팀이 이 방식이었다.
- 사례: 팔로알토가 CrewAI, AutoGen 기반 앱에서 SQL 인젝션, BOLA, 메타데이터 토큰 유출 등을 재현했다.
- MCP, 스킬, 프레임워크는 유기적으로 연결돼 있어 하나의 묶음으로 다루는 게 낫다.
- 세 영역 모두 정적+동적 하이브리드에 LLM 가드레일을 붙이는 추세다. 오픈소스 예로 SkillScan(LLM 가드+정규식), MCP DIFF(AST·그래프·임베딩 비교 정적 분석)를 들었다.
- 스킬 스캐너, MCP 스캐너, 프레임워크 어댑터를 병렬로 돌리는 아키텍처를 제안했다. 공개 데이터로 새 취약점을 못 찾을 리스크는 있다.

### 4. 연구 범위와 목표 설정

박용준은 "이것도 저것도 검사"가 아니라 무엇을 검사할지 좁히고, 관련 논문 2~3편의 조건·데이터셋·지표를 확인해 목표치를 정하자고 했다. 예를 들어 기존 연구 환경에서 한 가지를 바꿔 동일하게 돌렸을 때의 결과를 비교하는 식이다. 단순히 "해봤다"보다 기존 구조의 문제를 측정하고 개선을 수치로 보여줘야 의미가 있다는 입장이다.

양유상은 개별 스캐너보다 AI 워크플로 공급 쪽의 공백은 확실하다고 봤다. 역할을 MCP, 스킬, 권한, 시각화로 나누는 안을 제시했고, 논문을 목표로 하지 않아도 된다는 입장이었다. 현재 흔한 탐지 대상으로는 악성코드, 프롬프트 인젝션, MCP 서버 자체 취약점, 위험 스킬, 민감정보 유출이 정리됐다.

선행 연구 조사가 부족하다는 점에 공감했다. 발표 이후 1인당 영어 논문 2편과 국내 논문 1편 정도를 읽으며 한계점을 찾자는 제안이 나왔다.

### 5. 기타

- **stateful/stateless 설명 (박용준)**: 세션 인증과 토큰 인증의 차이, 서버 다중화 시 장단점을 설명했다. MCP 개정도 같은 맥락이다.
- **아키텍처 시각화 도구**: Perplexity, 교수님이 언급한 아키파이 등을 추천했다.
- **PPT 제작 도구**: GPT, Gamma, Manus 등을 써봤으나 결과물이 아쉬웠다. Gamma는 워터마크가 남는다.
- **노션 자료 정리**: 조사 문서는 개인 폴더로 나누지 말고 한 문서 DB에 이름을 붙여 모두 올리기로 했다. 생성순·카테고리로 정렬할 수 있다.
