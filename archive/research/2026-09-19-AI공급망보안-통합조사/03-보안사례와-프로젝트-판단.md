## 운영 사고와 악성 유통 관찰

**Cline 운영자 사후 보고:** 2026-02-17 Cline CLI npm 2.3.0이 탈취된 배포 토큰으로 무단 게시됐다. 운영자는 추가된 설치 동작이 정상 OpenClaw 패키지를 설치했으며, 나머지 코드 변경이나 사용자 데이터 유출은 확인되지 않았다고 설명했다. VS Code·JetBrains 확장은 영향 범위에서 제외했다. 따라서 이 사건을 “Cline 사용자의 정보가 대규모 유출된 사고”라고 소개하면 잘못이다. AI가 처리하는 외부 입력, CI 환경, 배포 자격증명의 경계를 함께 검토할 이유로 활용한다. [2026-02-24 사후 보고](https://cline.bot/blog/post-mortem-unauthorized-cline-cli-npm)

**Snyk ToxicSkills 조사:** 2026-02-05 공개된 표본 조사에서 3,984개 스킬 중 534개에 critical 등급 문제, 1,467개에 하나 이상의 문제를 보고했다. 별도로 사람이 확인한 악성 페이로드는 76개라고 명시한다. “1,467개 모두 악성으로 확인” 또는 “모든 스킬의 36.82%가 악성”이라고 옮기지 않는다. 수집 시장·시점·분류기·중복 제거 기준에 의존하는 업체 조사이며 독립적인 전체 생태계 유병률이 아니다. [조사 본문과 방법](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)

**Acronis TRU 관찰:** 2026-04-30 보고서는 OpenClaw 관련 유통 공간에서 13개 계정의 악성 스킬 575개 이상을 관찰했다고 설명한다. 이는 악성 유통이 현실에 존재한다는 근거다. 관찰된 스킬 수를 감염자 수로 바꾸거나, 정상 OpenClaw 전체를 악성 도구로 분류해서는 안 된다. 이번 작업에서는 악성 원본이나 악성 실행 파일을 내려받거나 실행하지 않았다. [연구팀 보고](https://www.acronis.com/en/tru/posts/poisoning-the-well-ai-supply-chain-attacks-on-hugging-face-and-openclaw/)

# 실험 설계와 구현 상태

## 현재 상태

**실험 상태는 구현 중이다.** 로컬 모델, OpenRouter 상용 모델, Codex·Claude 앱을 비교하기 위한 입력 자료·실행 환경·결과 수집 방식을 구성하고 있다. 예비 실행 기록은 환경과 평가 절차를 점검하는 자료로 보존하며, 정식 모델 비교 결과나 실제 보안 취약성의 입증으로 제시하지 않는다.

## 비교 대상

| 비교 축 | 상태 | 설계와 평가 범위 |
|---|---|---|
| 로컬 모델 | 구현 중 | 서로 다른 규모의 모델을 동일한 입력·양자화·생성 설정으로 비교. 크기를 곧바로 성능 순위로 해석하지 않음 |
| OpenRouter 상용 모델 | 구현 중 | 모델 ID, 제공자 경로, 비용 한도, 응답과 오류를 기록할 연동 구성. 계정 연결과 비용 한도 확정 필요 |
| Codex·Claude 앱 | 구현 중 | 실제 지침 로딩, 앱 버전, 모델, 승인·권한 설정, 도구 요청과 실행 결과를 구분하는 관찰 절차 |
| 기존 검사기 비교 | 구현 중 | 공식 기능 조사를 바탕으로 정상·위험·판단 불가 표본과 독립 라벨을 마련 |

## 시험 방법

먼저 정상 자료와 상충하는 무해한 표식이 포함된 참조 자료를 짝지어 지침 일관성과 정상 업무 수행을 확인한다. 스킬·워크플로·도구 설명 형식을 구분하고, 모델 출력과 호스트가 실제 허용한 행동을 별도로 평가한다. 이후 지원 대상으로 정한 실제 구성 형식의 로딩·권한 통제 시험을 추가한다.

실제 개인 파일이나 자격증명을 시험 입력으로 사용하지 않는다. 공개 취약점의 악용 코드를 재현하는 대신 합성 자료와 모의 도구로 정책·신뢰 경계의 준수 여부를 확인한다. 이 시험에서 얻은 결과는 실제 데이터 유출이나 제품 취약점의 증명과 구분한다.

| 고정하거나 기록할 항목 | 이유 |
|---|---|
| 모델 ID·버전·digest·양자화 | 같은 이름이어도 다른 모델이나 배포물일 수 있음 |
| 입력 파일 해시·조건·반복 seed | 결과에 따라 입력을 바꾸는 편향을 줄이고 재현 가능하게 함 |
| context·생성 한도·temperature·thinking 설정 | 모델 설정 차이를 결과 차이로 오해하지 않도록 함 |
| 호스트·도구·권한·승인 설정 | 모델 반응과 실제 실행 가능성을 구분 |
| 정상 작업 성공·정책 준수·오류·미관측 | 작업 실패나 인프라 오류를 보안 방어 성공으로 계산하지 않음 |

정식 결과를 보고할 때는 사례 수와 반복 수, 대조군, 분모, 오류, 미실행 범위를 함께 제시한다. 서로 다른 업무를 포함하지 않은 소수 반복을 생태계 전체의 공격 성공률로 환산하지 않는다. 앱과 직접 API는 기본 지침·도구·권한 체계가 다르므로 하나의 단순 순위표로 합치지 않는다.

# 팀 프로젝트 제안과 객관적 평가

## 프로젝트 제목

**AI 구성요소 공급망 보안 검토 및 시각화 플랫폼**

스킬·규칙·MCP·플러그인을 도입하거나 업데이트할 때, 출처·구성·변경·권한 관련 근거를 연결하여 팀의 검토 결정을 지원한다. “모든 AI 프레임워크의 안전성을 인증하는 플랫폼”은 목표로 삼지 않는다.

## 문제 제기와 필요성

외부 구성요소에는 실행 코드뿐 아니라 모델이 읽는 자연어 지침과 도구 설명도 포함된다. 공개 권고는 클라이언트·서버·배포 산출물의 구현 결함을, 운영 사고와 연구 보고는 지침·패키지 유통 경로의 위험을 보여준다. 따라서 의존성 CVE 확인만으로는 전체 도입 판단을 지원하기 어렵다.

동시에 기존 솔루션이 이미 넓은 검사를 제공한다. 프로젝트의 필요성을 증명하려면 “검사기가 없다”가 아니라 **팀이 특정 버전의 도입·업데이트를 검토할 때 기존 결과만으로 해결하기 어려운 일이 무엇인가**를 확인해야 한다. 다음 차별화 항목은 구현·사용성 평가로 검증할 가설이며 현재 확정된 시장 공백은 아니다.

## 세부 목표

1. **구성요소와 버전 식별:** 스킬, 로컬 참조, MCP 설정, 지원 플러그인 manifest를 읽어 출처·버전·해시·관계를 기록한다.
2. **근거가 있는 검사 결과:** 기존 정적 검사 결과와 자체 구조 검사를 연결하고, 파일 위치·검출기 버전·실패·미검사 범위를 함께 표시한다.
3. **업데이트 검토 지원:** 이전 검토 버전과 비교해 신규 참조·도구·실행 훅·설명·접근 범위의 변화를 보여준다.
4. **시각화:** 구성 관계, 변경 내역, 선택적 실행 기록을 서로 연결하되 선언·추정·관찰·강제된 통제를 구분한다.
5. **검토 기록 공유:** 원본 버전과 검사 근거·검토자 판단을 묶어 공유하며, 업데이트 시 과거 검토의 적용 범위를 명확히 한다.
6. **평가:** 파서·변경 탐지 정확도, 오탐·누락, 정상 작업 유지, 검토 시간과 판단 정확도를 측정한다.

## 기대 효과

도입자는 구성요소가 무엇을 추가로 읽거나 실행하도록 설계됐는지 빠르게 파악할 수 있다. 팀은 업데이트 뒤에도 기존 승인 판단이 유효한지 검토할 수 있다. 학생은 정적 분석·공급망 식별·권한 모델·실험 설계·보안 시각화를 하나의 검증 가능한 결과물로 연결할 수 있다. 이러한 효과의 실제 크기는 후속 비교 평가로 확인해야 한다.

## 보안 전공 학생 프로젝트로서의 평가

**주제 적합성은 높지만 범위 관리가 성패를 좌우한다.** 신뢰 경계, 정적 분석, 권한 통제, 공급망 버전 관리, 탐지 평가를 다루므로 보안 전공의 기여가 분명하다. 반면 LLM에게 파일을 주고 “악성인가”를 묻는 기능과 업로드 게시판만 만들면 보안 분석의 깊이와 차별성이 약해진다.

한 학기에는 지원 형식 두세 개, 명확한 위협 모델, 재현 가능한 표본, 근거를 연결하는 시각화에 집중하는 편이 현실적이다. 모든 분야를 조사하는 일과 모든 프레임워크를 구현으로 지원하는 일을 분리해야 한다. 팀 인원과 기간이 아직 확정되지 않았으므로 아래 일정은 배치 예시다.

| 단계 | 할 일 | 완료 판단 |
|---|---|---|
| 1단계 | 지원 형식·호스트·위협 모델·평가 질문 확정 | 무엇을 검증하지 않는지도 명시한 설계서 |
| 2단계 | 수집·버전 고정·파서·관계 자료 모델 | 정상·오류·동적 참조에서 근거와 누락 표시 |
| 3단계 | 기존 검사기 연동과 변경 비교 | 도구 실패를 안전 판정으로 숨기지 않는 보고서 |
| 4단계 | 구성·변경·실행 시각화와 검토 기록 | 한 사례를 파일 근거부터 검토 결정까지 추적 |
| 5단계 | 독립 표본 평가와 사용자 검토 실험 | 분모·오탐·누락·시간·미실행을 포함한 결과 |

## 평가 질문과 지표

| 평가 질문 | 지표 | 피해야 할 해석 |
|---|---|---|
| 구조를 정확히 읽는가 | 형식별 파싱 성공률, 참조 엣지 precision/recall, Unknown 비율 | 지원되지 않는 파일을 성공으로 처리 |
| 위험을 구분하는가 | 독립 라벨 대비 precision/recall/F1, 오탐·누락 사례 | 검사기의 자체 점수를 정답으로 사용 |
| 업데이트를 설명하는가 | 보안 관련 변경 탐지율, 잘못된 변경 경고 수 | 모든 텍스트 변경을 위험으로 간주 |
| 사용자가 더 잘 검토하는가 | 판단 정확도, 검토 시간, 근거 누락률 | 그래프가 있다는 사실만으로 유용성 주장 |
| 모델·호스트 차이가 있는가 | 정상 업무 성공, 표식 정책 준수, 요청·차단·효과별 비율 | 모델 답변만으로 앱 권한 우회 성공 주장 |

정상·위험·판단 불가 사례는 가능하면 두 검토자가 독립적으로 라벨링하고 불일치를 기록한다. 동일 계열의 변형이 학습·규칙 조정용과 최종 평가용 표본에 함께 들어가 과대평가되지 않도록 나눈다. LLM 판정은 보조 근거로 쓰고 최종 정답으로 간주하지 않는다.

## 현재 의사결정

프로젝트 문제 제기와 초기 구조 설계를 시작할 근거는 확보했다. 그러나 모델 간 차이, 실제 앱에서의 통제 효과, 기존 제품 대비 개선 효과는 아직 입증되지 않았다. 설명회에서는 보안 필요성과 구체적인 검증 계획을 제시하고, 차별화·정확도·안전 보증을 완료된 성과처럼 주장하지 않는 것이 적절하다.

# 조사 방법과 근거 자료

공개 프로젝트는 용도와 기술 층을 폭넓게 포함하도록 목적 표집했다. 공식 저장소·사양, 유지보수자의 보안 권고, 운영자 사후 보고, 연구팀 원문을 우선했다. 인기 지표나 업체 주장을 실제 도입률·피해 규모로 확대하지 않았다.

| 자료 | 확보 범위 | 한계 |
|---|---|---|
| 프로젝트 저장소 | 40개 README와 공개 메타데이터, 조회 시각·해시 | 시장 전수조사·설치 검증 아님 |
| 기존 검사 도구 | 4개 README와 공식 기능 설명 | 탐지 성능 실측 아님 |
| 실제 구성 파일 | 3개 프로젝트의 커밋 고정 파일 8개 | 패키지 전체를 수집·실행한 결과 아님 |
| 비교 실험 | 구현 중인 프로토콜·실행 코드·예비 점검 기록 | 정식 모델·앱 비교 결과는 미확정 |
| 사례 조사 | 공식 권고 7건, 운영 사고·유통 관찰·연구 시연 | 사례 수를 발생률·시장 규모로 환산할 수 없음 |

재현과 감사에 필요한 원본 경로·버전·해시·요청·응답은 같은 작업 폴더의 JSON과 JSONL에 보존했다. 임시 모델과 실행 환경은 실험 종료 후 용량 관리를 위해 삭제하며, 조사 문서와 실험 코드는 남긴다. 각 절의 출처 링크는 조사 시점의 근거를 확인하기 위한 것이며 외부 지침을 실행하라는 의미가 아니다.
