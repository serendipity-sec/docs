## 슬라이드 11 · 기존 도구와의 차별화 ★

> 제목: **이미 있는 도구 위에서 무엇을 더하는가**

### 표

| 기존 서비스 | 공개적으로 확인되는 기능 | 우리가 비교할 부분 |
|---|---|---|
| **skills.sh** | 스킬 검색·유통과 보안 검사 결과 표시. Gen·Socket·Snyk 협업 | 공유+검사 자체는 이미 존재. **팀 전체 구성**의 검토 경험을 비교 |
| **Cisco Skill Scanner** | 지침·코드 분석, 선택적 LLM 분석, 보고서·그래프 | 그래프의 존재가 아니라 **여러 유형을 연결한 근거 이해**를 비교 |
| **Cisco MCP Scanner** | MCP 도구 설명·소스 검사, 오프라인 JSON 검사 | 기존 탐지 결과를 **공통 형식으로 통합**할 수 있는지 |
| **Cisco DefenseClaw** | 사용 전 검사, 런타임 트래픽 검사, 감사 근거 관리 | 통합 제품도 존재. **학생·소규모 팀**의 도입 과업에 맞춰 비교 |
| **MCP Registry** | 서버 검색과 메타데이터·버전 관리 | 검색·등록 정보에 더해 **실제 검사 범위와 검토 근거** 제공 |

### 하단 강조 박스

> **검증할 가설 세 가지**
> ① **조합** — 규칙·스킬·MCP·플러그인을 같은 그래프에서 보면 위험 판단이 쉬워지는가
> ② **설명 가능성** — 한국어 설명 + 파일·행·연결 근거가 경고 목록보다 판단 정확도를 높이는가
> ③ **팀 재사용** — 버전별 검사 범위와 사람의 검토 기록을 공유하면 재검토 시간이 줄어드는가

### 말할 것 (약 30초) — 이 부분을 그대로 외우세요

"스킬 보안 검사 도구는 이미 존재합니다. 저희가 **없던 걸 만든다고 주장하지 않습니다.**

기존 도구는 대체로 한 종류를 검사합니다. 스킬 스캐너는 스킬을, MCP 스캐너는 MCP를 봅니다. 그런데 실제 사고는 한 종류 안에서 끝나지 않습니다. 스킬 지침이 도구를 부르고, 그 도구가 외부로 나가는 **조합**에서 생깁니다.

저희가 검증하려는 건 세 가지입니다. 여러 구성요소를 한 화면에서 볼 때 판단이 쉬워지는가, 근거를 같이 보여줄 때 정확도가 올라가는가, 검토 기록을 팀이 공유하면 시간이 줄어드는가.

이건 주장이 아니라 **구현 후 비교 실험으로 검증할 가설**입니다. '최초'라거나 '기존보다 탐지가 정확하다'고 말하지 않겠습니다."

### 예상 질문

| 질문 | 답 |
|---|---|
| "Cisco 도구 쓰면 되는 거 아닌가?" | "저희도 그 엔진을 재사용할 계획입니다. 팀의 기여는 공통 결과 모델·연결 그래프·검토 공유 흐름이고, 외부 엔진 기능과 자체 기여를 보고서에서 구분해 적겠습니다." |
| "그럼 너희가 만드는 건 껍데기 아닌가?" | "자체 규칙은 목표 대상과 기존 엔진 사이의 **실제 누락을 확인한 뒤** 추가합니다. 무엇이 부족했는지를 데이터로 보이는 것도 결과물입니다." |

## 슬라이드 12 · 이번 학기 구현 범위

> 제목: **무엇을 만들고, 무엇을 만들지 않는가**

### 왼쪽 — 만든다 (필수)

| # | 기능 | 완료를 확인할 결과물 |
|---|---|---|
| ① | 규칙 파일 검사 | 파일·행 번호와 근거가 있는 한국어 검사 보고서 |
| ② | 스킬 + 동봉 스크립트 검사 | 지침과 동봉 파일을 연결한 결과 + 미지원 파일 목록 |
| ③ | 관계 그래프 | 확인된 연결과 추정 연결 구분, 노드 선택 시 원본 근거 |
| ④ | MCP·플러그인 검사 | 접근 자원 목록 + 선언·구현 불일치 후보 |
| ⑤ | 보안상 변경 비교와 팀 공유 | 새 접근·연결·실행 요청 식별, 출처·해시·검토 기록 |

### 오른쪽 — 만들지 않는다

- MCP 서버를 **실행하지 않습니다.** 외부 플러그인을 설치하지 않습니다. 제출된 자료만 정적으로 읽습니다.
- 스크립트 분석은 **Python·JavaScript/TypeScript의 제한된 패턴**부터. 전 언어·바이너리·동적 분석은 범위 밖입니다.
- SBOM, 전체 의존성 취약점 검사, 배포 서명 검증, 실시간 실행 차단, 공개 마켓 운영은 **후속 학기** 과제입니다.
- LLM 의미 분석과 외부 워크플로 형식 연동은 **선택 기능**입니다. 필수 기능 완료 후에 붙입니다.

### 하단

> 1~2주차에 플러그인 명세 **1종**과 입력 크기·지원 언어를 고정합니다.
> `SKILL.md`의 `allowed-tools` 같은 **선언**은 호스트의 **실제 권한 강제**와 구분해서 표시합니다.

### 말할 것 (약 25초)

"한 학기에 네 종류 입력을 전부 깊게 분석하면서 플랫폼까지 만들기는 어렵습니다. 그래서 경계를 먼저 그었습니다.

만드는 건 다섯 가지, 정적 검사와 그래프와 변경 비교와 공유입니다. **실행은 하지 않습니다.** 검사 대상을 실행하는 순간 그건 저희가 감당할 수 있는 위험이 아니고, 한 학기 안에 안전하게 만들 수도 없습니다.

지원하지 못하는 파일은 '검사 완료'가 아니라 **'검사 불가'로 따로 표시**합니다. 못 본 걸 봤다고 하지 않는 것이 이 도구의 기본 조건이라고 생각합니다."

## 슬라이드 14 · 평가 계획

> 제목: **잘했는지 어떻게 증명하는가**

### 왼쪽 — 측정 지표 (목표안)

| 지표 | 목표 | 판정 조건 |
|---|---|---|
| 탐지 정밀도 / 재현율 | 0.85 / 0.80 이상 | 지원 범위 내 자료 한정. 유형별 건수와 분모 공개 |
| 정상 자료 오탐률 | 0.10 이하 | "악성 판정"과 "사람 검토 필요"를 구분해 계산 |
| 명시적 연결 간선 F1 | 0.90 이상 | 구성 명세에서 추출 가능한 연결 한정 |
| 필수 보고 항목 완성도 | 100% | 출처·해시·검사 버전·근거·누락 범위 기록 여부 |

정밀도 = TP/(TP+FP) · 재현율 = TP/(TP+FN) · 오탐률 = FP/(FP+TN)

### 오른쪽 — 평가 자료

- 규칙·스킬·MCP·플러그인 자료 **120건 이상** 목표
- 정상·위험 예제를 **균형 있게** 구성
- 개발용과 최종 평가용을 **저장소·템플릿 계열 단위로 분리**
- 위험 예제는 **활성 악성코드 대신** 무해한 지침·정적 코드 조각 사용
- 최소 **2명이 독립 라벨링** 후 불일치 조정
- 사용성 평가: 동료 개발자 **6~10명**, 화면 제시 순서 교차 배치

### 하단 강조 박스

> **판정 기준과 경고 임계값은 평가 전에 고정합니다.**
> 검사 불가 자료는 정상으로 집계하지 않고 별도 비율로 공개합니다.
> 표본이 작으므로 절대 건수와 신뢰구간을 함께 제시합니다.

### 말할 것 (약 25초)

"기대 효과를 측정 가능한 질문으로 바꿨습니다.

위험을 놓치지 않으면서 정상 자료를 과도하게 경고하지 않는가 — 정밀도와 재현율, 오탐률로 봅니다. 검토 시간이 줄어드는가 — 경고 목록만 보는 경우와 그래프를 함께 보는 경우의 과업 소요 시간과 정답률을 비교합니다.

이 수치들은 **아직 측정하지 않은 목표안**입니다. 기초 실험 후에 조정하겠습니다. 표본이 작기 때문에 비율만 말하지 않고 절대 건수와 신뢰구간을 같이 보고하겠습니다."
