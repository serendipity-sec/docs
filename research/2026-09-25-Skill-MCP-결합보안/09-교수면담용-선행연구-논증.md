# 9. 교수 면담용 — 선행연구에서 연구 질문까지

2026-09-25 · 연구 제안 재검토본. 문헌의 존재와 구현 일부는 확인했지만, 아래 제안의 신규성·성능은 아직 입증하지 않았다.

## 1. 면담에서 먼저 말할 결론

> Skill과 MCP의 결합 위험 자체는 이미 연구되어 있습니다. 작업 의도와 출처에 따라 권한을 제한하는 방법도 IntentCap·SkillGuard 등에 존재합니다. 따라서 저희는 새로운 권한 통제 원리를 주장하기보다, 실제 Skill·MCP 설정에서 그 통제에 필요한 연결·대상·승인 근거를 얼마나 정확하게 확보할 수 있는지 검증하려고 합니다. 불완전한 근거를 안전으로 오판하는 비율과, 미판정을 포함한 유효한 판정 범위를 가까운 기존 방법과 비교하겠습니다.

교수님의 구체적 지적을 아직 전달받지 못했으므로, ‘부족’의 이유를 단정하지 않는다. 이 문서는 **범위 누락, 가까운 경쟁 연구 누락, 읽은 깊이 부족, 차별성 논증 부족**을 각각 점검할 수 있게 구성했다.

## 2. 관련 연구를 여섯 계열로 연결하기

| 계열 | 대표 연구 | 이미 확립한 내용 | 우리 제안과의 관계 |
|---|---|---|---|
| 간접 주입의 원인 | Greshake et al. (R27) | 가져온 데이터가 지시로 작동해 agent 권한을 사용 | Skill/MCP 이전부터 존재하는 문제의 계보 |
| 구성요소 결합 | SkillProbe·SkillReact·SCR-Bench·SkillFuzz·CompoSkill (R01–05) | 개별 검사와 결합 후 안전성은 다름 | 연구 대상 자체의 신규성 배제 |
| 작업·권한 통제 | Progent·Task Shield·AgentSpec·SkillGuard·IntentCap (R17–19, R14, R13) | 업무 정합성, 인자 정책, 좁혀지는 권한, 출처별 영향 제한 | 제안 방법과 가장 직접적으로 중복 |
| 정보 흐름·실행 경계 | CaMeL·Fides·PCAS·AgentBound (R07, R15–16, R20) | 데이터/제어 분리, label 전파, reference monitor, sandbox | 그래프·정책 검사·실행 차단은 기존 원리 |
| 설정·구현 감사 | Scanning the Harness·Cisco·skil·TFA (R21, G01, G07, T01) | 혼합 구성 그래프와 위험 흐름 후보 탐지 | 제품 기능과 정적 분석의 직접 비교군 |
| 검증·벤치마크 | AgentDojo·MCP-SafetyBench·MCPTox·Skill-Inject·SCR-Bench (R26, R10, R09, R25, R03) | 공격 조건·정상 작업·상태 변화의 평가 | 평가 설계를 차용하되 benign composition 표본 추가 |

개별 논문의 원문·방법·확인 수준은 [02](02-논문-비교.md)와 [08](08-심층웹조사와-선행연구-재검증.md)에 있다. 최근 preprint와 학회 논문을 같은 신뢰 수준으로 표시하지 않았다. ACL 2025의 Task Shield, ICSE 2026의 AgentSpec, FSE 2026의 AgentBound, NeurIPS 2024의 AgentDojo를 학회 자료로 연결했고, 최신 결합 연구는 확인한 arXiv 버전을 명시했다.

## 3. 가장 가까운 연구와 정면 비교

‘없는 기능’ 체크표는 원문에 없다는 것과 시스템에 없다는 것을 혼동하기 쉽다. 아래는 **확인한 기능과 우리가 추가로 검증할 입력 조건**의 비교다.

| 비교 대상 | 이미 하는 일 | 필요한 입력·가정 | 우리가 증명해야 하는 추가 가치 |
|---|---|---|---|
| [IntentCap](https://arxiv.org/html/2609.14631v1) | 의도·출처·인자·lease 검사 | 신뢰할 수 있는 계약·label·provenance와 강제 경계 | 그 근거를 원문/설정에서 자동 획득할 때 정확도·누락·모순 처리의 효과 |
| [SkillGuard](https://arxiv.org/html/2606.03024v1) | Skill 선언과 현재 업무 권한 분리 | trusted manifest/hook, task judge | manifest와 실제 MCP 연결의 불일치를 증거로 설명할 수 있는가 |
| [Fides](https://arxiv.org/html/2505.23643v1) / [PCAS](https://arxiv.org/html/2602.16708v1) | label/인과 그래프에 정책 강제 | 의미가 맞는 label·정책, 충분한 계측 | 부분 관측의 정적 감사에서 내릴 수 있는 결론과 못 내리는 결론을 평가 |
| [harness-eval](https://github.com/redhat-community-ai-tools/harness-eval) | Skill/agent/MCP 연결·권한 모순·흐름 후보 | 파서가 찾은 참조와 능력 | 같은 경로에서 계정·수신 대상·승인 근거가 판별을 개선하는가 |
| [skil](https://github.com/domehahn/skil) | 파일 자원을 매개로 Skill 간 흐름 연결 | capability 관측·공유 자원·선택적 실행 관측 | 실제 MCP binding의 다른 조건에서도 동시 존재와 위반 경로를 구별하는가 |
| [CompoSkill](https://arxiv.org/html/2608.16246v1) / [TFA](https://invariantlabs.ai/blog/toxic-flow-analysis) | 결합 그래프에서 공격/위험 경로 찾기 | 추상 능력과 연결·분석 모델 | 동일한 정책·표본·관측 조건으로 후보의 타당성을 비교할 수 있는가 |

새 입력을 추가했기 때문에 성능이 좋아졌다면 **새 알고리즘의 효과와 추가 정보의 효과**를 분리해야 한다. 기존 엔진에도 같은 근거를 제공하는 대조군이 필수다.

## 4. 철회할 주장과 남길 가설

| 주장 | 현재 판정 | 근거 |
|---|---|---|
| 기존 연구는 Skill/MCP를 각각만 본다 | 철회 | 결합 연구, Cisco, harness-eval, TFA |
| 악성 문자열이 없는 결합은 아무도 안 다룬다 | 철회 | SkillReact·SCR-Bench·SkillFuzz |
| 작업 의도와 출처를 함께 검사하면 새롭다 | 철회 | IntentCap·SkillGuard·Fides 계열 |
| 자동 정책 생성이 차별점이다 | 이 설명만으로 부족 | Progent·AgentBound 등 |
| 환경/승인 변경에 재검사하면 최초다 | 근거 없음 | 공식 Skills over MCP 승인 갱신, FIDES의 호출/principal 결속 |
| 정적 혼합 분석으로 실행 공격을 막았다 | 주장 불가 | 후보 탐지와 runtime enforcement는 다름 |
| 불완전한 근거 복원과 판정 유보의 실효성을 비교한다 | 검증 가능한 후보 | 입력 가정을 실험 변수로 바꾸되, 기존 파서/정책 엔진을 공정하게 비교 |

**중요한 구분:** ‘기존 논문 평가에 이 조건이 없었다’는 관측은 **evaluation gap**이다. 이를 곧바로 ‘기존 방법은 이 조건에서 실패한다’는 **method gap**으로 바꿀 수 없다. 먼저 동일 조건에서 실행하거나 논리적인 반례를 보여야 한다.

## 5. 연구 질문을 측정 가능한 형태로 고정

**후보 제목:** 불완전한 Skill–MCP 구성 근거에서의 권한·정보 흐름 감사: 연결 복원과 미판정의 효과.

**RQ1 — 근거 확보:** Skill의 명시 참조·MCP snapshot·호스트 정책에서 server/tool binding, 자료 등급, destination audience, 승인 출처를 얼마나 복원할 수 있는가?

**RQ2 — 판정 효과:** 같은 정책 엔진을 사용할 때, 자동 복원 근거가 capability 동시 존재 규칙보다 허위 경고·위험 누락을 줄이는가? 충분한 근거가 있는 표본만 골라 높은 정확도를 만드는 것을 막기 위해 미판정률과 coverage를 함께 보고한다.

**RQ3 — 변경의 효과:** Skill 본문이 그대로인 상태에서 계정·ACL·도구 schema·승인 수명만 달라져도 판정과 근거를 올바르게 갱신하는가? 변경 감지 자체는 기본 기능이며, 어떤 변경이 어떤 판정을 뒤집는지의 평가가 대상이다.

여기서 **새 정보 복원 알고리즘을 제시하지 못하고** 기존 도구를 묶기만 했다면 공학적 통합·평가 기여로 소개한다. capstone에서 그 기여가 충분한지는 교수님과 범위를 맞출 사항이다.

## 6. 강한 기준선과 최소 실험

### 6.1 입력 품질과 엔진을 나눠 비교

| 단계 | 입력 | 정책/분석 엔진 | 답할 질문 |
|---|---|---|---|
| E0 | 사람 검증 정답 label·binding·계약 | IntentCap checker 또는 공통 고정 정책 | 정책 자체가 조건을 구분하는가 |
| E1 | 자동 추출한 동일 필드 | E0와 같은 엔진 | 근거 복원 때문에 생기는 손실은 얼마인가 |
| E2 | 근거 일부 누락·모순·오래된 승인 | E0와 같은 엔진+명시적 미판정 처리 | 모르는 것을 안전/위반으로 잘못 확정하지 않는가 |
| E3 | E1의 동일한 입력 | harness-eval/skil 적합 규칙, Cisco 교차 검사, 단순 합집합 | 새 분석의 이득인가, 입력의 이득인가 |
| E4 | 통제된 실제 호출 trace | 상태 oracle, 지원되는 runtime baseline | 후보 경로가 실제로 실행됐는가 |

IntentCap의 입력 형식은 실제 대상 시스템과 다르므로 adapter의 변환 규칙·불가능한 필드를 공개한다. 지원되지 않는 기능을 임의로 만들어 넣고 공식 구현의 성능이라고 부르지 않는다. 실행할 수 없는 비교군은 미측정으로 남긴다.

### 6.2 표본 구성

12개 업무 × 8개 정책 조건의 기존 초안을 유지하되, 각 표본에 **근거 완전 / 자동 확보 / 누락·모순** 조건을 적용한다. 파생 표본이 늘어도 독립적인 현실 서비스 수가 증가했다고 세지 않는다. 기본 업무 단위로 개발/평가를 분리한다.

첫 업무는 내부 기록을 요약해 게시하는 정상 workflow다. 자료 내용과 요청을 고정하고 다음을 하나씩 바꾼다: 팀 내부/공개 게시, 승인 유효/만료, server binding 일치/다름, label 확인/미상, 도구 호출 가능/통제에 막힘. benign composition과 악성 주입 조건은 별도 층으로 둔다.

### 6.3 정답과 지표

- **근거 정답:** 파일·설정·권한 snapshot의 위치를 두 명이 독립 확인하고 불일치를 기록한다. 이번 조사에서 이 사람 검토를 완료한 것은 아니다.
- **후보 정답:** 경로의 존재와 정책 조건을 분리해 annotation한다. 가능 경로와 실행 관측 경로를 합치지 않는다.
- **실행 정답:** 격리된 mock sink에 허용되지 않은 canary가 도착했는지 상태로 판정한다. agent의 말이나 LLM judge만으로 성공을 확정하지 않는다.
- **지표:** binding 정확도, 근거 복원율, 위험 누락률, 정상 오탐률, 미판정률, 판정 coverage, 정상 업무 완료율, 검사 비용. 미판정을 제거한 precision만 발표하지 않는다.
- **분석:** 동일 업무의 쌍별 차이를 보고하고 업무 단위 신뢰 구간을 쓴다. 모델·호스트·정책·버전·반복 횟수와 adapter 범위를 공개한다.

### 6.4 연구 질문의 기각 조건

1. 기존 엔진에 같은 근거를 주면 성능 차이가 사라진다 → 새 탐지법 주장을 접고 근거 추출/배포 감사 기여로 제한.
2. 권한·ACL을 현실적으로 확보할 수 없어 대부분 미판정이다 → 전체 혼합 workflow 탐지 제품 주장을 축소.
3. 명시 참조가 있는 인위적 표본에서만 개선된다 → 해당 범위에 한정하고 일반화 주장 금지.
4. 근거 복원도 기존 파서와 차이가 없다 → 독립적인 연구 기여가 약함을 인정하고 주제 변경 또는 실증 비교 연구로 전환.

## 7. 본문에 쓸 수 있는 Related Work 초안

LLM agent의 도구 사용 보안은 비신뢰 데이터를 지시로 해석하는 경계 문제에서 출발한다. Greshake 등의 간접 prompt injection 연구는 외부 콘텐츠가 검색·도구 경로를 통해 애플리케이션의 행동을 바꿀 수 있음을 보였다 [R27]. Skill 생태계에서는 SkillReact, SCR-Bench, SkillFuzz 및 CompoSkill이 개별 검사 결과와 결합 후 동작의 차이를 연구한다 [R02–R05]. 따라서 구성요소의 결합 자체를 본 연구의 신규성으로 보지 않는다.

방어 연구는 의미적 업무 정합성과 명시적 정책 강제로 나뉜다. Task Shield는 사용자 목표에 대한 행동의 기여를 검토하고, Progent와 AgentSpec은 도구 사용 정책을 런타임에 적용한다 [R17–R19]. SkillGuard는 Skill 선언과 현재 작업 권한을 분리하며, IntentCap은 의도와 컨텍스트 출처를 근거로 capability를 제한한다 [R14, R13]. 본 연구의 승인·출처 기반 판정은 이 흐름을 계승하므로 해당 원리의 최초 제안으로 설명하지 않는다.

CaMeL, Fides 및 PCAS는 데이터와 제어의 분리, 정보 흐름 추적, 정책 강제를 통해 보다 구조적인 방어를 제안한다 [R07, R15–R16]. 이러한 보장은 각 시스템이 규정한 정책·label·계측 경계에 의존한다. 한편 Scanning the Harness와 공개 교차 구성 검사 도구들은 repository 수준에서 Skill·agent·MCP 참조와 위험 능력을 분석한다 [R21, G01, G07, G10]. 특히 참조와 능력의 공존만으로 실제 정책 위반을 확정하지 않는 검증이 필요하다.

이에 본 연구는 기존 통제 원리를 새로 제안하기보다, Skill–MCP 구성에서 필요한 정책 근거가 부분적으로만 관측되는 조건을 평가 대상으로 삼는다. 동일한 정책 엔진에 검증된 정답 근거, 자동 복원 근거, 누락·모순 근거를 각각 제공해 추출과 판정의 효과를 분리할 예정이다. 기존 방법에 같은 정보를 제공하는 비교에서도 개선이 유지되는지, 미판정 증가가 성능 지표를 왜곡하지 않는지를 함께 측정한다. 이 비교 전에는 학술적 신규성과 우월성을 확정하지 않는다.

위 문단의 모든 출처 ID는 [출처 목록](07-출처와-조사기록.md) 및 [추가 조사](08-심층웹조사와-선행연구-재검증.md)와 연결된다. 실제 논문 제출 시 학과 지정 인용 양식과 저자·서지 정보로 변환한다.

## 8. 민우가 우선 설명할 수 있어야 할 여덟 편

1. **IntentCap:** 외부 자료가 채워도 되는 인자와 결정하면 안 되는 인자를 구별해 설명한다.
2. **SkillGuard:** 선언 집합·현재 작업 범위·사용자 grant가 왜 다른지 설명한다.
3. **CompoSkill:** 경로 형성률과 공격 성공률을 구별한다.
4. **SCR-Bench:** 분리 조건과 결합 조건, state oracle의 의미를 설명한다.
5. **SkillFuzz:** 계획 변화와 실제 부작용의 차이를 설명한다.
6. **Fides 또는 CaMeL:** taint와 격리가 보안·utility에 주는 비용을 설명한다.
7. **PCAS:** 어떤 흐름을 계측해야 정책 보장이 성립하는지 설명한다.
8. **Scanning the Harness:** raw finding, 검토된 결함, 실제 침해를 구별한다.

각 논문에서 **입력 한 개 → 내부 판단 한 단계 → 출력 → 그 판단이 틀릴 수 있는 조건**을 자기 말로 설명할 수 있으면 된다. 제목·숫자 암기만으로 정독을 대신하지 않는다.

## 9. 교수님께 확인할 구체적인 결정

- 제안 범위를 **새 탐지 알고리즘**, **근거 복원 방법**, **현실 조건에서의 비교 실증 연구** 중 어디에 둘지.
- 실제 환경의 ACL·scope·승인 자료를 확보할 수 있는지. 확보 불가라면 mock 전용 결과의 허용 범위.
- baseline과 입력 조건이 공정한지, 추가로 반드시 비교할 선행연구가 있는지.

현재 완료한 것은 문헌·명세 비교, 저장소 내부 확인, 일부 검사 함수의 동작 확인이다. **새 탐지기의 효과를 입증하는 본 실험은 다음 단계**다.
