# 후보 1 AI로 만든 웹서비스의 배포 전 보안 검증

기록일: 2026-09-20 · 상태: 비교 후보 · 최종 채택 및 구현 착수 미정

## 사용자 관점의 출발점

“AI로 웹사이트는 만들었는데, 이거 공개해도 될까?”

AI의 도움으로 서비스를 만든 개발자가 화면과 정상 기능은 확인했지만, 악의적인 요청이나 다른 사용자의 접근까지 검증하지 못한 상황을 다룬다. 바이브 코딩이라는 제작 방식만으로 모든 서비스가 취약하다고 전제하지 않는다.

김민우의 이번 반응:

> 1번은 요즘 바이브 코딩 많이 하는데 나도 책에서 뭐 본적 있는거 같아 AI로 코드 만들어서 서비스 기능 자체는 잘 100프로 동작했는데 보안적으로는 뚫려 있었다는 그런 내용을 본적이 있는거 같고

책 제목·저자·문구는 아직 확인되지 않았다. 이는 주제에 공감하게 된 개인의 기억이며, 실제 사례나 통계의 검증된 출처로 인용하지 않는다. “100프로”도 측정 결과가 아니다.

## 제품 가설

대상 사용자는 AI로 첫 서비스를 만들거나 소규모 서비스를 운영하는 개발자다. 배포 전과 기능 변경 후 자신의 시험용 서비스를 검사해, 발견된 문제를 이해하고 수정한 뒤 같은 시험을 다시 수행한다.

입력 후보는 허가된 시험 서비스 주소, 소스코드, 시험 계정, 예상 동작·보호 규칙이다. 어떤 입력 조합을 필수로 할지는 미정이다. 서비스 주소만 받으면 모든 문제를 알 수 있다는 약속은 하지 않는다.

사용자가 얻을 결과는 취약점 이름 목록보다 다음에 가깝다.

- 어느 기능에서 무엇이 잘못되는지 보여 주는 재현 요청과 응답.
- 어떤 정보나 기능에 영향이 있는지 이해할 수 있는 설명.
- 수정할 코드·설정의 근거와 수정 후보.
- 수정 이후에도 같은 문제가 발생하는지 확인할 수 있는 재실행 시험.
- 시험하지 못한 경로와 판정이 불확실한 결과.

## 발전시켜 볼 핵심

가장 먼저 검증할 차별화 가설은 **초보 개발자가 보안 문제를 발견한 뒤 이해·수정·재검증까지 완료하는 과정의 개선**이다. 기존 검사 엔진의 이름만 가리고 자체 기술로 제시하지 않는다.

AI가 코드·사용 흐름을 읽어 시험 후보와 설명을 만들 수 있지만, 취약점 존재 여부를 AI의 문장만으로 확정하지 않는다. 시험 환경에서 확인한 요청·응답·상태 변화가 근거가 되어야 한다. 수정 제안 역시 실제로 문제를 해결하는지 별도 확인한다.

“기능이 잘 동작함”과 “보안 규칙이 유지됨”을 함께 검증하는 방법을 검토한다. 예를 들어 정상 예약은 유지하면서 다른 사용자의 예약 변경은 막히는지 시험할 수 있다. 인가 문제는 한 사례이며, 후보 전체를 인가 검사로 한정한 것은 아니다.

## 시연 후보

1. 팀이 만든 시험용 예약·게시판·문서 서비스 중 하나에서 정상 기능이 동작함을 보여 준다.
2. 허용되지 않아야 하는 요청을 시험하고, 실제 영향과 재현 근거를 제시한다.
3. 사용자가 수정 제안을 검토·반영한다.
4. 같은 보안 시험을 다시 실행하고 정상 기능 시험도 수행한다.
5. 수정 전후의 차이, 아직 남은 문제, 시험 범위를 표시한다.

단순히 준비된 취약한 예제를 맞히는 시연과, 독립된 평가 사례에서 성능을 측정하는 실험은 구분한다.

## 웹어플리케이션보안 산출물

웹 UI는 프로젝트 등록, 시험 범위와 계정 설정, 실행 상태, 재현 근거, 수정 전후 비교를 맡는다. 서버는 작업을 관리하고 검사 작업은 분리된 실행 환경에서 수행하는 구조를 검토한다.

설계·점검 대상은 시험 자격증명 보관, 사용자별 결과 접근 제어, 검사 대상 주소 검증과 SSRF 방어, 작업 격리, 보고서의 비밀정보 마스킹·XSS 방어다. 소스와 시험 자료가 외부 모델에 전송되는 범위도 명시한다.

최종 결과물 후보는 배포 가능한 검증 웹서비스, 시험용 대상 앱, 위협 모델, 재현 및 회귀 시험, 자체 서비스 보안 점검 리포트, 비교 평가 보고서다.

## 기존 도구와 아직 모르는 것

[Shannon 공식 설명](https://github.com/KeygraphHQ/shannon)은 AI 기반 웹앱·API 보안 검증과 재현 가능한 근거를 제공한다고 설명한다. 따라서 “AI가 웹 취약점을 찾고 재현한다” 자체를 독창성으로 삼을 수 없다. [Autorize](https://portswigger.net/bappstore/f9bbac8c4acf4aefa4d7dc92a991af2f)도 인가 검사의 기존 비교 대상이다. 확인일: 2026-09-20. 이번 세션에서는 실행 비교를 하지 않았다.

아직 확인할 질문:

- 기존 도구에서 초보 개발자가 실제로 막히는 지점은 어디인가?
- AI가 만든 서비스라는 대상을 정하는 것이 시험 설계나 사용자 경험에 실제 차이를 만드는가?
- 상용 AI에게 코드를 검토시키는 것만으로 충분한 경우와, 실행 검증이 필요한 경우를 구분할 수 있는가?
- 재현·수정·회귀 시험 가운데 팀이 직접 개선할 핵심 기술은 무엇인가?
- 독립된 정상·취약 사례와 실제 사용자를 구할 수 있는가?

## 평가 제안

기존 도구 또는 수동·AI 코드 검토와 동일한 시험 과업에서 비교한다. 실제 취약점 확인률, 잘못된 경고, 재현 성공률, 수정 후 문제 제거 여부, 정상 기능 유지, 사용자의 해결 시간과 설명 이해도를 측정한다. 숫자 목표는 아직 정하지 않는다.

계속 발전시킬 근거는 사용자가 자기 시험 프로젝트로 반복 사용하고 싶어 하며, 기존 방법보다 해결 과정을 개선한 증거다. 기존 도구의 보고서를 웹으로 옮기는 수준이라면 방향을 다시 검토한다.
