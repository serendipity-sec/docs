상태: **DESIGNED / 별도 9개 동적 기준·정적 스캐너 비교 COMPLETED / 원안 12개 전체 비교 NOT_RUN** · 2026-09-21

> 실행 연결: 실제 Skill·MCP 입력과 동적 효과는 [`platform/experiments/live-agent-security`](../../experiments/live-agent-security)에 고정했다. 실제 위험 효과와 정상 대조군을 독립 기준으로 삼아 Cisco Skill Scanner 2.1.0, Cisco MCP Scanner 4.8.4, SkillSpector 2.11.2, AgentShield 1.6.0의 실행 결과를 비교했다. ## 1. 먼저 확인할 결론

질문 4는 기존 도구의 실패를 보여 주는 실험으로 정하지 않는다. **질문 3의 동일 사례를 기존 방법으로 처리하여 무엇이 해결되고 무엇이 남는지 확인**한다. 기존 방법으로 충분하면 해당 기능을 재사용하고 차별성 가설을 축소한다.

새 플랫폼 화면이 더 좋다는 주장은 질문 5다. 이번에는 플랫폼 없이도 기존 방법의 입력·과정·출력·수동 작업량을 기록할 수 있다.

## 2. 비교 대상과 범위

| 대상 | 사용 목적 | 반드시 제공할 기능·입력 | 평가에서 제외할 잘못된 해석 |
|---|---|---|---|
| Cisco Skill Scanner | Skill 본문·참조·동봉 코드 검사 | 전체 디렉터리, 선택한 분석기와 규칙 기록 | behavioral 정적 dataflow를 실제 실행 관찰로 취급 |
| Cisco MCP Scanner | 고정 MCP 메타데이터 검사 | 동일 tools JSON, YARA 정적 모드 | 도구 설명의 무발견을 서버 구현·실효 권한 검증으로 취급 |
| NVIDIA SkillSpector | Skill 검사와 전후 비교 | raw 결과, 같은 경로의 baseline, 억제된 finding 표시, 지원하는 완료 상태 게이트 | 점수 변화가 없으면 자동으로 미탐 판정 |
| AgentShield | 호스트 설정·정책·공급망·검토 근거 | 실제 지원 호스트 형식, baseline, policy, supply-chain, evidence pack, runtimeConfidence | 예제 설정을 활성 런타임 설정으로 취급; evidence pack 기능 누락 |
| Git·digest·잠금 / 서명 검증 | 검사본과 설치본 동일성 | 전체 파일 목록과 해시, lock에 기록된 대상 범위, 가능한 실제 서명 검증 | 출처 동일성을 취약점 부재로 취급 |
| Snyk Agent Scan, 확장 | 지원 호스트의 Skill/MCP 분석 | 정상 API 모드·현재 형식, 동일 입력, 자체 MCP 서버 | API·서버 실행을 꺼 놓고 전체 제품의 한계로 일반화 |

공식 근거·커밋은 [자료 기록](자료선정과-조사기록.md)에 있다. 도구 수를 늘리는 것보다 위 핵심 기능을 정상 사용했는지가 우선이다.

**실행 트랙을 분리한다.**

- **T1 로컬 정적 비교:** 네트워크 없이 가능한 모드. 외부 조회가 빠지면 그 범위를 기록한다. SkillSpector의 `--no-llm`도 OSV 의존성 조회를 시도할 수 있으므로 완전 오프라인과 동일시하지 않는다.
- **T2 정상 온라인/LLM 비교:** 각 제품의 지원 분석기를 사용하고 API·모델·전송 범위·비용을 기록한다. T1과 결과를 별도로 제시한다. 계정이 없으면 `NOT_RUN`이며 제품 실패가 아니다.
- **T3 실행 통제, 선택:** 실제 지원 호스트에 기존 통제를 적용해 A·B를 반복한다. 현재 정적 플랫폼 범위와 분리한다. Q4를 정적 비교까지만 수행했다면 runtime 제품 전체의 충분성을 결론 내리지 않는다.

## 3. 공정한 대조 조건

| 조건 | 구성 | 용도 |
|---|---|---|
| B0 원본 검토 | 원문·Git diff·정책·검사 보고서 | 현재 수작업 절차 관찰 |
| B1 강한 기존 방법 | 위 도구의 적용 가능한 기능 + digest/lock + 기존 evidence pack/카드 + 수동 검토 | 질문 4의 주 대조군 |
| B2 단순 통합, 후속 | B1의 같은 정보·같은 엔진을 한 화면에 모음 | 단순 편의와 추가 분석을 구분 |
| B3 우리 제안, 후속 | B2 + 대상 연결·변경 요약·조건 추적 | 질문 5의 추가 효과 평가 |

B1을 단순 경고 목록으로 축소하지 않는다. NVIDIA의 검사·카드·서명 체계와 AgentShield의 검증 가능한 증거 묶음도 기존 수단이다. 자체 자료를 NVIDIA 공식 서명본처럼 꾸미지 않고, 합성 자료의 digest 확인과 실제 서명본 검증을 구분한다. [S04](자료선정과-조사기록.md#s04-agentshield) · [S06](자료선정과-조사기록.md#s06-nvidia-신뢰-파이프라인)

모든 조건에 같은 정책·파일·호스트 설정·시간 범위와 원본 접근권한을 제공한다. 특정 제품이 모르는 자체 `workflow.json`을 지원한다고 가정하지 않는다. 지원되는 원문·설정으로 전달하고, 추가 수동 해석이 필요하면 그 작업을 기록한다.

## 4. 버전과 설정 고정

1. 실행할 release 또는 commit **하나를 프로필별로 고정**한다. `latest`로 설치하지 않는다.
2. 도구 버전, 소스 커밋, 설치 패키지/이미지 digest, 의존성 lock, 규칙·모델·API 버전을 기록한다.
3. 해당 버전의 `--help`와 공식 문서를 대조하고 실제 명령·설정 파일을 결과에 보관한다.
4. 정상 예제와 알려진 finding 예제로 분석기가 입력을 실제로 읽는지 확인한다. 파싱되지 않는 입력은 미탐에 합산하지 않는다.
5. 지원하지 않는 옵션은 제거하고 제한을 명시하거나 별도 개발 커밋 트랙을 둔다. 오류를 숨기고 같은 조건이라고 보고하지 않는다.

**특히 SkillSpector:** 확인한 최신 release는 `v2.11.2`, 현재 main 커밋은 `d162d9b343e559be13df8ebba093df3bc9d58c90`이다. 현재 main README의 `--fail-on-incomplete` 설명은 확인했지만 v2.11.2 README에는 같은 설명이 없다. 옵션 부재를 단정하지 말고 실행할 버전의 help/소스를 확인한다. 이번 설계의 개발 커밋 후보를 이전 실험의 릴리스와 섞지 않는다.

## 5. 실제 비교 절차

### 5.1 사전 점검

Cisco 공개 평가 사례 중 정상 1개·위험 신호 1개로 입력 연결을 점검한다. 제작자의 `_expected.json`은 회귀 점검 참고값이다. 공개 개발용 사례를 독립 탐지율 평가셋으로 사용하지 않는다.

### 5.2 12개 자체 사례

- A: v1을 스캔·승인하고 v2를 적용한 뒤 보고서 동일성·참조 변경·현재 판단을 확인한다.
- B: 같은 Skill digest에 좁은/넓은 host 설정을 각각 공급한다. 설정 지원 여부, 위험 근거, 수동 확인 필요 항목을 기록한다.
- C: 실제 도구의 완료 상태 출력과 통합 어댑터의 오류 처리를 따로 확인한다. 모의 timeout을 실제 제품 오류라고 세지 않는다.

**baseline은 같은 작업 경로에서 비교한다.** 보존한 v1·v2 입력은 불변 디렉터리에 두고, 폐기 가능한 동일 경로 `work/subject/`에 한 번에 한 버전씩 배치한다. v1의 검토된 finding만 사유와 함께 baseline에 수용한 뒤 v2로 바꿔 검사한다. 원본 보고서와 억제된 finding을 함께 보관한다. 위험한 v1 finding까지 무조건 수용하는 기본값을 만들지 않는다.

아래는 공식 문서에서 확인한 **명령 형태의 예시**이며 실행 결과가 아니다. 설치할 버전·분석기·정책 파일을 고정한 후 사용한다.

```text
skillspector scan work/subject --no-llm --format json --output runs/v1.json
skillspector baseline work/subject --no-llm -o runs/baseline.yaml
skillspector scan work/subject --no-llm --baseline runs/baseline.yaml --show-suppressed --format json --output runs/v2.json

agentshield scan --path work/host --baseline runs/agentshield-baseline.json --policy policy/agentshield.json --supply-chain --evidence-pack runs/agentshield-evidence
agentshield evidence-pack verify runs/agentshield-evidence --json

mcp-scanner --analyzers yara static --tools inputs/tools-list.json
```

AgentShield baseline·policy 파일은 선택 버전의 정식 생성 명령과 스키마로 만든다. 명령 성공만으로 policy P1 전체를 표현·검증했다고 간주하지 않는다. MCP JSON 출력 형식·저장 옵션은 선택 버전의 help에서 확인하여 어댑터에 고정한다.

### 5.3 공개 현실 사례로 넓히기

핵심 12개가 작동하면 공개 Skill 6개 정도를 별도 소집합으로 선정한다. 정상 후보 2, 위험 신호 후보 2, 불확실 후보 2를 미리 정한 기준으로 골라 원문·번들·해시·라이선스를 확인한다. 이는 사례 확인용 구성이지 현실 분포가 아니다.

실제 버전 쌍이 필요한 경우 공개 저장소의 같은 Skill 경로에서 두 커밋을 확보한다. ClawHub의 최신 버전 중심 자료가 과거 승인 기록이나 버전 쌍을 제공한다고 가정하지 않는다. 버전 쌍을 찾지 못하면 자체 쌍으로 남기고 현실 업데이트 재현이라고 쓰지 않는다.

## 6. 판정은 점수가 아니라 근거로 한다

| 평가 항목 | 성공 기준 | 실패/제한 처리 |
|---|---|---|
| 현재 대상 확인 | 보고서·설치본·설정의 적용 관계를 정확히 표시 | 이름만 같아 승인 재사용하면 잘못된 연결 |
| 정책 위반 파악 | P1을 위반하는 파일/접근 범위를 구체적으로 찾음 | 경고 개수만 늘면 성공 아님 |
| 정상 변경 처리 | A04·B03을 근거에 따라 허용 | 전부 보류하면 정상 처리 비용으로 집계 |
| 불완전성 표시 | 오류·미지원·제외 범위를 보존 | 모의 통합 오류와 실제 제품 출력을 구분 |
| 검토 과업 완결 | 검토자가 적용 조건과 다음 행동을 설명 가능 | 수동 연결이 필요하면 횟수·시간 기록 |

도구별 실행 상태는 `COMPLETED / PARTIAL / ERROR / UNSUPPORTED / NOT_RUN`, 과업 해결 상태는 `SOLVED / PARTIAL / UNRESOLVED / NOT_ASSESSED`로 분리한다. `UNSUPPORTED`를 전체 제품의 미탐 점수로 합산하지 않는다.

위험 승인·정상 거부는 사람의 결정 자료가 있을 때만 계산한다. 기술 비교에서는 위반/정상/불확실 사례별 잘못된 허용·불필요한 보류·누락 근거 수를 원래 분모와 함께 보고한다. 12개는 회귀·데모용이며 일반 탐지 정확도를 추정할 표본이 아니다.

성공·실패 판단은 비교 출력과 독립적으로 정한 정책·원본·자원 관찰로 한다. 평가 시스템과 같은 규칙 함수를 정답 생성기로 재사용하지 않는다.

## 7. 결과에 따른 프로젝트 결정

| 관찰 결과 | 다음 행동 |
|---|---|
| B1이 핵심 과업을 모두 해결하며 도입 부담도 수용 가능 | 기존 도구를 채택; 해당 과업의 신규 분석기 필요성 주장을 중단 |
| B1이 탐지하나 원본·설치본·조건 인계에 반복 수작업 필요 | 그 연결 과업만 프로토타입으로 만들어 Q5 비교 |
| 지원 범위 안에서 중요한 누락이 재현됨 | 입력·버전·설정·원본 출력으로 재현하고 독립 검토 후 좁은 가설 유지 |
| 미지원 형식에서만 차이가 남음 | 추가 지원 범위라는 기여로 표현; 기존 탐지 성능 열등 주장 금지 |
| 우리 안이 모두 보류하거나 위험 승인을 늘림 | 성공으로 발표하지 않고 설계 수정 |

별도 9개 사례의 현재 판정은 **동적 기준 결과와 실행 가능한 정적 스캐너 비교 완료**다. Cisco MCP YARA는 M01 도구 설명 주입을 HIGH로 탐지했지만 실제 전송 효과가 난 M02 응답 주입은 SAFE였다. Cisco Skill Scanner와 SkillSpector 기본 `--no-llm`은 실제 효과가 확인된 S01·S03에 위험 신호를 내지 않았다. SkillSpector의 `--fail-on-incomplete` gate는 정상 S00을 포함한 네 사례를 모두 exit 1로 차단해 불완전성은 드러냈지만 공격을 구분하지 못했다. AgentShield는 `filesScanned=0`이므로 `NOT_ASSESSED`, Snyk와 외부 LLM 의미 분석 모드는 `NOT_RUN`이다. 따라서 실행한 모드만으로는 충분하지 않았다고 결론 내리되, 모든 최신 도구·모드의 전체 미탐률로 일반화하지 않는다. 원안 A·B·C 12개와 강한 B1 전체 비교는 아직 실행하지 않았다.
