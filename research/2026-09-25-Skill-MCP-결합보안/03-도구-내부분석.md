## G01. Cisco Skill Scanner

소스: [고정 commit](https://github.com/cisco-ai-defense/skill-scanner/tree/4f8bec3437dd9af8dc024b63fdaf23422f3a148e) · Apache-2.0

확인한 처리 흐름:

`SkillLoader → SkillScanner → 각 analyzer → finding 정규화/정책 → Report`

- [`behavioral_analyzer.py`](https://github.com/cisco-ai-defense/skill-scanner/blob/4f8bec3437dd9af8dc024b63fdaf23422f3a148e/skill_scanner/core/analyzers/behavioral_analyzer.py#L18): Python AST와 정적 데이터 흐름 분석. 이 모드가 대상 Skill을 실행하는 것은 아니다.
- [`cross_skill_scanner.py`](https://github.com/cisco-ai-defense/skill-scanner/blob/4f8bec3437dd9af8dc024b63fdaf23422f3a148e/skill_scanner/core/analyzers/cross_skill_scanner.py#L57): Skill 집합에 대해 데이터 릴레이, 공통 외부 URL, 상보적인 트리거, 공통 수상한 코드 패턴을 찾는다.
- 같은 파일의 `_detect_data_relay_pattern`: 수집 관련 단어와 네트워크 관련 표현을 가진 Skill 집합을 구성한다. **실제 동일 데이터가 이동했는지 확인하는 taint 추적과는 다르다.**
- [`scanner.py`](https://github.com/cisco-ai-defense/skill-scanner/blob/4f8bec3437dd9af8dc024b63fdaf23422f3a148e/skill_scanner/core/scanner.py#L1575): `check_overlap`을 켜면 설명 중복 검사뿐 아니라 `CrossSkillScanner.analyze_skill_set()`도 실행한다. 이름만 보고 기능을 놓치기 쉽다.

**무엇을 놓칠 수 있나:** Skill 안에 외부전송 표현이 없어도 MCP 도구가 외부 발행 능력을 제공할 수 있다. 반대로 민감 정보와 네트워크 표현이 함께 있어도 데이터가 연결되지 않거나 승인된 내부 전송일 수 있다. 이번 결과는 [실험 문서](05-실험과-재현.md)에 있다.

**우리 활용:** 경쟁자를 없다고 가정하지 말고 필수 비교군으로 사용한다. 원래 finding을 보존하고 혼합 경로 분석을 추가하는 구조가 현실적이다. 개별 보고서만 보여주면 `cross_skill_findings`가 누락되므로 집합 결과도 표시해야 한다.

## G02. Cisco MCP Scanner

소스: [고정 commit](https://github.com/cisco-ai-defense/mcp-scanner/tree/9e47aabdf2017b82e78f3419f39a75f20b6f98fa) · Apache-2.0

- [`static_analyzer.py`](https://github.com/cisco-ai-defense/mcp-scanner/blob/9e47aabdf2017b82e78f3419f39a75f20b6f98fa/mcpscanner/core/analyzers/static_analyzer.py#L84): 독자적인 탐지 엔진이 아니라 **저장된 JSON을 읽어 하위 분석기에 전달하는 조정자**다. `scan_tools_file()`은 도구 설명과 입력 schema 등을 분석한다.
- [`yara_analyzer.py`](https://github.com/cisco-ai-defense/mcp-scanner/blob/9e47aabdf2017b82e78f3419f39a75f20b6f98fa/mcpscanner/core/analyzers/yara_analyzer.py): 패키지의 규칙을 컴파일하고 문자열 매칭을 finding으로 변환한다.
- [`behavioral/code_analyzer.py`](https://github.com/cisco-ai-defense/mcp-scanner/blob/9e47aabdf2017b82e78f3419f39a75f20b6f98fa/mcpscanner/core/analyzers/behavioral/code_analyzer.py#L18): MCP 등록 함수 추출 → AST/호출 그래프/데이터 흐름 맥락 → LLM으로 설명과 구현의 불일치 비교. **이번에 실행한 YARA 모드와 별도 기능**이다.

**한계:** 도구가 설명대로 읽고 설명대로 발행해도, 두 호출 사이의 업무 정책은 위반할 수 있다. 저장된 JSON만으로 원격 구현이나 실제 권한을 입증할 수 없다. 선택적 LLM/API 모드의 효과를 이번 무경고 결과에서 추정하지 않는다.

**우리 활용:** MCP 명세 검사와 소스 정합성 분석 결과를 입력으로 받되, 서버와 계정·대상 범위를 붙여 Skill 지시와 연결한다. 실제 서버 연결 없이 제공받은 명세를 검사하는 모드는 기존 프로젝트의 정적 검사 범위와 맞는다.

## G03. Snyk Agent Scan / Toxic Flow Analysis

소스: [고정 commit](https://github.com/snyk/agent-scan/tree/4e8d20dba67916b2e837f108c1708f7c2049eaf3) · Apache-2.0

확인한 파일: `inspect.py`, `skill_client.py`, `mcp_client.py`, [`verify_api.py`](https://github.com/snyk/agent-scan/blob/4e8d20dba67916b2e837f108c1708f7c2049eaf3/src/agent_scan/verify_api.py#L434), `models/api/v20260710.py`.

CLI는 구성요소를 수집·정규화하고 `analyze_machine()`에서 분석 API로 전달한다. 최신 확인 경로에는 Snyk 인증 분기가 있고, `skip_pushing`도 분석 API 호출을 없애는 옵션으로 볼 수 없다. **공개 CLI 소스가 분석 백엔드 전체의 공개를 뜻하지 않는다.**

TFA의 공식 설명은 신뢰·민감도·외부전송 가능성을 가진 tool-flow graph에서 위험 경로를 찾고, 정적·런타임 정보를 함께 사용할 수 있다는 것이다. 이 부분은 우리가 제안하는 것과 상당히 겹친다. [TFA 원문](https://invariantlabs.ai/blog/toxic-flow-analysis)

**한계 판단:** 이번에는 원격 분석을 실행하지 않았으므로 Skill×MCP를 못 잡는다고 결론 내릴 수 없다. 공개 계약에서 입력과 출력 형태는 확인했지만 백엔드의 경로 추론·정확도는 확인하지 못했다. 실제 사용자 설정이나 사내 Skill을 업로드하지 않았다.

**우리 활용:** 공개 기능 설명을 최소 경쟁 기준으로 삼고, 비교 가능한 동일 합성 fixture의 보고서를 확보한 뒤 차별성을 다시 판정한다. ‘완전 로컬·재현 가능한 근거’는 구현 목표가 될 수 있지만 그 자체가 탐지 정확도 기여는 아니다.

## G04. SCR-Bench

소스: [고정 commit](https://github.com/saint-viperx/SCR_Bench/tree/b8bb3e9e3cf7e72db091655f2d5e8ef15b273848) · MIT

확인 경로: `SCR-CapFlow/run_privilege_experiment_pipeline.py` → `run_all_privilege_experiments.py` → [`scripts/experiment_case1.py`](https://github.com/saint-viperx/SCR_Bench/blob/b8bb3e9e3cf7e72db091655f2d5e8ef15b273848/SCR-CapFlow/scripts/experiment_case1.py).

각 case에 발견 데이터와 부작용 파일을 두고, `verify_ground_truth()`에서 같은 대상이 후속 변경에 쓰였는지 확인한다. `control / A_only / B_only / A+B_neutral / A+B_explicit` 조건이 있다. 독립 평가 단위·대조군·상태 판정 방식을 참고하기 좋다.

**실행하지 않은 이유:** 확인한 runner는 실제 Claude CLI와 `--dangerously-skip-permissions`를 호출한다. fixture의 `sandbox` 폴더명은 OS 격리의 증거가 아니다. 기존 프로젝트는 검사 대상 Skill/MCP 실행을 범위 밖으로 정하고 있으며, 이번에는 연구코드와 조건만 분석했다. 이는 재현 완료가 아니다.

README의 여러 CLI 표와 하단의 현재 Claude Code 중심 지원 설명도 구분한다. 코드 경로 확인 없이 다중 호스트 지원을 완료했다고 쓰지 않는다.

## G05. CompoSkill

소스: [고정 commit](https://github.com/Limax666/CompoSkill/tree/d7dc9d314f491eaace0b9e7c18e0c21ed3b71577)

구성: metadata snapshot → `scene_scg_builder.py` → [`chain_search_ksp.py`](https://github.com/Limax666/CompoSkill/blob/d7dc9d314f491eaace0b9e7c18e0c21ed3b71577/scripts/chain_search_ksp.py#L98) → attack-plan 생성 → Nanobot/OpenClaw 평가 → scanner adapter 비교.

실제로 읽은 `search_candidates()`는 역할과 연결된 이웃을 따라 DFS로 후보를 열거한다. `k*5`에서 조기 중단하고, 지정 길이에서는 점수순, 길이 미지정에서는 긴 경로 우선으로 정렬한다. **일반적인 전역 최적 k-shortest-path 보장이라고 설명하면 안 된다.** 상단 주석의 길이 2–3 설명과 코드의 `MAX_LEN=10`도 다르다.

이번 실행은 수작업 그래프의 3단계 경로가 나오는지와 간선을 끊으면 없어지는지만 확인했다. 역할 추출·의미 필터·피해 에이전트·ASR는 검증하지 않았다. LLM client를 생성하거나 공격 유도 단계를 호출하지 않았다.

**라이선스:** 루트 LICENSE가 없고 README는 관련 논문의 라이선스를 참조한다. 명확한 소프트웨어 재배포 허용으로 간주하지 않았다. 소스는 개인 검토용 임시 경로에만 두고 제출물에는 원본 코드를 복사하지 않았다.

## 이전 데모/자료와의 연결

기존 `platform/experiments/capability-diff/RESULTS-combined.md`는 SkillSpector 2.11.2의 `--no-llm` 모드에서 **11개의 의도적으로 만든 변경 쌍**을 비교한 기록이다. 문서와 표를 다시 확인했지만 당시 데모 영상을 보거나 해당 스캐너를 재실행하지는 않았다.

그 결과의 9/11은 **그 표본에서 finding 변화가 없었던 횟수**다. 이것을 모든 스캐너의 결합 탐지 실패율로 확장하면 안 된다. 특히 새 조사에서 Cisco 교차 Skill 검사와 여러 결합 연구가 확인되므로, 기존 문서의 “기존 스캐너는 표면 패턴만 본다”는 일반화는 지금 프로젝트 주장으로 재사용하지 않는다.

기존 플랫폼 구조의 수집→파서→검사→근거 그래프→변경 검토는 재사용 가능하다. 이번 제안은 개별 finding만 합치는 대신 **연결 환경을 포함한 경로 판정 계층**을 추가하는 것이다. 팀 합의 없이 기존 범위를 동적 차단 제품으로 변경하지 않는다.
