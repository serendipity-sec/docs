# 선행조사 — AI 에이전트 구성요소 공급망 보안 생태계

조사일 2026-09-17 · 조사자 김민우 · 제안서 v2 이후 확인된 내용

> **요약**: 제안서 v2(2026-09-16 기준)의 경쟁 도구 분석은 이미 뒤처져 있다.
> NVIDIA·Snyk가 진입했고, **정적 스캐너가 90% 이상 우회된다는 연구**가 나왔으며,
> OWASP가 스킬 전용 Top 10(AST10)을 따로 발표했다. 동시에 **팀이 좁히려던 방향이
> AST07 "Update Drift"라는 이름으로 표준에 올라가 있고**, 67,453건짜리 공개 평가
> 데이터셋이 존재한다. 위협이자 기회다.

## 1. 생태계 규모 — 얼마나 큰가

| 구성요소 | 규모 | 출처 |
|---|---|---|
| 공개 스킬 | 69,000개 이상 (skills.sh, 2026-02) · **67,453개 버전** (ClawHub 데이터셋) | [S03] · [N01] |
| MCP 서버 | 공식 레지스트리 **9,652개** 서버 / **28,959개 서버-버전 레코드** (2026-05-24) | [N08] |
| MCP 서버 (전체 추정) | 10,000개 이상 (2026-03), 4개 주요 레지스트리 기준 약 9,400개 (2026-04) | [N08] |
| MCP SDK | 월 다운로드 약 5억 회 (2026-07) · 월 9,700만 회 (2025-12, Anthropic) | [S04] · [N08] |
| 기업 도입 | 소프트웨어 조직 **41%**가 MCP 서버를 제한적/광범위 프로덕션 운영 (Stacklok 2026) | [N08] |

**해석**: 성장은 확실하다. 특히 **버전 레코드가 서버 수의 3배**라는 점(28,959 / 9,652)이 중요하다.
평균적으로 서버 하나가 세 번 넘게 업데이트됐다는 뜻이고, 이는 곧 **업데이트마다 재검토
지점이 생긴다**는 의미다. 제안서의 "변경 비교" 방향을 뒷받침하는 숫자다.

| 사례 | 규모 | 출처 |
|---|---|---|
| Acronis TRU 연구 | 13개 계정, 악성 스킬 575개 이상 | [S06] |
| **ClawHavoc 캠페인** (Koi Security) | 단일 캠페인에서 악성 스킬 **341개**. SKILL.md가 "설치 전제조건"을 가장해 정보 탈취 도구를 받아 실행하도록 지시 | [N03] |

| 26,000 에이전트 사건 | 가짜 스킬 하나가 **모든 보안 스캐너를 통과**하고 26,000개 에이전트에 도달 | [N04] |

### 2-2. MCP 고유 공격 — 이름이 붙은 공격 유형

| 공격 | 내용 |
|---|---|
| **Tool Poisoning** | 도구 설명·파라미터 스키마·응답에 적대적 지시를 심음 |
| **Rug Pull** | 승인 시점엔 깨끗하고, 이후 서버가 도구 설명을 바꿔 탈취 지시를 넣음. **CVE-2025-54136 (CVSS 8.8)** 로 실증 |
| **Tool Shadowing** | 다른 서버의 도구 동작을 가로챔 |
| **Cross-server attack** | 서버 간 경계를 넘는 공격 |
| **Confused deputy / OAuth** | 권한 위임 체인 악용 |

공통 원인: **MCP 클라이언트가 서버로부터 신뢰를 상속받되 지속적으로 검증하지 않는다.**
"승인은 한 순간이지만 신뢰는 지속되어야 한다."

실제 사고: GitHub MCP 취약점(저장소 콘텐츠를 통한 간접 프롬프트 인젝션),
CVE-2025-6514(mcp-remote OS 명령 주입 → 악성 서버 연결 시 RCE).

### 2-3. ★ 정적 스캐너 우회 — 팀 접근법에 직접 영향

**이 항목이 이번 조사에서 가장 중요하다.**

| 연구 | 결과 |
|---|---|
| **SkillCloak** (홍콩과기대) | 악성 동작은 그대로 두고 겉모습만 바꿈. ① 의심 토큰·경로·URL을 런타임에 재조립되는 동등 형태로 치환 ② 실제 페이로드를 스캐너가 건너뛰는 디렉터리에 숨기고 깨끗한 표지를 씌움 → **패킹 기법이 모든 스캐너를 90% 이상 통과** |
| **Trail of Bits** | ClawHub·Cisco·Vercel skills.sh의 악성 스킬 탐지기를 우회. **4건 중 3건이 1시간 미만**에 개발됨 |
| **CSA 연구 노트** | "AI Agent Skill Scanners: Bypassed Across the Board" |
| **멀티모달 은닉** | 이미지 등에 지시를 숨겨 스캐너를 통과하는 공격 |
| 대응 연구 | **SkillDetonate** — 샌드박스에서 실제 실행하며 파일 접근·네트워크·데이터 이동을 관찰 |

**팀에 주는 의미** (뒤집어 읽어야 한다):

- 나쁜 소식: "정적 검사로 악성을 잡겠다"는 목표는 이미 학계가 실패를 입증한 목표다.
- 좋은 소식: **제안서는 원래 "악성 판정"이 아니라 "검토 근거 제시"를 목표로 했다.**
  ("안전 인증으로 표시하지 않는다", "검사 불가를 정상으로 집계하지 않는다")
  우회 연구는 이 설계가 **옳았다는 증거**로 쓸 수 있다. 정적 단독 판정은 못 믿으니
  사람이 볼 근거와 경로를 보여줘야 한다 — 이게 정확히 팀이 만들려는 것이다.

## 3. 표준 — 어떻게 분류되고 있는가

### 3-1. OWASP Top 10 for Agentic Applications (2025-12)

- **ASI04 Agentic Supply Chain Vulnerabilities** — 제3자 도구·프레임워크·레지스트리·에이전트 구성요소
- LLM03(정적 공급망, 배포 전)과 달리 **ASI04는 실행 중 동적 구성**을 다룸

### 3-2. ★ OWASP Agentic Skills Top 10 (AST10, 2026) — 제안서에 없는 표준

스킬 전용 Top 10이 별도로 나왔다. **제안서 v2에는 이 표준이 언급되지 않는다.**

| ID | 항목 | 우리 프로젝트와의 관계 |
|---|---|---|
| AST01 | Malicious Skills | 검사 대상 |
| AST02 | Supply Chain Compromise | 프로젝트 주제 그 자체 |
| AST03 | Over-Privileged Skills | ④ 접근 범위 검사 |
| AST04 | Insecure Metadata | ② 선언·구현 불일치 |
| AST05 | Untrusted External Instructions | ① 규칙 파일 검사 |
| AST06 | Weak Isolation | 범위 밖 (런타임) |
| **AST07** | **Update Drift** | **★ 팀이 좁히려는 방향 그 자체** |
| **AST08** | **Poor Scanning** | **★ 스캐너 불일치 문제** |
| **AST09** | **No Governance** | **★ 검토 기록·공유** |
| AST10 | Cross-Platform Reuse | 여러 호스트 간 재사용 |

**이건 결정적이다.** 제안서 15장이 "핵심 질문을 업데이트의 보안상 변경 탐지로 좁히자"고
했는데, 그게 **AST07 Update Drift라는 이름으로 국제 표준 항목에 올라가 있다.**
"우리가 임의로 좁힌 범위"가 아니라 "표준이 지목한 위험 항목"이 된다.
설명회에서 범위 축소를 방어할 때 이보다 강한 근거는 없다.

### 3-3. MITRE ATLAS — 공백이 있다

ATLAS는 14개 전술을 다루지만 **에이전트 제어 평면(control plane) 계층을 아직 다루지 않는다.**
오케스트레이션 메타데이터·위임 토큰 체인·MCP 같은 프로토콜 계층을 악용하는 기법은
ATLAS에 자리가 없다.

## 4. 방어 도구 지형 — 누가 이미 무엇을 하는가

> **제안서 13장의 비교표는 갱신이 필요하다.** skills.sh + Cisco 3종만 적혀 있는데,
> 그 사이 NVIDIA와 Snyk가 들어왔다.

### 4-1. 스킬 검사

| 도구 | 주체 | 특징 |
|---|---|---|
| **SkillSpector** | **NVIDIA** (2026-08, Apache) | NVIDIA-Verified Agent Skills 프로그램의 스캐닝 계층. 디렉터리·zip·단일 SKILL.md·Git URL을 받아 findings + 위험 점수 + 권고 반환 |
| Skill Scanner | Cisco AI Defense | 패턴 탐지 + LLM-as-a-judge + 행위 데이터플로 분석 |
| **agent-scan** | **Snyk** | 에이전트·MCP 서버·스킬을 한 도구로. 스킬 자동 발견 지원 |
| **skillfence** | 오픈소스 | **런타임 행위 추적.** 파일·프로세스·네트워크를 계측해 선언된 capability manifest와 대조. AST01~AST10 커버 표방 |
| SkillDetonate | 연구 | 샌드박스 동적 탐지 |

### 4-2. MCP 검사 · 변경 방어

| 도구 | 특징 |
|---|---|
| Cisco MCP Scanner | 메타데이터·소스 검사, 오프라인 JSON 검사 |
| **MCP-Scan** (Invariant) | 클라이언트 설정·도구 메타데이터 정적 분석. **신뢰 도구 피닝으로 rug pull 식별** |
| MCPScan.ai | 호스티드. 지속적 저장소 모니터링 |
| **mcpdef_pin** | 승인 시 도구의 통제 필드 해시를 기록 → 이후 `tools/list`에서 드리프트하면 거부하고 `rug_pull` 감사 로그 |
| **ETDI** | 프로토콜 계층 해결책. 도구 정의에 서명 요구, 변경 시 새 서명 버전 강제, 해시 불일치 시 재승인 |

### 4-3. 통합·거버넌스

Cisco DefenseClaw(사용 전 검사 + 런타임 트래픽 + 감사 근거),
Manifold Manifest(AI 에이전트 생태계 공급망 인텔리전스),
TrueFoundry(에이전트 구성요소 어드미션 컨트롤),
JFrog(스킬·MCP 도구 통합) 등 **기업용 통합 제품이 이미 여럿 있다.**

## 5. ★ 확인된 빈 곳 — 우리가 들어갈 자리

### 5-1. 스캐너 불일치 (AST08 Poor Scanning)

논문 *ClawHub Security Signals: When VirusTotal, Static Analysis, and SkillSpector Disagree*
(OpenClaw Foundation + NVIDIA) 의 실측치:

| 측정 | 값 |
|---|---|
| 분석 대상 | 공개 스킬 최신 버전 **67,453건** |
| 두 스캐너 쌍의 최대 겹침 | 합집합 양성의 **10.4%** 이하 |
| 세 스캐너 모두가 지목한 비율 | **0.69%** |
| **단일 스캐너만 지목한 비율** | **81.9%** |
| SkillSpector | 의심(suspicious) 행 25,504건 중 19,209건 양성(75.3%) — 그러나 악성(malicious) 행 206건 중 14건(6.8%)만 양성 |
| VirusTotal | 악성 행 206건 중 150건(72.8%) 양성 |

논문 결론: **"에이전트 스킬 보안은 단일 스캐너의 허용/차단 결정이 아니라 계층적
거버넌스를 요구한다."**

> **이게 우리 프로젝트의 존재 이유를 대신 증명해 준다.**
> 스캐너마다 보는 게 다르고(SkillSpector는 의미적 위험, VirusTotal은 번들 코드 멀웨어),
> 81.9%는 한 곳만 잡는다. 그렇다면 **여러 결과를 공통 형식으로 모아 근거와 함께
> 사람에게 보여 주는 계층**이 필요하다. 제안서의 "공통 결과 모델"이 바로 그것이다.

추가로 확인된 것: 어떤 스캐너는 **JavaScript·TypeScript만 검사**한다는 문서화된 공백이 있다.
Snyk는 확인된 악성 스킬의 **91%가 전통적 멀웨어 패턴과 프롬프트 인젝션을 결합**해
양쪽 방어를 모두 무력화한다고 보고했다.

### 5-2. 업데이트 드리프트 (AST07) — 구성요소별 편차

| 구성요소 | 변경 탐지 수준 |
|---|---|
| MCP 서버 | **이미 있음** — MCP-Scan 피닝, mcpdef_pin, ETDI |
| 스킬 | **약함** — 기존 규칙은 "rug pull을 가능하게 하는 셋업 패턴"(원격 로딩, base64 실행, post-install 훅)을 탐지할 뿐, **진짜 rug pull 탐지는 시간에 따른 해시 비교가 필요**하다고 명시됨 |
| 규칙 파일 | 사실상 없음 |
| 플러그인 | 매니페스트 버전 고정 논의 단계 |

→ **MCP는 이미 풀렸고, 스킬·규칙·플러그인 쪽이 비어 있다.**
제안서의 "보안상 변경 비교"는 MCP가 아니라 **스킬·규칙 쪽에 초점을 맞춰야 차별화된다.**

### 5-3. 조합·경로

단일 구성요소 판정 도구는 많지만, **규칙 → 스킬 → 도구 → 접근 자원** 경로를
원본 근거와 함께 보여 주는 도구는 확인되지 않았다. 다만 Cisco IDE 스캐너가
"cross-tool attack chains"를 언급하므로, **실제 기능을 확인해 봐야 한다.** (미확인)

## 6. ★ 평가 데이터셋 — 직접 쓸 수 있는 것을 찾았다

제안서 16장은 "평가 자료 120건 이상을 직접 구성"한다고 했다. 그런데:

**ClawHub Security Signals** (HuggingFace: `OpenClaw/clawhub-security-signals`)

- 공개 스킬 최신 버전 **67,453건**
- 각 행 = 정제된 SKILL.md 내용 + 번들 파일 + ClawScan 레지스트리 최종 판정
  + **3개 스캐너 계열(VirusTotal / 정적 휴리스틱 / SkillSpector)의 근거**
- 라이선스·재배포 조건은 **직접 확인 필요**

**주의 (논문이 직접 명시한 한계)**:
- 라벨은 레지스트리의 **자동 판정**이지 사람이 라벨링한 ground truth가 아니다 ("silver-standard")
- 초기 버전(v1) 스냅샷이며 사람이 라벨링한 부분집합은 개발 중

**팀에 주는 의미**: 이 데이터셋을 **개발·탐색용**으로 쓰고, 최종 평가용으로는
제안서대로 사람이 라벨링한 소규모 세트를 따로 만드는 2단 구성이 가능하다.
"120건을 처음부터 만든다"보다 훨씬 현실적이고, **기존 스캐너 3종의 판정이 이미 붙어 있어
우리 결과와 직접 비교할 수 있다.** 5-1의 불일치 가설을 검증할 재료가 그대로 들어 있다.

## 9. ★ 그래서 무엇이 남는가 — 차별화 재정의

빈 곳 세 자리 중 둘이 줄어들었다. 그래도 **남는 것이 있고, 오히려 더 날카로워졌다.**

### 9-1. 핵심 구분 — findings diff ≠ capability diff

AgentShield와 SkillSpector의 베이스라인은 둘 다 **"알려진 findings를 억제"** 하는 방식이다.
즉 답하는 질문은 **"어떤 경고가 새로 떴는가"** 이다.

우리가 답하려는 질문은 다르다. **"이 구성요소가 새로 무엇을 할 수 있게 됐는가"** 이다.

| | findings diff (기존) | capability diff (우리) |
|---|---|---|
| 기준 | 스캐너 규칙 | 구성요소가 요구하는 접근·연결·실행 |
| 예 | "규칙 R12가 새로 발동함" | "v1에는 없던 외부 호스트 전송이 v2에 생김" |
| **맹점** | **두 버전 모두 규칙을 발동시키지 않으면 변화가 안 보인다** | 규칙 발동 여부와 무관하게 역량 변화를 본다 |

**이게 결정적이다.** 어떤 스킬이 v1에서도 v2에서도 아무 규칙을 건드리지 않으면서
접근 범위만 넓혔다면, 베이스라인 방식은 **아무것도 보고하지 않는다.**
AST07 Update Drift의 본질은 규칙 발동이 아니라 역량 변화다.

### 9-2. SARIF는 형식이지 의미 통합이 아니다

SARIF로 모으는 것은 쉬운 부분이다. 어려운 부분은 **[N01]이 보여 준 불일치를 어떻게 다룰 것인가**다.
지목된 스킬의 81.9%를 단일 스캐너만 잡고, 셋 다 일치하는 건 0.69%다.
SARIF는 이 판정들을 같은 파일에 넣어 줄 뿐, **왜 갈렸는지를 사람에게 보여 주지 않는다.**

→ 우리 기여는 "SARIF 파서"가 아니라 **서로 다른 스캐너의 근거를 같은 대상 위에 나란히 놓고
사람이 판단하게 하는 계층**이다. 이건 도구가 아니라 검토 경험의 문제다.

### 9-3. 도구가 이미 있다는 건 오히려 좋은 소식이다

AgentShield(MIT)와 SkillSpector(Apache-2.0)가 **둘 다 재사용 가능한 라이선스**이고
**둘 다 SARIF를 뱉는다.** 즉 우리는 스캐너를 만들 필요가 없다.

제안서 15장이 이미 이렇게 썼다 — "기존 검사 엔진을 재사용하고, 팀은 공통 결과 모델·연결
그래프·검토 및 공유 흐름에 집중한다." **그 판단이 맞았고, 이제 실행 경로까지 확인됐다.**

15주 안에 스캐너를 새로 만드는 건 불가능하지만, 두 엔진을 붙이고 그 위에 capability diff와
근거 비교 계층을 올리는 건 가능하다.

### 9-4. 수정된 차별화 진술

> 기존 도구는 **"이 구성요소가 지금 위험한가"** 를 판정한다.
> 우리는 **"이 구성요소가 지난번 검토 이후 무엇을 할 수 있게 바뀌었고, 그 판단의 근거가
> 스캐너마다 왜 다른가"** 를 사람에게 보여 준다.
> 전자는 판정이고 후자는 검토다. 스캐너가 90% 우회되는 환경에서는 후자가 필요하다.

## 10. 확인하지 못한 것 (남은 것)

- Cisco IDE 스캐너의 "cross-tool attack chains" 실제 수준 — **직접 설치해야 판단 가능**
- Snyk agent-scan의 출력 형식과 라이선스 — 미확인
- skillfence·SkillDetonate의 성숙도 — 연구 단계인지 실사용 가능한지
- AgentShield·SkillSpector의 베이스라인이 **capability 수준 변화**를 정말 놓치는지 —
  **가설이다. 직접 실험해 확인해야 하며, 이것이 우리 첫 실험이 되어야 한다**
- 위 수치들은 **각 연구·업체의 발표값**이며 우리가 재현한 결과가 아니다
