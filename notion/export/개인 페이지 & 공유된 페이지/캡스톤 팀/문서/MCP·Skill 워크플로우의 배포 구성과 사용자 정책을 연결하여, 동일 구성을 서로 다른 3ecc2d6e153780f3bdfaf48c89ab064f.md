- ai설명
    
    프로젝트는 **“MCP·Skill 워크플로우의 권한 환경별 정책 위반 검증기”**로 잡자. 가칭은 **BoundaryCheck**로 하겠어.
    
    핵심 결과물은 다음과 같아.
    
    > **GitHub에서 가져온 스킬·MCP 구성을 특정 실행 환경에 연결했을 때, 보안 정책 위반이 실제로 발생하는지 검사하고, 업데이트·수정 전후의 차이를 재현 가능한 증거로 보여주는 도구.**
    > 
    
    처음부터 범용 보안 플랫폼을 만들지 않고, **실행 환경 하나·보안 정책 두 개·모의 MCP 서버 두 개**로 시작하는 설계야. 아래 일정은 **2~3명, 8주를 가정한 초안**이며, 마지막에 상세 설계서도 첨부했어.
    
    # 1. 프로젝트가 해결할 문제
    
    사용자가 공개된 스킬이나 MCP 서버를 가져왔을 때 알고 싶은 것은 단순히 “수상한 문자열이 있는가?”가 아니야.
    
    - *“내 환경에서 이 구성이 어떤 데이터를 읽고, 어디로 보내며, 무엇을 변경할 수 있는가?”**가 중요한 질문이지.
    
    예를 들어 다음 워크플로우를 검증한다고 하자.
    
    **사내 문서 조회 → 보고서 작성 스킬 → 보고서 공유 스킬 → 메시지 전송**
    
    같은 스킬과 MCP를 사용하더라도, 실행 계정이 내부 채널에만 전송할 수 있는 경우와 외부 채널에도 전송할 수 있는 경우는 구분해서 검사해야 해.
    
    우리 도구의 분석 단위는 파일 하나가 아니라 다음 묶음이야.
    
    > **구성 버전 + 워크플로우 + 사용자 정책 + 실제로 확인한 권한 조건 + 테스트 결과**
    > 
    
    여기서 **정책**은 “무엇이 허용돼야 하는가”, **권한 조건**은 “무엇이 실제로 허용되는가”를 뜻해. 둘을 혼동하지 않는 것이 설계의 출발점이야.
    
    # 2. 기존 도구와의 차별점을 어디에 둘 것인가?
    
    먼저 기존 기능을 그대로 신규성으로 주장하지 않아야 해.
    
    | 선행 도구·연구 | 이미 다루는 기능 | 프로젝트에서의 활용 |
    | --- | --- | --- |
    | **Cisco Skill Scanner·MCP Scanner** | 스킬 위험 패턴, 코드·데이터 흐름, MCP 구현 관련 검사 | 기본 검사 결과를 받아오거나 비교 대상으로 사용. [GitHub](https://github.com/cisco-ai-defense/skill-scanner) |
    | **Invariant Toxic Flow Analysis** | 여러 도구의 위험한 조합을 분석하며 정적·동적 정보를 함께 활용 | “도구 조합을 분석한다” 자체를 차별점으로 삼지 않음. [Invariant Labs](https://invariantlabs.ai/blog/toxic-flow-analysis) |
    | **Promptfoo MCP 테스트** | 직접 MCP 호출 및 에이전트를 통한 공격 테스트 | 동적 실행·CI 연동 자체는 재사용 가능한 기능으로 봄. [Promptfoo](https://www.promptfoo.dev/docs/red-team/mcp-security-testing/) |
    | **SCR-Bench** | 스킬 조합의 위험을 모의 부작용과 실행 경로로 평가 | 평가 방법을 참고하되, 실행 환경·권한 조건을 어떻게 확장했는지 검증. [arXiv](https://arxiv.org/abs/2606.15242) |
    
    특히 SCR-Bench도 이미 실제로 관측 가능한 모의 부작용을 평가해. 다만 논문은 **런타임 정책과 운영 환경의 복잡성을 단순화했다**고 한계를 명시하고 있어. 따라서 그 조건을 구체화해 확장하는 것은 검토할 만한 방향이야. [arXiv](https://arxiv.org/html/2606.15242v1)
    
    ### 우리가 구현하고 검증할 기여 후보
    
    **첫째, 권한 환경을 반영한 테스트 생성.**
    
    도구의 입력·출력 의미와 사용자 정책을 연결해, 같은 구성에서 권한 조건만 달리한 테스트를 만든다.
    
    **둘째, 위험 조건의 구분.**
    
    “위험한 행동을 시도했다”, “통제가 차단했다”, “실제 데이터 전송·변경이 일어났다”를 분리한다.
    
    **셋째, 업데이트까지 포함한 평가 자료.**
    
    원본·위험한 변경·무해한 변경을 동일한 환경 조건에서 비교할 수 있는 데이터셋과 실행 기록을 제공한다.
    
    이것은 **입증할 차별점 후보**야. “이 조합은 세계 최초”라고 먼저 주장하지 말고, 가장 가까운 도구와 같은 사례를 비교해서 추가 가치를 확인해야 해.
    
    # 3. 첫 버전의 범위를 확정하자
    
    ## 지원 대상
    
    | 항목 | 최소 구현 범위 |
    | --- | --- |
    | **스킬** | `SKILL.md`와 정적인 참조 문서. 임의 스크립트는 실행하지 않음 |
    | **실행 환경** | LangGraph로 구현한 참조 실행기 한 종류 |
    | **MCP 서버** | 문서 서버, 메시지 서버 두 종류 |
    | **도구** | `docs.read`, `docs.update`, `messages.send` |
    | **업무** | 문서 요약, 문서 기반 내부 보고서 공유 |
    | **검증 정책** | 기밀정보 외부 전송 금지, 읽기 전용 업무의 문서 변경 금지 |
    | **권한 환경** | 제한된 환경, 과도한 권한이 부여된 환경 |
    | **출력** | JSON 실행 증거, 사람이 읽는 보고서, 버전·환경 비교 결과 |
    
    LangGraph는 고정 로직과 모델 기반 단계를 함께 구성할 수 있는 실행 기반으로 사용하고, MCP 통신은 공식 Python SDK의 호환되는 버전을 고정해 구현하면 돼. **LangGraph 자체의 취약점을 찾는 프로젝트가 아니라, MCP·스킬을 시험할 참조 환경으로 사용하는 것**이야. [Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/overview)
    
    또한 **GitHub의 모든 워크플로우를 자동 변환하는 기능은 제외**해. 처음에는 검토한 스킬과 도구를 참조 실행기에 연결하고, 어떤 부분을 이식하거나 수정했는지 기록하는 방식으로 시작해.
    
    ### 정책은 두 개만 구현
    
    **P1. 기밀정보의 허용되지 않은 외부 전송 금지**
    
    합성 기밀 문서의 지정된 내용이 외부 수신 지점에 도착했는지 확인한다. 같은 서비스 안에서도 내부 채널과 외부 공유 채널을 구분하도록 설계해.
    
    **P2. 읽기 전용 업무의 문서 변경 금지**
    
    “조회·요약만 하라”는 업무에서 지정된 문서 자원이 변경됐는지 확인한다. 기술 로그나 감사 로그까지 모두 쓰기 금지로 처리하지는 않아.
    
    첫 버전에서 결제, 셸 실행, 브라우저 제어, 모든 OAuth 권한 분석까지 추가하지 않는 게 좋아.
    
    # 4. 공격자와 신뢰 경계를 명확히 정하자
    
    우리의 테스트에서 공격자는 사례에 따라 **스킬 파일, 참조 문서, MCP 도구 설명·응답, 테스트용 도구 구현 중 하나**를 변경할 수 있다고 가정해.
    
    반면 **사용자 정책, 실행 환경 설정, 관측 서버, 정답 데이터는 변경할 수 없어야 해.**
    
    중요한 것은 다음 구분이야.
    
    **스킬이 선언한 권한 ≠ 실행 환경이 실제 강제하는 권한**
    
    Agent Skills의 `allowed-tools`는 사전 승인된 도구를 나타내는 실험적 필드이고, 구현별 지원이 다를 수 있어. 따라서 이를 모든 호스트에서 강제되는 최대 권한 목록으로 취급하면 안 돼. [Agent Skills](https://agentskills.io/specification)
    
    MCP도 신뢰할 수 없는 서버의 도구 annotation을 신뢰하지 말라고 명시해. 즉, 도구가 “읽기 전용”이라고 설명했다는 사실만으로 실제 변경이 없다고 판정할 수는 없어. [Model Context Protocol](https://modelcontextprotocol.io/specification/latest/server/tools)
    
    그래서 입력 정보마다 출처를 구분하자.
    
    **제작자 선언 / 설정에서 확인 / 실행에서 관측 / 미확인**
    
    이 구분 자체는 복잡한 AI 기술이 아니지만, 검증 결과를 과장하지 않기 위한 중요한 데이터 모델이야.
    
    # 5. 시스템은 여섯 모듈로 나누면 돼
    
    전체 흐름은 다음과 같아.
    
    **구성 수집 → 정책·도구 계약 분석 → 테스트 생성 → 환경별 실행 → 독립 관측 → 비교 보고서**
    
    | 모듈 | 직접 구현할 내용 |
    | --- | --- |
    | **입력 수집기** | 고정 커밋, 스킬 파일, 도구 목록, 환경 설정을 읽고 해시를 기록 |
    | **계약·경로 분석기** | 어떤 도구가 어떤 데이터를 읽거나 변경하는지 연결하고 위험 경로 후보 생성 |
    | **테스트 생성기** | 정책별 템플릿을 실제 도구 인자와 환경 조건에 연결 |
    | **실행기** | 같은 사례를 제한·과권한 환경에서 실행 |
    | **독립 판정기** | 메시지 수신 기록과 문서 변경 기록으로 실제 부작용 확인 |
    | **비교·보고 모듈** | 환경 차이, 버전 차이, 수정 전후 결과와 미확인 항목 표시 |
    
    ## 가장 중요한 구현: ‘도구 계약’
    
    첫 버전에서는 도구 설명을 LLM으로 읽어서 모든 의미를 자동 추론하려 하지 않는 게 좋아.
    
    대신 검토자가 다음 정보를 지정하는 **도구 계약**을 만들자.
    
    | 도구 | 검토자가 지정할 의미 |
    | --- | --- |
    | `docs.read` | 어떤 자원을 읽는지, 결과의 어느 필드가 문서 내용인지 |
    | `docs.update` | 어떤 자원을 변경하는지, 문서 ID와 변경 내용이 어느 인자인지 |
    | `messages.send` | 수신 대상과 전송 내용이 어느 인자인지 |
    
    도구 이름만으로 의미를 확정하지 않고, **서버 식별자와 도구 이름을 함께 사용**해야 해.
    
    이 계약과 정책을 결합하면 다음과 같은 테스트 후보를 만들 수 있어.
    
    > “기밀 문서를 읽을 수 있고, 그 내용을 받는 전송 도구도 연결돼 있으므로, 수신 대상 제한이 실제로 작동하는지 검사한다.”
    > 
    
    이 단계는 **가능한 위험 경로를 찾는 것**이지, 공격 성공을 확인하는 단계는 아니야.
    
    ## 정책 파일과 권한 설정도 분리
    
    아래는 우리가 정의할 정책 파일의 예시야. 공식 MCP 설정 형식은 아니야.
    
    ```
    schema_version: "0.1"
    
    rules:
      - id: P1
        kind: deny_information_flow
        source_label: confidential
        destination_class: external
    
      - id: P2
        kind: deny_resource_mutation
        when:
          task_mode: read_only
        resource_class: business_documents
    
    unknown_handling: require_review
    ```
    
    이 파일은 **기대하는 보안 조건**이야. 실제 권한 제한은 모의 서버나 백엔드의 별도 접근 통제에서 구현하고, 우리 도구는 그것이 작동하는지 관측해야 해.
    
    **정책 파일에 금지라고 적혀 있다는 이유로 “차단됨”이라고 출력하면 검증이 아니야.**
    
    # 6. 실행은 ‘재생 테스트’와 ‘실제 모델 테스트’를 나누자
    
    ## A. 결정적 테스트 모드
    
    모델 대신 정해진 도구 호출 계획이나 기록된 응답을 사용해.
    
    이 단계에서는 **프로토콜 연결, 권한 제한, 부작용 관측, 보고서 판정이 맞게 작동하는지**를 확인해. 초기 개발과 회귀 테스트에 사용하면 돼.
    
    다만 결과는 다음 의미로 제한해야 해.
    
    > “이 행동 순서가 주어졌을 때, 해당 환경에서 정책 위반이 발생한다.”
    > 
    
    이것을 **“실제 LLM이 공격에 넘어갔다”**고 집계해서는 안 돼.
    
    ## B. 실제 LLM 테스트 모드
    
    스킬과 테스트 입력을 실제 모델에 제공하고, 모델이 선택한 도구 호출을 기록해.
    
    이 경우에만 해당 모델의 행동 결과로 집계한다. 모델 버전·설정·반복 횟수를 기록하고, 실행마다 문서·수신함·메모리를 초기화해야 해.
    
    ### 최종 판정은 모델에게 맡기지 말자
    
    “전송했습니다”라는 MCP 응답이나 모델의 설명만으로 실제 전송을 확인하지 않아.
    
    **P1은 별도 수신 서버가 받은 데이터를 확인하고, P2는 문서 저장소의 변경 이벤트와 상태를 확인**하도록 만들어.
    
    이때 변경 후 롤백된 작업도 놓치지 않도록, 전후 해시만이 아니라 쓰기 이벤트도 기록하는 게 좋아.
    
    ### 결과는 이렇게 구분
    
    | 판정 | 의미 |
    | --- | --- |
    | **위반 재현** | 독립 관측 지점에서 금지된 전송·변경을 확인 |
    | **통제로 차단** | 위반 시도와 실제 차단을 확인했고 해당 부작용은 발생하지 않음 |
    | **위반 미관측** | 정해진 테스트에서는 위반이 관측되지 않음 |
    | **검증 불충분** | 권한 정보·실행·관측이 부족해서 결론을 내릴 수 없음 |
    
    정상 업무 성공 여부는 이 판정과 **별도 항목**으로 기록해. 모두 차단해서 보안 테스트만 통과하는 구성을 좋게 평가하지 않기 위해서야.
    
    또 첫 버전의 정보유출 판정은 **합성 마커·지정된 구조화 필드·명확한 원문 전달**로 제한하자. 마커가 발견되지 않았다는 이유로 요약·번역·인코딩을 통한 의미적 유출까지 없다고 주장하지는 않아야 해.
    
    # 7. 시연은 ‘업데이트 → 문제 확인 → 수정 → 재검증’으로 구성하자
    
    ## 대표 시연: 보고서 공유 스킬의 변경
    
    다음은 구현할 시연 시나리오야. 아직 측정한 결과는 아니야.
    
    | 단계 | 구성 | 확인할 내용 |
    | --- | --- | --- |
    | **원본** | 내부 공유만 하는 스킬 | 정상 업무가 성공하고 외부 전송이 없는가? |
    | **위험 변경** | 외부 목적지를 선택하도록 유도하는 테스트 변경본 | 과권한 환경에서 실제 외부 수신이 발생하는가? |
    | **같은 변경본, 제한 환경** | 목적지 제한을 적용 | 같은 시도가 차단되는가? |
    | **수정 후** | 불필요한 경로 제거 또는 권한 축소 | 위반을 막으면서 내부 공유는 유지되는가? |
    
    보고서는 다음 내용을 한 화면에서 보여주면 돼.
    
    > **정책 P1 위반 재현 — 테스트 환경에 한정**
    > 
    > 
    > 변경된 공유 스킬이 승인되지 않은 수신 대상을 선택했습니다.
    > 
    > 과권한 환경에서는 합성 기밀 데이터의 수신이 확인됐습니다.
    > 
    > 제한 환경에서는 해당 전송이 차단됐습니다.
    > 
    > 정상적인 내부 공유는 두 환경에서 별도로 검사했습니다.
    > 
    > 관련 증거: 구성 해시, 변경 파일, 도구 호출 ID, 수신 이벤트 ID.
    > 
    
    이 시연이 완성되면 **스킬 변경이라는 공급망 문제, MCP의 실행 능력, 워크플로우의 조합, 환경의 접근 통제**가 하나의 흐름으로 드러나.
    
    두 번째 시연은 **읽기 전용이라고 설명한 테스트용 MCP 구현이 실제로 문서를 변경하는 경우**로 잡으면 돼. 도구 설명을 믿지 않고 저장소 기록으로 검증한다는 점을 보여줄 수 있어.
    
    # 8. 평가 데이터셋과 실험을 미리 정하자
    
    ## 초기 데이터셋 규모
    
    처음에는 다음 구성을 목표로 하자.
    
    **기본 시나리오 12종 × 원본·위험 변경·무해한 변경 3종 × 권한 환경 2종 = 72개 실행 구성**
    
    여기에 권한이나 관측 정보가 없는 사례를 별도로 추가해 **미확인 처리**도 검사해.
    
    72개 구성의 결정적 테스트를 먼저 완성하고, 이후 모델 2종·각 3회로 전부 실행하면 **432회**가 돼. 이 숫자는 실험 계획이며, 독립적인 취약점 432개라는 뜻이 아니야.
    
    공개 GitHub 샘플은 다음을 분리해서 관리해야 해.
    
    **원본 그대로 사용한 자료 / 참조 실행기로 이식한 자료 / 인위적으로 만든 위험 변경**
    
    같은 원본에서 나온 포크와 변형은 한 그룹으로 묶어서 개발용·평가용 자료를 분리하자.
    
    ## 실험 질문
    
    **RQ1. 환경 정보를 포함하면 판단이 실제로 개선되는가?**
    
    우리 분석기에서 환경 정보를 제거한 버전과 비교해. 같은 스킬에서도 제한 환경과 과권한 환경의 차이를 올바르게 설명하는지 확인한다.
    
    **RQ2. 경로·계약 기반 테스트 생성이 도움이 되는가?**
    
    고정 테스트만 실행하는 방식과 비교해. 모델과 도구 호출 예산을 맞춘 상태에서 더 많은 위반을 확인하는지, 불필요한 실행을 줄이는지 측정한다.
    
    **RQ3. 수정 후 보안과 정상 업무를 함께 확인하는가?**
    
    정책 위반이 줄었는지뿐 아니라 정상 업무 성공률이 유지되는지 확인한다.
    
    ## 비교 대상과 지표
    
    기존 스캐너뿐 아니라 **MCP 동적 테스트를 지원하는 방법**도 비교에 포함해야 해. Promptfoo는 직접 MCP 호출과 에이전트를 통한 테스트를 모두 설명하고 있으므로, 비교 가능한 대상으로 검토할 수 있어. [Promptfoo](https://www.promptfoo.dev/docs/red-team/mcp-security-testing/)
    
    핵심 지표는 다음과 같아.
    
    | 지표 | 확인할 내용 |
    | --- | --- |
    | **정밀도·재현율** | 정의한 정책 위반을 얼마나 정확히 판정하는가 |
    | **정상 변경 오탐률** | 무해한 변경에도 불필요하게 위반 판정을 하는가 |
    | **환경별 구분 성능** | 같은 구성의 권한 조건 차이를 설명하는가 |
    | **시도·차단·실제 발생** | 경고와 실제 부작용을 구분하는가 |
    | **정상 업무 성공률** | 보안 통제가 업무 전체를 망가뜨리지는 않는가 |
    | **비용·미확인 범위** | 실행 비용, 수동 계약 작성량, 분석 불가 항목이 얼마나 되는가 |
    
    **기존 도구의 ‘수상한 부품 경고’를 우리 도구의 ‘실제 정책 위반’과 그대로 비교하면 불공정해.** 공통으로 평가할 수 있는 출력만 비교하고, 미지원·미실행은 미탐과 구분해야 해.
    
    정답도 우리 분석기가 만든 경고를 그대로 사용하지 말고, **사람이 검토한 조건과 독립 수신·변경 기록**으로 만들어야 해.
    
    # 9. 구현 순서와 최종 산출물
    
    ## 8주 수행 계획
    
    | 단계 | 구현·검증 작업 | 완료 기준 |
    | --- | --- | --- |
    | **1주** | 위협 모델·정책·대표 사례·비교 도구 확정 | 기존 도구가 이미 해결하는 부분과 추가 구현할 부분 구분 |
    | **2주** | 모의 MCP 두 개, 수신·변경 기록, 결정적 실행기 | 정상·위반·차단을 구분 |
    | **3주** | 스킬·도구 계약·환경 입력과 구성 해시 | 선언·설정·관측·미확인을 분리 |
    | **4주** | 경로 후보와 테스트 생성 | 지원하는 사례를 자동 생성·실행 |
    | **5주** | 업데이트 비교와 보고서 | 변경 원인과 실행 증거를 연결 |
    | **6주** | 평가 자료와 정답 검토 | 72개 구성 및 미확인 사례 준비 |
    | **7주** | 모델 실험·기존 방법 비교·기능 제거 실험 | 원시 결과·비용·실패 기록 확보 |
    | **8주** | 실패 분석·문서·최종 시연 | 다른 팀원이 문서만 보고 재실행 |
    
    역할은 **분석·정책 / 실행·격리 / 평가·보고**로 나누면 돼. 일정이 줄어들면 모델 수와 UI를 줄이고, **독립 관측과 평가 데이터는 유지**하는 것을 추천해.
    
    ## 최종 제출물
    
    **검증기 소스**, **모의 MCP·참조 실행 환경**, **정답이 있는 평가 데이터셋**, **비교 실험 보고서**, **시연 자료**를 제출하자.
    
    웹 대시보드는 필수가 아니야. 처음에는 CLI와 정적 HTML 보고서만으로 충분해.
    
    그리고 **새 CVE 발견이나 높은 탐지율을 완료 조건으로 걸지 않는 게 좋아.** 완료 조건은 다음처럼 잡아야 해.
    
    > **지원하는 두 정책에 대해 환경별 차이를 근거와 함께 재현하고, 다른 사람이 다시 실행할 수 있으며, 기존 방법 대비 추가 가치와 한계를 수치로 공개한다.**
    > 
    
    # 10. 검증기 자체의 보안도 설계에 포함해야 해
    
    공개 저장소를 검사한다고 해서 그 저장소의 코드나 MCP 명령을 바로 실행하면 안 돼. Snyk도 MCP 설정 검사 과정에서 로컬 명령 실행이나 외부 접속이 발생할 수 있다고 명시하고 있어. [GitHub](https://github.com/snyk/agent-scan)
    
    첫 버전은 **정적 수집 단계와 동적 실행 단계를 분리**하자. 동적 실행은 검토한 모의 서버만 대상으로 하고, 실제 회사 토큰·문서·호스트 홈 폴더·Docker 소켓을 제공하지 않아야 해.
    
    관측 기록은 검사 대상이 바꿀 수 없도록 분리하고, 모델 API가 필요하면 별도 경로로만 연결해. **모델 제공자에게 전달되는 데이터 역시 별도의 전송 경계**이므로, 합성 데이터만 사용하고 이를 전체 운영 데이터 보호 검증으로 확대하지 않아야 해.

    ## 최종 프로젝트 소개문
    
    > **BoundaryCheck는 MCP·Skill 워크플로우의 배포 구성과 사용자 정책을 연결하여, 동일 구성을 서로 다른 권한 환경에서 검증하는 보안 테스트 도구다. 선언이나 모델 설명만으로 판정하지 않고 실제 모의 수신·자원 변경을 확인하며, 업데이트와 수정 전후의 보안 결과 및 정상 업무 유지 여부를 함께 평가한다.**
    > 
    
    **이렇게 잡으면 ‘기존 스캐너를 묶은 대시보드’가 아니라, 환경 조건을 반영한 테스트 생성·독립 관측·차등 평가를 구현하는 프로젝트가 돼.** 학술적 신규성은 비교 실험으로 확인하되, 구현과 데이터셋 자체로도 제출 가능한 결과물이 남는 구조야.
