03 · 빈 곳

우리가 들어갈 수 있는 세 자리

세 자리 모두 OWASP가 이름을 붙여 둔 항목이다. 우리가 임의로 좁힌 범위가 아니라는 뜻이다.

AST07Update Drift

승인한 다음에 바뀌는 것을 아무도 안 본다

MCP 서버는 해시 피닝·서명으로 이미 막혀 있다. 그런데 스킬·규칙 파일·플러그인에는 같은 장치가 없다. 기존 규칙은 rug pull을 가능하게 하는 셋업 패턴(원격 로딩, base64 실행, post-install 훅)을 잡을 뿐이고, 실제 드리프트 탐지는 시간에 따른 비교가 필요하다고 규칙 문서가 직접 적고 있다.

MCP 서버-버전 레코드 28,959건 대 서버 9,652건 — 평균 세 번 넘게 갱신됐다. 갱신마다 재검토 지점이 생긴다. [N08] [N10] [N14]
AST08Poor Scanning

스캐너끼리 판정이 안 맞는데 합칠 곳이 없다

공개 스킬 67,453건을 세 스캐너 계열로 돌린 결과, 두 스캐너가 겹치는 비율은 합집합 양성의 10.4% 이하였고 셋 다 지목한 건 0.69%에 그쳤다. 지목된 스킬의 81.9%는 한 스캐너만 잡았다. SkillSpector는 의미적 위험을, VirusTotal은 번들 코드 멀웨어를 본다 — 보는 대상 자체가 다르다.

논문 결론: “에이전트 스킬 보안은 단일 스캐너의 허용/차단 결정이 아니라 계층적 거버넌스를 요구한다.” [N01]
경로조합 분석

구성요소 하나씩은 보는데, 이어지는 경로를 안 본다

단일 구성요소를 판정하는 도구는 많다. 그런데 규칙 → 스킬 → 도구 → 접근 자원으로 이어지는 경로를 원본 근거와 함께 보여 주는 도구는 확인하지 못했다. 실제 사고는 한 구성요소 안에서 끝나지 않고 읽기와 전송이 이어지는 조합에서 생긴다.

Snyk 보고: 확인된 악성 스킬의 91%가 전통적 멀웨어 패턴과 프롬프트 인젝션을 결합해 양쪽 방어를 동시에 무력화했다. 한 종류만 보는 검사로는 잡히지 않는다. [N16]
04 · 우리 위치

그래서 무엇을 만드는가

정적 검사로 악성을 판정하겠다는 목표는 이미 학계가 실패를 입증했다 — SkillCloak이 90% 넘게 통과한다. 그래서 목표를 판정이 아니라 검토 근거 제시로 둔다. 제안서가 처음부터 “안전 인증으로 표시하지 않는다”고 쓴 것은 결과적으로 옳은 설계였다.

만든다

  • 버전 간 보안상 변경 비교 — 스킬·규칙 파일을 대상으로. 새 파일 접근, 새 외부 연결, 새 실행 요청을 단순 해시 변경과 구분한다
  • 여러 스캐너 결과의 공통 형식 통합 — 어느 스캐너가 무엇을 근거로 지목했는지 나란히 놓는다
  • 관계 그래프 — 확인된 연결은 실선, 추정은 점선. 노드를 누르면 원본 파일과 행으로 간다
  • 검토 기록과 팀 공유 — 누가 어느 버전을 봤는지 남기고, 바뀐 버전에는 재검사를 요구한다

만들지 않는다

  • MCP 변경 탐지 — 이미 MCP-Scan·mcpdef_pin·ETDI가 있다. 여기서 경쟁하지 않는다
  • 런타임 실행·샌드박스 관찰 — skillfence·SkillDetonate의 영역이고, 한 학기에 안전하게 만들 수 없다
  • 자체 탐지 엔진으로 기존 스캐너 이기기 — NVIDIA·Cisco·Snyk와 정면으로 붙지 않는다
  • 전 언어·바이너리·동적 분석 — Python·JS/TS의 제한된 패턴부터 시작한다

평가 데이터를 처음부터 만들지 않아도 된다

제안서는 평가 자료 120건을 직접 구성한다고 했다. 그런데 OpenClaw/clawhub-security-signals 데이터셋에 공개 스킬 67,453건이 세 스캐너의 판정과 근거가 붙은 채로 공개돼 있다. 우리 “스캐너 불일치” 가설을 검증할 재료가 그대로 들어 있다.

주의 — 논문이 직접 밝힌 한계: 라벨은 레지스트리의 자동 판정이지 사람이 라벨링한 정답이 아니다 (silver-standard). 라이선스와 재배포 조건은 사용 전에 반드시 확인해야 한다. 탐색·개발용으로 쓰고, 최종 평가용 소규모 세트는 제안서대로 사람이 라벨링하는 2단 구성이 현실적이다. [N01]
05 · 일정

15주에 어떻게 얹는가

9주차 중간발표 시점에 한 바퀴가 도는 최소 기능을 먼저 완성하고 나머지를 그 위에 올린다.

3–4주
범위 확정위협 모델·입력 형식·플러그인 1종 고정 · 지도교수 승인
5–6주
설계와 공통 결과 모델기존 스캐너 3종의 출력 형식 확인 후 공통 스키마 설계 · 위협 모델링
7–8주
규칙·스킬 검사 구현파일 정규화, 출처·해시 기록, 근거 위치가 포함된 보고서
9주
중간발표 — 여기까지 반드시 돈다검사 보고서 + 근거 추적 시연
10–11주
버전 간 변경 비교AST07. 새 접근·연결·실행 요청을 단순 해시 변경과 구분
12주
관계 그래프 + 플랫폼 자체 보안 점검Zip Slip · 업로드 제한 · 출력 이스케이프 · 스캐너 권한 제한
13주
검토 기록·팀 공유, 배포등록 → 검사 → 검토 → 공유 전체 시연
14–15주
평가 실험과 최종 발표스캐너 불일치 가설 검증 · 사용성 평가 · 한계 보고
06 · 미결

다음 회의에서 결정할 것

결정과 담당은 노션 액션 아이템에 기록한다. 여기서는 무엇을 물어야 하는지만 적는다.

세 빈 곳 중 무엇을 중심에 둘 것인가

셋 다 하면 또 범위가 넓어진다. AST07(변경 탐지)을 중심에 두고 AST08(결과 통합)을 보조로 두는 안이 일정상 가장 현실적이다.

ClawHub 데이터셋을 쓸 수 있는가

라이선스와 재배포 조건 확인이 먼저다. 못 쓰면 평가 자료를 직접 만들어야 하고 그만큼 일정이 밀린다.

기존 스캐너를 실제로 붙일 것인가

SkillSpector(Apache)·Snyk agent-scan·Cisco의 입출력 형식을 확인해야 공통 결과 모델을 설계할 수 있다. 라이선스는 THIRD_PARTY.md에 먼저 기록한다.

규칙 파일 검사 도구가 정말 없는가

매트릭스에서 유일하게 “미확인”으로 남은 칸이다. 없다면 우리 기여가 명확해지고, 있다면 범위를 조정해야 한다.
