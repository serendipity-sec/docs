# 중간발표 대비 MVP 파이프라인(A→B→C) 구현 방향 회의

- **일시**: 2026-10-17
- **참석자**: 준서, 용준, 민우, 유상

## 안건별 논의 내용

### 1. A(그래프화) 진행 상황 공유

A 단계에서 두 가지 분석을 구현함: ① 변경점을 거슬러 올라가 시작 지점을 찾는 기능, ② 해당 변경이 어느 출력까지 영향을 줄 수 있는지(도달 범위) 계산하는 기능. 현재 그래프는 노드 간 실행 흐름 화살표 수준이며, 그 안에서 값이 어디서 와서 어디로 가는지 계산할 수 있게 만듦. 결과는 `analysis.json`으로 저장되어 B로 전달됨.

### 2. 전체 파이프라인 현황과 중간발표 범위

현재는 데모(목업) 수준으로, 변경점을 넣어 한 번 돌려보는 실험만 성공한 상태. 원래 흐름은 A가 워크플로우를 그래프화 → B가 분석 결과와 입력 담당의 핸드오프 내용을 받아 벡터 DB에서 유사 취약점을 찾아 실행 계획 생성 → C가 계획대로 도구를 돌려 취약점 실제 발생 여부를 점검. 다만 알려진 취약점 기준으로 취약 여부를 판단하는 것이 생각보다 어려워, 중간발표에서는 **한 사이클이 제대로 돌아가는 것**을 보여주는 데 집중하자는 의견이 모임. 핸드오프 내용은 아직 이해가 부족하다는 언급이 있었음.

### 3. 테스트용 워크플로우와 취약점 선정

전체 취약점 자료를 다 임베딩하기엔 시간이 부족하므로, 특정 취약점 하나만 발생하는 n8n 워크플로우를 정하고 그 분야 자료만 우선 임베딩하기로 함. 선택지는 ① 실제로 취약점이 보고된 워크플로우(전·후 버전)를 찾아 사용, ② 정상 워크플로우에 일부러 취약한 변경을 가함, ③ 워크플로우부터 직접 제작. ①이 최선이고 안 되면 ②. 금융 관련 워크플로우나 가벼운 워크플로우에 몇 줄 추가하는 방안도 언급됨. 환경은 고정하고, 변동 입력은 업데이트된 n8n 워크플로우로 두는 방향이 제안됨. 취약점은 정책(제한)과 결합해 터지므로 정책 설정도 필요하다는 의견이 나왔으나 범위는 결론 나지 않음.

### 4. 취약점 데이터 소스와 임베딩

NIST의 CVE 데이터베이스(NVD) API를 활용할 수 있음을 확인. CVE 데이터는 이미 구조화되어 있어 별도 구조 설계나 크롤링 없이 주제 관련 데이터만 가져와 임베딩하면 됨. 구조 설계는 나중에 실험 결과를 다시 임베딩해 재사용할 경우에만 필요. 상용 API로 임베딩하면 비용이 들어 로컬 임베딩 모델을 쓰기로 함. 시험 기간 노트북(RAM 8GB) 사양 우려가 있었으나 작은 모델로 충분할 것이라는 의견.

### 5. 공용 DB 서버와 LLM 연결

DB를 도커 이미지로 배포해 각자 띄우는 방식은 임베딩 데이터가 추가될 때마다 익스포트·마이그레이션이 필요하고 누락 위험이 있어, 서버 하나(AWS든 Supabase 같은 서비스든)를 띄워 공유하기로 함. B의 계획 생성용 LLM 연결은 개인 API 크레딧(약 4.87달러)으로 우선 테스트하고, 커넥터를 인터페이스화할 예정. DB 스키마 관련 SQL 파일과 테이블·속성 설명 문서는 이미 이슈/PR로 올라가 있음.

### 6. C(검증) 단계 구현 방식

1주일 안에 실행 환경을 만들 수 있을지가 관건. 공개된 n8n 검사 도구를 그대로 가져다 써도 되며, 단 우리가 발생시킬 취약점을 그 도구가 잡을 수 있는지는 확인 필요. 당장은 정적 검사 위주, 동적 샌드박스는 시간이 남으면 시도. 목표는 기존 도구 적용 → 결과가 DB에 저장되는 것까지이며, 여유가 있으면 로컬 서버로 결과 페이지를 띄움. 테스트에 쓴 취약 워크플로우와 실행 결과는 데이터셋으로 따로 정리해두자는 의견.

### 7. 결과 페이지 프레임워크

FastAPI가 템플릿 엔진을 지원해 헤더·푸터·사이드바 등 공통 레이아웃을 재사용하고 값만 DB에서 불러오는 구조가 가능하다고 확인. Next.js 대신 FastAPI를 쓰기로 함. 페이지는 기준 버전으로부터의 변경 이력을 git 브랜치 히스토리처럼 보여주는 형태로 구상.

### 8. 협업 도구 운영

회의 기록과 질문은 GitHub 이슈나 슬랙에 남기고, 이슈를 올리면 슬랙/카톡에도 한 번 알리기로 함. 노션은 사람이 직접 읽어야 하는 문서를 모아 보는 용도로만 사용. PR을 올리면 이슈 알림도 같이 오는 슬랙 연동 문제는 담당자가 확인 예정.

## 결정사항

- 중간발표는 **취약점 하나만 발생하는 워크플로우로 A→B→C 한 사이클이 정상 동작**하는 MVP를 보여주는 것을 목표로 한다.
- 실제 취약 사례 워크플로우(전·후 버전)를 우선 찾고, 없으면 정상 워크플로우에 취약한 변경을 가해 사용한다.
- 임베딩 데이터는 NIST NVD API에서 주제 관련 CVE만 가져와 별도 구조화 없이 임베딩한다.
- 임베딩은 비용 문제로 로컬 임베딩 모델을 사용한다.
- DB는 공용 서버 하나를 띄워 팀 전체가 같은 데이터를 사용한다 (도커 이미지 개별 배포 방식은 채택하지 않음).
- C 단계는 기존 오픈소스 n8n 검사 도구를 그대로 사용해도 되며(해당 취약점 탐지 가능 여부 확인 전제), 정적 검사 우선·동적 샌드박스는 여유 시 진행한다.
- 결과 페이지는 FastAPI(템플릿 엔진)로 구현한다.
- 회의·질문 기록은 GitHub 이슈 또는 슬랙에 남기고, 노션은 열람용 문서 보관에만 쓴다.
