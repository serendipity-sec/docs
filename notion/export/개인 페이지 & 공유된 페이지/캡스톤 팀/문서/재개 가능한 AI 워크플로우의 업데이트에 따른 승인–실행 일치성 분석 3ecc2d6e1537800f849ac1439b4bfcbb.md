    # 2. 가장 중요한 검증 사례: 각 버전은 정상인데 버전 전환은 위험하다
    
    이 프로젝트의 대표 사례는 단순히 “승인 코드를 삭제했다”가 아니어야 해.
    
    **이전 버전과 새 버전을 각각 실행하면 문제가 없지만, 이전 버전에서 중단된 실행을 새 버전에서 재개하면 문제가 생기는 상황**을 중심에 두는 게 좋아.
    
    LangGraph 공식 문서는 체크포인트에서 재개할 때 중단된 노드의 처음부터 다시 실행될 수 있고, 코드 변경이 기존 실행과 어떻게 상호작용하는지 고려해야 한다고 설명한다. 최신 그래프 정의가 기존 체크포인트에서 재개되는 실행에도 적용될 수 있다는 점도 명시돼 있어. [Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/interrupts)
    
    ## 대표 시나리오
    
    설명을 위한 가상 워크플로우야.
    
    고객 문서를 특정 담당자에게 전송하는 에이전트가 있고, 전송 직전에 사용자 승인을 받는다고 하자. 업데이트에서 담당자 결정 로직이 변경돼.
    
    | 실행 방식 | 사용자에게 제시한 작업 | 실제 실행 | 판정 |
    | --- | --- | --- | --- |
    | 이전 버전에서 시작하고 종료 | 담당자 A에게 전송 | A에게 전송 | 일치 |
    | 새 버전에서 시작하고 종료 | 담당자 B에게 전송 | B에게 전송 | 일치 |
    | 이전 버전에서 승인 요청 후, 새 버전에서 재개 | A에게 전송 | B에게 전송 | 불일치 가능 |
    
    핵심은 **새 버전이 B에게 전송한다는 사실 자체가 문제가 아니라는 것**이야. 사용자가 B를 승인했다면 정상일 수 있어.
    
    문제는 **A에 대한 승인이 B의 실행에 사용되는 것**이야.
    
    이 실패 유형 자체는 Loopjacking 선행 연구와 겹친다. 해당 연구도 사람이 검토한 작업과 실제 실행되는 작업 사이의 결합 실패를 다루므로, 프로젝트의 새로움을 “새로운 공격 발견”이라고 주장하면 안 돼. [arXiv](https://arxiv.org/html/2609.21081v1)
    
    **ApprovalDiff의 기여 후보는 이런 실패를 코드 변경과 재개 동작에서 자동으로 찾아내고, 실제 테스트로 연결하는 것**이야.

    # 3. 연구 기여는 세 가지로 제한한다
    
    ## 기여 1. 승인 대상을 추적하는 중간 표현
    
    워크플로우에 승인 노드가 있는지만 보는 것이 아니라 다음 관계를 명시적으로 표현한다.
    
    **무엇을 보여줬는가 → 무엇을 승인했는가 → 어떤 값이 바뀌었는가 → 무엇을 실행했는가**
    
    여기에 코드 버전과 중단·재개 경계를 붙여서, 같은 변수라도 승인 전과 재개 후의 값을 구분한다.
    
    ## 기여 2. 재개와 버전 전환을 고려한 관계 분석
    
    두 버전에서 발생한 경고 목록을 빼는 방식이 아니라, **같은 작업·같은 승인·같은 외부 조건에서 두 실행이 어떻게 달라지는지**를 비교한다.
    
    특히 다음 두 가지를 별도로 지원한다.
    
    **독립 실행 비교:** 이전 버전과 새 버전을 각각 처음부터 실행한다.
    
    **버전 전환 비교:** 이전 버전에서 승인 요청까지 실행한 뒤, 동일한 체크포인트를 이전 버전과 새 버전에서 각각 재개한다.
    
    ## 기여 3. 정적 분석 후보를 실행 증거로 연결
    
    경고마다 지원 가능한 경우 다음 자료를 생성한다.
    
    **불일치를 만드는 입력, 승인 응답, 외부 상태 변화, 이전·이후 도구 호출 기록.**
    
    단순한 코드 위치 보고가 아니라 **“이 조건에서 실제로 달라진다”는 재현 자료**를 제공하는 거야.
    
    ### 선행 연구와의 경계
    
    | 선행 연구·프로젝트 | 활용하거나 비교할 부분 | ApprovalDiff가 추가로 검증할 부분 |
    | --- | --- | --- |
    | **Agent Audit** | 에이전트 코드 분석과 신규 경고 비교 | 경고 목록이 아니라 승인 대상 값과 실행 값의 관계 비교. [GitHub](https://github.com/HeadyZhang/agent-audit) |
    | **Agentproof** | 그래프 구조와 승인 경로 검증 | 그래프 구조가 같아도 내부 값이 바뀌는 경우, 재개·업데이트의 영향. [arXiv](https://arxiv.org/html/2603.20356v1) |
    | **Loopjacking** | 승인–실행 불일치의 위협 모델과 사례 | 해당 결함을 찾는 변경 중심 분석과 재현 자동화. [arXiv](https://arxiv.org/html/2609.21081v1) |
    | **CTRLRun LangGraph 연동** | 승인 인자와 실행 행동을 결합하는 방어 구현 | 기존 워크플로우의 결합 실패를 찾아내고 수정 효과를 검증. [파이썬 패키지 색인](https://pypi.org/project/ctrlrun-langgraph/) |
    | **OWASP Agent Security Regression Harness** | 시나리오 실행과 실행 기록 평가 | 코드 변경에서 관련 시나리오를 도출하는 분석·생성 로직. [GitHub](https://github.com/OWASP/Agent-Security-Regression-Harness) |
    
    또한 **두 프로그램의 관계를 검증하는 방법 자체도 새로운 것은 아니야.** SymDiff 같은 기존 연구가 있으므로, 연구 기여는 LangGraph의 승인·체크포인트·재개 동작에 대한 모델링과 자동화에서 찾아야 해. [Microsoft](https://www.microsoft.com/en-us/research/project/symdiff-differential-program-verifier/?utm_source=chatgpt.com)
    
    **이 조합의 학술적 신규성은 구현과 비교 실험으로 확인해야 하며, 지금 단계에서 “최초”라고 확정하지 않는다.**

    # 4. 위협 모델과 검증할 보안 속성
    
    ## 4.1 보호할 대상
    
    프로젝트가 보호하려는 것은 비밀번호나 모델 자체가 아니라 **사용자의 승인이 부여하는 권한**이야.
    
    예를 들어 “이 문서를 담당자 A에게 보내도 좋다”는 승인이 다음 작업으로 확장되지 않아야 한다.
    
    **다른 수신자에게 보내기, 다른 문서를 보내기, 다른 계정으로 실행하기, 추가 작업까지 수행하기.**
    
    ## 4.2 두 가지 상황을 구분한다
    
    **업데이트에 의한 보안 회귀**
    
    정상적인 개발 과정에서 리팩터링·도구 변경·설정 변경 때문에 기존 승인 보장이 깨지는 경우다. 악의적인 공격자가 없어도 발생할 수 있는 결함으로 다룬다.
    
    **공급망에서 유입된 변경의 악용**
    
    공유 워크플로우, 로컬 도구 패키지, 제공된 하위 코드가 변경되고, 그 변경이 승인을 잘못 소비하게 만드는 경우다.
    
    단, 공격자에게 분석 정책이나 검사기를 바꿀 권한까지 주면 검증 의미가 사라져. 따라서 **분석기, 외부 정책 파일, 테스트 실행기, 승인 기록 수집기는 신뢰하는 구성요소**로 둔다.
    
    외부 상태를 변경하는 공격 시나리오는 **그 공격자가 해당 상태를 변경할 수 있다는 근거가 있을 때만** 성립하는 것으로 판정한다. 임의로 체크포인트를 수정해 놓고 실제 취약점이라고 부르지 않는다.
    
    ## 4.3 승인 계약
    
    보호 대상 작업을 다음과 같이 표현하도록 설계한다.
    
    ```
    Operation
      tool: 실행할 도구
      arguments: 보안상 중요한 인자
      resource: 대상 문서·레코드·수신처
      principal: 실행 계정 또는 주체
      run_scope: 어느 실행의 작업인가
      intent_id: 어느 논리적 작업에 대한 승인인가
    ```
    
    승인은 이 작업에 대한 **허용 조건**을 가진다.
    
    검증할 핵심 속성은 다음과 같아.
    
    \[
    \text{보호 작업 실행}
    \Rightarrow
    \text{해당 작업을 허용하는 유효한 승인이 존재}
    \]
    
    여기서 “허용한다”에는 다음 조건이 포함된다.
    
    **보호 필드가 승인 범위 안에 있고, 승인 대상 실행과 작업이 맞으며, 일회성 승인을 다른 작업에 재사용하지 않았을 것.**
    
    기본 정책은 보호 필드의 정확한 일치로 두되, 허용된 정규화나 사용자의 명시적인 수정 승인은 별도로 표현한다.
    
    ### 오탐을 막기 위한 중요한 경계
    
    **사용자가 승인 화면에서 수신자를 B로 수정하고 B를 승인했다면 B를 실행하는 것은 정상일 수 있다.** 최초 제안 A와 다르다는 이유만으로 경고하면 안 된다. LangGraph도 사람이 도구 호출을 검토·수정하는 패턴을 지원하므로 이 구분이 필요하다. [Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/interrupts)
    
    또한 초기 시스템은 **구조화된 승인 요청과 응답**을 대상으로 한다. 실제 UI가 무엇을 보여줬는지, 사람이 설명을 이해했는지까지 증명하지 않는다. 자연어 요약만 있고 보호 필드를 복원할 수 없다면 **명세 부족 또는 분석 불가**로 보고한다.

    # 5. 구현 범위
    
    ## 반드시 지원할 범위
    
    | 영역 | 핵심 지원 범위 |
    | --- | --- |
    | 언어 | Python의 명시적으로 정의한 부분집합 |
    | 프레임워크 | 버전을 고정한 LangGraph Graph API |
    | 그래프 | 명시적 노드 등록, 정적 연결, 해석 가능한 조건 분기 |
    | 상태 | 문자열·정수·불리언·사전 등 구조화된 값 |
    | 승인 | 지원 패턴의 `interrupt()`와 승인 응답 분기 |
    | 도구 | 등록 위치와 구현을 찾을 수 있는 함수·래퍼 |
    | 재개 | 승인 요청 이후 동일 버전에서 재개 |
    | 업데이트 | 두 버전 독립 실행 및 이전 체크포인트의 새 버전 재개 |
    | 외부 작업 | 모의 메시지 전송과 모의 레코드 수정 |
    | 설정 | 분석자가 지정한 외부 입력과 변동 가능한 설정 |
    
    **두 종류의 외부 작업이면 충분해.** 수십 개 SaaS를 연결하는 대신, 전송과 수정이라는 서로 다른 효과를 정확하게 모델링하는 데 집중한다.
    
    ## 별도 확장으로 두는 범위
    
    하위 그래프 호출, 다중 승인, 알려진 상태 reducer, 로컬 의존 패키지 변경은 핵심 엔진 위에 추가하는 확장 대상으로 둔다.
    
    ## 제외할 범위
    
    임의의 동적 코드 생성, 일반적인 리플렉션·메타프로그래밍, 제한 없는 재귀와 병렬 스케줄, 모든 원격 MCP 서버의 내부 동작, 실제 클라우드 계정 권한 검증은 제외한다.
    
    **분석 범위를 벗어난 코드는 안전으로 처리하지 않는다.** 지원하지 못한 함수·분기·외부 호출을 별도로 기록하고, 그 영향이 보호 작업까지 연결되면 최종 판단도 제한한다.

    # 6. 시스템 아키텍처
    
    ```
    두 코드 버전 + 외부 승인 정책
                  ↓
          안전한 소스 수집·파싱
                  ↓
       승인·실행 중간 표현 생성
                  ↓
          변경 영향 범위 계산
                  ↓
      재개·버전 전환 관계 분석
                  ↓
         불일치 재현 조건 생성
                  ↓
           격리된 모의 실행
                  ↓
      코드 근거 + 실행 증거 + 보고서
    ```
    
    ## 6.1 소스 수집기와 프런트엔드
    
    **입력:** 저장소의 특정 커밋 두 개 또는 로컬 스냅샷 두 개.
    
    **역할:** 파일 구조, 노드 함수, 도구 등록, 승인 호출, 상태 접근, 관련 함수 호출을 추출한다.
    
    파싱에는 Python AST나 LibCST를 사용하고, 저장소 코드를 `import`해서 구조를 알아내는 방식은 사용하지 않는 것을 원칙으로 한다.
    
    수집 결과에는 **커밋, 파일 경로, 코드 위치, 파일 해시, 의존성 스냅샷**을 기록한다. 자동으로 해석하기 어려운 프로젝트에는 사람이 작성하는 진입점 설정을 허용하되, 평가에서 그 작성 부담을 측정한다.
    
    ## 6.2 승인–실행 중간 표현
    
    단순한 노드 그래프에 다음 이벤트를 추가한다.
    
    ```
    PROPOSE       작업을 승인 대상으로 제시
    APPROVE       승인 또는 수정된 승인 수신
    READ          상태·설정·외부 값을 읽음
    WRITE         보호 값에 영향을 주는 값 변경
    SUSPEND       실행 중단
    RESUME        체크포인트에서 재개
    EXECUTE       보호된 외부 작업 수행
    INVALIDATE    기존 승인을 무효화
    ```
    
    각 이벤트에 **코드 버전, 실행 구간, 값의 출처, 논리적 작업 식별자**를 붙인다.
    
    예를 들어 `recipient`라는 같은 변수라도 다음을 구분해야 해.
    
    ```
    recipient@approval
    recipient@resume
    recipient@execution
    ```
    
    그 변수의 이름이 같다는 사실이 아니라, **세 값이 같은 승인 범위를 유지하는지**를 분석하는 거야.
    
    코드 해시가 바뀌었다는 이유만으로 불일치라고 판정하지 않는다. 해시는 출처를 식별하는 증거이고, 위험 판단은 행동과 값의 관계에 근거한다.
    
    ## 6.3 변경 영향 분석
    
    모든 코드를 동일한 비용으로 분석하기보다, 다음 위치에서 출발해 영향 범위를 좁힌다.
    
    **승인 payload, 승인 응답 처리, 보호 인자 생성, 외부 설정 조회, 도구 호출, 재개 지점.**
    
    변경된 함수가 보호 인자에 영향을 주는지 역방향·순방향으로 추적한다.
    
    다만 코드가 직접 바뀌지 않았더라도 호출한 보조 함수가 바뀌면 영향이 있을 수 있어. 따라서 단순한 줄 단위 diff가 아니라 **호출 관계와 데이터 의존 관계**를 함께 사용한다.
    
    노드 이름 변경이나 함수 이동 때문에 버전 간 대응을 찾지 못하는 경우도 기록해야 한다. 자동 대응이 불확실하면 임의로 같은 작업이라고 연결하지 않는다.
    
    ## 6.4 관계 분석 엔진
    
    첫 구현은 **제한된 기호 실행과 SMT 제약**을 사용하는 방향을 추천한다.
    
    실제 값 대신 “승인 전 수신자”, “재개 후 수신자” 같은 기호를 두고, 정책을 위반하는 입력과 변경 조건이 존재하는지 찾는 방식이야.
    
    두 실행 비교에서는 다음 조건을 유지한다.
    
    **동일한 논리적 작업, 동일한 초기 입력, 대응되는 외부 응답, 같은 승인 정책.**
    
    외부 응답은 단순히 “첫 번째 호출에는 A, 두 번째 호출에는 B”처럼 호출 횟수로만 맞추지 않는다. 가능하면 **같은 자원에 대한 같은 종류의 조회**끼리 대응시켜, 코드 리팩터링으로 호출 순서가 달라진 것을 가짜 취약점으로 만들지 않는다.
    
    ### 버전 전환 모드의 처리
    
    이전 버전에서 만든 체크포인트와 승인 요청을 고정한다. 그 뒤 다음을 비교한다.
    
    **같은 체크포인트를 이전 코드로 재개했을 때의 작업**
    
    **같은 체크포인트를 새 코드로 재개했을 때의 작업**
    
    체크포인트를 새 버전이 읽지 못하면 그것은 우선 **호환성 실패**야. 이를 승인–실행 취약점과 별도로 분류한다.
    
    LangGraph 문서도 상태 스키마 변경, 노드 이름 변경 같은 기술적 호환성 문제와 비즈니스 로직 변경을 구분하므로, 분석기의 오류 분류도 이를 반영하는 게 좋다. [Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/backward-compatibility)
    
    ## 6.5 재현 실행기
    
    정적 분석이 만든 반례 후보를 실제 LangGraph 실행으로 확인한다.
    
    기본 구성은 다음과 같아.
    
    **고정된 모델 응답, 합성 데이터, 모의 도구, 독립된 체크포인트 저장소, 외부 통신 차단.**
    
    관측할 것은 최소한 다음 네 가지다.
    
    **승인 요청의 보호 필드, 승인 응답, 재개 후 보호 필드, 모의 도구가 최종적으로 받은 인자.**
    
    LLM을 고정 응답으로 대체하면, 결과를 모델의 우연한 출력이 아니라 **워크플로우 구현의 실행 의미**에 연결할 수 있어. 대신 이를 실제 프롬프트 인젝션 공격 성공률로 해석해서는 안 된다.
    
    ## 6.6 결과 분류
    
    보고서는 다음 네 상태로 구분하는 게 좋다.
    
    | 상태 | 의미 |
    | --- | --- |
    | **재현 확인** | 명시한 환경과 조건에서 프로그램 실행으로 불일치를 확인 |
    | **정적 후보** | 분석 모델에서 위반 경로를 찾았지만 실행 재현은 미완료 |
    | **분석 범위 내 위반 미발견** | 지원한 모델·경로·입력 범위에서 발견하지 못함 |
    | **판단 불가** | 지원하지 않는 코드나 환경 정보 부족으로 결론을 내리지 못함 |
    
    **‘재현 확인’도 실제 운영 환경의 공격 가능성을 자동으로 증명하는 것은 아니야.** 공격자가 어떤 값을 바꿀 수 있는지까지 확인되지 않았다면 그 조건을 함께 표시한다.

    # 7. 핵심 결함 분류
    
    탐지 규칙은 무작정 늘리지 말고, 다음 여섯 가지를 중심으로 구성한다.
    
    | ID | 결함 | 예시 |
    | --- | --- | --- |
    | **AD-01** | 승인 후 보호 인자 변경 | A를 승인받은 뒤 수신자가 B로 재할당됨 |
    | **AD-02** | 재개 시 보호 값 재계산 | 중단 전에는 A였던 설정 조회 결과가 재개 후 B가 됨 |
    | **AD-03** | 승인 대상 객체의 간접 변경 | 승인 payload와 공유한 사전·리스트가 다른 함수에서 변경됨 |
    | **AD-04** | 도구 구현 변경에 따른 실제 대상 변경 | 같은 도구 이름과 입력이 변경된 래퍼에서 다른 자원으로 전달됨 |
    | **AD-05** | 승인 범위 재사용 | 한 작업에 대한 승인 플래그가 다음 작업에도 적용됨 |
    | **AD-06** | 버전 전환 시 기존 승인 오적용 | 이전 버전의 승인 요청에 대한 응답이 새 버전의 다른 작업에 적용됨 |
    
    AD-04는 특히 범위를 제한해야 해. **소스를 확보한 로컬 래퍼와 관측 가능한 효과만 분석**하고, 원격 서비스 내부의 숨은 행동까지 확인했다고 주장하지 않는다.
    
    각 결함에는 반드시 정상 대조 사례를 둔다.
    
    예를 들어 사용자 자신이 인자를 수정해 승인한 경우, 동등한 표현으로 정규화한 경우, 값 변경 후 다시 승인을 받은 경우, 기존 승인을 명시적으로 폐기한 경우는 경고하지 않아야 한다.

    # 8. 벤치마크와 평가 설계
    
    ## 8.1 데이터셋 구성
    
    아래 숫자는 **이미 확보한 데이터가 아니라 설계 목표**야.
    
    | 데이터셋 | 제안 규모 | 목적 |
    | --- | --- | --- |
    | **승인 동작 기준 워크플로우** | 30개 | 서로 다른 구현 패턴을 확보 |
    | **통제된 변경 쌍** | 120쌍 | 각 기준 워크플로우에 위험 변경 2개, 정상 변경 2개 적용 |
    | **위험 변경의 수정 버전** | 위험 변경마다 추가 | 수정 후 결함이 사라지고 정상 작업이 유지되는지 확인 |
    | **공개 저장소 적용 사례** | 적격 프로젝트 20개 목표 | 실제 코드에서 분석 가능 범위·설정 부담·오탐을 평가 |
    
    30개 기준 워크플로우는 단순히 변수 이름만 바꾼 예제가 아니라, 다음처럼 구현 구조를 다르게 구성한다.
    
    **노드 내부 승인, 독립 승인 노드, 도구 내부 승인, 보조 함수에서 인자 생성, 공유 객체 사용, 외부 설정 참조, 체크포인트 재개, 도구 구현 교체.**
    
    공개 저장소에서 적격 사례가 충분히 발견되지 않으면 실제 확보 수를 그대로 보고한다. 승인 기능이 없는 프로젝트에 임의로 승인을 삽입한 것은 **실제 사례가 아니라 변형 사례**로 분리한다.
    
    ## 8.2 정답 라벨
    
    각 사례에는 단순한 `vulnerable=true` 대신 다음 자료를 남긴다.
    
    ```
    분석 대상 커밋
    승인 계약
    보호 대상 작업과 필드
    허용한 외부 상태 변화
    공격자 또는 변경 주체의 권한
    기대되는 위반 여부
    위반을 일으키는 실행 조건
    정상 대조 조건
    수정 버전과 수정 근거
    ```
    
    정답은 두 명이 독립적으로 검토하고, 불일치는 다른 팀원이 판정한다.
    
    특히 **변경을 만들었다는 이유만으로 취약 라벨을 붙이지 않는다.** 해당 경로가 도달 가능하고, 승인 범위를 실제로 벗어나며, 정의한 위협 모델에서 성립해야 한다.
    
    ## 8.3 데이터 누수 방지
    
    같은 기준 워크플로우에서 만든 변형들은 한 그룹으로 묶는다. 개발용과 최종 평가용에 같은 계열이 섞이지 않도록 분리한다.
    
    공개 저장소의 포크·템플릿 복제본도 같은 계열로 관리한다. 통계 계산에서도 120개의 변형을 모두 독립적인 프로젝트처럼 취급하지 않는다.
    
    ## 8.4 비교 대상
    
    비교는 네 종류로 구성한다.
    
    **기존 정적 분석:** Agent Audit의 기본 분석과 신규 경고 모드.
    
    **구조 기반 검증:** Agentproof의 승인 경로 검사.
    
    **단순 변경 분석:** 승인·도구 관련 코드 변경만 보고 경고하는 자체 기준선.
    
    **기능 제거 실험:** ApprovalDiff에서 재개 의미, 값 추적, 버전 전환, 실행 재현을 각각 제거한 버전.
    
    공통 지원 범위와 각 도구의 고유 범위를 따로 보고하고, 기준 도구에 필요한 노드·도구 표시도 공정하게 제공한다. 실행하지 못한 도구를 “탐지율 0%”로 계산하지 않는다.
    
    ## 8.5 연구 질문
    
    | 연구 질문 | 핵심 측정 |
    | --- | --- |
    | **RQ1. 구조 검사보다 보호 값 추적이 도움이 되는가?** | 같은 수준의 오탐에서 추가로 발견한 결함 |
    | **RQ2. 재개 의미를 반영해야 하는가?** | 재개 모델을 제거했을 때의 누락 증가 |
    | **RQ3. 버전 전환 검사가 독립 버전 검사와 다른가?** | 두 버전 독립 실행으로는 발견하지 못한 사례 |
    | **RQ4. 정적 후보가 실행으로 확인되는가?** | 재현 성공률과 실패 원인 |
    | **RQ5. 실제 프로젝트에 적용 가능한가?** | 분석 가능 비율, 수동 설정량, 경고 검토 부담 |
    
    정밀도·재현율뿐 아니라 **판단 불가 비율**을 반드시 공개해야 해. 어려운 사례를 전부 판단 불가로 제외하고 높은 정확도를 주장하면 안 된다.
    
    또한 분석 시간·메모리 사용량, 정상 변경의 오탐, 수정 후 정상 작업 유지 여부를 측정한다. 성능 수치는 실험 결과이지 미리 보장할 목표가 아니다.
    
    ---
    
    # 9. 네 명의 역할 분담
    
    한 명을 발표·프런트엔드 전담으로 두기보다, **네 명 모두 독립적인 연구·구현 책임을 가지는 구조**가 적합해.
    
    | 담당 | 책임 | 주요 산출물 |
    | --- | --- | --- |
    | **A. 언어·정적 분석** | Python 프런트엔드, 호출·데이터 흐름, 중간 표현, 객체 변경 추적 | 파서, 함수 요약, 승인–실행 IR |
    | **B. 형식 모델·관계 검증** | 승인 계약, 재개 의미, 버전 대응, 제한된 기호 실행, 제약 생성 | 검증 엔진, 반례 조건, 분석 보장·한계 명세 |
    | **C. 실행·재현 시스템** | LangGraph 어댑터, 체크포인트 처리, 모의 도구, 실행 기록, 재현 테스트 생성 | 격리 실행기, 차등 재현, 결과 판정기 |
    | **D. 실증 평가·도구 통합** | 공개 사례 조사, 정답 데이터 관리, 기준 도구 실행, 평가 자동화, CLI·보고서 | 벤치마크, 실험 파이프라인, 사용자용 결과물 |
    
    D가 단순한 데이터 정리 역할이 되면 안 돼. **변경 연산자 설계, 정상 대조 사례 구성, 평가 방법론**이 독립적인 연구 기여가 되도록 해야 한다.
    
    통합을 위해 가장 먼저 합의할 인터페이스는 네 가지야.
    
    **승인 계약 형식, 중간 표현 형식, 실행 이벤트 형식, 발견 결과 형식.**
    
    각 모듈은 이 계약을 기준으로 테스트하고, 특정 담당자의 내부 구현을 다른 모듈이 직접 가정하지 않게 설계한다.

    # 10. 최종 결과물의 형태
    
    ## 10.1 CLI
    
    다음은 **구현할 명령 인터페이스의 예시**야.
    
    ```
    approvaldiff compare ./base ./head \
      --contract ./policy/approval.yaml \
      --mode independent-and-resume \
      --output ./report
    ```
    
    실행 검증은 별도 명령으로 분리한다.
    
    ```
    approvaldiff reproduce ./report/candidate-001.json \
      --fixture ./fixtures/message_workflow \
      --output ./evidence
    ```
    
    첫 명령이 자동으로 외부 코드를 설치하거나 실행하지 않도록 해야 한다.
    
    ## 10.2 검토 보고서
    
    보고서의 중심은 점수가 아니라 **근거**야.
    
    ```
    발견: AD-06 기존 승인의 새 버전 오적용
    상태: 모의 실행에서 재현 확인
    
    승인 요청:
      tool = send_message
      recipient = recipient_A
    
    새 버전 실행:
      tool = send_message
      recipient = recipient_B
    
    관련 변경:
      routing.py의 수신자 결정 로직
    
    성립 조건:
      이전 버전에서 승인 대기 상태인 실행을 새 버전으로 재개
    
    대조:
      이전 버전으로 재개 → A
      새 버전으로 재개 → B
      수정 버전으로 재개 → 기존 승인 거부 또는 재승인
    
    미확인:
      실제 운영 배포에서 버전 전환이 허용되는지
    ```
    
    ## 10.3 공개 연구 아티팩트
    
    저장소에는 다음을 함께 제공한다.
    
    | 산출물 | 내용 |
    | --- | --- |
    | **분석기** | 설치 가능한 패키지, CLI, 지원 범위 |
    | **명세** | 위협 모델, 승인 계약, 분석 의미, 한계 |
    | **벤치마크** | 코드 버전, 정답 근거, 정상 대조, 수정 버전 |
    | **재현 환경** | 고정 의존성, 합성 데이터, 모의 도구 |
    | **실험 도구** | 기준 도구 설정, 실행 스크립트, 결과 집계 |
    | **연구 보고서** | 기여, 선행 연구, 평가, 실패 사례, 제한 사항 |
    
    데모는 **정상 버전 → 위험한 업데이트 → 반례 재현 → 수정 검증**을 한 흐름으로 보여주면 된다.

    # 11. 완성 기준과 범위 조정 기준
    
    ## 기능적으로 완성됐다고 볼 기준
    
    **여섯 결함 유형마다 위험 사례·정상 대조·수정 사례를 처리한다.**
    
    **버전별 독립 검사와 체크포인트 버전 전환 검사를 구분해 결과를 낸다.**
    
    **보고서의 코드 위치·승인 값·실행 값이 재현 기록과 연결된다.**
    
    **지원하지 못한 부분을 숨기지 않고 결과에 포함한다.**
    
    **동적 검증 없이 저장소를 분석할 수 있고, 동적 검증은 격리된 명시적 동작으로 분리돼 있다.**
    
    ## 연구적으로 확인해야 할 기준
    
    **어떤 분석 요소가 기존 검사보다 추가 정보를 제공했는지 기능 제거 실험으로 설명할 수 있어야 한다.**
    
    성능이 좋아졌다면 단순히 “더 많은 규칙을 넣어서”인지, 재개 의미나 승인 대상 추적 때문에 좋아졌는지 분리해야 해.
    
    반대로 가장 가까운 기준 도구가 같은 문제를 충분히 처리한다면, 그 부분은 새 기여에서 제외한다. 그 경우에도 **정확한 벤치마크와 자동 재현 체계, 검증된 확장 모듈**은 결과물로 남길 수 있지만, 최초성이나 우월성을 주장하면 안 된다.
    
    ## 반드시 피할 성공 조건
    
    **새 CVE 발견, 유명 프로젝트의 취약점 발견, 논문 채택**을 필수 성공 조건으로 두지 않는 게 좋아.
    
    프로젝트의 완성은 **정의한 보안 속성을 분석하고, 결과를 재현하고, 한계를 평가하는 시스템**에 달려 있어야 해. 외부 신고 결과나 우연한 취약점 발견 여부에 종속되면 안 된다.

    # 12. 가장 중요한 한계
    
    이 프로젝트는 **AI 워크플로우 공급망 전체를 검증하는 제품이 아니다.**
    
    검증하는 것은 그중에서도 다음의 좁고 중요한 문제야.
    
    > **“가져온 코드나 업데이트가, 이미 부여된 사람의 승인을 다른 행동으로 확장시키는가?”**
    > 
    
    실제 계정 권한, 원격 서버 내부 구현, UI의 정직성, 자연어 설명의 충분성은 별도 문제로 남는다. 코드가 임의의 경로로 외부 작업을 수행할 수 있는데 관측하지 못했다면, 테스트를 통과했더라도 전체 실행의 안전을 보증할 수 없다.
    
    또한 제한된 모델에서 위반이 발견되지 않았다는 결과를 **전체 Python 프로그램에 대한 안전성 증명**으로 확대하지 않는다. 형식적 보장을 제시한다면, 정의한 중간 표현과 지원 연산, 탐색 범위에 한정하고 실제 LangGraph 동작과의 일치 여부를 별도로 검증해야 한다.

    ## 최종 제안
    
    **네 명이 만들 핵심은 ‘AI 보안 스캐너’가 아니라, 승인이라는 보안 경계가 코드 변경과 실행 재개를 거치며 유지되는지 검증하는 시스템이야.**
    
    프로젝트의 가장 설득력 있는 장면은 다음과 같아.
    
    **이전 버전도 정상이고 새 버전도 정상이다. 그런데 기존 승인을 새 버전에서 소비하면 다른 행동이 실행된다. ApprovalDiff가 그 조건과 원인 코드를 찾아내고, 재현하고, 수정 효과까지 확인한다.**
    
    이 문제에 집중하면 **분석 방법, 시스템 구현, 벤치마크, 비교 실험**이 하나의 연구 주장으로 연결된다.
