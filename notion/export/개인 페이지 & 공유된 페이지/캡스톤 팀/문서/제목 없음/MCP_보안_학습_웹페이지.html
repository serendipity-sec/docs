MCP의 구조와 보안 검증

AI 애플리케이션이 외부 도구와 데이터를 호출하는 과정을 따라가며, 실제 취약점과 검사 도구의 증거 수준을 구분하는 학습 페이지

기준 사양: MCP 2026-07-28 · 출처 확인일: 2026-10-01

먼저 잡아야 할 질문

“위험 신호가 발견되었다”와 “권한 밖의 데이터가 실제 외부로 나갔다” 사이에는 여러 검증 단계가 있다. 이 페이지는 그 사이를 연결한다.
사양

요청·응답·전송 규칙을 정한다. 사양이 있다고 서버 구현이나 사용자 권한이 자동으로 안전해지는 것은 아니다.

구현

SDK와 서버 코드가 인자·경로·URL·인증을 실제로 검사한다. CVE는 주로 이 계층의 결함을 가리킨다.

행동

Host와 모델이 도구 설명·문서·반환값을 어떻게 해석하고 다음 호출을 만드는지가 별도의 위험면이다.

1. MCP 구성요소

실제 피해는 마지막 외부 API의 권한과 최종 상태까지 확인해야 한다.

2. 개정 전과 개정 후 통신

2025-11-25

초기화와 세션

initialize→기능 응답→initialized→tools/list

버전·기능을 먼저 교섭하고 정상 작업을 시작한다.

2026-07-28

요청별 자기 설명

server/discover 선택→tools/list→tools/call

초기 handshake와 프로토콜 수준 세션 헤더를 제거했다. 각 요청이 버전·클라이언트 정보·기능을 전달한다.

POST /mcp
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"search","arguments":{"q":"otters"},
 "_meta":{"io.modelcontextprotocol/clientInfo":{"name":"my-app","version":"1.0"}}}}

무상태는 서버에 업무 상태가 없다는 뜻이 아니다. 상태가 필요하면 서버가 핸들을 만들고, 다음 호출마다 사용자 권한을 다시 확인해야 한다.

3. 도구 발견부터 결과 사용

사용자 요청→tools/list→모델 선택→Host 승인·정책→tools/call→서버 실행→결과 사용
{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}
→ {"result":{"tools":[{"name":"get_weather","description":"Get current weather...",
   "inputSchema":{"type":"object","properties":{"location":{"type":"string"}}}}]}}

{"jsonrpc":"2.0","id":2,"method":"tools/call",
 "params":{"name":"get_weather","arguments":{"location":"Seoul"}}}
→ {"result":{"content":[{"type":"text","text":"Current weather..."}],"isError":false}}
핵심: JSON Schema를 통과했다는 것은 입력 모양이 맞다는 뜻이지, 호출자가 그 파일·이슈·테넌트·수신자에 접근할 권한이 있다는 뜻이 아니다.

4. 공격 표면은 입력 위치와 다음 권한 결정의 조합

진입 지점공격자가 바꾸는 것다음에 바뀌는 권한 결정검증 증거
도구 설명목적·사용 지시모델의 선택·인자 생성원본 설명, 모델 출력, 실제 호출
문서·반환값검색 본문·파일 내용자료가 후속 지시가 되는지원문, 후속 호출, 변형 값
호출 인자경로·URL·이름·옵션서버 파서·하위 명령·외부 요청정규화 경로, 최종 argv/URL
인증 헤더토큰 유무·발급자익명 요청이 서비스 계정으로 바뀌는지실제 계정·객체 감사 로그
패키지·설치실행 코드·버전설치 후 파일·네트워크 동작해시, 출처, 설치·전송 로그

그래서 검증 경계는 진입 지점마다 달라진다. 대시로 시작하는 자원 이름은 최종 argv의 옵션 해석 문제이고, 문서 안의 “이 주소로 보내라”는 문장은 Host·모델의 의미 해석과 후속 호출을 봐야 한다.

5. 의미 조작과 구현 취약점

의미 조작

모델의 판단을 바꾸는 입력

  • Prompt injection: 문서·검색 결과·도구 결과가 지시처럼 작동
  • Tool poisoning: 도구 설명 안에 숨은 악성 지시
  • Tool shadowing: 한 서버의 설명이 다른 정상 도구 규칙까지 변경
구현 취약점

문자열이 위험한 실행 의미로 바뀌는 결함

  • 명령·인자 주입
  • 경로 순회와 SSRF
  • 인증·객체 권한 오류
  • DoS와 공급망 악성 코드
악성 설명이 위험한 인자를 만들고, 서버의 구현 결함이 그 인자를 실행으로 통과시키는 연쇄도 가능하다.

6. 실제 사례를 증거 단계로 읽기

3.9.0 미만에서 resourceType/name에 대시를 넣어 --server 같은 kubectl 옵션으로 재해석될 수 있었다.

경계: 안전한 자원 이름과 하위 명령 옵션의 구분
증거: 최종 argv → 목적지 → 가짜 토큰 수신

CVE-2026-77254

MCP Atlassian

0.22.0 미만 HTTP 배포에서 Authorization이 없으면 전역 Jira/Confluence 자격증명으로 fallback될 수 있었다.

경계: 익명 요청과 서비스 계정의 연결
증거: 실제 계정·도구·객체 감사 로그

CVE-2026-27735

공식 Git MCP

2026.1.14 미만 git_add에서 ../ 경로가 저장소 밖 파일을 인덱스에 올릴 수 있었다.

경계: 저장소 경계
증거: 정규화 경로·인덱스·커밋·푸시

공급망

악성 postmark-mcp

Postmark 사칭 npm 패키지가 1.0.16에서 이메일을 외부 주소로 BCC하도록 바뀌었다.

경계: 배포 출처·코드 무결성
증거: 버전·해시·메일 로그·외부 수신

공개 권고의 “가능한 영향”은 특정 조직의 실제 침해 확인과 다르다.

7. 검사 도구가 보는 것과 놓치는 것

도구 이름이 아니라 실제 기능 기준으로 보자. 설명·코드만 읽으면 정적, 대상 서버를 실행하고 이벤트를 관찰하면 동적, 두 증거를 연결하면 하이브리드다.

도구·연구주로 검사원리주요 한계
Cisco MCP Scanner악성 설명, 알려진 패턴, 코드 위험 동작·데이터 흐름YARA, API/LLM 의미 분석, AST·cross-file flow
정적 중심		특정 Host가 실제로 따르는지, 외부 객체 변경·수신이 있었는지 기본 증명하지 않음
Snyk Agent ScanPrompt injection, poisoning/shadowing, toxic flow, private data·destructive capability, skills·malware구성 자동 발견 + 설명/서버 분석. 설정에 따라 원격 조회·stdio 실행
혼합		검사 자체가 untrusted config를 실행하거나 원격에 연결할 수 있음. 사용자·테넌트 권한과 최종 전송은 별도 필요
VIPER-MCP도구 입력에서 파일·셸·네트워크 sink로 이어지는 taint 경로JS/TS/Python 정적 경로 + 목표형 prompt·runtime oracle
하이브리드		지원 언어·sink·실험 환경 밖, 원격 객체 권한·실제 조직 데이터는 별도
FlowGuard의미 위험 신호가 schema-valid probe에서 실행 증거로 이어지는지semantic triage + 유효 입력 + 응답·실행 evidence adjudication
하이브리드		응답이 외부 공격자에게 도착했는지, 다른 계정·시점에도 같은지 알기 어려움
MCP-SandboxScan런타임 외부 입력→sink 노출, 파일·환경·HTTP fetch intent, WASI 위반WASM/WASI 샌드박스 실행 + source/sink 연결
동적		샌드박스와 실제 배포 권한 차이, 변형된 민감정보, 최종 수신 확인
mcp-sec-audit정적 위험과 프로세스·네트워크 이벤트정적 분석 + 동적 detector이벤트가 정책 위반인지는 사용자·객체 권한과 대조해야 함
TrustShiftProbe처음에는 정상, 임계점 뒤 바뀌는 서버 행동상태 있는 단계적 공격 생성 + runtime 방어 평가연구 시나리오·모델·임계값 밖 장기 운영 행동
AgentBox·AGT실행 권한 제한과 정책 강제취약점 탐지보다 sandbox·governance 계층차단 정책이 있다고 서버 취약점이나 최종 피해가 사라지는 것은 아님

8. 왜 검사하지 못하는가

실행 조건의 폭발

계정·테넌트·객체·날짜·호출 횟수·이전 핸들에 따라 다른 경로를 탄다. 모든 조합을 실행할 수 없다.

의미 변형

기밀이 요약·번역·인코딩·부분 문자열로 바뀌면 단순 매칭이 놓칠 수 있다. 짧은 공통 문자열은 오탐을 만든다.

서버 간 연결

A가 읽고 모델이 변형하고 B가 전송하는 흐름은 단일 서버 검사만으로 완성되지 않는다.

환경 차이

샌드박스의 파일·네트워크·토큰 권한과 실제 배포의 권한이 다르다.

설치 단계 위험

설명을 읽으려 config의 stdio 명령을 실행하거나 원격 서버에 연결하면 검사 자체가 공격 표면이 된다.

차단 뒤 상태

blocked 로그만으로 부분 쓰기·중복 호출·비동기 외부 처리를 부정할 수 없다.

9. 경고에서 실제 피해까지

1 위험 신호
설명·코드·패키지→2 가능한 경로
입력 → sink→3 실행 관찰
argv·파일·네트워크→4 권한 위반
사용자·객체·정책→5 최종 피해
수신·변경·중단

탐지됨은 신호가 분석에 걸렸다는 뜻이다. CONFIRMED는 해당 검사기의 oracle을 통과했다는 뜻이다. 차단됨은 특정 시점에 정책이 거부했다는 뜻이다. 어느 표시도 그 자체로 데이터 유출·원격 객체 변경·조직 침해를 증명하지 않는다.

10. 연구와 도구를 읽는 체크리스트

  1. 대상 버전과 배포 방식은 무엇인가? 사양·SDK·서버 패치를 분리한다.
  2. 공격 입력의 출처는 어디인가? 설명·문서·인자·인증·패키지 중 하나로 특정한다.
  3. 실제로 서버를 실행했는가? 어떤 계정·파일·네트워크를 관찰했는가?
  4. 성공 판정은 응답·프로세스 이벤트·목적지 수신·원격 객체 상태 중 무엇인가?
  5. 변형된 민감정보, 서버 간 흐름, 다른 테넌트·객체, 설치 후 동작, 차단 후 상태를 검사했는가?
결론: MCP 보안 평가는 경고 점수의 순위를 매기는 작업이 아니라 입력의 출처에서 최종 목적지와 결과까지 증거를 이어 붙이는 작업이다.
