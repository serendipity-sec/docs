# FlowDelta의 10주 실행 계획과 논문 평가 명세

기준: 4명 전담, 8~10주, 2026년 10월 3일 설계. 숫자는 확보·성능 실적이 아닌 계획이다. 주차는 착수일 기준 상대 주차다. 8주까지 시제품과 핵심 비교 결과를 확보하고, 9~10주에 확장 실험·오류 분석·논문 초안을 완성한다.

## 시간과 자원 가정

매일 10시간씩 4명이 8~10주를 사용하면 명목 투입량은 2,240~2,800시간이다. 실제 구현·실험 계획에는 회의·리뷰·재현 실패·문서·버퍼를 위해 35%를 남겨 약 1,456~1,820시간을 배정한다. 35%는 계획용 가정이며 팀의 측정 생산성 수치가 아니다. 추가 시간은 지원 프레임워크 수 확대보다 오류 분석과 반복 재현에 우선 사용한다.

일반 개발 PC 외에 Linux 실행 VM과 증거 저장 공간이 필요하다. API 모델을 사용할 경우 자체 학습 GPU는 필수가 아니다. 동시 실행 수는 CPU·메모리·모델 rate limit과 관측기의 안정성을 측정한 뒤 설정한다. 불신 패키지 실행과 연구자 개발 환경을 분리한다.

## 네 명의 모듈 책임

아래 A~D는 기술 역할이다. 기존 팀장·발표·서기 역할과 별도로 실제 역량에 따라 배정한다.

| 담당 | 주 책임 | 구체적인 산출물 | 교차 검토 |
|---|---|---|---|
| A 그래프와 변경 분석 | n8n 어댑터, 표현식 부분집합, 의미 계약, 의존성·영향 추적 | Snapshot·Graph·ChangeSet, 근거 위치, coverage | C가 실행 의미 검증, B가 조건 연결 검토 |
| B 지식과 시험 생성 | 출처 수집, 카드 정규화, 검색, LLM 가설, 스키마·조건 검사 | ScenarioCard·Hypothesis·TestPlan, 검색 평가 | D가 정답 누수·검색 관련성, A가 경로 근거 검토 |
| C 실행과 독립 관측 | VM·fixture, n8n 연결, 모의 도구, oracle, 초기화·반복 | ExecutionRun·EvidenceEvent, 전후·수정 재현 | D가 oracle 적정성, A가 어댑터 계약 검토 |
| D 평가와 결과 제품 | 데이터 분할, baseline, 통계, CLI·보고서·최소 웹 | Benchmark·Finding, 실험 집계, 논문 표·그림 | B가 출처, C가 결과와 원시 증거 연결 검토 |

D 한 명에게 모든 라벨링을 맡기지 않는다. 네 명이 교차 라벨링하고 작성자는 자기 사례의 단독 최종 판정자가 되지 않는다. UI는 D가 구조를 정하되 공통 결과 포맷을 활용해 최소화한다. 네 명 모두 자기 모듈의 실패 사례와 논문 부분을 작성한다.

## 첫 72시간

첫날에는 보호 정책 P1·P2, 공격자 표면, snapshot·graph·scenario·evidence·finding 필드를 합의한다. 정상 workflow 1개, 위험 변경 1개, 정상 변경 1개를 손으로 먼저 정의한다. 지원 n8n 버전·노드 버전·모델·컨테이너 digest와 기존 실험의 재사용 범위를 기록한다.

둘째 날에는 도구 호출을 고정한 상태에서 모의 문서 조회·내부 전송·외부 역할 수신·문서 변경을 실행한다. 정상, 위반, 대상 통제 차단, 관측기 고장을 각각 구분한다. 합성 canary를 공격 입력에 넣지 않아야 한다.

셋째 날에는 작은 변경 그래프에서 카드 5~10개를 검색하고, 하나의 구조화 시험 계획을 실행기까지 전달한다. 사람 작성 plan으로 전체 흐름을 먼저 확인하고 자동 생성으로 교체한다. 이 시점의 결과를 탐지 성능으로 발표하지 않는다.

## 우선순위와 범위 조정

필수 P0는 n8n 어댑터, 정책 P1·P2, 변경·경로 분석, 시나리오 검색·시험 계획, 독립 효과 관측, 전후 비교, 정상 업무 검증, 정답 데이터·baseline·보고서다.

P1은 제한된 승인 계약, 두 번째 모델 일부 실험, 실제 권한 수집기 1종, 지식 카드 웹, 검색 순위 개선이다. P2는 LangGraph 전면 어댑터·재개 분석, 다양한 프레임워크 지원, 선택적 재분석 최적화, 사용자 계정·공개 서비스다.

| 문제가 생긴 시점 | 조정 |
|---|---|

## 지원 동작의 작은 계약

첫 구현의 12개 후보는 Manual Trigger, Webhook, Edit Fields, If, 단순 Merge, HTTP 조회, HTTP 전송·수정, AI Agent, Chat Model 연결, 고정 Execute Sub-workflow, Call n8n Workflow Tool, 구조화된 승인 wrapper다. 마지막 wrapper는 프로젝트의 시험 어댑터일 수 있으므로 n8n의 모든 native HITL 동작을 지원한다고 표시하지 않는다.

노드 유형 하나가 모든 동작·버전·배치 의미를 지원한다는 뜻은 아니다. 각 계약에는 지원 파라미터, 필드 매핑, source·sink, 외부 효과, 오류 동작, 버전, 테스트 fixture를 적는다. Merge는 지원한 병합 방식만, 표현식은 상수·필드 참조·제한된 문자열 결합·단순 비교부터 다룬다. item linking·동적 URL·임의 Code node를 완전히 해석한다고 주장하지 않는다.

## 데이터셋 설계

목표는 독립적인 workflow 계열 30개와 각 계열의 변경 비교쌍 4개다. 위험 변경 2개와 정상 변경 2개를 만들면 120쌍이며, 위험 60·정상 60쌍이다. 별도로 누락 의존성·동적 참조·권한 미확인·관측 실패 등을 포함한 unknown 20개를 구성한다.

독립 계열은 이름만 바꾼 예제가 아니다. 데이터 이동·분기·하위 호출·도구 노출·권한·승인 위치가 다른 구현 패턴으로 구성한다. 공개 템플릿에서 가져온 자료, 참조 실행기에 이식한 자료, 연구자가 작성한 합성 자료를 별도 집계한다.

| 분할 | workflow 계열 | 변경 쌍 | unknown 사례 |
|---|---:|---:|---:|
| 개발 | 15 | 60 | 10 |
| 검증 | 5 | 20 | 4 |
| 최종 평가 | 10 | 40 | 6 |
| 합계 | 30 | 120 | 20 |

가능하면 공개 프로젝트의 실제 변경 10쌍을 추가 심층 사례로 확보한다. 10쌍은 필수 충족 실적이 아니며, 적격한 사례만 사용한다. 실제 원본에 팀이 위험 변경을 삽입했다면 실제 취약 이력으로 분류하지 않는다. 공개 workflow 약 50개를 추가로 정적 분석해 node·path coverage와 수동 계약 부담을 평가할 수 있지만, 이 집합 전체가 안전 또는 취약하다고 라벨링하지 않는다.

정상 변경에는 화면 좌표 이동만 넣지 않는다. 참조를 보존한 이름 변경, 허용된 수신자 변경, 불필요한 민감 필드 제거, 권한 축소, 동등한 분기 재구성, 하위 함수 분리, 정당한 재승인 등을 포함한다. 위험이 있는 원본의 무해 변경은 새 회귀가 없더라도 기존 위험이 유지되는 별도 사례다.

## 정답과 데이터 누수 관리

정답은 정책·공격자 통제 범위·코드 또는 구성의 의미·독립 실행 증거로 작성한다. 분석기의 경고나 생성 모델의 판단을 그대로 정답으로 쓰지 않는다. 두 명이 독립 검토하고 불일치는 제3자가 조정한다. 판단이 어려운 사례는 그 상태를 유지한다.

같은 원본, fork, 템플릿 파생물, 같은 원인의 수정본과 공격 변형은 한 계열로 묶는다. 최종 평가셋의 결과를 보고 규칙·검색 순위·프롬프트를 바꾸면 그 자료는 개발 데이터가 되며 별도 새 평가가 필요하다.

RAG에는 두 평가 모드를 둔다.

* 알려진 취약점 적용성: 정확한 공개 공지 검색을 허용하고 제품·버전·조건을 맞추는 능력을 평가한다.
* 보지 않은 변경·조합 일반화: 최종 계열의 구체적 코드·정답·공격 payload·패치 해설을 KB에서 제외한다. 일반 공격 원리 카드는 사용할 수 있다. 별도의 공격 원리 보류 실험을 한다면 그 원리 카드도 제외한다.

시나리오 지식 corpus와 평가 corpus의 해시·별칭·출처·근접 중복을 점검한다. private knowledge에도 최종 정답이나 oracle 소스를 넣지 않는다. 공개 모델의 사전학습 누수는 완전히 배제할 수 없으므로 한계로 보고한다.

## 연구 질문과 비교군

주 연구 질문은 **같은 시험 예산에서 변경과 그래프 조건을 사용하는 검색·시험 선택이 확인된 회귀 수를 높이는가**다. 보조 질문은 조건 검사로 잘못된 CVE·시나리오 적용을 줄이는지, 환경·의존성 정보가 부모 파일만 볼 때의 누락을 줄이는지다.

| 비교군 | 사용 정보 | 측정 목적 |
|---|---|---|
| B0 노드·설정 규칙 | 전체 정적 구성 | 단순 스캐닝 수준의 후보 탐지 |
| B1 전체 재분석 후 결과 비교 | 양쪽 전체 그래프·동일 정책 | 변경 분석의 정답 기준, 최적화와 의미 비교 |
| B2 일반 RAG | 텍스트 diff와 동일 KB·LLM·예산 | 그래프 조건이 없는 검색과 비교 |
| B3 그래프 조건과 고정 시나리오 | 전체 구조·정책·정해진 카드, LLM 검색 없음 | RAG 추가 가치와 지식 검색 비용 |
| B4 제안 방법 | 변경·영향 그래프·조건·혼합 검색·LLM | 종단 간 방법 |
| B5 고정 회귀 시험 | 같은 등록 시나리오와 대상, 변경별 검색·우선순위 없음 | 기존 회귀 시험을 모두 수행하는 방식의 예산 효율 |

외부 도구 비교는 별도로 한다. FlowGuard·n8n Audit은 공통 정적 규칙만, OWASP 하네스·Promptfoo는 공통 동적 시나리오만 비교한다. 도구가 입력을 지원하지 않거나 환경에서 실행하지 못했다면 미탐이 아니라 UNSUPPORTED 또는 NOT_RUN이다. 공개 기능 설명에 해당 기능이 없다는 이유로 실제 성능을 0점으로 쓰지 않는다.

기능 제거 실험은 B4에서 변경 정보 제거, 환경 제거, 하위 의존성 제거, 지시 영향 제거, 검색 제거를 각각 수행한다. 검색 실험에서는 generator·victim 모델, KB snapshot, 최대 토큰·시도·시간을 맞춘다. 같은 코드를 두 번 검사하는 방식과 비교하지 않으면 변경 분석의 가치를 설명할 수 없다.

선택적 재분석을 구현할 때만 성능 주장을 추가한다. 같은 의미 모델의 전체 분석과 판정·근거 집합을 대조하고, 불일치가 있으면 원인을 해결하거나 최적화의 한계를 보고한다.

## 실행량과 비용 계획

기본 재현 실험 예시는 변경 40쌍 × 이전·이후 2버전 × 정상·공격 2조건 × 3회 × 모델 1종 = 480 episodes다. 확인된 위험 중 20쌍의 수정본을 정상·공격 2조건으로 3회 검증하면 120 episodes가 추가된다. 여기서 40쌍은 최종 평가 40쌍과 자동으로 같은 집합이라는 뜻이 아니며, 실제 평가에서 분할·용도를 지정한다. 최종셋에 포함된 실행은 freeze 후에만 수행한다.

별도의 예산 효율 실험은 최종셋의 위험 변경 20쌍에서 B2·B3·B4·B5의 4개 방법 × 2버전 × 버전당 최대 10회 공격 시도를 적용하면 상한 1,600 episodes다. 위험 여부의 정답은 방법에 제공하지 않는다. B5는 공통 시험을 실행할 수 있는 OWASP 하네스 또는 Promptfoo로 구성하며, 호환성 때문에 자체 실행기를 사용하면 그 차이를 공개한다. B0·B1은 정적 분석 비교군으로 유지한다. 정상 변경의 오탐은 앞선 고정 평가에서 별도로 측정한다. 정상 업무 대조는 대상이 같으면 동일 조건의 공통 실행을 참조할 수 있으며, 같은 실행을 독립 표본처럼 여러 번 세지 않는다. 방법별 중복 실행과 재사용 규칙을 로그에 기록한다.

이 두 실험은 고정 시험의 재현성과 검색·생성의 효율을 각각 보는 것이다. 에피소드 하나의 내부 도구 호출 수가 다를 수 있어 에피소드뿐 아니라 총 모델 토큰, 도구 호출, 벽시계 시간, 인프라 비용을 함께 제한한다. 실패한 시도도 예산에 포함한다.

첫 20~30개 pilot에서 에피소드별 토큰·지연·비용을 측정한다. 총 비용은 다음처럼 추정한다.

`모델 비용 = 입력 토큰 합계 × 입력 단가 + 출력 토큰 합계 × 출력 단가 + 임베딩·재정렬 비용`

단가의 단위는 제공자의 실제 청구 단위에 맞춰 환산한다. 예를 들어 2,000 episodes의 평균 모델 비용이 각각 0.03·0.10·0.30달러라면 합계는 60·200·600달러다. 이 값은 민감도 분석용 가정이며 현재 제공자의 가격 견적이 아니다. 실행 VM·저장·반복 실험 비용은 별도다. 파일럿 후 팀 지출상한과 실행 예산을 정하고, 초과 예상 시 사례 품질과 대조군을 유지하면서 반복·확장 범위를 줄인다.

## 측정할 지표

| 단계 | 지표 | 분모와 해석 |
|---|---|---|
| 추출 | 지원 노드·동작·필드·위험 경로 coverage | 전체 입력 대비 지원 비율, 수동 계약 비율 별도 |
| 검색 | Recall@5, nDCG@5, 적용 가능한 카드 비율 | 사람이 관련성을 라벨링한 질의 집합 |
| 생성 | 유효 계획 비율, 조건 모순 비율, 근거 없는 인용 비율 | 생성된 모든 계획, 거부된 계획 포함 |
| 후보 발견 | Precision·Recall·정상 변경 FPR | 정답이 있는 변경 쌍, 위험과 정상의 분모 공개 |
| 실행 | oracle 판정 정확도, 실행 실패율, 관측 불완전 비율 | 모든 계획·실행, 성공한 실행만 선택하지 않음 |
| 최종 확인 | unique confirmed regressions@budget | 같은 예산에서 독립 정답 회귀 중 확인한 수 |
| 회귀 비교 | 공격 성공률 차이와 효과 크기 | 이전·이후의 실제 시도수 및 대응 조건 |
| 기능 보존 | 정상 업무 성공률, 수정 후 성공률 | 공격 없는 정상 업무, 전부 차단한 구성을 감점 |
| 비용 | 확인 1건당 비용, 시간, 검토 시간 | 시나리오 작성·초기화·실패 처리 시간 포함 |
| 신뢰성 | UNKNOWN·abstention·미실행 비율 | 높은 정확도와 낮은 판정 coverage를 함께 표시 |

정적 후보 precision과 실행 확인 precision을 혼합하지 않는다. UNKNOWN을 true positive로 세지 않으며, 판단 가능한 사례만의 수치와 전체 사례에서 확정 결론을 내린 비율을 함께 낸다. 실제 공개 저장소 집합은 모든 취약점의 정답을 알 수 없으므로 전체 recall을 계산하지 않는다.

예산 효율의 주 지표는 정해진 예산 내 확인한 회귀 수다. 고정 시험 결과와 생성·탐색 결과를 구분한다. 동일 원인·동일 계열의 payload 변형을 여러 신규 취약점으로 세지 않는다.

통계는 workflow 계열을 재표집 단위로 한 bootstrap 신뢰구간 등을 사용한다. 120쌍을 120개의 완전히 독립적인 제품처럼 취급하지 않는다. 단일 사례의 반복 결과에는 성공 횟수와 시도 수를 같이 제시하고, 구버전 0회 성공을 안전 증명으로 해석하지 않는다. 작은 표본에서 유의성이 없으면 그 한계를 그대로 쓴다.

## 사전 성공 목표와 완료 조건

아래 수치는 검증셋에서 조정할 수 있는 초기 목표다. 최종 평가 후 기준을 낮춰 달성으로 보고하지 않는다.

| 목표 | 초기 기준 |
|---|---|
| 후보 탐지 | 지원 범위의 정밀도 85% 이상, 재현율 80% 이상을 도전 목표로 설정 |
| 정상 변경 | 정상 변경 FPR 10% 이하 목표, UNKNOWN 비율 별도 |
| 검색 | 독립 라벨 질의에서 Recall@5 80% 이상 목표 |
| 종단 간 효율 | B2 대비 같은 예산의 확인 회귀 수 증가 여부 측정. 효과 크기는 결과로 보고 |
| 증거 연결 | 확정 finding 모두에 source·변경·시험·독립 증거 링크 존재 |
| 미확인 처리 | 관측 실패·미지원·미실행을 통과로 처리하는 계약 오류 0건 |
| 속도 | 명시한 장비·100노드 이하 지원 입력에서 정적 compare P95 30초 목표. 모델 실행 시간 별도 |

프로젝트 구현 완료에는 다음이 필요하다: 설치 가능한 코어, 버전 고정 재현 환경, P1·P2 전체 경로, 데이터셋과 라벨 근거, 최소 정적·동적 baseline, 수정 후 정상 업무 검증, 실패·UNKNOWN 보고, 다른 팀원의 clean-machine 재실행. P3를 추가했다면 그 지원 범위와 별도 평가를 명시한다.

연구 완료에는 비교 실험이 어떤 가설을 지지하거나 지지하지 않는지, 수동 입력·추가 정보·비용의 차이가 무엇인지 설명해야 한다. 수치가 목표에 못 미쳐도 원인과 한계가 있는 완성된 연구가 될 수 있다. 단순 UI 완성이나 경고 수 증가만으로 연구 기여를 입증한 것은 아니다.

## 논문과 공개 아티팩트

가제는 “FlowDelta: Change-Aware Scenario Retrieval and Differential Validation for AI Workflow Security”로 둔다. 제목의 기능들은 제안 내용이며 구현 전에 완성 성과처럼 초록에 쓰지 않는다.

논문은 문제·동기, 위협 모델과 정책, 보안 그래프와 변경 의미, 조건 기반 검색·시험 생성, 실행 판정, 변경 벤치마크, 비교·기능 제거 실험, 사례 연구, 한계 순으로 작성한다. 2주차부터 서론·위협 모델을 쓰고, 6주차에 평가 계획을 고정하며, 8주차에 결과를 넣는다.

공개 후보 아티팩트에는 소스·lock·digest, 스키마·지원 계약, 재배포 가능한 workflow와 카드, 출처·라이선스, 라벨 근거, baseline 설정, 실행 명령, 원시 결과와 집계 스크립트, 실패 사례, 재현 가이드를 포함한다. 미공개 취약점·사내 데이터는 별도 취급하고 공개 저장소에 자동 업로드하지 않는다.

8~10주 동안은 재현 가능한 논문 초안을 목표로 한다. 구체적인 학회·저널 선택과 투고일은 결과의 깊이·모집 일정·공개 정책을 확인한 뒤 정한다. 최상위 학회 채택이나 신규 CVE 수를 일정의 성공 기준으로 두지 않는다.
