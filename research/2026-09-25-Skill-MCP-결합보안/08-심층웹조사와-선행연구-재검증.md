# 8. 심층 웹 조사 — 기존 제안을 선행연구로 다시 검증하기

2026-09-25 추가 조사. **앞선 12편에 16편을 추가해 논문·학술 연구 28편을 검토 범위에 넣었다. 28편 모두를 전문 정독하거나 재현했다는 뜻은 아니다.** 방법·한계 확인, 초록 확인, 코드 확인, 부분 실행을 아래에서 구분한다. 교수 면담용 종합은 [09](09-교수면담용-선행연구-논증.md)이다.

## 1. 앞선 제안에서 바뀐 결론

1. **‘Skill+MCP+작업 의도+권한’도 이미 직접 다룬다.** IntentCap이 가장 가까운 반례다. 승인·출처를 추가했다는 이유로 신규성을 주장할 수 없다.
2. **Skill을 MCP로 전달하는 공식 확장이 있다.** 로컬 Skill이 MCP 도구를 쓰는 경로와, MCP가 Skill 파일을 전달해 호스트 행동을 지시하는 경로를 구분해야 한다.
3. **비교군을 강화해야 한다.** 개별 스캐너·단순 권한 합집합뿐 아니라 IntentCap, SkillGuard, Fides/PCAS, harness-eval, skil과 비교해야 한다.
4. 남길 후보는 **현실의 불완전한 설정에서 정책 판정에 필요한 근거를 복원하고, 모르는 것은 미판정으로 남기는 분석의 효과**다. 이 역시 아직 새로운 방법임을 입증하지 못했다.

이 수정은 처음 세운 결론을 방어하기 위한 자료 추가가 아니라, 새로 확인한 연구에 따라 연구 질문을 줄인 결과다.

## 2. 검색 범위와 신뢰도

- 추가 검색 **12차, 검색어 48개**와 논문 참고문헌·저자 GitHub·공식 명세 링크 추적을 수행했다. [검색어와 포함 근거 JSON](evidence/deep-web-research.json)에 기록했다.
- 검색 축: Skill composition → MCP poisoning → task intent/capability → information-flow control → runtime policy → repository/configuration audit → 표준·호스트 권한 의미.
- 직접 관련 연구는 Skill/MCP라는 단어의 유무보다 **입력, 위협 모델, 강제 지점, 검증 가정**이 겹치는지로 골랐다.
- 원문·학회 사이트·저자 공개 구현·공식 문서를 근거로 썼다. Reddit, 재게시 사이트, AI 요약은 탐색 단서로만 썼다. 검색 결과 수는 포함 논문 수로 세지 않았다.
- 같은 이름의 다른 AgentSpec·AgentBound·SkillGuard를 구별했다. SkillWeaver 등 일반적인 도구 재사용을 ‘skill’이라 부르는 연구를 SKILL.md 보안의 직접 증거로 세지 않았다.
- 이 조사는 **체계적 문헌고찰 완료본이 아니다.** 데이터베이스 전체 export, 중복 심사자 독립 판정, 포괄적인 전방 인용 추적을 하지 않았다. 공개 구현을 못 찾았다는 것과 존재하지 않는다는 것은 다르다.

## 3. 가장 가까운 선행연구

### R13. IntentCap — 직접 중복을 먼저 인정해야 하는 연구

[LLM Agent Capabilities Should Follow Task Intent and Context Source, 2026-09, v1](https://arxiv.org/html/2609.14631v1). 설계·평가·한계 확인, 공개 checker 코드 확인 및 부분 실행. Preprint.

| 질문 | 원문을 바탕으로 한 답 |
|---|---|
| 무엇을 막나 | 외부 자료가 목적지·도구 선택·승인 권한을 획득하는 문제 |
| 원리 | 사용자 의도·workflow 지시·tool schema·환경 정보를 구분하고, 인자별 권한과 좁혀지는 capability lease를 검사 |
| 정적/동적 | 정책 구성과 결정적 경계 검사; 공개 수치는 주로 trace replay |
| 실제 문제 | PDF의 내용은 보고서 본문에 들어갈 수 있어도 게시할 저장소를 임의로 정하지 못해야 함 |
| 확인한 한계 | 올바른 label·lease·provenance의 확보가 필요. replay와 실사용 공격 성공률은 다름 |
| 우리 질문 | 동일 checker에 사람이 만든 근거와 자동 추출 근거를 넣을 때 판정·미판정이 얼마나 달라지는가 |

저자는 3,746개 보안 관련 이벤트 replay를 보고한다. 이를 3,746건의 실제 침해 차단으로 발표하면 안 된다. **우리 제안의 ‘작업 의도·출처·실제 대상에 따른 판정’은 이 연구와 겹친다.**

### R14. SkillGuard — Skill별 선언과 현재 작업 권한의 구분

[A Permission Framework for Agent Skills, 2026-06, v1](https://arxiv.org/html/2606.03024v1). 설계·평가·§11.2 한계 확인. Preprint.

| 질문 | 답 |
|---|---|
| 무엇 | Skill 지시와 도구 사용 사이의 과잉 권한 |
| 원리 | manifest의 선언 집합, 작업별 축소 범위, 사용자 grant를 분리하고 호출 직전 검사 |
| 방식 | manifest·권한 매핑 + LLM task judge + 런타임 hook |
| 취약점 | 다른 Skill의 권한을 현재 작업에서 재사용하거나, 출처를 허위로 귀속 |
| 한계 | trusted manifest/hook 가정, judge 의존; 논문 평가의 모델·호스트 범위 제한 |
| 우리 질문 | 선언 자체가 누락·과대·환경과 불일치할 때 어떤 근거를 확보할 수 있나 |

[저자 저장소](https://github.com/Dianshu-Liao/SkilLGuard)의 README·평가 코드·git tree를 확인했다. `skillguard`는 **gitlink(commit `6a9cbe2…`)**이며 현재 checkout에 구현 파일이 내려와 있지 않고 `.gitmodules` URL 매핑도 없다. 따라서 README에 나온 hook의 내부 동작을 이번에 검증했다고 쓰지 않는다. 논문이 없거나 구현이 존재하지 않는다는 주장도 아니다.

### R15. Fides — 데이터 유출과 제어 오염을 함께 보는 기준선

[Securing AI Agents with Information-Flow Control, 2025-05](https://arxiv.org/html/2505.23643v1). 설계·§5·§9 확인. [Microsoft Research 원출처](https://www.microsoft.com/en-us/research/publication/securing-ai-agents-with-information-flow-control/)도 확인.

| 질문 | 답 |
|---|---|
| 무엇 | 민감 데이터의 유출, 비신뢰 입력의 계획 오염 |
| 원리 | 기밀성·무결성 label 추적, 정보 숨김과 제한된 질의, 결정적 정책 강제 |
| 방식 | 런타임 IFC 및 planner 설계 |
| 취약점 | 외부 문서가 쓰기 동작을 좌우하거나 비공개 데이터가 공개 sink로 흐름 |
| 한계 | label·도구 모델·통합 가정, 보수적인 taint와 작업 수행성의 trade-off |
| 우리 질문 | 배포 설정의 label 근거가 충분한지 사전에 감사할 수 있나 |

**현재 프레임워크까지 확인:** [Microsoft Agent Framework 공식 문서](https://learn.microsoft.com/en-us/agent-framework/agents/security)는 FIDES를 실험적 기능으로 설명한다. 세션별 상태, 구체적 호출에 묶인 승인, principal 변경 시 재승인, MCP label 신뢰 설정까지 다룬다. 따라서 “출처나 승인 변경을 기존 방법이 전혀 처리하지 않는다”도 틀린다. 이 배포 구현은 문서 확인만 했고 설치·실행하지 않았다.

### R16. PCAS — 정책을 인과 그래프 위에 강제

[Policy Compiler for Secure Agentic Systems, 2026-02, v1](https://arxiv.org/html/2602.16708v1). 설계 개요·§6.1 가정 확인. Preprint.

| 질문 | 답 |
|---|---|
| 무엇 | agent 행동·정보 흐름의 명시적 정책 위반 |
| 원리 | 인과 의존 그래프와 Datalog 정책, 도구 경계의 reference monitor |
| 방식 | 정책 컴파일 + 계측된 런타임 강제 |
| 취약점 | 원치 않는 데이터 전파와 행동 연쇄 |
| 한계 | 정책 관련 흐름을 계측해야 함. 임의 코드·파일·네트워크·공유 상태 우회에는 추가 격리·관측 필요 |
| 우리 질문 | 계측이 없거나 부분적인 환경에서 무엇을 결론 낼 수 있는지 범위를 명시할 수 있나 |

그래프나 결정적 정책 엔진을 만든다는 것 자체는 차별점이 아니다. v1의 공개 구현 계획과 현재 재현 가능 상태를 혼동하지 않는다. 이번 실행은 없다.

### R21. Scanning the Harness — 정적 감사 연구와도 직접 비교

[2026-09, v1](https://arxiv.org/html/2609.07360v1). §4.7·5·6 확인, harness-eval 구현 확인. Preprint.

| 질문 | 답 |
|---|---|
| 무엇 | agent/Skill/MCP 설정과 여러 구성요소를 가로지르는 보안 결함 |
| 원리 | repository parser, component graph, 규칙 기반 교차 검사와 판정 검토 |
| 방식 | 정적 감사; LLM adjudication은 실제 침해 재현과 구분 |
| 취약점 | 권한 모순, 없는 MCP 서버 참조, credential/network 결합 후보 |
| 한계 | 감사한 3,171개 repository에서 credential exfiltration 경로는 확인되지 않음. 사람의 독립 정답 판정·recall 측정 부재 |
| 우리 질문 | 연결 후보를 실제 정책 위반으로 과대 해석하지 않으면서 정확한 근거를 복원할 수 있나 |

이 연구는 **reference가 있다는 사실만으로 유출 경로라고 판단하면 오탐이 생긴다**는 직접적인 경고다. raw rule finding과 검토 후 확인된 결함을 같은 통계로 쓰지 않는다.

## 6. 공식 Skills over MCP가 바꾸는 위협 모델

[공식 stable 명세](https://github.com/modelcontextprotocol/ext-skills/blob/b0b3272f1d4c01a79c8171252c70b06dcada18bf/specification/stable/skills.mdx), [SEP-2640 병합](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2640), [공식 overview](https://modelcontextprotocol.io/extensions/skills/overview)를 확인했다. 2026-09-13 병합된 Final 확장이며, 모든 SDK·호스트가 지원한다는 뜻은 아니다.

**경로 A:** 로컬 Skill → 호스트 → MCP tools. **경로 B:** MCP server → Skill 지시·참조 파일 → 호스트의 MCP 또는 로컬 도구. B에서는 서버가 제공한 파일이 단순 데이터에서 호스트의 행동 지시로 사용된다.

| 명세가 이미 요구하는 것 | 아키텍처에 반영할 내용 |
|---|---|
| originating server identity와 Skill URI를 함께 식별 | 이름·URI만으로 로컬/원격 Skill을 합치지 않음 |
| manifest의 URI·digest·size와 받은 파일 검증 | 파일 묶음과 변경 범위 기록. digest는 서버 자체 제공의 일관성 자료이며 독립적 신뢰 인증이 아님 |
| 활성 Skill의 파일 묶음 유지, 변경 시 승인 무효화 | hash·승인·활성 상태를 함께 versioning |
| 원격 Skill의 host-side 실행·추가 권한은 명시적 승인 | 제공 서버의 신뢰와 로컬 실행 권한을 구분 |
| nested Skill activation과 cross-server resource 접근 통제 | 참조 파일 읽기와 새 Skill 활성화를 구분 |
| lazy retrieval, dynamic resources의 제한 | 일반 호스트가 접속만으로 모든 참조 파일을 미리 읽는 수집 설계를 피함 |

명세 준수 검사는 제품의 기본 요건이다. 기존 표준의 요구사항을 구현하는 것만으로 새 연구 방법이라고 주장하지 않는다.

**호스트 의미도 구분:** [Claude Code 공식 Skills 문서](https://code.claude.com/docs/en/skills)의 `allowed-tools`는 invocation turn의 사전 승인이고, 사용할 수 있는 전체 도구를 제한하는 목록이 아니다. 다음 사용자 메시지에서 이 grant는 해제되지만 Skill 내용은 컨텍스트에 남을 수 있다. 따라서 **지시가 남는 기간과 권한이 유지되는 기간은 별도 상태**로 표현해야 한다. 이 설명을 모든 Skill 호스트의 공통 의미로 일반화하지 않는다.

## 7. 사례 증거를 섞지 않기

- Invariant의 GitHub MCP 시연은 비신뢰 issue가 정상 기능을 조종하는 근거다. SKILL.md가 쓰인 실피해 사건으로 바꾸어 말하지 않는다.
- Puppet·Skill-Inject는 악성 metadata 또는 악성 Skill이 있는 실험이다. ‘각각 benign’인 표본과 따로 평가한다.
- [Check Point의 CVE-2025-59536·CVE-2026-21852 공개](https://research.checkpoint.com/2026/rce-and-api-token-exfiltration-through-claude-code-project-files-cve-2025-59536/)는 project 설정·hook·MCP를 통한 경계 문제와 수정 사례다. 구성요소가 모두 정상이라는 가정의 증거나 현장 피해 통계로 쓰지 않는다.

**이 조사에서 확정하지 못한 것:** 이름이 확인된 benign Skill + benign MCP의 실제 현장 피해 사건, 기존 모든 방어가 실패하는 새 공격, 우리 분석기의 일반화된 우월성. 연구 질문은 이 공백을 입증하는 실험으로 이어져야 한다.
