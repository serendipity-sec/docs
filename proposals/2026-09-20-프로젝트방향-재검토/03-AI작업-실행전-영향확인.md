# 후보 3 AI 작업의 실행 전 영향 확인과 승인

기록일: 2026-09-20 · 상태: 비교 후보 · 최종 채택 및 구현 착수 미정

## 사용자 관점의 출발점

“AI가 일을 대신해 주는 건 좋은데, 실제로 무엇이 바뀌는지 먼저 알고 싶어.”

초기 예시는 메일·일정 정리였지만, 김민우는 더 넓게 **AI에게 대략적인 목표를 맡기고 여러 작업을 수행하게 할 때의 영향 확인**에 가치를 느꼈다.

김민우의 이번 반응:

> 3번은 좀 더 꼭 메일이나 일정 정리 뿐 아니라 진짜 AI로 사실 대충 맡겨놓고 많이 하자너 그런거 할때 미리 알고 있음 좋을거 같다는 생각도 들긴 하네

메일·일정은 설명용 예시다. 최종 범위를 그 두 분야로 제한하기로 결정하지 않았다. 동시에 모든 AI 앱·터미널·외부 서비스를 통제할 수 있다고 가정하지도 않는다.

## 제품 가설

AI가 작업을 제안하고, 사용자가 실제 대상과 영향을 확인·수정한 뒤, 서버가 확정된 작업을 실행한다. 작업 완료 후에는 승인 내용과 실제 결과를 대조한다.

입력은 사용자의 목표, 선택한 작업 환경·연결 도구, 허용 범위다. 출력은 실행 예정 작업, 변경·전송 대상, 사용자 결정, 실행 결과와 차이다.

대상 작업 후보:

- 파일 정리: 이동·이름 변경·삭제 대상과 덮어쓰기 충돌.
- 데이터 정리: 수정·삭제되는 행과 영향 범위.
- 코드·설정 변경: 수정할 파일, 적용할 변경, 후속 실행.
- 외부 작업: 게시·발송·업로드 대상, 수신자와 전송 내용.

이는 확장 가능한 사례 목록이다. 첫 시연과 평가에 사용할 작업군은 별도로 고른다.

## 발전시켜 볼 핵심

AI가 작성한 “안전하게 정리하겠습니다”라는 설명을 승인 화면에 그대로 내보내는 것으로 끝내지 않는다. 실행기가 받을 실제 명령·인자·대상에서 미리보기를 만들어야 한다.

사용자가 파일 세 개의 이동만 승인했으면, 이후 모델이 네 번째 파일 삭제를 추가해도 같은 승인으로 실행되지 않게 한다. 승인과 실행의 대상·내용을 묶는 것이 핵심 기술 후보다.

다음 사항을 함께 검토한다.

- 무엇을 읽고, 바꾸고, 삭제하고, 외부로 전송하는지 구분한다.
- 사용자가 일부 작업을 제외하거나 대상을 수정할 수 있게 한다.
- 승인 뒤 대상 파일·레코드가 바뀌면 재확인을 요구할 조건을 정의한다.
- 중복 요청·재시도에서 같은 작업이 두 번 실행되지 않도록 한다.
- 다단계 작업이 일부만 성공했을 때 현재 상태를 명확히 보여 준다.
- 복구 가능한 작업은 복구 방법을 제공하고, 발송처럼 되돌릴 수 없는 효과는 구분한다.

이 모두가 확정 구현 범위는 아니다. 외부 프로그램이나 임의 셸 스크립트의 모든 영향을 실행 전에 정확히 예측하는 것은 별개 문제다. 미리보기로 확정할 수 없는 효과는 불확실로 표시하거나 지원 대상에서 제외하는 규칙이 필요하다.

## 시연 후보

1. 합성 파일이 있는 작업 공간에서 “지난 자료를 정리해 줘”라고 요청한다.
2. 이동·이름 변경·삭제 예정 목록과 충돌을 보여 준다.
3. 사용자가 중요한 파일을 제외하고 일부 대상을 수정한다.
4. 확정된 작업만 실행해 전후 상태를 대조한다.
5. 승인 뒤 대상이 바뀌거나 실행 내용이 달라지는 사례에서 재확인·거절 처리를 보여 준다.

두 번째 시연으로 데이터 정리나 외부 전송을 검토할 수 있다. 현재 메일·일정·파일 중 어느 것을 우선할지 결정하지 않았다.

## 웹어플리케이션보안 산출물

웹 UI는 작업 요청, 영향 미리보기, 부분 승인·수정, 실행 상태와 결과 대조를 제공한다. 서버의 정책·실행 계층이 승인된 작업을 검증하고, 지원 도구 어댑터가 실제 작업을 수행하는 구조를 검토한다.

웹서비스가 볼 수 없는 경로에서 AI가 직접 실행한다면 통제 효과를 보장할 수 없다. 통제 가능한 실행 경로와 우회 가능한 경로를 위협 모델에 명시해야 한다.

설계·점검 대상은 작업별 인가, 승인 위조·재사용, 승인 후 내용 변경, 동시성, 중복 실행, 명령·경로 주입, 연결 자격증명 관리, 감사 로그의 무결성과 민감정보다. CSRF 등 승인 요청 자체에 대한 웹 공격도 포함한다.

최종 결과물 후보는 작업 검토·실행 웹서비스, 지원 도구 연결, 승인과 실행의 일치 검증, 상태 전이·위협 모델, 공격·실패 사례 점검 리포트, 사용자 영향 이해도 평가다.

## 기존 도구와 아직 모르는 것

[LangChain Human-in-the-loop 공식 문서](https://github.com/langchain-ai/docs/blob/main/src/oss/langchain/human-in-the-loop.mdx)는 도구 호출의 승인·수정·거절을 지원한다고 설명한다. 확인일: 2026-09-20. 따라서 승인 버튼이나 실행 중단 자체를 새 기술로 주장하지 않는다.

기존 에이전트 호스트·자동화 서비스의 미리보기, 승인, 변경 비교 기능과 상세 비교해야 한다. 이번 세션에서는 기능의 우열이나 시장 공백을 입증하지 않았다.

아직 확인할 질문:

- 사용자가 AI에 맡겼다가 “실행 전에 알았으면 좋았겠다”고 느끼는 작업은 무엇인가?
- 기존 승인 화면에서 사용자가 이해하기 어려운 정보가 구체적으로 무엇인가?
- 실제 영향을 정확히 미리 보여 줄 수 있는 첫 작업군은 무엇인가?
- 사용자가 매번 승인하는 부담보다 얻는 이익이 큰가?
- 승인한 내용과 실제 실행을 연결하는 기술이 기존 도구보다 어떤 점에서 개선되는가?
- 사용자가 이용하는 AI 환경과 연결할 수 있는가? 자체 데모 에이전트에서만 되는 기능인지 구분할 수 있는가?

## 평가 제안

일반적인 도구 호출 승인 화면과 비교해 사용자가 영향 대상을 얼마나 정확히 이해하는지, 잘못된 작업을 얼마나 발견하는지, 검토 시간이 얼마나 드는지 평가한다.

시스템 측면에서는 승인 외 작업의 거절, 대상 변경 후 재확인, 중복 실행 방지, 부분 실패 표현, 실제 전후 상태와 보고서의 일치 여부를 확인한다. 모델이 계획을 말한 것과 실제 효과가 발생한 것을 구분한다.

계속 발전시킬 근거는 사용자가 과도한 부담 없이 실제 영향을 이해하고 원치 않는 작업을 줄이는 증거다. 기존 승인 기능을 보기 좋게 포장하는 수준이면 재검토한다.
