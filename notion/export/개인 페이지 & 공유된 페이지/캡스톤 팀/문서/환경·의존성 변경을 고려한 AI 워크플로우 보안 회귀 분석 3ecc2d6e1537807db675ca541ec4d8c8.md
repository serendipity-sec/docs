    ### 소스코드에서 확인한 구체적인 비교 포인트
    
    FlowGuard는 이름만 확인한 것이 아니라, 조사 시점의 커밋 `03b348d…`에서 하위 워크플로우 관련 규칙을 읽었어.
    
    해당 규칙은 트리거에서 하위 워크플로우 호출까지 경로를 추적하면서, `VALIDATION_NODES`에 해당하는 노드를 만나면 탐색을 중단해. 이 집합에는 **IF·Switch·Filter**가 들어 있어. 해당 규칙 함수 안에서는 하위 워크플로우 본문이나 실제 연결 계정의 권한까지 조회하지 않아.
    
    여기서 바로 실험할 수 있는 질문이 나와.
    
    > **“중간에 IF 노드가 있다”와 “그 IF가 해당 위험을 실제로 제한한다”를 구분할 수 있는가?**
    > 
    
    예를 들어 `언어가 한국어인가?`라는 조건은 외부 전송이나 기밀정보 접근을 제한하지 않아. 반대로 `수신자가 승인된 내부 계정인가?`라는 조건은 정책과 연결될 수 있지.
    
    이것은 **특정 규칙의 코드 검토로 얻은 비교 가설**이야. 아직 “FlowGuard의 취약점을 실험으로 재현했다”는 뜻은 아니야. 우리 프로젝트에서는 이 차이를 테스트 데이터와 실행 결과로 보여줘야 해.

    ## 3. 제안 프로젝트: WorkflowDelta
    
    ### 한 문장 정의
    
    > **AI 워크플로우와 하위 의존성, 연결 환경을 함께 분석해 변경으로 새로 생긴 보안 위험과 재검토 필요성을 설명하는 도구.**
    > 
    
    초기 사용자는 일반 템플릿 구매자보다 **여러 워크플로우를 구축·관리하는 개발팀, 자동화 구축사, 사내 플랫폼·보안팀**으로 설정하는 것을 권해. 이들이 실제로 겪는 검토 비용과 지불 의사는 인터뷰로 확인해야 할 가설이야.
    
    ### 분석 대상부터 다르게 정의한다
    
    검사 입력을 워크플로우 파일 하나가 아니라 다음 묶음으로 정의하자.
    
    **W + D + E + P**
    
    여기서 **W**는 부모 워크플로우, **D**는 하위 워크플로우·도구·모델 등 의존성, **E**는 실제 또는 선언된 권한·데이터·전송 대상에 관한 환경 증거, **P**는 조직의 보안 정책이야.
    
    예를 들어 부모 워크플로우의 JSON이 그대로여도 다음 변경은 의미가 있어.
    
    > 하위 워크플로우가 공개 FAQ 대신 고객 계약서를 조회하게 됐다.
    > 
    > 
    > 연결 계정이 공개 자료 전용 계정에서 기밀자료 접근 계정으로 바뀌었다.
    > 
    > 외부 전송 대상이 승인된 테넌트에서 다른 테넌트로 바뀌었다.
    > 
    
    이때 **권한이 넓어졌다는 사실**, **기밀자료에 도달할 수 있는 경로**, **실제로 데이터를 읽거나 보냈다는 증거**는 따로 표시해야 해. 세 가지를 같은 의미로 취급하면 과장된 경고가 돼.
    
    ### 차별화 가설은 세 가지로 제한한다
    
    **① 환경을 포함하면 놓치는 위험이 줄어드는가?**
    
    같은 부모 워크플로우라도 하위 구성과 환경에 따라 판정이 달라져야 해. 파일만 검사하는 방식보다 환경·의존성 변경으로 새로 생긴 위험을 더 잘 찾는지 비교하자.
    
    **② 변경의 보안 의미를 해석하면 불필요한 재검토가 줄어드는가?**
    
    노드 위치 변경과 외부 수신자 변경을 구분하고, 무관한 IF와 실제 권한 제한 조건을 구분하자. 모든 변경에 경고하는 방식보다 검토 부담을 줄이되 위험을 놓치지 않는지가 핵심이야.
    
    **③ 이전 검증 결과를 어디까지 재사용할 수 있는가?**
    
    변경된 의존성에 영향을 받는 경로와 정책을 찾아 재검사하자. 초기에는 전체 재검사를 해도 되고, 후반에 선택적 재검사로 최적화해도 돼. **전체 분석과 같은 판정을 유지하면서 검사 비용을 줄이는지** 측정하면 추가 연구 기여가 될 수 있어.
    
    **추천하는 주된 기여는 ①과 ②야. ③은 일정이 허용될 때 추가하는 편이 안전해.**

    ## 4. MVP는 어디까지 만들 것인가?
    
    처음부터 모든 SaaS, MCP, n8n, LangGraph를 지원하면 분석 정확도를 입증하기 어려워. **n8n의 고정된 한 버전과 제한된 노드 집합**으로 시작하자.
    
    | 영역 | MVP에 포함 | 초기에는 제외 |
    | --- | --- | --- |
    | **입력** | 부모·하위 워크플로우 JSON 번들, 환경 프로필, 정책 파일 | 모든 플랫폼 자동 발견 |
    | **의존성** | 고정 ID로 참조하는 하위 워크플로우, 모델·도구 연결 | 임의 코드로 생성되는 모든 동적 의존성 |
    | **환경** | 권한·데이터 분류·허용 목적지를 명시한 프로필, 증거 수준 구분 | 모든 OAuth·SaaS 권한의 자동 수집 |
    | **분석** | 약 12~15개 노드 유형, 제한된 표현식, 필드 흐름, 변경 영향 | 임의 JS/Python의 완전한 의미 해석 |
    | **검증** | 합성 데이터·모의 도구를 이용한 재현 시험 | 운영 데이터로 공격 실험 |
    | **결과** | 위험 경로·깨진 가정·미확인 영역·재검토 여부, JSON/SARIF/HTML | 근거 없는 종합 보안 점수 |
    | **제어** | CI 또는 승인 단계에서 사용할 판정 결과 | 모든 직접 편집·배포 경로를 통제하는 런타임 보안 플랫폼 |
    
    ### 정책은 여섯 개면 충분해
    
    초기 정책은 다음 범위로 고정하는 것을 권해.
    
    | 정책 | 검사할 내용 |
    | --- | --- |
    | **WD01: 기밀정보 전송** | 기밀자료가 허용되지 않은 모델 제공자·수신자·테넌트로 전달될 가능성이 있는가? |
    | **WD02: 외부 입력의 행동 통제** | 낮은 신뢰 입력이 민감 도구의 대상 자원·수신자·외부 목적지를 결정하는가? 별도의 제한이 있는가? |
    | **WD03: 의존성·권한 변화** | 부모가 그대로여도 하위 워크플로우나 권한 변경으로 새로운 민감 경로가 생겼는가? |
    | **WD04: 승인 우회** | 중요한 작업으로 가는 경로가 승인을 우회하거나, 승인 후 실행 인자가 달라지는가? |
    | **WD05: 기존 검증 무효화** | 도구·모델·엔드포인트·정책 변경으로 이전 검토의 가정이 더는 유효하지 않은가? |
    | **WD06: 미확인 상태 처리** | 중요한 경로에 미지원 코드·불명확한 권한·동적 참조가 있는데도 안전으로 통과시키려 하는가? |
    
    하드코딩된 키 탐지나 알려진 패키지 취약점 확인은 필요한 기본 기능이지만, **연구 기여로 내세우기보다 기존 도구 결과를 활용하는 영역**으로 두는 편이 좋아.

    ## 5. 구현 구조와 중요한 설계 결정
    
    전체 구조는 다음 정도면 돼.
    
    ```
    워크플로우 번들 + 환경 증거 + 정책
                      ↓
              파싱·의존성 해석
                      ↓
           실행·데이터·권한 관계 분석
                      ↓
              변경 전후 위험 비교
                      ↓
          선택적 모의 실행·재현 시험
                      ↓
       증거 보고서 + 재검토/배포 판정
    ```
    
    ### A. 그래프는 그리기 위한 것이 아니라 분석하기 위한 것이다
    
    실행 순서, 데이터 전달, 도구 호출 가능성, 자격증명 사용 관계를 구분해야 해.
    
    특히 AI Agent에 연결된 도구를 일반적인 `A → B → C` 실행 순서와 동일하게 처리하면 안 돼. 우리 모델에서는 **“Agent가 호출할 수 있다”는 관계**를 별도로 두고 보수적으로 분석하자.
    
    또한 데이터에 다음 두 속성을 따로 붙이는 것을 제안해.
    
    **기밀성:** 공개 / 내부 / 기밀 / 미확인
    
    **입력 신뢰:** 신뢰하는 사용자 / 외부 입력 / 미확인
    
    기밀성은 유출 위험을, 입력 신뢰는 외부 콘텐츠가 행동을 통제할 위험을 판단하는 데 사용해. **LLM이 요약했다는 이유만으로 기밀 라벨을 제거하지 않는 것**도 정책으로 명시하자.
    
    ### B. “권한을 확인했다”는 표현에 엄격해야 한다
    
    환경 프로필에는 다음을 구분해서 저장해야 해.
    
    > 설정에 선언된 권한 / 제공자 API로 확인한 사실 / 테스트에서 관측한 행동 / 확인하지 못한 사실
    > 
    
    수동으로 작성한 환경 파일은 **선언된 환경**이지 실제 권한 검증 결과가 아니야. 초기 MVP는 모의 환경으로 연구 질문을 검증하고, 이후 지원 가능한 SaaS 한 곳에만 읽기 전용 증거 수집기를 붙이는 편이 현실적이야.
    
    원시 API 키나 OAuth 토큰을 분석 서버로 모으는 구조는 피하자. 자격증명 참조, 계정·테넌트 식별자, 권한 증거의 출처와 수집 시각만 보관하는 설계를 권해.
    
    ### C. 승인 기록은 환경과 버전에 묶는다
    
    검증 기록에는 최소한 다음 정보가 필요해.
    
    > 부모·하위 워크플로우 해시, 환경 증거 식별자, 정책 버전, 분석기 버전, 테스트 버전, 검사 시각, 미확인 항목
    > 
    
    이 중 중요한 부분이 바뀌면 기존 통과 기록을 재사용하지 않고 재평가하는 방식이야.
    
    다만 **기록을 서명했다고 워크플로우가 안전해지는 것은 아니야.** 출처·무결성과 안전성은 다른 문제이고, 구성목록·provenance는 이미 CycloneDX와 SLSA에서 다루고 있으므로 기존 개념을 활용하면 돼. [CycloneDX](https://cyclonedx.org/capabilities/mlbom/)
    
    ### D. 보고와 실제 차단을 구분한다
    
    MVP의 CI 실패 결과가 실제 배포를 막으려면 배포 경로가 그 검사를 반드시 거쳐야 해. 운영자가 직접 수정하거나 API로 우회 배포할 수 있다면 **“배포 차단 기능”이 아니라 “배포 판단에 사용할 검사 결과”**라고 설명해야 해.
    
    검사 직후 환경이 바뀌는 문제도 남아. 보호된 배포 경로에서는 실행 직전 스냅샷 대조와 증거 유효기간을 적용할 수 있지만, **관측할 수 없는 원격 서버 내부 행동까지 보증하는 목표는 제외**하자. 도구 호출의 안전성과 실제 도구 구현의 안전성 사이의 간극은 관련 연구에서도 별도로 다뤄지고 있어. [arXiv](https://arxiv.org/abs/2605.16976)

    ## 6. 발표에서 보여줄 대표 데모
    
    다음 하나의 시나리오를 처음부터 끝까지 완성하면 프로젝트의 메시지가 분명해져.
    
    ### 1단계: 공개 자료만 쓰는 정상 구성
    
    부모 워크플로우가 공개 FAQ를 조회하는 하위 워크플로우를 호출하고, 정해진 정책 안에서 응답을 만든다.
    
    **목표 결과:** 지정된 테스트 환경과 지원 범위에서 통과.
    
    ### 2단계: 부모는 그대로인데 하위 구성만 변경
    
    하위 워크플로우 또는 연결 권한을 바꿔 고객 계약서에도 접근할 수 있게 한다. 해당 자료를 외부로 전달할 수 있는 경로도 존재하도록 구성한다.
    
    **목표 결과:**
    
    > “부모 워크플로우 변경은 없지만, 하위 구성 변경으로 기밀자료가 외부로 전달될 수 있는 새 경로가 생겼습니다.”
    > 
    
    ### 3단계: 무관한 IF를 추가
    
    중간에 `언어가 한국어인가?`라는 IF를 넣는다.
    
    **목표 결과:** 보안 조건이 아니므로 기존 위험을 제거하지 않음.
    
    ### 4단계: 실제로 위험을 제한하는 수정
    
    필요한 필드만 전달하고, 수신자를 제한하거나 실행 내용에 결부된 승인을 추가한다.
    
    **목표 결과:** 동일한 모의 시험을 다시 실행해 해당 정책 위반 경로가 해소됐는지 확인.
    
    ### 5단계: 환경 증거 만료
    
    권한 증거의 유효기간을 만료시킨다.
    
    **목표 결과:** 이전 통과 결과를 무조건 재사용하지 않고 재검토 요청.
    
    이 데모에서는 **합성 계약서와 모의 메일함만 사용**하자. 정적 분석 결과는 “가능한 위험”, 실제 테스트에서 확인한 결과는 “모의 환경에서 재현됨”으로 구분해야 해.

    ## 7. 차별점을 입증할 평가 설계
    
    여기가 프로젝트의 핵심이야. 화면보다 **기존 방식 대비 무엇을 더 잘했는지 보여주는 데이터**가 중요해.
    
    ### 데이터셋: 변경 사례를 중심으로 만든다
    
    초기 목표로 **30개 독립 워크플로우 계열 × 6개 변경 비교쌍 = 180쌍**을 제안해.
    
    계열마다 위험 변화 3개, 무해 변화 2개, 미확인 변화 1개를 만들면 **위험 90쌍·무해 60쌍·미확인 30쌍**이 돼. 이 수치는 수집 완료 실적이 아니라 프로젝트 계획이야.
    
    변경에는 부모 불변·하위 변경, 권한만 변경, 외부 목적지 변경, 승인 우회, 무관한 IF, 유효한 제한 조건, 레이아웃 변경 등을 포함하자.
    
    중요한 것은 **같은 워크플로우의 변형을 개발용과 테스트용에 나눠 넣지 않는 것**이야. 계열 단위로 분리하고, 두 명이 도구 출력을 보지 않은 상태에서 정책 위반 여부를 라벨링해야 해.
    
    공개 템플릿을 사용할 때는 출처·버전·재배포 조건을 확인하고, 실제 계정 권한을 모르는 부분은 가상의 환경 조건으로 명시해야 해.
    
    ### 비교군은 두 종류가 필요하다
    
    **외부 도구 비교:** FlowGuard, Agentic Radar, n8n Audit의 지원 범위에서 실제 결과를 비교한다. 서로 지원하지 않는 기능을 무조건 탐지 실패로 계산해서는 안 돼.
    
    **우리 방법의 구성요소 비교:** 동일한 분석기를 다음처럼 축소해 비교한다.
    
    > 부모만 분석 → 하위 의존성 추가 → 환경 증거 추가 → 조건 의미 분석 추가
    > 
    
    이렇게 해야 성능 차이가 새로운 구성요소 때문인지 설명할 수 있어.
    
    변경 기반 재검사를 구현한다면, **동일한 엔진의 전체 재검사 결과**를 기준으로 판정 일치도와 비용을 비교하자.
    
    AgentDojo의 정상 업무·공격 동시 평가 방식은 참고할 수 있지만, 그대로 가져와서 n8n 공급망 변경 벤치마크라고 부를 수는 없어. [arXiv](https://arxiv.org/abs/2406.13352)
    
    ### 사전 목표
    
    아래 숫자는 **달성한 성능이 아니라 실험 전에 정할 도전 목표**야.
    
    | 지표 | 제안 목표 |
    | --- | --- |
    | 지원 범위에서 위험 변화 탐지 정확도 | Precision·Recall 각각 90% 이상 |
    | 중요 경로의 UNKNOWN을 안전으로 통과 | 단위 테스트에서 0건 |
    | 불필요한 재검토 | “변경 시 무조건 재검토” 대비 30% 감소를 목표로 하되, 위험 탐지율도 함께 보고 |
    | 변경 기반 재검사 | 공개 테스트 집합에서 전체 재검사와 같은 판정, 검사 비용 30% 감소 목표 |
    | 설명의 유용성 | 선택적으로 8~12명에게 위험 이해율·검토 시간 측정 |
    | 분석 범위 | 지원 노드·경로 비율과 미확인 원인을 별도 공개 |
    
    **UNKNOWN을 정확한 탐지로 부풀리면 안 돼.** 또한 전부 차단해서 안전해 보이는 도구가 되지 않도록 정상 작업 성공률과 검토 부담을 같이 측정해야 해.

    ## 8. 12주 개발 계획과 전환 기준
    
    | 기간 | 주요 작업 | 종료 기준 |
    | --- | --- | --- |
    | **1~2주** | 선행 도구 버전 고정·실행, 예제 10개, 사용자 인터뷰, 정책 확정 | 단순 검사 이상으로 검증할 사례 최소 3개 확보 |
    | **3~4주** | 파서·하위 의존성 해석·분석 그래프 구현 | 고정 하위 호출과 미지원 동적 참조를 구별 |
    | **5~6주** | 환경 증거·정책 6개·제한적 조건 분석 | 부모 불변·권한 변화·무관한 IF 사례 판별 |
    | **7~8주** | 변경 비교·검증 기록·모의 재현·보고서 | 대표 데모 전체 동작 |
    | **9~10주** | 독립 라벨링·비교군·구성요소별 실험 | 정확도·분석 범위·미확인·재검토 비용 보고 |
    | **11~12주** | 검토자 평가·오류 수정·문서·데모 정리 | 다른 사람이 재실행할 수 있는 산출물 완성 |
    
    역할은 **분석 코어**, **환경·의존성·통합**, **데이터·평가·보고서**로 나누는 것이 적절해. 라벨링과 구현 결과 검토는 서로 교차 담당해야 해.
    
    진행 여부도 중간에 판단하자.
    
    **2주차에** 이미 존재하는 도구와 구분되는 사례를 찾지 못하면, 독립 제품보다 **Agentic Radar나 FlowGuard 확장 프로젝트**로 전환할 수 있어.
    
    **6주차에** 동적 코드와 권한 미확인 때문에 경고가 과도해지면, 안전하다고 추정하는 대신 **지원 노드와 환경 범위를 줄여야 해.**
    
    최종적으로 차별화가 입증되지 않더라도 **재현 가능한 n8n 보안 변경 벤치마크**는 별도의 프로젝트 성과가 될 수 있어. 다만 그것이 논문으로 충분한지는 데이터의 독창성과 평가 품질에 달려 있어.
