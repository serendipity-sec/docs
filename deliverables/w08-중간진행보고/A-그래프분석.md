# 중간 진행 보고 — A: 그래프·변경·영향 경로 분석 (김민우)

## 1. 담당 범위

A는 변경 전후 n8n workflow와 입력 담당이 만든 노드 의미 정보(Handoff)를 받아 세 가지를 계산하고, 그 결과를 `analysis.json`으로 B(검색·검사 계획)에 넘긴다.

1. 노드 사이의 실행·데이터 관계 그래프
2. 원본 위치(JSON Pointer)가 붙은 변경 목록
3. 각 변경이 응답·외부 요청·하위 workflow 호출·마지막 노드까지 닿을 수 있는 정적 영향 경로

모든 관계와 경로는 정적 가능성이다. 실제 실행 효과와 보안 위험 판정은 A의 출력에 넣지 않는다.

## 3. 결과 예시

**선정 사례 n8n-claw (Handoff 전 사전 확인).** 기능 추가 쌍 `9ebf36b → 63a7f2e`에서 A는 변경 5개를 원본 위치와 함께 찾았다.

- Memory Delete·Update 추가
- 두 도구 → AI Agent `ai_tool` 연결 추가
- Memory Search 안내 문구 변경

변경마다 `도구 → AI Agent → 이후 노드` 영향 경로를 만들었다(그림: `deliverables/w09-중간발표/A-n8n-claw-분석.png`). 첫 보완 쌍 `4d1b1b7 → eb6d7bc`에서는 도구 4개의 `jsCode`·설명 변경 6개를 찾았다. 소유권 검사가 들어간 `jsCode` 내부 의미는 A가 판단하지 않고, C의 정적 검사 대상으로 넘긴다.

**팀 예제 (문의 분류).**

- If 노드의 임계값을 바꾸면 경로 두 개가 나온다.
  - `priority → standard → merge → summary`(하위 workflow 호출)
  - `… → summary → result`(마지막 노드)

  두 경로 모두 "하위 workflow 안으로는 따라가지 않았다"는 한계가 붙는다.
- `split` 노드 이름만 바꾸고 참조를 고치지 않으면, 수정 후 그래프에서 사라진 참조(`split → urgent`, `split → standard`)를 수정 전 그래프에서 따라가 결과 노드까지의 경로를 남긴다.

## 4. 확인한 한계

- **정책 규칙 연결 없음**: 정책이 자연어뿐이라 경로에 `policy_rule_ids`를 붙일 근거가 없다. 입력 담당과 구조화된 정책·자원 대응표 형식을 협의 중이다(#48·#49).
- **AI agent 노드 의미가 아직 없음**: 선정 사례 n8n-claw도 AI 연결이 있어 의미 어댑터가 노드 전부를 미지원으로 처리한다. 그래서 영향 경로의 지원 범위(`support`)는 모두 `UNKNOWN`이고, 효과를 모르는 노드가 모두 끝점이 되어 경로가 상한(20개)에 걸린다. 입력 담당에게 필요한 노드 의미(AI Agent, toolCode, 채팅 모델)를 요청했다(#48·#49).
- **아직 없는 관계**: 권한·능력, 의존성·보호, 지시 영향. ID가 바뀐 노드의 구조 대응과 code 노드 내부 의미도 아직 없다.
- **공용 DB 저장 없음**: 저장 인터페이스와 파일 구현까지 했다. DB adapter는 공통 migration 틀이 정해지면 붙인다.

## 5. 다음 계획 (중간발표 10/30까지)

1. n8n-claw Handoff가 오면 A 분석을 실행해 실제 `analysis.json`과 재현 명령을 B에 넘긴다.
2. 정책 binding 형식이 정해지면 #61의 연결 로직에 변환을 붙여 경로에 정책 규칙 ID를 연결한다.
3. AI 하위 노드 연결을 권한·지시 영향 관계로 분류한다(검증기 범위 조정 합의 후).
4. 공용 DB adapter와 A 테이블 migration을 B의 migration 틀 위에 구현한다.
5. B가 실제 A 결과를 수작업 수정 없이 읽어 계획을 만든 기록을 남긴다.
