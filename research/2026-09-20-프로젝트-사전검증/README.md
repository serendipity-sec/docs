# AI 워크플로 신뢰 플랫폼 사전검증 조사

조사 기준일: **2026-09-20 (Asia/Seoul)**  
대상: serendipity의 「AI 워크플로 구성요소의 공급망 보안 검사 및 공유 플랫폼」 기획

## 이번 조사가 답하는 것

최종 목표는 **사용자가 외부 AI 워크플로 구성요소를 보안 근거에 따라 믿고 사용할 수 있는 플랫폼**이다. 보안 점검은 그 목표의 핵심이다. 다만 검사한 버전·구성·실행 환경과 검사 범위를 기록해야, 검사 결과를 실제 사용 대상에 적용할 수 있다. “문제가 발견되지 않았다”와 “어떤 환경에서도 취약점이 존재하지 않는다”를 같은 의미로 사용하지 않는다.

후속 요청에 따라 질문 **1·2·4·5를 각각 독립 문서로 작성**했다. 질문 3의 사고 사례·공격 재현은 이번 조사 범위에서 제외했다. 번호는 기존 질문과 대응하도록 유지한다.

| 질문 | 현재 결론 | 문서 |
|---|---|---|
| 1. 외부 구성요소를 실제로 가져다 쓰는가? | MCP의 배포·다운로드와 Skills의 프로젝트 내 재사용은 확인된다. 플러그인·워크플로의 유통 기능과 업무 사용도 확인되지만, 외부 템플릿을 가져다 쓰는 전체 사용자 비율은 알 수 없다. | [01 — 실사용과 도입 근거](01-외부구성요소-실사용과-도입근거.md) |
| 2. 출처·권한·변경을 파악하기 어려운가? | 여러 계층의 정보를 결합해야 하는 구조는 확인된다. 현재 도구로 해결되는 부분도 많다. 우리 대상 사용자의 실제 소요 시간·오류율은 미측정이다. | [02 — 출처·권한·변경 검토](02-출처-권한-변경정보의-검토공백.md) |

## 근거를 읽는 방법

- **문헌 확인**: 원문 논문·사양·제작사 문서·공개 소스에서 확인했다. 제품 기능의 문헌 확인은 우리가 실행해서 검증했다는 뜻이 아니다.
- **업체 보고**: 설치 수·고객 사례·제품 성능 등 업체가 발표한 수치다. 독립적으로 재측정하지 않았다.
- **해석**: 확인된 자료를 바탕으로 한 프로젝트 관점의 판단이다.
- **미검증 / 제안**: 우리 팀이 앞으로 확인해야 할 가설·평가 설계·기능 후보다.

출처 ID는 문서 간 공통이다. [출처·검색·검증 기록](출처와-조사기록.md)에 URL, 자료 성격, 사용할 수 있는 주장과 한계를 정리했다. [저장소 확인 기록](evidence/repository-snapshots.json)은 GitHub API에서 확인한 커밋과 릴리스 정보를 담는다. 웹 원문 전체를 별도로 보관한 아카이브는 아니다.

## 조사 방법과 수행 범위

단순 검색 결과 요약으로 끝내지 않고 다음 순서로 조사했다.

1. **기존 자료 대조**: 저장소의 통합조사·제안서·생태계·선행조사 문서를 읽고 검증할 주장을 추렸다.
2. **실사용 근거 탐색**: 등록 개수, 다운로드, 저장소 재사용 흔적, 업무 사용 사례를 서로 구분했다.
3. **원문 확인**: 논문의 수집 방법과 한계, 공식 사양, 공개 저장소의 실제 필드와 현재 문서를 확인했다.
4. **반대 근거 탐색**: 잠금 파일·서명·기존 baseline·증거 묶음·통합 거버넌스처럼 우리 기능과 겹치는 사례를 추가 조사했다.
5. **평가 가능성 검토**: 공개 데이터의 라벨 출처, 대조군, 측정 단위와 실패 기준을 정리했다.

이번에 수행한 것은 공개 자료 조사와 읽기 전용 소스·메타데이터 확인이다. **보안 스캐너 설치 및 실행, 실제 공격 재현, 사용자 인터뷰, 사용자 실험은 수행하지 않았다.** 이 문서의 평가 절차와 예시 결과 형식은 실행 결과가 아니다. 체계적 문헌고찰의 전체 검색 집합이나 시장 전체를 망라했다고 주장하지 않는다.

## 이전 문서에서 보정해야 할 해석

기존 문서와 원본 자료는 보존한다. 다음 사항은 이번 추가 확인을 우선 적용한다.

| 기존 자료를 읽을 때 생길 수 있는 해석 | 이번 조사에서 적용할 기준 |
|---|---|
| Skill은 Markdown이어서 버전·무결성 관리가 불가능하다. | 일반 Git 관리가 가능하며 Vercel Skills에도 출처·해시를 기록하는 잠금 파일이 있다. |
| MCP Registry에는 출처 확인 기능이 없다. | 네임스페이스 소유 확인은 제공한다. 코드의 안전성 검사는 별개의 책임이다. |
| 기존 도구에는 규칙 파일 검사·변경 감지·공유 가능한 검토 근거가 없다. | AgentShield, SkillSpector, DefenseClaw, Docker, NVIDIA의 기능과 직접 겹친다. |
| findings diff와 capability diff가 다르므로 차별성은 이미 입증됐다. | 개념적 구분은 유효하다. 기존 제품이 실제 과업을 못 해결한다는 증거는 별도로 필요하다. |
| 공개 데이터셋의 holdout이 있으므로 객관적 보안 성능 평가가 해결됐다. | 라벨이 자동 판정인지, 계보·복제본 누출이 있는지부터 확인해야 한다. |
| 스캐너 불일치율이나 특정 연구의 우회율이 모든 현재 제품의 실패율이다. | 대상 버전·입력·판정 기준이 다른 결과를 일반화하지 않는다. |

## 프로젝트에서 먼저 결정할 것

**제안:** 첫 실증 대상은 개발용 호스트 한 종류에서 함께 사용하는 Skill·MCP 설정·프로젝트 정책으로 좁힌다. “기존 검토에서 승인한 구성과 지금 구성의 차이를 근거까지 추적할 수 있는가”를 작은 과업으로 비교한다. n8n·Dify는 확장 가능성을 검토하되 서로 다른 권한 체계를 무리하게 하나의 안전 점수로 합치지 않는다.

채택 여부는 기능 수가 아니라 다음 관문으로 판단한다.

1. 실제 대상 사용자가 외부 구성요소를 반복해서 도입·변경하는가?
2. 기존 도구를 제대로 제공해도 같은 검토 공백이 남는가?
3. 우리 구현이 그 공백을 정확하게 줄이는가?
4. 위험한 구성을 더 많이 통과시키지 않으면서 정상 작업의 검토 부담을 줄이는가?

이 네 관문이 충족되면 “검증 가능한 근거로 안전한 사용을 돕는 플랫폼”이라는 주장을 뒷받침할 수 있다. 현재 단계에서는 **추진할 근거가 있는 가설**이며, 제품 효과가 입증된 상태는 아니다.
