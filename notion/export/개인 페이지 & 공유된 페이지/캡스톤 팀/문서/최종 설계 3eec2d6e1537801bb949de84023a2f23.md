    # AI 워크플로우 변경에 따른 결합 취약점 탐지와 실행 검증 설계
    
    작성 및 자료 확인일: 2026년 10월 3일, Asia/Seoul. 대상 독자: 프로젝트 구성원 4명과 지도교수. 상태: 회의 방향을 구체화한 구현·연구 제안. 아래 규모·성능·일정은 목표이며, 본 설계에서 실제 탐지 실험이나 성능 측정을 수행한 것은 아니다.
    
    **가칭 FlowDelta는 워크플로우의 변경과 실행 환경을 함께 분석하고, 관련 취약 시나리오를 검색하여 시험을 생성한 다음, 변경 전후의 실행 증거로 새 보안 위험을 확인하는 도구다.** 8주에 하나의 플랫폼에서 전체 흐름을 완성하고, 9~10주에 독립 평가와 논문 초안을 완성한다. 논문 채택이나 신규 CVE 발급은 완료 조건으로 두지 않는다.
    
    이 프로젝트의 중심 질문은 다음과 같다.
    
    > 같은 업무를 수행하는 AI 워크플로우를 업데이트했을 때, 어떤 변경이 어떤 보안 경계를 약화시켰으며, 제한된 시험 예산으로 그 영향을 얼마나 정확하게 찾아 재현할 수 있는가?
    > 
    
    상세 [조사 근거](https://app.notion.com/p/research-evidence.md), [10주 실행 계획과 평가 명세](https://app.notion.com/p/execution-plan.md), [공통 데이터 계약 예시](https://app.notion.com/p/contracts.example.json)를 함께 사용한다. 예시 계약은 제안 형식이며 실행 가능한 제품 설정이나 공식 MCP 형식이 아니다.
    
    전체 흐름을 쉽게 이해하려면 [대화형 HTML 아키텍처](https://app.notion.com/p/architecture.html)를 먼저 본다. 여섯 단계의 입력·처리·출력, 변경 전·후·수정 후의 설명용 예시, 분석·실행·증거 영역을 살펴볼 수 있다. HTML은 외부 라이브러리 없이 동작하며 실제 취약점 검사를 실행하지 않는다.
    
    ## 기존 설계에서 통합한 내용
    
    공유된 Notion 5개 문서의 펼쳐진 본문을 브라우저에서 읽었다. Notion 커넥터는 접근 오류를 반환했으며, 본문에 첨부된 HTML의 별도 내부 내용은 조사 범위에 포함하지 않았다. 기존 문서의 2~3명·12주 등의 가정은 사용자의 최신 조건인 4명·8~10주로 대체한다.
    
    | 기존 설계 | 이번 설계에 반영한 부분 | 배치 |
    | --- | --- | --- |
    | FlowDelta와 WorkflowDelta | 환경·하위 의존성을 포함한 보안 의미 비교 | 핵심 입력과 분석 엔진 |
    | ApprovalDiff | 승인한 대상과 실행한 대상의 일치 | 기본 승인 계약에 반영, LangGraph 재개 분석은 확장 |
    | MCP·Skills 경계 위반 검증 | 독립 관측, 실제 효과와 시도 구분 | 실행 검증과 판정 엔진 |
    | BoundaryCheck | 같은 구성의 권한 환경별 대조 | 필수 통제 실험 |
    | 이번 회의 방향 | 변경 경로에 맞춘 RAG와 LLM 시험 생성 | 새로 구체화할 연구 중심 |
    
    원문 링크와 반영 관계는 조사 근거 문서에 기록했다. 로컬의 기존 실험 디렉터리와 문서도 확인했다. 모의 MCP, 수신 기록, 상태 변경 확인, 초기화 코드는 재사용 후보지만, 과거 결과를 새 제품의 성능으로 인용하지 않는다. 이번 턴에는 기존 실험을 재실행하지 않았다.
    
    ## 문제의 사실 확인과 연구 주장
    
    “워크플로우 업데이트 시 보안 검사가 전반적으로 부족하다”는 생태계 전체의 빈도 주장은 현재 확보한 자료만으로 확정할 수 없다. 대신 좁고 검증 가능한 문제를 제시한다.
    
    - n8n Workflow Reviews는 특정 버전의 노드와 연결을 검토한다. 공식 문서는 설정, 자격증명, 변수, 데이터 테이블, 하위 워크플로우가 해당 리뷰의 승인·차이 비교 범위에 포함되지 않는다고 설명한다. 이는 검토 단위와 실제 실행 구성 사이의 구체적인 차이를 보여준다. [n8n 공식 문서](https://docs.n8n.io/build/manage-workflows/workflow-reviews)
    - 구성요소 결합으로 위험이 발생할 수 있다는 근거는 있다. Invariant의 Toxic Flow Analysis와 SCR-Bench는 도구·스킬을 연결했을 때의 위험을 다룬다. 따라서 조합 위험 자체를 처음 발견한다고 주장할 수 없다. [Toxic Flow Analysis](https://invariantlabs.ai/blog/toxic-flow-analysis), [SCR-Bench 논문](https://arxiv.org/abs/2606.15242)
    - 변경 후 회귀 검사를 수행하는 도구도 존재한다. OWASP Agent Security Regression Harness는 에이전트와 MCP 시스템의 실행 가능한 보안 시나리오와 정책 assertion을 제공한다. [공식 저장소](https://github.com/OWASP/Agent-Security-Regression-Harness)
    
    따라서 제안하는 연구 주장은 **“변경과 그 영향 경로를 이용해 관련 시나리오를 고르고 구체화하면, 같은 시험 예산으로 새 회귀를 더 많이 확인할 수 있다”**이다. 이는 실험 전 가설이다. 기존 방법보다 우수하다는 결론은 평가 후에만 쓴다.
    
    논문 기여 후보는 세 개로 제한한다.
    
    1. **변경된 실행·데이터·권한·지시 영향 관계에서 보안 시나리오의 사전 조건을 연결하는 방법.**
    2. **구조화한 시나리오 지식과 RAG를 이용해 변경별 실행 시험을 생성·선택하고, 독립 관측으로 검증하는 파이프라인.**
    3. **정상 변경, 위험 변경, 미확인 변경을 포함하는 버전 쌍 벤치마크와 수정 후 재검증 자료.**
    
    그래프를 사용했다는 사실, 벡터 DB에 CVE를 넣었다는 사실, LLM이 공격 입력을 작성한다는 사실은 각각 독립적인 신규성 주장이 되기 어렵다. 관련 연구와의 차이는 [조사 근거](https://app.notion.com/p/research-evidence.md)에 명시한다.
    
    ## 사용자와 작업 흐름
    
    첫 사용자는 n8n 기반 업무 자동화를 Git으로 관리하는 개발자와 검토자다. 초기 사용 사례는 고객 문의 요약, 사내 문서 검색과 내부 공유, 읽기 전용 보고서 생성이다. 운영 사고 빈도나 구매 의사는 아직 조사하지 않았으며 첫 주에 개발자 인터뷰와 공개 변경 사례 조사로 확인한다.
    
    사용자는 이전·이후 구성 묶음, 환경 프로필, 정책을 지정한다. 도구는 먼저 정적 분석 결과를 내고, 실행 검증이 가능한 후보에 대해 격리된 실험을 수행한다. 결과에서 새 위험, 기존 위험, 위험 증가, 수정 확인, 판단 불가를 구분한다. 사용자는 원인 변경·경로·근거·수정 제안을 확인하고 같은 시험을 다시 실행한다.
    
    초기 기능의 범위는 다음과 같다.
    
    | 영역 | 8주 필수 범위 | 9~10주 또는 후속 확장 |
    | --- | --- | --- |
    | 워크플로우 | n8n 한 릴리스와 명시된 노드 동작 집합 | 두 번째 릴리스, 이후 LangGraph 어댑터 |
    | 입력 | 상위·고정 참조 하위 JSON, 설정·권한 스냅샷 | 패키지 형식과 추가 수집기 |
    | MCP | 제공된 도구 목록·스키마·설명·연결 정보, 팀이 관리하는 모의 서버 | 검토한 공개 구현의 격리 재현 |
    | Skill | 본문·정적 참조 파일·해시와 워크플로우 연결 선언 | 실행 스크립트의 언어별 분석 |
    | 보안 분석 | 민감정보 전송, 비신뢰 입력의 인자 영향, 읽기 업무의 쓰기 | 제한된 승인 불일치(P3), 상태 지속·재개와 다중 승인 |
    | RAG | 구조화 시나리오 카드 60개, 메타데이터 필터와 텍스트·벡터 검색 | 100개 카드, 검색 순위 개선 |
    | 실행 | 합성 데이터, 내부 모의 수신처, 문서 저장소, 모델 1종 | 모델 2종의 일부 교차 평가 |
    | 결과 | CLI, JSON, 로컬 그래프·비교 보고서 | 웹 지식 카드·검색 화면 |
    
    임의 Python/JavaScript 전체 의미 해석, 모든 SaaS 실효 권한 수집, 임의 원격 서버 내부 검증, 범용 자동 취약점 공격 플랫폼, 자체 모델 학습을 8주 범위에 넣지 않는다. Skill과 MCP는 프레임워크와 구분한다. n8n의 구성요소를 연결하는 인터페이스로 지원하는 것이며 모든 호스트에서 동일하게 실행된다고 가정하지 않는다.
    
    ## 위협 모델과 판정할 보안 계약
    
    공격자는 사례별로 외부 문의·문서·도구 응답, 제공된 도구 설명, 또는 공급자가 관리하는 업데이트 파일을 통제한다. 정상 개발자의 변경 실수도 보안 회귀 원인이 될 수 있다. 공격자 통제 표면은 각 시험에 하나 이상 명시하되, 통제하지 못하는 파일이나 정책을 임의로 바꾸어 취약점을 만들지 않는다.
    
    정책·관측기·평가 정답·실행 제어기는 신뢰 기반이다. 분석 대상이 제출한 “안전함”, “읽기 전용”, `allowed-tools`를 실효 권한 증거로 받아들이지 않는다. MCP 공식 명세는 신뢰할 수 없는 서버의 tool annotation을 비신뢰 데이터로 다루도록 한다. Agent Skills의 `allowed-tools`도 구현별 지원이 다른 실험적 필드다. [MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools), [Agent Skills](https://agentskills.io/specification)
    
    정책의 출처는 제품이 약속한 경계, 조직이 정한 경계, 연구자가 만든 실험 경계로 구분한다. 연구용 정책 위반을 곧바로 제품 CVE나 MCP 프로토콜 취약점으로 발표하지 않는다.
    
    | 정책 | 판정 대상 | 허용되는 정상 사례 |
    | --- | --- | --- |
    | P1 기밀 전송 제한 | 기밀 필드가 허용되지 않은 수신자·테넌트·모델 제공자로 전달되는가 | 허용된 내부 수신처로 승인된 공유 |
    | P2 읽기 업무의 쓰기 제한 | 읽기 전용 업무가 보호 문서를 수정하는가 | 감사 로그 등 명시적으로 허용한 부수 기록 |
    | P3 승인과 실행 결합 | 실행 도구·주체·수신자·자원·보호 인자가 승인 범위에 속하는가 | 사용자가 수정한 인자를 다시 승인한 실행 |
    
    P1·P2는 처음부터 끝까지 실행 판정하는 필수 범위다. P3는 핵심 흐름과 평가 시간을 확보한 경우 추가하며, n8n에서 명시적으로 모델링한 승인 경로와 구조화 인자에 한정한다. LangGraph 체크포인트를 구버전에서 생성하고 신버전에서 재개하는 실험은 별도의 확장이다.
    
    위험 분류와 증거 상태는 별개다. 분류는 알려진 구현 취약점, 결합 정책 위반, 악성 구성요소 행동, 환경 의존 위험, 미확인으로 저장한다. 증거는 추론 후보, 정적 조건 성립, 시험 실행, 실제 효과 관측으로 세분화한다.
    
    ## 전체 아키텍처
    
    ```mermaid
    flowchart TD
        A[이전 구성과 환경] --> C[어댑터와 공통 보안 그래프]
        B[이후 구성과 환경] --> C
        P[조직 정책] --> D[변경 의미와 영향 범위]
        C --> D
        D --> E[경로와 사전 조건 검사]
        K[시나리오 카드와 출처 저장소] --> R[메타데이터 텍스트 벡터 검색]
        E --> R
        R --> H[LLM 시험 가설 생성]
        H --> V[스키마와 조건 검증]
        E --> V
        V --> X[격리된 이전 이후 실행]
        X --> O[독립 수신 기록과 상태 판정]
        O --> F[원인 변경과 수정 재검증]
        F --> U[CLI 그래프 보고서와 CI 결과]
        K --> W[프레임워크 지식 웹사이트]
    ```
    
    정적 규칙으로 찾은 후보는 RAG가 관련 문서를 못 찾았더라도 유지한다. 검색 실패는 안전의 근거가 아니다. LLM은 그래프에 없는 경로나 권한을 사실로 추가할 수 없다. 제안한 새로운 연결은 별도의 미확인 가설로만 등록한다.
    
    처음부터 분산 마이크로서비스를 만들지 않는다. Python 코어·작업 실행기와 PostgreSQL 하나로 시작한다. n8n 표현식의 지원 부분집합은 명시적인 파서와 의미 계약으로 처리하며 임의 표현식을 평가하지 않는다. 복잡한 표현식은 UNKNOWN으로 남긴다. 그래프 계산은 메모리의 NetworkX 등으로, 벡터 검색은 pgvector로 구현하는 방안을 권한다. API가 필요하면 FastAPI, 보고서 UI는 React와 Cytoscape.js를 사용한다. 이는 구현 제안이며 버전·라이선스·팀 숙련도는 첫 주에 고정한다.
    
    ## 분석 입력과 재현 가능한 스냅샷
    
    분석 단위를 `Snapshot = Workflow + Dependencies + Environment + PolicyRef + RuntimeConfig`로 정의한다.
    
    - Workflow에는 노드, 연결, 필드 매핑, 조건, 프롬프트, 모델 설정을 넣는다.
    - Dependencies에는 하위 워크플로우, tool descriptor, Skill 전체 정적 파일 트리, 관련 패키지와 버전을 넣는다.
    - Environment에는 계정·테넌트의 비밀이 아닌 참조, 리소스별 허용 동작, 허용 목적지, 승인 설정과 관측 출처를 넣는다.
    - RuntimeConfig에는 프레임워크·모델 식별자, 실행 옵션, 의존성 lock, 컨테이너 digest, 세션·메모리 초기화 규칙을 넣는다.
    
    실제 토큰·키는 별도 비밀 저장소에서 실행기에 주입하며 스냅샷, 임베딩, 보고서에 넣지 않는다. 환경 사실은 `declared`, `static_inferred`, `observed`, `unknown`으로 표시하고 관측 시간·유효 범위·출처를 저장한다. 수동 환경 파일이 실효 권한 확인을 대체하지 않는다.
    
    같은 파일이라도 권한·모델·외부 descriptor가 바뀌면 새 스냅샷이다. 반대로 문서 지식만 갱신되면 “워크플로우 회귀”와 구분해 “새 지식에 따른 재평가”로 처리한다.
    
    산출물 해시와 보안 의미 비교용 정규화 해시는 분리한다. 화면 좌표처럼 실행에 영향이 없는 필드는 정규화할 수 있지만, 노드 이름을 참조하는 표현식·도구 설명·프롬프트는 삭제하지 않는다. 같은 MCP 도구 이름은 서버 식별자와 묶고, 승인 기록은 스냅샷·정책·분석기·시험 버전에 결합한다.
    
    ## 그래프와 변경 분석
    
    그래프는 단순한 순서도가 아니다. 다섯 관계를 독립적으로 기록한다.
    
    | 관계 | 예시 | 주의할 점 |
    | --- | --- | --- |
    | 제어 흐름 | 분기 A가 참일 때 노드 B 실행 | 오류·재시도 경로도 포함 |
    | 데이터 흐름 | 문서 본문에서 메시지 body로 전달 | 필드·변환·출처를 추적 |
    | 지시 영향 | 비신뢰 문서나 도구 설명이 모델의 수신자 선택에 영향 가능 | 가능한 영향이며 실제 모델 행동의 증명이 아님 |
    | 권한·능력 | 실행 계정이 기밀 저장소를 읽고 외부 전송 도구 사용 가능 | 선언과 관측된 권한을 구분 |
    | 의존성·보호 | 하위 workflow, 버전, allowlist, 승인과 실행의 결합 | 승인 노드 존재만으로 보호된다고 단정하지 않음 |
    
    노드는 workflow, agent, tool, skill/reference, data resource, identity, endpoint, guard, approval 등으로 표현한다. 각 노드·간선에 원본 JSON pointer 또는 코드 위치, 근거 종류, 스냅샷, 의미 계약 버전을 붙인다. 정적 그래프는 가능한 동작을 나타내고 실행 trace는 관측한 동작을 나타낸다. 실행에서 관측하지 못한 간선을 제거해 안전하다고 추정하지 않는다.
    
    데이터에는 민감도와 지시 신뢰도를 각각 붙인다. 공개 웹페이지도 비신뢰 지시를 포함할 수 있고, 기밀 사내 문서의 내용도 실행 지시 권한을 갖지 않는다. 요약·번역·Base64 변환은 자동 비식별화나 민감도 제거로 인정하지 않는다. 의미 변환 이후의 실제 유출은 지원된 oracle이 없으면 미확인이다.
    
    ### 변경 종류
    
    새 노드·새 간선뿐 아니라 다음 변경을 검사한다.
    
    | 변경 | 왜 검사해야 하는가 |
    | --- | --- |
    | 수신자 상수에서 모델 생성 값으로 변경 | 동일한 연결에서 외부 입력의 영향이 늘어남 |
    | 읽기 계정의 접근 범위 확대 | 그래프 외형이 같아도 새 기밀 자원에 접근 가능 |
    | 승인·필터 삭제 또는 조건 약화 | 기존 경로의 보호가 사라짐 |
    | 하위 워크플로우·참조 스크립트 변경 | 부모 파일이 그대로여도 실제 효과 변경 |
    | 도구 설명·입력 스키마·endpoint 변경 | 다른 도구 선택·인자·실행 대상으로 이어질 수 있음 |
    | 모델·system prompt·memory 정책 변경 | 구조가 같아도 행동 분포 변화, 동적 재시험 필요 |
    | 불명확한 동적 참조로 교체 | 경고 감소가 아닌 분석 가능성 감소 |
    
    노드 대응은 안정 ID, 원본 경로와 동작, 제한적 구조 대응 순으로 수행한다. 모호한 대응은 사용자 확인 또는 전체 재분석 대상으로 표시한다. 멋대로 동일 노드로 병합하지 않는다.
    
    ### 영향 범위와 경로 후보
    
    1. 양쪽 스냅샷을 같은 의미 계약과 정책으로 분석해 기준 결과를 만든다.
    2. 변경된 노드·속성·의존성과 삭제된 보호 조건을 찾는다.
    3. 변경 지점의 상류 입력과 하류 민감 동작을 추적하고, 같은 agent context·공유 memory·권한 관계까지 확장한다.
    4. 경로별로 공격자 통제 입력, 필요한 권한, 민감 자원, 외부 효과, 우회되지 않는 보호 조건을 결합한다.
    5. 충족되는 조건은 후보로, 모순되는 조건은 제외 사유로, 판단 못 하는 조건은 UNKNOWN으로 남긴다.
    
    위험 조합은 AND 조건을 포함한다. 예를 들어 비신뢰 지시가 문맥에 들어감, 기밀 문서 접근 가능, 전송 능력 존재, 목적지 제한 부재가 함께 필요한 사례를 단일 연결선 하나로 축약하지 않는다. 호출하지 않은 도구의 설명도 문맥에 포함되면 다른 도구 사용에 영향을 줄 수 있으므로 descriptor-to-context 관계를 포함한다. [도구 오염과 shadowing 사례](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)
    
    모든 단순 경로를 열거하지 않는다. 정책별 source–sink 도달성과 요약을 먼저 계산하고, 후보당 설명에 필요한 짧은 witness를 만든다. 순환은 강연결 요소와 반복 요약으로 다루고 상한 도달은 coverage 제한으로 기록한다. 처음에는 전체 재분석 후 의미 결과 비교를 정답 구현으로 두고, 선택적 재분석은 후반 최적화로 추가한다. 최적화의 결과는 같은 엔진의 전체 분석과 일치해야 한다.
    
    ### 승인 검사의 실제 의미
    
    승인이 위험 동작의 모든 지원 경로를 지배하는지 확인하고, 승인 후 수신자·자원·주체·보호 인자가 변하는지도 확인한다. “언어가 한국어인가”라는 IF는 외부 수신자 제한이 아니다. 사람이 승인했다는 로그만으로 실행 인자와의 결합을 증명하지 않는다. 보호 인자를 복원할 수 없는 자연어 승인, 미지원 분기, 승인 후 원격 동작 변경은 판단 한계를 표시한다.
    
    ## 취약 시나리오 지식과 RAG
    
    벡터 DB는 검색 인덱스다. 사실·버전·관계의 원본은 구조화 데이터베이스와 출처 저장소에 둔다. 한 문서 전체를 임베딩해 유사도만으로 취약 판정을 내리는 구조는 사용하지 않는다.
    
    ### 지식의 세 계층
    
    | 계층 | 내용 | 활용 |
    | --- | --- | --- |
    | 알려진 구현 취약점 | CVE·GHSA·OSV, 패키지·버전·조건·수정 | 정확한 식별자·버전 매칭과 적용성 검토 |
    | 일반 취약 시나리오 | 도구 오염, 권한 혼동, 승인 우회, 기밀 전송 등 | 조건이 닮은 경로의 시험 설계 |
    | 통제와 정상 대조 | allowlist, 최소 권한, 재승인, 무해 변경 | 오탐 억제와 수정 검증 |
    
    CVE가 없는 조합 결함도 두 번째 계층에서 다룬다. 다른 프레임워크의 취약점 문서는 공격 원리를 참고할 수 있지만, 제품명·버전이 다르면 같은 CVE가 적용된다고 출력하지 않는다. OSV는 패키지 버전·커밋을 기준으로 질의할 수 있고, 그 결과도 실제 경로의 도달성과 배포 조건 확인을 대체하지 않는다. [OSV API](https://google.github.io/osv.dev/api/), [OSV 스키마](https://ossf.github.io/osv-schema/)
    
    ### 시나리오 카드
    
    카드에는 다음 필드를 저장한다.
    
    `scenario_id`, 원문 URL·구간·확인 날짜·내용 해시, 출처 종류, 공개일·수집일, 관련 CVE/GHSA 별칭, 제품·패키지·영향 버전, 공격자 통제 표면, source·sink 종류, 필요한 권한, 신뢰 경계, 보호 조건, 위험을 만드는 변경, 시험 템플릿, 판정 oracle 종류, 정상 대조, 수정·완화 방법, 적용 한계, 사람 검토 상태, 카드 버전.
    
    하나의 문서가 여러 원인을 다루면 카드도 원인별로 나눈다. 같은 CVE의 여러 기사나 같은 PoC의 포크는 같은 원인 집합으로 묶는다. 논문상의 가설, 공급자 문서의 지원 기능, 실제 재현 보고를 동일한 근거 수준으로 저장하지 않는다. 저자 보고 수치는 자체 측정과 구분한다.
    
    수집 순서는 공식 보안 공지·수정 커밋, 공식 문서·명세, 논문·공개 벤치마크, 원발견자의 분석 글 순으로 둔다. 출처의 신뢰도와 무관하게 문서의 명령문은 분석 데이터다. 문서가 실행 명령이나 비밀 입력을 요구해도 수행하지 않는다.
    
    ### 검색과 적용성 검증
    
    1. 변경 종류와 영향을 받는 경로에서 질의를 생성한다. 예: `recipient가 fixed에서 model_generated로 변경`, `external_input → agent_context`, `confidential_read + message_send`.
    2. 알려진 CVE는 제품·ecosystem·버전·필수 설정을 정확히 확인한다. 불명확한 버전은 적용성 UNKNOWN으로 남긴다.
    3. 일반 시나리오는 필수 능력·source·sink·공격자 표면으로 후보를 좁힌다. 이름이 다르더라도 동작이 유사한 사례를 남긴다.
    4. 키워드 검색과 벡터 검색 결과를 결합하고, 구조 조건 적합도와 출처 품질로 재정렬한다. MVP는 PostgreSQL 텍스트 검색과 pgvector를 사용하며, 별도 BM25 엔진은 필요시 추가한다.
    5. 개발셋의 초기 설정은 텍스트·벡터 각각 상위 20개, 통합 재정렬 후 상위 5개로 둔다. 최종값은 개발셋에서만 조정한다.
    6. LLM에 변경 요약, 원본 위치, 관련 하위 그래프, 정책, 상위 카드의 근거 구간을 전달한다. 불필요한 전체 저장소와 비밀정보는 보내지 않는다.
    
    검색 점수는 취약 확률이 아니다. 적용 조건이 틀린 상위 검색 결과, 무관한 CVE, 검색 결과 없음에 대한 음성 사례를 평가에 포함한다. 필요 조건이 거짓이면 해당 시나리오는 제외하고, 알 수 없으면 가설 상태를 유지한다.
    
    ### LLM 출력 계약
    
    LLM은 자연어 판정문 대신 구조화한 시험 가설을 반환한다.
    
    - 어떤 정책 위반을 주장하는지와 새 위험·기존 위험 중 무엇을 의심하는지.
    - 원인 변경 ID와 실제 그래프의 노드·간선 ID.
    - 조건별 `satisfied / contradicted / unknown` 및 근거.
    - 공격자가 바꿀 수 있는 입력 위치와 시험용 입력 변형.
    - 참조 카드·출처 구간, 적용이 직접 매칭인지 유추인지.
    - 등록된 시험 템플릿과 oracle ID, 정상 대조, 실행 예산.
    
    스키마 검증기가 존재하지 않는 ID, 허용되지 않은 도구, 잘못된 인자 타입, 사전 조건 모순, 근거 없는 CVE 적용을 거부한다. LLM이 임의 Python·셸 코드를 생성해 실행하는 기능은 MVP에 없다. 입력 문구와 사전 등록된 템플릿의 허용 파라미터만 생성한다. 최종 판정 oracle의 코드는 생성 모델이 수정할 수 없다.
    
    ### 알려지지 않은 조합의 발견
    
    기존 카드의 도구 이름을 바꾸는 것 외에, 일반 정책에서 출발한 탐색을 유지한다. 기밀 데이터가 도달 가능한 신규 sink, 승인 보호가 약해진 작업, 공유 문맥으로 이어진 서로 다른 도구의 권한을 조합해 후보를 만든다. 문서가 없어도 정적 정책 위반 후보는 실행 대상이 될 수 있다.
    
    새롭다는 표현을 구분한다. 새로 추가된 경로, 기존 사례를 다른 구성에 적용한 유사 결함, 공개되지 않은 구현 취약점은 서로 다른 주장이다. 마지막 유형은 코드·공격자 권한·기존 공개 여부를 별도 검토한 후에만 사용한다.
    
    ## 실행 검증과 변경 원인 확인
    
    ### 실험 환경
    
    제어·지식 저장 구역, 폐기 가능한 실행 구역, 독립 증거 구역을 분리한다. 임의 외부 코드·설치 스크립트를 다루는 실행은 별도 VM 안에서 수행한다. 컨테이너만 존재한다는 사실을 충분한 격리 근거로 삼지 않는다. 개인 홈, 운영 토큰, 호스트 Docker 소켓, 클라우드 메타데이터를 노출하지 않는다.
    
    실험실의 인터넷 차단과 대상 정책을 분리한다. 외부 유출 시험에서는 실제 인터넷 대신 격리망 내부의 “조직 정책상 외부 수신자” 역할 서버를 둔다. 이곳에 합성 기밀 데이터가 도착했는지 확인해야 전송 의도를 넘어 실제 효과를 확인할 수 있다. 호스트 방화벽이 차단한 결과를 대상 애플리케이션의 방어 성공으로 계산하지 않는다.
    
    모델 API는 별도 중계기를 통해 허용된 제공자에만 연결한다. 실행 대상에 API 키를 주지 않고 합성 데이터만 모델에 전달한다. LLM 호출 자체도 데이터 전송 경계로 그래프에 포함한다.
    
    ### 두 종류의 실행
    
    **결정적 재생**은 고정된 도구 호출로 어댑터·권한·관측기·판정을 검증한다. 이 결과는 해당 행동이 가능한지의 증거다.
    
    **실제 모델 실행**은 실제 프롬프트·도구 설명·응답으로 모델이 어떤 행동을 선택하는지 본다. 이 실행에서만 모델 기반 공격 성공률을 계산한다. 모델 버전·옵션·반복·요청 ID를 기록하고 seed가 있어도 완전 재현을 보장한다고 가정하지 않는다.
    
    ### 판정 oracle
    
    | 검사 | 관측 근거 | 한계 |
    | --- | --- | --- |
    | 기밀 전송 | 실행별 합성 canary 또는 지정 필드가 독립 수신처에 도착 | 자유로운 요약·은유·암호화까지 모두 검출하지 못함 |
    | 문서 변경 | 독립 저장소의 쓰기 이벤트와 전후 상태 | 최종 상태만 같아도 중간 쓰기 후 롤백이 있을 수 있음 |
    | 승인 불일치 | 승인 이벤트의 보호 인자와 실제 효과의 인자·주체·자원 비교 | 실제 사람이 화면을 이해했는지까지 검증하지 않음 |
    | 차단 | 정책 거부 이벤트와 금지 효과의 미발생 | 실행·관측 실패와 구분해야 함 |
    | 정상 업무 | 기대 문서·내부 메시지 등 업무별 독립 assertion | 모델의 성공 선언만으로 성공 처리하지 않음 |
    
    Canary는 공격 입력에 포함하지 않고 보호 자원에만 배치한다. 대상 프로세스는 증거 저장소와 oracle 설정을 수정할 수 없다. canary가 로그에 없다는 사실만으로 유출이 없었다고 판단하지 않는다. oracle 건강 상태와 관측 범위를 결과에 붙인다.
    
    ### 변경 전후의 공정한 비교
    
    1. 동일 업무·합성 자원·정책을 준비하고 이전 버전과 이후 버전을 각각 깨끗한 상태에서 실행한다.
    2. 외부 응답은 도구 호출 횟수보다 논리적 자원·질의 키로 대응시킨다. 호출 순서가 바뀌었다고 다른 데이터를 제공하지 않는다.
    3. 동일한 공격 입력을 적용할 수 있으면 양쪽에 적용한다. 새로 추가된 도구가 공격 표면이면 구버전에는 동일 표면이 없음을 명시하고, 새 표면 도입에 관한 실험으로 분류한다.
    4. 프롬프트·모델·권한 등을 동시에 바꾼 경우 변경 묶음 효과를 먼저 측정한다. 단일 변경씩 되돌리거나 조합을 줄여 원인을 좁힌다.
    5. 확인된 사례에는 수정본과 정상 업무 대조를 추가한다. 수정으로 전체 기능이 멈추면 성공한 수정으로 계산하지 않는다.
    
    변경을 되돌렸을 때만 효과가 사라진다는 실험은 해당 조건에서의 원인 근거다. 비결정적 모델과 상호작용하는 모든 조건의 수학적 인과 증명은 아니다. 최소화는 관측된 조건 내 결과이며 여러 변경의 결합 효과를 남길 수 있다.
    
    ### 결과의 두 축
    
    | 실행 상태 | 의미 |
    | --- | --- |
    | EFFECT_CONFIRMED | 독립 관측에서 금지 효과 확인 |
    | BLOCKED_BY_TARGET_CONTROL | 대상의 특정 통제가 시도를 막았다는 근거 확인 |
    | ATTEMPT_OBSERVED | 시도는 확인했으나 실제 효과는 확인하지 못함 |
    | NO_VIOLATION_OBSERVED | 정의한 시험을 완료했으나 위반은 관측되지 않음 |
    | INCONCLUSIVE | 실행·권한·관측의 불완전성으로 판단 불가 |
    | NOT_RUN | 시험 미실행 |
    
    여기에 변경 판정을 따로 붙인다. `newly_observed`, `persistent`, `increased`, `remediated_in_tests`, `unresolved`다. 구버전 0회·신버전 여러 회 성공은 “시험에서 새로 관측”한 증거다. 구버전의 모든 상황이 안전했다는 증명이 아니며, 공격 성공률 차이는 표본수와 신뢰구간을 함께 보고한다.
    
    이전 버전에서도 위반이 확인되면 새 취약점이라고 세지 않는다. 구버전 설치 실패나 관측 실패는 회귀 확정을 방해한다. 동일한 스냅샷에 새 CVE 지식을 적용해 찾은 문제는 새 지식 발견으로 구분한다.
    
    ## 대표 시나리오와 시연
    
    아래는 구현할 시험이며 이번 조사에서 재현한 결과가 아니다.
    
    | 번호 | 변경 | 예상 후보 | 정상 또는 수정 대조 |
    | --- | --- | --- | --- |
    | S1 | 고정 내부 수신자를 모델이 정하도록 변경 | 외부 문의가 수신자 결정에 영향 | 도구 수준 recipient allowlist |
    | S2 | 기밀 검색 도구를 기존 요약 agent에 추가 | 조회 능력과 기존 전송 도구의 결합 | 공개 자료 전용 계정 |
    | S3 | 부모는 유지하고 하위 공유 workflow만 변경 | 새로운 외부 전송 또는 민감 필드 포함 | 참조를 보존한 무해 리팩터링 |
    | S4 | 연결 계정만 과권한 계정으로 교체 | 같은 그래프에서 보호 자원 접근 확대 | 권한 축소, 관측 권한 미확인 별도 처리 |
    | S5 | 승인 이후 인자 재계산 또는 승인 우회 분기 | 승인한 대상과 실행 대상 불일치 | 변경 인자를 다시 승인 |
    | S6 | 도구 설명 또는 Skill 참조 문서 변경 | 다른 도구의 선택·인자에 영향 | 무해한 설명 변경, 도구 본문 불변 대조 |
    | S7 | 무관한 IF를 추가 | 기존 위험이 유지되는지 검사 | 정책 관련 조건과 비교 |
    | S8 | endpoint는 같고 테넌트·수신 채널이 변경 | 동일 호스트 내 조직 경계 이탈 | 명시적으로 허용한 다른 내부 채널 |
    | S9 | 지원 노드를 동적 코드로 교체 | 분석 가능성 감소 | UNKNOWN을 통과로 표시하지 않음 |
    | S10 | 관련 패키지의 영향 버전으로 교체 | CVE 적용 후보와 workflow 도달성 | 수정 버전·조건 불충족 사례 |
    
    대표 시연은 S1과 S2를 하나의 업무에서 보여준다. 외부 문의를 읽고 공개 FAQ를 내부 메일함에 공유하는 정상 구성에서 출발한다. 기밀 문서 검색과 모델 결정 수신자라는 변경을 넣고, 관련 위험 경로와 시나리오 검색 근거를 표시한다. 격리된 외부 역할 수신처에 합성 데이터가 도착하는지 확인한다. 수신자 제한을 넣은 수정본에서 같은 공격 시험과 정상 내부 공유가 어떻게 달라지는지 보여준다.
    
    시연의 경고 카드에는 “왜 이번 업데이트를 검사하는가”가 먼저 나온다. 다음으로 변경 위치, 위험 경로, 필수 조건, 참조 시나리오, 실행 결과, 정상 업무 결과, 수정 제안, 미확인 사항을 보여준다. 논문이나 CVE 링크만 나열하는 카드로 끝내지 않는다.
    
    ## 보고서와 지식 웹사이트
    
    분석 결과 화면과 지식 웹사이트는 같은 출처·카드 저장소를 사용한다. 분석기는 카드 버전을 고정해 실행하고, 웹사이트는 그 카드의 사람이 읽기 좋은 표현을 제공한다.
    
    검토 화면에는 변경 전후 그래프, 보안 의미 차이, 관련 경로, 실행 증거, 수정 후 결과를 표시한다. 관측된 연결·정적 추론·미확인 관계를 색뿐 아니라 선 스타일·텍스트로 구분한다. 변화와 무관한 전체 그래프는 접어 두고, 원본 JSON pointer나 파일 위치로 이동할 수 있게 한다.
    
    지식 웹사이트에는 n8n, LangGraph, CrewAI, AutoGen 등의 프레임워크 카드와 MCP·Agent Skills의 프로토콜·포맷 카드를 구분한다. 각 카드에는 목적과 사용법, 버전별 변경, 보안상 주의점, 관련 공지와 패치, 적용 조건, 최소 정상 예제, 관련 시험·지원 상태, 마지막 확인일을 넣는다. 프레임워크 소개가 있다고 그 프레임워크의 자동 분석을 지원하는 것은 아니다.
    
    “과거에 약했던 부분”은 특정 버전·구성·출처에 묶는다. 수정된 이슈를 현재 모든 버전의 결함처럼 표시하지 않는다. 원문 전체를 복제하는 대신 허용 범위의 요약과 링크를 제공하고, 재사용 코드·데이터의 라이선스를 기록한다. 자동 수집된 변경은 검토 대기 상태로 두고 사람이 확인한 카드만 기본 검색에 사용한다.
    
    8주 결과는 로컬 보고서와 카드 검색의 최소 화면이다. 여러 사용자 계정, 공개 커뮤니티 게시판, 마켓, 과금 기능은 후속이다. 9~10주에도 실험이 밀리면 웹 확장보다 평가를 우선한다.
    
    ## 공통 데이터와 인터페이스
    
    | 객체 | 책임 |
    | --- | --- |
    | Snapshot | 원본·환경·의존성의 정확한 분석 대상을 고정 |
    | SemanticGraph | typed node·edge와 근거·지원 범위를 표현 |
    | ChangeSet | 추가·삭제·속성·권한·보호 변경과 대응 불확실성 |
    | ScenarioCard | 출처가 있는 시나리오와 적용 조건 |
    | Hypothesis | 경로·변경·정책에 연결된 시험 후보 |
    | TestPlan | 검토된 어댑터·fixture·입력 변형·예산 |
    | ExecutionRun | 모델·환경·시험·관측기 버전과 실행 상태 |
    | EvidenceEvent | 시도·수신·변경·승인 이벤트의 독립 근거 |
    | Finding | 문제 종류, 증거 상태, 변경 판정, 정상 업무 결과 |
    
    모든 관계는 불변 ID와 해시를 통해 연결한다. 재실행마다 run ID를 새로 만들고 이전 결과를 덮어쓰지 않는다. JSON Schema 또는 Pydantic 모델로 검증하고, 다른 담당자가 내부 함수나 DB 테이블을 직접 가정하지 않게 한다.
    
    제안 CLI는 아래와 같다. 아직 구현된 명령이 아니다.
    
    ```
    flowdelta snapshot --bundle before --environment env-before.json
    flowdelta compare --before snapshot-a --after snapshot-b --policy policy.yaml
    flowdelta plan --comparison comparison-a --knowledge knowledge-v1
    flowdelta verify --plan plan-a --profile isolated-lab
    flowdelta report --comparison comparison-a --format html
    ```
    
    `compare`와 `plan`은 대상 코드를 실행하지 않는다. `verify`만 실행 구역의 등록된 어댑터를 호출한다. 원격 도구 목록 조회를 위해 서버를 시작해야 한다면 이를 단순 파싱이 아닌 실행 작업으로 분류한다.
    
    API를 추가할 경우 `POST /snapshots`, `POST /comparisons`, `POST /test-plans`, `POST /runs`, `GET /findings/{id}`, `GET /knowledge/scenarios` 정도로 시작한다. 원문 파일과 상세 trace는 인증된 내부 저장소에, 정제한 공개 지식은 별도 공개 뷰에 둔다. 공개 지식 사이트에 사내 workflow·권한·증거를 자동 게시하지 않는다.
    
    CI는 실행 상태와 coverage를 포함한 구조화 결과로 `pass / review_required / fail / error`를 반환한다. 고위험 미확인을 무조건 pass로 처리하지 않는다. CI 실패가 실제 배포를 막는지는 보호된 배포 경로가 그 검사를 강제하는지에 달려 있다.
    
    ## 프로젝트 자체의 보안과 주요 한계
    
    불신 문서와 패키지는 분석기 자체를 공격할 수 있다. 압축 경로 탈출, 크기·중첩 제한, 외부 참조, 파서 자원 고갈, RAG 프롬프트 주입, 결과 HTML 삽입을 처리한다. 검색 문서와 LLM 응답은 명령 권한이 없고, 시험 템플릿과 oracle은 별도 검토·버전 관리한다.
    
    최종 보고서에는 자동 추출 coverage, 수동 계약 작성량, unknown 이유, 시간·시도 상한, oracle이 검사하는 변환 범위, 실행·관측 실패를 반드시 포함한다. 원격 MCP의 내부 동작이 메타데이터와 다를 수 있으므로 descriptor 해시만으로 동작 무결성을 보장하지 않는다.
    
    기밀 전송·권한·승인 위험을 묶은 탐색은 조합 수가 빠르게 늘어난다. 정책 중심 요약과 예산을 사용하되 생략된 경로를 기록한다. 선택적 분석이 전체 분석보다 빠르다는 것은 측정할 가설이며, 분석 오차를 허용해서 얻은 속도는 따로 보고한다.
    
    가장 큰 일정 위험은 UI가 아니라 정확한 의미 계약과 독립 판정기다. 이 두 부분을 첫 2주부터 구현하고 데이터셋을 동시에 만든다. RAG가 유효한 개선을 주지 않으면 그 결과를 숨기지 않고 규칙·구조 검색과의 비교를 보고한다. 프로젝트 산출물은 분석기, 변경 벤치마크, 독립 실행 근거, 실패 분석이 함께 있어야 완성된다.
