# 6. 민우의 회의 설명문과 예상 질문

2026-09-26 토요일 22:00 회의 준비용. 아래는 발표할 때 자신의 말로 설명할 초안이며, 아직 하지 않은 검증을 완료했다고 말하지 않는다.

## 3분 설명문

제 담당은 Skill과 MCP를 따로 검사했을 때는 문제가 없는데, 함께 쓰면서 생기는 위험입니다. Skill은 작업 방법을 알려주고, MCP는 실제 자료 조회나 발행 같은 기능을 제공합니다. 그래서 안전성은 파일 하나의 성질만이 아니라, 어떤 자료를 읽어서 어디로 보내는지에 달려 있습니다.

예를 들어 보고서 작성 Skill이 자료를 읽고 요약해서 게시하도록 되어 있다고 하겠습니다. 자료 조회와 게시 도구는 각각 정상적으로 구현될 수 있습니다. 내부 자료를 허용된 팀에 보내는 것은 정상인데, 같은 요약을 공개 공간에 보내면 정책을 위반할 수 있습니다. 코드가 갑자기 악성으로 바뀐 게 아니라 자료와 공개 범위의 연결이 문제입니다.

그런데 이 개념 자체는 이미 연구돼 있습니다. MCP 쪽에는 Toxic Flow Analysis가 있고, Skill 쪽에도 SkillProbe, SkillReact, SCR-Bench, SkillFuzz, CompoSkill이 있습니다. 특히 Cisco 코드에 교차 Skill 검사가 실제로 들어 있었습니다. 그래서 우리가 ‘결합 탐지를 최초로 만든다’고 말하면 반박당합니다.

저는 Cisco 도구 두 개를 직접 설치해 무해한 문서와 도구 명세를 검사했습니다. Skill Scanner는 비공개 자료를 읽는 Skill과 webhook 발행 Skill을 묶었을 때 경고했습니다. 하지만 MCP 도구 이름으로만 읽기와 발행을 표현한 표본에는 경고하지 않았습니다. 이것은 실제 유출 성공률이 아니라 검사 입력의 차이에 따른 관측입니다.

제가 제안하는 연구 질문은 여기서 한 단계 좁힙니다. **Skill의 지시와 MCP의 실제 도구·권한·공개 대상을 연결하면, 단순한 권한 합집합보다 정상 업무와 위험한 결합을 잘 구별할 수 있는가**입니다. 같은 워크플로에서 목적지만 내부 팀과 공개 공간으로 바꾼 대조군이 핵심입니다.

첫 구현은 비공개 자료가 요약을 거쳐 공개되는 경로에 집중하는 게 좋겠습니다. 파일을 모으고, 명시된 도구 연결을 추출하고, 근거가 있는 경로와 추정 경로를 나눈 다음, 권한과 공개 승인 조건을 검사합니다. 결과는 위험 후보, 통제로 차단된 경로, 근거 부족으로 구분합니다. 이후 기존 교차 검사보다 오탐이나 누락이 줄어드는지 비교해야 차별성이 검증됩니다.

## 예상 질문 15개

**1. 그럼 그냥 prompt injection 탐지 아닌가?**

주입이 경로를 활성화하는 경우도 있지만, 악성 문장 없이 잘못된 공개 대상 때문에 생기는 정책 위반도 따로 평가한다. 문자열 탐지와 데이터 흐름/권한 조건 검사를 분리한다.

**2. 각각 안전하다면서 왜 문제가 생기나?**

‘개별 검사에서 무경고’라는 조건부 표현이다. 도구가 설명대로 실행돼도 읽은 자료를 다음 도구에 전달하는 일이 업무 범위를 벗어날 수 있다. 절대적 안전을 증명한 것은 아니다.

**3. 실제 Skill×MCP 사고가 있나?**

정상 MCP 도구를 통한 공개 이슈→비공개 정보→공개 PR 시연은 확인했다. Skill 결합 논문도 있다. 하지만 둘을 합쳐 **명명된 Skill×MCP 실피해 사고를 확인했다**고 말할 수는 없다. 우리의 혼합 표본은 설계·검증 대상이다.

**4. Cisco가 이미 잡는데 왜 만드나?**

그 질문이 핵심이다. 교차 검사까지 비교군으로 두고 실제 MCP 대상·scope·승인 조건을 넣었을 때 이득을 보여야 한다. 차이가 없으면 주장을 바꿔야 한다.

**5. TFA와 다른 게 뭔가?**

큰 원리는 겹친다. 제안은 Skill 지시와 구체적 MCP 바인딩, 환경 변경, 근거 부족 처리를 재현 가능하게 연결하는 좁은 범위다. TFA 백엔드보다 우수하다는 증거는 아직 없다.

**6. LLM에게 전부 읽히면 되지 않나?**

외부 원문 자체가 주입 입력이고 결과가 불안정할 수 있다. 파서는 구조와 근거를 보존하고 정책은 검증 가능한 조건으로 판단한다. LLM은 애매한 연결 후보를 돕되 승인이나 안전 인증을 생성하지 않도록 한다.

**7. 정적 검사로 실제 흐름을 알 수 있나?**

완전히 알 수 없다. 명시된 연결과 가능한 경로를 보고한다. 실제 호출·인자·결과 추적은 별도 관측 증거다. 데이터가 부족하면 미판정이지 안전이 아니다.

**8. 읽기 권한과 발행 권한이 있으면 원래 허용 아닌가?**

기술적인 권한과 이번 업무의 승인은 다르다. 회사 내부 자료 읽기 권한이 있다고 그것을 공개할 권한까지 생기는 것은 아니다.

**9. `allowed-tools`나 read-only만 지키면 되지 않나?**

Skill 선언의 강제 여부는 호스트에 달려 있다. 읽기 도구로 가져온 내용을 다른 쓰기 도구가 외부로 전달할 수도 있다. 최종 대상과 정보 이동을 함께 본다.

**10. 요약하면 원문이 아니니까 괜찮지 않나?**

민감한 의미가 요약에도 남을 수 있다. 출처를 유지하고 정책상 허용되는 집계/비식별화가 실제 수행됐는지 별도 확인해야 한다.

**11. 탐지율이 얼마나 나오나?**

아직 일반 탐지율은 없다. 이번은 작은 합성 입력 실험이다. 특히 수작업 조건 8개를 맞춘 것은 설계 검산이지 100% 정확도 증명이 아니다.

**12. 논문 성공률 80%는 뭘 뜻하나?**

CompoSkill의 해당 수치는 CFR, 즉 경로 형성률이다. ASR, 실제 위협 효과 발생률과 구분해야 한다. 논문의 모델·작업·조건을 벗어나 일반화하지 않는다.

**13. 안전하게 실험하려면?**

실제 비밀과 공개 서비스 대신 canary 자료와 mock sink를 사용한다. 실제 agent 실행 단계에는 폐기 가능한 격리 환경과 제한된 도구만 준다. 현재 실험은 문서 검사와 순수 그래프 함수까지만 했다.

**14. 기존 데모는 쓸모없나?**

수집·파서·근거 그래프·버전 비교 구조는 이어 쓸 수 있다. 다만 작은 단일 도구 실험을 전체 스캐너의 한계로 일반화했던 문장은 새 조사에 맞게 좁혀야 한다.

**15. 한 학기에 가능한가?**

데이터 공개 범위 위반 한 종류, 명시적인 Skill→MCP 바인딩, 고정된 정책 계약부터 하면 범위를 통제할 수 있다. 모든 공격·언어·호스트의 실시간 차단을 동시에 목표로 하면 어렵다.

## 회의에서 결정할 네 가지

1. 최초 정책을 **비공개 자료의 비인가 공개**로 제한할지.
2. Skill 파서와 MCP 파서가 주고받을 근거·scope·대상 필드를 무엇으로 고정할지.
3. 정적 검사 MVP를 먼저 만들고, 격리된 실행 평가는 별도 단계로 둘지.
4. Cisco 교차 검사/TFA 비교를 포함한 대조 실험에서 어떤 결과가 나오면 연구 주장을 기각할지.
