# 05. 보안 효과와 사용자 판단 개선을 입증하는 평가 설계

조사 기준일: 2026-09-20  
질문: 우리 플랫폼을 쓰면 위험한 구성을 더 잘 걸러내고 정상 구성을 더 정확하고 빠르게 사용할 수 있는가?

**현재 상태: 미검증.** 이 문서는 관련 연구의 검토와 앞으로 수행할 평가 설계다. 우리 플랫폼의 탐지율·차단율·사용자 성능 결과를 보고하는 문서가 아니다.

## 1. 보안 점검으로 믿고 사용할 수 있게 한다는 목표

보안 점검을 통해 취약한 부분을 찾아 수정하고, 필요한 제한을 적용하고, 그 근거를 제공하면 사용자가 믿고 사용할 수 있는 조건을 만들 수 있다. 이것이 프로젝트의 중심 목표다. 따라서 효과 평가도 화면에 대한 호감이나 승인 속도만으로 끝내서는 안 된다. **실제 보안상 중요한 누락과 잘못된 통과가 줄어드는지**가 우선이다.

다만 “점검에서 문제가 발견되지 않았다”는 결과는 검사 대상·방법·조건에 묶인다. 미래의 모든 입력·업데이트·호스트·원격 서비스까지 취약점이 없다는 증명은 아니다. 이 구분을 명시해야 사용자가 과도한 확신 대신 근거에 맞는 신뢰를 가질 수 있다.

| 확인 내용 | 할 수 있는 표현 | 그 결과만으로 할 수 없는 표현 |
|---|---|---|
| 특정 배포물의 서명·digest 일치 | 검토한 배포물과 동일성이 확인됨 | 제작자가 선의이며 코드에 취약점이 없음 |
| 지정 엔진·규칙의 검사 완료와 미발견 | 기록한 범위에서 해당 검사 항목의 문제를 발견하지 못함 | 모든 종류의 문제를 탐지할 수 있음 |
| 명시한 구성 정책 준수 | 이 설정은 확인한 정책 조건을 만족함 | 지원하지 않는 정책·실행 경로까지 모두 제한됨 |
| 고정 환경의 통제 점검 | 시험한 조건에서 제한이 적용됨 | 모든 입력·환경·새 버전에서도 적용됨 |
| 사용자 과업에서 성능 향상 | 평가한 사용자·과업에서 개선을 관찰함 | 모든 사용자에게 항상 더 안전하고 빠름 |

NVIDIA의 서명 문서 역시 서명을 배포물 동일성 확인과 연결하며 스킬 자체의 안전성 증명과 구분한다. 검사·서명·카드의 역할을 분리하는 선행 설계로 참고할 수 있다. [R32](https://docs.nvidia.com/skills/signing-agent-skills)

## 2. 관련 연구가 제공하는 근거와 반대 근거

### 2.1 권한 정책을 제공한다고 자동으로 더 안전해지지는 않는다

2026-08-27의 preprint *Do User-Authored Permission Policies Improve Protection Against AI Agent Overreach?*는 전문 소프트웨어 배경이 없는 113명을 세 조건으로 나누어 18개 행동 중 7개가 과업 범위를 넘는 모의 상황을 평가했다. 사용자 정책 조건은 매 행동 승인 조건보다 범위 초과 행동 차단이 조정치 기준 20.1%p 낮았다. 질문 수는 줄었지만 설정을 포함한 전체 개입 시간이 확실히 감소했다고 보지는 않았다. [R38: 원문](https://arxiv.org/html/2608.27443v1)

자동 검토 조건과의 차이도 제시되지만 다중 비교 보정 후에는 같은 수준의 유의성을 유지하지 못했다. 이 연구는 비개발자·모의 실행·특정 정책 UI의 결과이며 스킬 설치 검토와 동일하지 않다. **권한 화면이나 사용자 선택권을 늘렸다는 사실만으로 보안 향상을 주장할 수 없다는 반대 근거**로 사용한다. [R38](https://arxiv.org/html/2608.27443v1)

### 2.2 설명이 신뢰를 높여도 정답률을 높이지 않을 수 있다

Bansal 등의 CHI 2021 연구는 세 데이터셋의 의사결정 과업에서 AI 설명이 인간·AI의 상호 보완적 성능을 추가로 높이지 못한 조건을 보고했다. 설명은 추천의 정오와 관계없이 수용을 늘릴 수 있었다. 보안 설치 과업의 실험은 아니므로 그 효과 크기를 가져오지 않고, **설명의 설득력과 판단 정확도를 별도 측정해야 한다는 설계 근거**로 사용한다. [R39: 저자 원문](https://aiweb.cs.washington.edu/ai/pubs/bansal-chi21.pdf)

### 2.3 더 안전한 판단이 항상 더 편한 경험은 아니다

Buçinca 등의 2021년 연구는 199명 실험에서 숙고를 유도하는 개입이 단순 설명보다 과도한 AI 의존을 줄일 수 있지만, 효과가 큰 설계의 주관적 선호는 낮을 수 있음을 보고했다. 인지적 동기에 따른 효과 차이도 있었다. 일반 의사결정 연구이므로 우리 플랫폼의 보안 효과로 직접 일반화하지 않는다. [R40: 논문](https://arxiv.org/abs/2102.09692)

**평가에 반영할 점:** 사용자가 좋아하는 화면, 빠른 승인, 높은 신뢰 응답만으로 성공을 정하지 않는다. 위험 승인·정상 거부·작업 완료·시간·확신도를 함께 기록한다.

### 2.4 권한은 인터페이스와 실제 강제를 연결해야 한다

21개 연구 시스템·제안과 5개 상용 에이전트를 검토한 2026년 연구는 인터페이스, 내부 정책 표현, 강제를 함께 분석한다. 우리의 효과 평가도 “정책이 화면에 보인다”와 “실제 실행 경로에서 적용된다”를 구분해야 한다. 이 연구 자체가 우리 제품의 개선을 검증한 것은 아니다. [R19](https://arxiv.org/html/2607.13718v1)

### 2.5 자동 판정 데이터셋을 그대로 정답으로 쓰면 안 된다

ClawHub Security Signals의 라벨은 registry 자동 판정이다. 스캐너 간 불일치가 나타난다고 어느 쪽이 정답인지 확정되지 않는다. 이 자료를 비교 대상 엔진의 정답으로 사용하면 입력 신호와 최종 라벨 사이의 순환 평가가 생길 수 있다. 공개 train/test/holdout 구분이 있어도 이 문제나 복제·계보 누출이 자동으로 해결되지는 않는다. [R37](https://arxiv.org/html/2606.01494v1)

따라서 공개 자료는 사례 발굴·분포 파악·외적 검증 후보로 활용하고, 핵심 성능 평가는 독립적인 근거와 판정 절차를 갖춘 과업 집합으로 수행한다.

## 3. 세 가지 효과를 따로 입증하기

| 평가 축 | 핵심 질문 | 필요한 증거 | 가능한 기여 |
|---|---|---|---|
| A. 기술적 검토 정확성 | 대상을 정확히 식별하고 문제·미검사·중요 변경을 놓치지 않는가? | 고정 사례, 정답 근거, 엔진 상태, 원본 결과 | 분석·증거 결합의 정확성 |
| B. 사용자 결정 품질 | 위험 승인을 줄이고 정상 사용을 과도하게 막지 않는가? | 무작위 비교, 결정·근거·시간·확신도 | 검토 지원의 효과 |
| C. 운영에서의 통제 | 검토 조건이 실제 사용·업데이트에도 유지되는가? | 적용된 정책·게이트·변경 후 재검토 기록 | 검사와 사용의 연결 |

정적 보고서만 만드는 MVP라면 A와 B를 먼저 평가할 수 있다. C에서 구현하지 않은 runtime 차단 효과를 성과에 포함하지 않는다. 공유 링크를 제공한 것과 실제 호스트가 그 승인 조건을 강제하는 것도 다른 구현이다.

## 4. 평가 전에 고정할 문제 정의

### 4.1 위협과 정상 과업

첫 평가는 다음과 같은 **검토상 실패**에 집중한다.

- 현재 설치본과 다른 버전의 검사 결과를 적용하는 경우.
- 필수 검사 실패·미지원·누락을 “문제 없음”으로 처리하는 경우.
- 명시적인 정책 위반이나 접근 범위 변경을 놓치는 경우.
- 이전 승인 조건이 달라졌는데 그대로 재사용하는 경우.
- 정상적인 변경·권한 축소·근거 있는 허용을 불필요하게 거부하는 경우.

평가용 자료는 무해한 합성 설정과 정적으로 검토할 수 있는 고정 문서로 구성한다. 외부 운영 시스템에 공격하거나 유출을 재현할 필요가 없다. 실제 사고 전체를 재현하지 않으므로 결과도 정의한 검토 실패에 한정한다.

### 4.2 판정은 세 갈래다

| 정답 상태 | 정의 | 적절한 결정 |
|---|---|---|
| 허용 가능 | 명시한 목적·정책·검사 조건을 충족하는 근거가 있음 | 해당 조건 안에서 허용 |
| 허용 불가 | 독립 근거로 정책 위반 또는 필수 조건 불충족이 확정됨 | 거부 또는 수정 요구 |
| 근거 부족 | 필요한 정보가 없거나 해석·검사가 완료되지 않음 | 보류 및 추가 근거 요청 |

허용 가능은 “절대적으로 안전”을 뜻하지 않는다. 근거 부족은 악성과도 다르다. 세 번째 상태를 억지로 안전/위험 이진 라벨로 바꾸면 검토 성능의 중요한 부분을 잃는다.

### 4.3 정책과 목적은 참가자에게 제공한다

예를 들어 “이 작업은 지정된 프로젝트 자료의 읽기와 지정 출력 위치의 쓰기만 허용한다”처럼 판단 기준을 명시한다. 불필요한 권한 여부는 목적에 의존하므로, 어떤 작업을 하려는지 숨기고 넓은 권한을 모두 정답상 악성으로 처리하지 않는다.

## 5. 사례 집합 설계 — 미실행

### 5.1 구성과 분할

첫 기술 pilot는 검토 가능한 60~120개 사례를 만드는 안으로 시작할 수 있다. 이 수는 **작업량 가정**이며 충분한 통계 검정력을 보장하는 숫자가 아니다. 개발·튜닝용과 최종 평가용을 먼저 나누고 같은 원본의 파생본은 같은 집합에 넣는다.

| 사례 계층 | 포함할 내용 | 피해야 할 편향 |
|---|---|---|
| 정상·허용 가능 | 제한된 접근, 정당한 외부 연결, 권한 축소, 설명만 변경 | 위험한 단어가 있는 문서를 전부 위반으로 라벨링 |
| 명시적 위반·조건 불충족 | 정한 정책과 모순된 설정, digest 불일치, 필수 검사 미완료 | 엔진 규칙과 똑같은 패턴만 만들어 정답률 부풀리기 |
| 근거 부족 | 원격 코드 미확인, 빠진 정책, 해석 불가 입력 | 모두 거부해도 성공한 것처럼 계산 |
| 관계·변경 사례 | 명시적 참조, 같은 호스트에만 등록, 정상 변경과 중요한 변경 쌍 | 함께 등장했다는 이유로 확정 흐름 만들기 |

현실에서의 발생 빈도를 모르면 위 계층을 균형 있게 구성해 범위별 성능을 보고한다. 그 정확도를 실제 시장의 탐지 정밀도로 그대로 환산하지 않는다. 현실 빈도를 가정해 시뮬레이션한 결과는 실측치와 분리한다.

### 5.2 독립 정답 작성

1. 고정된 목적·정책·원본 파일·설정·digest를 먼저 준비한다.
2. 평가할 스캐너 출력과 플랫폼 판단을 보지 않은 두 검토자가 독립적으로 판정한다.
3. 각 판정에 근거 위치, 적용 정책, 충분하지 않은 정보, 허용 가능한 결정의 집합을 기록한다.
4. 불일치는 제3의 검토 또는 합의 절차로 정리하고 합의 전 결과도 보존한다.
5. 끝내 결정할 수 없는 사례는 근거 부족으로 유지한다. 모호한 사례를 결과 확인 후 임의로 삭제하지 않는다.

학생 팀 구성원이 사례를 만든 경우 그 사람이 자기 시스템의 정답을 단독 확정하지 않도록 분리한다. 외부 검토자를 확보하지 못하면 내부 검증이라는 한계를 명시한다. 이는 형식적 “gold”라는 이름보다 중요하다.

### 5.3 누출 방지

원본 저장소·작성자 계보·내용 유사도·버전 쌍을 기준으로 묶는다. 같은 스킬을 경로만 바꿔 train/test에 나누지 않는다. 개발자는 최종 사례의 정답에 맞춰 규칙과 화면 문구를 조정하지 않는다. 공개 benchmark를 엔진 개발자가 이미 활용했을 수 있으면 독립 holdout이라고 단정하지 않는다.

사례가 정제되거나 민감 문자열이 제거되면 검사 신호가 달라질 수 있다. 원본 실행을 재현했다고 주장하지 말고 정제된 평가 자료의 범위에 맞춰 결과를 발표한다.

## 6. A축: 기술적 검토 정확성 평가

### 6.1 대조군

| 조건 | 제공되는 것 | 무엇을 비교하는가 |
|---|---|---|
| A0 | 선택한 기존 검사·잠금·baseline·증거 기능 | 현실적인 기존 방법의 기준 |
| A1 | A0와 동일 엔진·동일 입력 + 우리 대상 연결·변경·상태 처리 | 근거 결합 자체의 추가 효과 |
| A2, 선택 | A1 + 새 분석 규칙 또는 추가 엔진 | 새 탐지 기능의 별도 효과 |

도구마다 지원 범위가 다르면 공통 범위와 추가 범위를 분리한다. 동일한 입력 접근권한·네트워크 조건·시간 제한을 제공한다. 미지원 형식의 수집 실패를 탐지 성공으로 세지 않는다.

### 6.2 핵심 지표

| 지표 | 계산·단위 | 주의점 |
|---|---|---|
| 위반 누락률 | 위반으로 확정된 사례 중 필요한 위반을 놓친 비율 | finding 개수와 사례 개수를 섞지 않기 |
| 잘못된 통과율 | 허용 불가 사례 중 시스템이 사용 가능으로 표시한 비율 | 단순 finding 미발견률과 구분 |
| 정상 오탐·과잉 보류 | 허용 가능 사례 중 불필요한 문제·보류를 만든 비율 | 모두 보류하는 시스템의 허위 성공 방지 |
| 불완전 검사 은폐율 | 실패·미실행·미지원인데 완료·통과로 표시한 비율 | 대상 전체 중 비율과 오류 사례 중 비율을 함께 기록 |
| 대상 매칭 정확도 | 보고서·설치본·버전·설정 연결의 정답률 | 이름만 같은 대상을 연결하지 않기 |
| 중요 변경 탐지 | 정답으로 정의된 변경 항목의 precision·recall | 정상 변화와 권한 축소를 포함 |
| 관계 복원 정확도 | 명시적 근거가 있는 edge의 precision·recall | 추정·동시 설치를 확정 edge와 구분 |
| 비용 | 검사 시간, 수집 시간, API 사용·운영 비용 | cold/warm, 로컬/API 조건 분리 |

점수를 하나로 합치기 전에 위반 종류·형식·심각도·근거 부족 유형별 결과를 제시한다. 결과가 0건이면 실제 완료된 필수 검사가 몇 개인지 같이 보여 준다.

### 6.3 동작 안정성

동일 파일·정책·엔진·규칙·설정으로 결과가 바뀌는지 확인한다. LLM 분석은 모델 식별자·프롬프트·설정·응답을 기록하고, 반복 실행의 변동과 API 실패를 별도로 보고한다. 가능한 모든 검사를 무한 반복하지 않고 개발 pilot에서 변동을 확인한 뒤 사전 고정한 횟수만 수행한다.

### 6.4 실행 무결성의 최소 관문

최종 평가 전 다음 경우가 “통과”가 되지 않는지 확인한다.

- 필수 엔진의 실행 오류 또는 timeout.
- 결과 파일 파싱 실패나 미지원 스키마.
- 검사 입력과 표시된 대상 digest 불일치.
- 승인 이후 적용 정책·설정의 변경.
- 일부 파일·형식의 제외 사실이 누락된 전체 통과 표시.

이 관문을 통과했다는 것은 상태 처리의 정확성이지 전체 취약점 부재의 증명은 아니다.

## 7. B축: 사용자 결정 평가

### 7.1 비교 조건

핵심 실험에서는 **기존 도구를 충분히 쓴 화면**과 **동일 자료를 제공하는 우리 화면**을 비교한다. 기존 쪽에 원문만 주고 우리 쪽에 전문가 정답을 주는 식의 비교를 피한다.

| 조건 | 화면·자료 | 분리하려는 효과 |
|---|---|---|
| B0 | 기존 보고서·diff·카드·evidence pack과 사용법 | 현재 현실적인 검토 |
| B1 | 같은 정보의 일관된 목록·상세 화면 | 정보 정리·탐색 개선 |
| B2, 선택 | B1 + 관계 그래프·변경 연결 | 그래프와 관계 표현의 추가 가치 |

참가자 수가 적으면 B0 대 B1을 주 비교로 하고 B2는 별도 pilot로 둔다. 분석기를 바꾸는 실험과 동시에 수행하면 보안 향상이 UI 때문인지 엔진 때문인지 구분하기 어렵다.

### 7.2 배정과 진행

모집 대상은 실제 외부 구성 도입 경험이 있는 개발자와 초보 사용자를 구분한다. 초기 사용성 pilot 6~8명은 지시문·과업 길이·기록 오류를 고치는 데 사용할 수 있지만 효과 입증 표본으로 합산하지 않는다.

동일 참가자가 두 조건을 경험하는 설계에서는 난이도가 비슷한 서로 다른 사례 집합을 사용하고 순서를 교차 배정한다. 같은 파일의 정답을 기억해서 빨라지는 효과를 피한다. 참가자 간 설계를 선택한다면 사전 경험을 층화해 배정하고 필요한 표본 수를 다시 계산한다.

각 과업에서는 목적·정책을 읽은 뒤 허용/거부/보류, 이유, 추가로 필요한 정보, 확신도를 기록한다. 도구 교육·연습 과업과 본 평가를 분리한다. 조건별 전체 과업 시간에는 실제 검토·필요한 재탐색을 포함하며 실패·중도 포기 시간을 삭제하지 않는다.

### 7.3 주 지표와 보조 지표

| 지표 | 정의 | 원하는 방향 |
|---|---|---|
| 위험 승인율 | 허용 불가 사례 중 참가자가 허용한 비율 | 감소 |
| 정상 거부율 | 허용 가능 사례 중 거부한 비율 | 감소 또는 허용한 한도 내 유지 |
| 근거 부족의 적절한 처리 | 필요한 정보를 식별하고 보류한 비율 | 증가 |
| 정확한 결정까지의 부담 | 결정 정확도와 전체 소요 시간의 공동 결과 | 정확도를 훼손하지 않는 시간 감소 |
| 근거 이해 | 대상 버전·범위·필수 제한을 정확히 설명한 비율 | 증가 |
| 과도한 확신 | 틀린 결정에 높은 확신을 준 비율 | 감소 |
| 검토 범위 | 확정 결정을 내린 비율과 보류율 | 안전성 지표와 함께 해석 |
| 주관적 사용성 | 편의·부담·만족·신뢰 응답 | 보조 결과로만 사용 |

시간을 “맞힌 과업만” 비교하면 조건마다 남는 사례가 달라지는 선택 편향이 생긴다. 전체 과업의 시간·실패·timeout과 정확도를 함께 보고하고, 정답 과업만의 시간은 보조 분석으로 표시한다.

확신도를 이진 확률로 받는다면 명확히 허용/불가로 판정된 사례에서 보정 곡선이나 Brier score를 사용할 수 있다. 근거 부족 사례에는 별도의 응답 척도를 사용하고 억지로 이진 정답을 부여하지 않는다.

## 8. C축: 검사 결과가 사용 조건과 연결되는지

### 8.1 정적 MVP에서 주장 가능한 범위

처음에는 검사 입력과 승인 대상을 묶고, 변경 시 승인이 재검토 상태가 되며, 공유한 근거가 같은 대상으로 연결되는지를 확인할 수 있다. 이것만 구현했다면 **사용 전 검토·배포 과정의 근거 관리**라고 표현한다.

### 8.2 실행 통제를 추가했을 때의 평가

특정 호스트의 기존 정책·gateway와 연결했다면, 직접 관리하는 시험 환경에서 허용된 정상 작업의 성공과 금지된 무해한 테스트 작업의 거부를 확인한다. 실제 서비스 자격 증명·개인정보 대신 시험용 자원만 사용한다. 목적은 설정한 제한의 적용 여부 확인이며 알려진 취약점의 공격 재현이 아니다.

결과에는 호스트·OS·connector·정책·실제 강제 지점을 기록한다. 다른 환경에서도 동작한다고 확대하지 않는다. 감사 로그에 거부 이벤트가 있다는 것과 최종 자원이 변경되지 않았다는 것은 별개의 관측이므로, 구현이 주장하는 효과에 맞는 최종 상태 증거가 필요하다.

### 8.3 유효성 조건

승인 대상은 다음 정보를 연결해야 한다.

`구성요소 digest + 구성·정책 digest + 호스트 조건 + 필수 검사 완료 증거 + 승인·예외 기록`

이는 하나의 파일 해시로 보안 전체를 증명한다는 뜻이 아니다. 변경이 발생했을 때 어떤 근거를 재검토할지 식별하는 기준이다. 원격 서버처럼 동일성을 확인할 수 없는 항목은 미확인 상태와 갱신 조건을 따로 둔다.

## 9. 표본 수와 분석 계획

### 9.1 인원을 임의로 “충분하다”고 정하지 않기

Lakens의 *Sample Size Justification*은 최소 관심 효과, 기대 정밀도, 검정력, 자원 제약 등 표본 수의 근거를 명시할 것을 다룬다. 작은 pilot에서 크게 나온 효과만 이용해 표본을 줄이는 방식은 피한다. [R41: 논문](https://doi.org/10.1525/collabra.33267)

우리 주 지표인 위험 승인율에 대해 기존 조건의 비율과 최소 개선 폭을 먼저 정한다. 참가자와 사례가 반복되는 설계이면 그 구조를 반영한 모의 검정력·민감도 분석으로 필요한 규모를 정한다. 학기 일정상 필요한 인원을 모집할 수 없다면 결과를 **탐색적 평가**로 명시하고 신뢰구간을 보고한다. “30명이라 통계적으로 충분하다”는 식으로 정하지 않는다.

### 9.2 분석 단위

한 참가자의 20개 응답을 20명의 독립 표본으로 취급하지 않는다. 같은 스킬의 여러 수정본도 완전히 독립된 구성으로 취급하지 않는다. 사용자 결정에는 참가자·사례 효과를 고려하는 혼합 모형 등을 사용하고, 기술 사례에는 원본 계보를 고려한 집계·구간 추정을 사용한다. 표본이 작아 복잡한 모형이 불안정하면 참가자별 결과·원자료 분포·단순한 사전 지정 비교로 범위를 줄인다.

### 9.3 사전 고정할 사항

- 주 지표와 주 대조군, 허용하는 안전성 저하 한도 및 최소 관심 개선 폭.
- 참가자 모집·제외·중단·결측·timeout 처리 방식.
- 사례 분할, 무작위 배정, 순서 교차 방식.
- 분석식·구간 추정·다중 비교 처리·보조 분석 목록.
- 엔진·규칙·모델·정책 버전과 결과 표시 방식.
- 결과가 가설과 반대일 때도 공개할 표와 실패 사례.

주 지표를 결과를 본 뒤 선택하지 않는다. 통계적으로 유의하지 않은 차이를 “동일함”이나 “성능 저하 없음”으로 해석하지 않는다. 비열등성 주장이 필요하다면 허용 한도와 그에 맞는 설계를 사전에 정한다.

### 9.4 실패가 0건인 결과의 한계

독립적인 N개 위험 사례에서 누락이 0건이어도 실제 누락 확률이 0임을 증명하지 않는다. 단순 이항모형의 단측 95% 상한은 `1 - 0.05^(1/N)`이다. 예를 들어 N=100이면 약 2.95%다. 이는 **계산 예시**이며 이번 플랫폼의 실험값이 아니다. 사례가 서로 유사하거나 같은 사용자가 반복 판단했다면 이 독립 가정도 그대로 적용할 수 없다.

## 10. 성공·실패 기준

수치 목표는 현장 요구와 pilot의 변동을 확인한 후 본 실험 전에 정한다. 현재 단계에서 목표치를 달성했다고 기록하지 않는다.

| 결과 | 인정할 수 있는 결론 |
|---|---|
| 중요한 누락이 줄고 정상 과업의 부담도 수용 범위에 있음 | 정의한 범위의 보안 검토 효과 향상 |
| 기술적 탐지는 같지만 사용자 위험 승인이 감소 | 근거 전달·판단 지원 효과 |
| 보안상 동등함을 적절한 설계로 확인하면서 시간이 줄어듦 | 검토 효율 개선 |
| 신뢰·만족만 증가 | 사용성·인식 변화만 확인. 보안 효과 주장은 보류 |
| 시간이 줄지만 위험 승인이 증가 | 안전한 플랫폼 목표에 미달 |
| 모든 것을 보류해 위험 승인이 감소 | 사용 가능성과 검토 범위를 같이 보아야 함 |
| 기존 도구 조합과 의미 있는 차이가 없음 | 새로운 차별성 가설을 입증하지 못함 |

학술적 성과와 제품적 성과도 구분한다. 차이가 없다는 결과를 정확히 설명하는 비교 연구는 가치가 있지만, 그 결과로 새 제품이 더 필요하다고 주장할 수는 없다.

## 11. 결과 보고와 보관 형식

다음은 **빈 결과 양식**이다. 실제 수행 전에는 값 대신 `NOT_RUN`을 유지한다.

| 항목 | 현재 상태 | 실행 후 채울 근거 |
|---|---|---|
| 사례·정답 집합 | NOT_RUN | 버전·계보·판정 근거·합의 기록 |
| 기존 도구 실행 | NOT_RUN | 입력·명령·설정·환경·원본 결과·오류 |
| 플랫폼 기술 평가 | NOT_RUN | 사례별 예측·상태·매칭·변경 결과 |
| 사용자 평가 | NOT_RUN | 동의한 익명 기록·조건 배정·결정·시간·확신 |
| 실행 통제 평가 | NOT_RUN | 적용 정책·최종 상태·지원 환경 |
| 통계 분석 | NOT_RUN | 사전 계획·집계 코드·효과 크기·구간 |

보관할 논리 단위는 `case`, `reference_decision`, `scan_run`, `finding`, `configuration_snapshot`, `review_decision`, `study_trial`이다. 각 결과에서 입력까지 거슬러갈 수 있게 식별자를 연결한다. 비밀정보가 포함된 원문·키·전체 사용자 작업 기록을 불필요하게 모으지 않는다.

## 12. 사용자에게 보여 줄 신뢰 표현

아래는 **표시 설계 예시**이며 실제 검사 결과가 아니다.

| 사용자에게 제공할 내용 | 목적 |
|---|---|
| “이 버전·이 설정에 대해 검토 완료” | 결과의 적용 대상을 고정 |
| “검사한 항목 / 제외·실패한 항목” | 미검사를 무발견으로 오해하지 않게 함 |
| “허용 조건과 필요한 제한” | 안전한 사용을 구체적인 행동과 연결 |
| “발견한 문제·수정·수용한 예외” | 무조건적인 녹색 배지의 과신 방지 |
| “변경되어 다시 확인할 항목” | 과거 결과의 무제한 재사용 방지 |
| “검토 근거와 책임자” | 다른 사람이 검토를 이어갈 수 있게 함 |

제품 문구는 “취약점 0개 인증”보다 **“명시한 범위의 점검을 통과했으며 이 조건에서 사용하도록 검토됨”**이 적절하다. 필요한 통제가 실제 적용되는 제품이라면 적용 상태도 함께 보여 줄 수 있다. 이 표현의 이해도와 과신 여부 자체를 사용자 평가에서 확인한다.

## 13. 실행 순서 제안

1. **대상 고정:** 호스트 한 종류·구성 형식·목적·정책·첫 검토 과업을 정한다.
2. **문제 관찰:** 실제 사용자 도입 사례와 기존 도구의 처리 과정을 확인한다.
3. **독립 사례 작성:** 정상·위반·근거 부족을 포함하고 개발/최종 집합을 분리한다.
4. **강한 대조군 실행:** baseline·증거 묶음까지 사용해 남는 문제를 기록한다.
5. **추가 기능 구현:** 확인된 문제를 해결하는 기능만 더한다.
6. **기술 관문 통과:** 대상 불일치·불완전 검사 은폐부터 확인한다.
7. **사용자 pilot와 본 평가:** 안전성·시간·과신을 함께 측정한다.
8. **결론 갱신:** 개선·무차이·악화를 모두 근거에 따라 보고한다.

최종적으로 입증하려는 것은 사용자가 더 안심한다는 느낌만이 아니다. **검사한 구성과 실제 사용하는 구성을 연결하고, 확인된 위험을 줄이며, 근거가 부족한 상황을 올바르게 드러내는 플랫폼이 실제로 작동하는지**다.
