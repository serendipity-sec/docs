본 논문은 OpenAI Agents SDK 계열의 워크플로우 10개를 대상으로 방법의 실행 가능성과 진단 가치를 평가한다. 범용적인 안전성 증명이나 상용 시스템 전체에 대한 검증 결과를 제시한 연구는 아님.

## 왜 이런 연구가 필요한가?

### 최종 답변만으로는 내부 동작을 알 수 없다

다음은 이해를 위한 가상 예시이다.

고객 지원 시스템에 세 에이전트가 있다고 가정한다.

- 접수 담당: 사용자 요청을 적절한 담당자에게 전달
- 안내 담당: 규정과 자주 묻는 질문에 답변
- 환불 담당: 환불 도구를 사용해 처리

사용자가 “환불해 주세요”라고 했을 때 시스템이 “환불 요청을 처리했습니다”라고 답했다고 해도, 이 답변만으로는 다음을 알 수 없다.

1. 환불 담당에게 실제로 전달했는가?
2. 환불 담당이 환불 도구를 호출했는가?
3. 접수 담당이 권한 없이 환불 도구를 직접 호출했는가?
4. 실제 처리는 하지 않고 완료했다고 말했는가?

따라서 **결과의 품질과 내부 경로의 실행 여부는 별도로 확인**해야 한다.

논문이 지적하는 문제도 같다. 기존의 과제 성공률·최종 답변 품질 중심 평가에서는 일부 도구, 금지된 접근 관계, 위임 경로가 시험되지 않은 채 남을 수 있다.

### 커버리지는 “얼마나 시험했는가”를 나타낸다

커버리지는 전체 시험 대상 중 실제로 시험한 부분의 비율이다.

예를 들어 프로그램에 분기가 10개 있는데 시험 중 7개를 실행했다면, 해당 기준의 커버리지는 70%이다. 다만 70%를 실행했다는 사실이 그 부분의 모든 동작이 올바르다는 뜻은 아니다.

이 논문은 이러한 생각을 에이전트 시스템에 적용한다. 코드의 문장이나 분기 대신 에이전트, 도구 접근 관계, 위임 관계를 시험 대상으로 삼는다.

## 핵심 아이디어: 워크플로우를 그래프로 표현한다

논문은 워크플로우를 유형이 있는 협업 그래프(typed coordination graph)로 표현한다. 

여기서 그래프는 구성요소와 연결 관계를 나타내는 자료구조이다. “유형이 있다”는 것은 연결마다 의미가 다르다는 뜻.

| 구성 요소 | 의미 |
| --- | --- |
| 에이전트 노드 | 작업을 판단하고 수행하는 에이전트 |
| 도구 노드 | 에이전트가 호출하는 기능 |
| 허용 도구 간선 | 특정 에이전트가 특정 도구를 사용하도록 허용된 관계 |
| 금지 도구 간선 | 특정 에이전트가 특정 도구를 사용하지 못하도록 선언된 관계 |
| 위임 간선 | 한 에이전트에서 다른 에이전트로 작업·제어가 넘어가는 관계 |

이 구조를 수식으로 표현하면 다음과 같다.

$$
G(S)=(V_A,V_T,E_{\text{allow}},E_{\text{restrict}},E_{\text{del}}) 
$$

- $S$: 정규화한 워크플로우 명세
- $V_A$: 에이전트 집합
- $V_T$: 도구 집합
- $E_{\text{allow}}$: 허용된 에이전트–도구 관계
- $E_{\text{restrict}}$: 금지된 에이전트–도구 관계
- $E_{\text{del}}$: 에이전트 사이의 위임 관계

이 그래프가 “무엇을 시험해야 하는가”를 결정한다. LLM이 중요해 보이는 시험 대상을 임의로 고르는 구조가 아니다.

두 가지 조건도 중요하다.

1. 시작 에이전트에서 위임 경로를 따라 도달 가능한 에이전트와 관계만 커버리지 대상으로 삼는다. 명세상 존재하지만 시작점과 연결되지 않은 에이전트는 대상에서 제외된다.
2. 허용·금지 관계가 모두 선언되지 않은 에이전트-도구 조합은 미지정 관계로 취급하며 시험 의무를 만들지 않는다. 따라서 “허용되지 않은 모든 조합을 자동으로 금지 시험한다”고 이해하면 부정확하다.

## 커버리지 기준

논문은 그래프에서 네 종류의 시험 의무(obligation)를 만든다. 시험 의무란 “이 항목을 시험했다는 실행 증거가 필요하다”는 뜻이다.

| 기준 | 확인하는 대상 | 필요한 증거 |
| --- | --- | --- |
| **C1: 에이전트 커버리지** | 도달 가능한 각 에이전트 | 실행 기록에 해당 에이전트가 나타남 |
| **C2: 허용 도구 커버리지** | 허용된 각 에이전트–도구 관계 | 해당 에이전트가 해당 도구를 호출함 |
| **C3: 금지 도구 커버리지** | 금지된 각 에이전트–도구 관계 | 금지 접근에 대한 명시적인 관찰 기록 |
| **C4: 위임 커버리지** | 선언된 각 위임 관계 | 해당 에이전트 사이의 위임이 발생함 |

여기서 C2는 도구 자체만 세지 않는다. 같은 도구를 두 에이전트가 사용할 수 있다면, 각 에이전트가 그 도구를 사용하는 관계를 따로 시험한다.

### C3: 호출이 없었다는 사실만으로는 부족하다

금지된 도구 호출이 한 번도 없었다고 해도 다음 두 상황을 구분해야 한다.

- 금지된 동작을 요구했지만 시스템이 차단한 경우
- 그 동작을 요구한 적이 없어서 호출되지 않은 경우

후자는 금지 경계를 시험했다는 증거가 아니다. 논문은 거절·정책 이벤트·차단·금지 호출 시도 등 명시적인 관찰이 필요하다고 정의한다.

다만 실제 실험의 C3 집계는 금지 호출 시도를 유도했는지를 센다.

따라서 실험표에서 C3의 “성공”의 의미는 다음과 같다.

> 공격적인 사용자 요청으로 목표 에이전트의 금지 도구 호출 시도를 관찰했다.
> 

이는 안전하게 차단했다는 뜻이 아니며, C2·C4의 성공과 방향이 반대이므로 결과 해석에서 반드시 구분해야 한다.

### 커버리지 수식

기본 계산은 다음과 같다.

$$
\text{커버리지}
=
\frac{\text{실행 증거가 확보된 시험 의무 수}}
{\text{전체 시험 의무 수}}
$$

- 예시: 허용된 에이전트-도구 관계가 5개이고, 그 중 3개를 관찰했다면 C2는 3/5 = 60%이다.

시험을 100번 실행했더라도 같은 관계만 반복해서 관찰했다면 커버리지는 늘지 않는다. 중요한 것은 ‘새로운 시험 대상을 실제로 실행했는가’이다.

## 시스템은 어떻게 시험을 만드는가?

논문의 처리 순서는 명세 추출 → 그래프 구성 → 시험 의무 도출 → 자연어 시나리오 생성 → 실행 증거 확인이다.

### 1. 소스에서 워크플로우 명세를 추출한다

프로토타입은 python 진입점을 불러와 에이전트, 도구, handoff 객체를 조사하고 정규화한 명세를 만든다.

handoff는 작업을 다른 에이전트에게 넘기는 기능이다. 외부 python 코드에서 담당 에이전트를 바꾸는 일부 워크플로우는 기존 제어 이전을 그래프에 나타내도록 추출 단계에서 변환했다. 따라서 모든 벤치마크가 단순한 객체 탐색만으로 동일하게 처리된 것은 아니다.

### 2. 각 시험의무를 구체적인 목표로 바꾼다

목표는 네 가지 형태이다. 

| 목표 | 의미 |
| --- | --- |
| `Reach(a)` | 에이전트 $a$가 실행되게 하라 |
| `UseTool(a,t)` | 에이전트 $a$가 허용 도구 $t$를 호출하게 하라 |
| `RestrictTool(a,t)` | 에이전트 $a$의 금지 도구 $t$ 경계를 시험하라 |
| `Delegate(a,b)` | 에이전트 $a$에서 $b$로 위임되게 하라 |

한 시험이 여러 목표의 증거를 제공할 수도 있다. 예를 들어 특정 에이전트의 도구 호출을 관찰했다면, 그 에이전트가 실행됐다는 증거도 함께 확보된다.

구현은 이런 호환 가능한 목표를 일부 묶지만, 서로 다른 종류의 목표를 무제한으로 합치는 방식은 아니다.
