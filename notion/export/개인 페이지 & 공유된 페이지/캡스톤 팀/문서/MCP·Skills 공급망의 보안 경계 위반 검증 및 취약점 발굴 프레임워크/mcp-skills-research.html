01
WHY THIS PROJECT

확장 기능의 위험은 이미 보고됐습니다.

AI가 파일과 도구를 실제로 다루면서, 확장 패키지의 지시문과 구현 결함이 사용자 자원에 영향을 줄 수 있습니다. 필요한 것은 위험 후보를 실제 피해 가능성과 연결하는 검증입니다.

위 값은 각 연구의 표본·탐지 기준에서 보고된 수치입니다. 전체 생태계의 취약 비율이나 실제 공격 성공률을 뜻하지 않습니다.

문제 01

설명과 행동은 다를 수 있다

읽기 전용이라고 소개돼도, 실제 파일 접근·전송·프로세스 동작은 별도로 확인해야 합니다.

문제 02

경고만으로는 결론을 못 낸다

의심스러운 기능이 정상 목적일 수도 있고, 경고가 없는 구현에 경계 검증 누락이 있을 수도 있습니다.

문제 03

버전과 구성이 판단을 바꾼다

같은 이름의 패키지도 스크립트·참조 파일·의존성·권한 변경으로 보안 영향이 달라질 수 있습니다.

설계 선택근거구현에서 확인할 것
스킬 패키지 전체 분석공식 명세

정책을 대상 밖에서 관리공식 명세 + 팀의 설계 판단
Skills의 allowed-tools 지원은 구현마다 다르며, 불신 MCP 서버의 도구 어노테이션은 신뢰할 수 없습니다.[8][10]		제품이 약속한 경계·배포 사용자의 정책·연구 가정을 구분하고, 연구 가정 위반을 곧바로 제품 취약점으로 보고하지 않음
직접 호출과 에이전트 시험 분리선행프로젝트 + 팀의 설계 판단
Promptfoo는 직접 MCP 시험과 에이전트 시험을 구분합니다.[7]		구현 자체의 문제와 에이전트를 통해 도달한 문제를 분리; 호스트·모델·승인·호출 설정 고정

분류 원칙: 외부 입력 공격, 정상 구현의 결함, 악성 공급자·업데이트, 과도한 배포 권한을 구분합니다. 악성 패키지의 코드가 실행됐다는 사실만으로 MCP 프로토콜 취약점이라고 부르지 않습니다.

HOW VERIFICATION WORKS

“시도했다”와 “실제로 성공했다”를 구분합니다.
