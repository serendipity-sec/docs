# 지도교수 면담: 프론트 페이지 시안 공유와 캡스톤 경진대회 방향

- **일시**: 2026-11-12

## 안건별 논의 내용

### 1. 프론트 페이지 시안 공유
아직 디자인만 한 상태로, 확정되면 그대로 개발에 넘길 계획임. 화면은 **공개**와 **관리자** 두 부분으로 나뉨.
- **공개**: 로그인 없이 워크플로우별 검증 결과와 보안 의심 정황을 보여 줌. 상세 페이지에서는 케이스별 문제 발생 여부를 보여 줌(예: `order lookup` 워크플로우 2번째 버전의 `order-001-normal` 케이스 결과). 일반 사용자는 검증을 요청할 수 없고 보기만 가능함. 실시간성이 크게 의미 없어서 일정 주기 자동 갱신이나 새로고침으로 반영함.
- **관리자**: GitHub 조직에 등록된 사용자만 GitHub OAuth로 인증하며, 세션은 하루 동안 유지됨. 실패·드래프트 건과 그 사유까지 보여 줌. 페이지 안에서 검증을 바로 실행하거나, 로컬에서 검증한 결과를 API 엔드포인트로 보내 저장할 수 있게 할 예정임.

### 2. 검증 방식과 진행 현황
검증에 LLM이 들어가며, 외부 LLM과 로컬 LLM 둘 다 쓸 수 있지만 결과 품질 때문에 외부 LLM을 우선 쓸 예정임. 현재 등록된 워크플로우는 1개이고, 위험한 변형 조합을 모두 테스트해 본 뒤 수준이 괜찮아지면 워크플로우를 한꺼번에 추가할 계획임. 정적·동적 분석은 테스트가 더 필요함. 남은 작업은 벡터 DB 연결이며, 이번 주말에 연결해 결과물을 뽑고 수정해 나가기로 함. 전체 연결은 다음 주 중 완료 예정임.

### 3. 검증 결과 저장 구조
PostgreSQL(RDB)로 검증 결과를 저장하고, 피드백 데이터도 같은 DB에 둘 예정임. 결과는 JSON이나 텍스트 속성으로 넣고, 실행 로그가 커지면 나중에 NoSQL로 분리하는 방안을 검토함. 교수는 전체 데이터는 JSON 파일로 두고 비교 등 중요한 요소만 DB에 넣으라고 제안함. 또 워커가 큐로 요청을 받아 천천히 처리하고 결과를 나중에 돌려주는 방식을 제안했고, 팀도 문제없다고 답함.

### 4. 캡스톤 경진대회 제출 방향
제출 문서는 다음 주까지 작성해야 함. 교수는 단일 워크플로우 검사 결과만 보여 주지 말고, **"n8n 워크플로우 종합 포털"("n8n의 네이버")** 시나리오로 내세우라고 제안함.
- 워크플로우별로 소개·기능, 버전업(변경) 이력, 버전별 취약점 분석 보고서를 한 곳에서 제공함. "우리가 검사·인증한 워크플로우를 가져다 쓰면 된다"는 메시지임.
- 초기 화면에는 여러 워크플로우 목록을 보여 줌. 분석이 끝난 것은 체크 표시하고, 요청됐지만 아직 분석하지 않은 것은 완료 예정 시점을 표시함.
- 실제 분석된 것이 몇 개뿐이더라도 "서버 자원 제약으로 현재 일부만 제공 중이며 백그라운드에서 계속 분석하고 있고, 업데이트되면 보고서도 자동 갱신된다"는 전체 계획을 함께 제시함.
- 단순 평점만 주는 기존 서비스와 달리, 클릭하면 용도·이력·취약점까지 볼 수 있다는 점을 차별점으로 내세움.
- 제목 후보: "보안 검증을 포함한 n8n 자동화 도구 사용 플랫폼", "n8n 워크플로우 종합 포털 서비스(취약점 분석 보고서 포함)". 포스터에는 "n8n 네이버"를 쓰자는 의견이 나옴.

### 5. 워크플로우별 검사 항목 차이
교수가 워크플로우 성격에 따라 검사해야 할 항목이 달라지지 않느냐고 질문함. 팀은 실행 단계는 같은 계획서를 쓰지만 계획 자체는 워크플로우마다 달라진다고 설명함. 교수는 범용(general) 검사 워크플로우를 만들어야 하고, 아직 그렇지 않더라도 그 방향으로 간다고 제시하라고 함. 동적 분석은 고정 기준을 두지 않고 워크플로우별 계획에 맞춰 검사하는 방향으로 이야기됨.

### 6. 프론트 서버 분리 여부
페이지 수가 적어서 워커가 있는 프로젝트 안에 FastAPI로 페이지까지 함께 올릴지, 프론트를 따로 분리할지 질문이 나옴. 교수는 화면이 포털처럼 보이는 시나리오를 강조했고, 분리 여부는 결론이 나지 않음.

## 결정사항
- 공개 페이지는 열람 전용으로 하고, 결과 등록·검증 실행은 GitHub OAuth로 인증한 조직 구성원(관리자)만 할 수 있게 한다.
- 검증 결과는 PostgreSQL에 저장하고, 워커는 큐로 요청을 받아 비동기로 처리하는 방식으로 진행한다.
- 다음 주까지 백엔드 검사 파이프라인 연결을 마치고, 그 뒤 프론트를 경진대회 목적에 맞게 다듬는다.
- 경진대회 제출 문서는 "n8n 워크플로우 종합 포털(취약점 분석 보고서 포함)" 시나리오로 작성하되, 현재 구현 범위와 전체 계획을 구분해 제시한다.
- 연결이 끝나면 동적 검증에 1~2명을 더 투입하고, 나머지는 완성도를 높인다.

## 액션 아이템
| 담당자 | 할 일 | 기한 |
|---|---|---|
| 미정(백엔드) | 벡터 DB 연결 후 결과물 뽑기 | 이번 주말 |
| 팀 전체 | 검사 파이프라인 전체 연결 완료 | 다음 주 중 |
| 팀 전체 | 경진대회 제출 문서 작성, 제출 전 교수 피드백 받기 | 다음 주 |
| 프론트 담당 | 초기 화면을 포털형으로 개편(워크플로우 목록, 분석 완료·요청·완료 예정 표시) | 백엔드 연결 이후 |
| 미정(1~2명) | 동적 검증 보강 | 연결 완료 후 |
| 미정 | 장비 1대를 교수에게 반납(서버 용도) | 미정 |

## 미결 사항
- 프론트를 FastAPI 백엔드에 포함할지, 별도 서버로 분리할지
- 워크플로우별로 달라지는 검사 항목을 범용 검사 구조로 어떻게 정리할지
- 경진대회 최종 제목
