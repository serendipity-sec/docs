# FlowDelta 상세 설계 제안

2026년 11월 20일 · 양유상 개인 설계 초안 · 팀 검토용

자체 호스팅 n8n 사용자가 **검증 이력이 있는 워크플로를 고르고, 가져간 버전을 수정한 뒤에도 필요한 보안 조건과 정상 동작이 유지되는지 확인**하는 서비스다. 팀이 사전에 검사한 카탈로그와 사용자가 신청한 재검증에 같은 엔진을 쓴다. 아래에서 **구현**은 기준 커밋에 들어간 기능, **수정·연동**은 기존 기능을 확장할 작업, **신규**는 새로 마련할 기능을 뜻한다. 운영 배포 확인 범위는 별도로 적었다. [전체 아키텍처 그림](flowdelta-deployment.png) · [확대용 SVG](flowdelta-deployment.svg) · [팀 의견 요청 PR](https://github.com/serendipity-sec/docs/pull/90)

## 1. 누가 무엇을 검증받는가

AI·자동화 도구를 쓰는 사람은 노드를 연결해 코드를 직접 작성하지 않고도 업무를 바꿀 수 있다. 반면 알림 노드를 교체하거나 커뮤니티 노드를 업데이트했을 때, 어느 수신자로 어떤 필드가 전달되고 기존 업무가 계속 동작하는지는 편집 화면만 보고 판단하기 어렵다. 비개발자도 **바뀐 점, 검사한 범위, 확인한 근거**를 읽을 수 있게 하는 것이 목적이다.

첫 검사 대상은 **자체 호스팅 n8n**이다. n8n Cloud에서 설치 가능한 커뮤니티 노드는 n8n의 검증을 거친 패키지로 제한된다. 자체 호스팅 환경에서는 미검증 커뮤니티 패키지나 직접 만든 노드도 사용할 수 있다. 커뮤니티 노드는 인스턴스와 흐르는 업무 데이터에 접근할 수 있고, 패키지 업데이트로 기존 동작이 달라질 수 있다. 한편 검증된 노드를 조합해도 연결과 설정에 따라 데이터가 새로운 곳으로 전달될 수 있다. 이 두 경우가 각각 노드 검사와 워크플로 검사를 할 이유다. [n8n 설치 정책](https://docs.n8n.io/integrations/community-nodes/installation/) · [n8n의 커뮤니티 노드 검증·위험 안내](https://docs.n8n.io/integrations/community-nodes/risks/)

| 검증 대상 | 식별과 입력 | 결과의 의미 |
|---|---|---|
| 워크플로 버전 | 워크플로 원본 JSON, 버전·해시, 업무와 정책, 사용한 노드·의존성. 비교가 가능하면 이전본과 수정본을 함께 고정한다. | 연결·설정 변경이 업무 결과나 정책에 미친 영향을 그 버전의 보고서로 남긴다. |
| 커뮤니티·자체 제작 노드의 패키지 버전 | 설치한 패키지명·버전 또는 소스 리비전과 실제 검사할 코드·의존성. 워크플로에 적힌 노드 이름만으로는 검사한 패키지 구현을 특정하기 어렵다. | 패키지 자체에서 확인한 사실을 해당 버전에 귀속하고, 그 버전을 참조한 워크플로와 연결한다. |
| 사용자가 만든 수정본 | 출발한 원본 버전, 수정된 JSON, 의도한 변경과 유지할 조건 | 원본의 검증 기록과 수정본의 새 결과를 각각 보존한다. 원본에 붙은 검증 표시는 원본 버전에만 적용한다. |

메인 카탈로그에는 팀 기준을 충족해 **FlowDelta 검증 표시**를 받은 워크플로·노드 버전을 모으는 방향이다. 표시에는 검사 대상·버전·조건을 명시하고, 상세 이력에는 공개가 허용된 과거 검사의 범위와 부분 완료·실패 사유도 보여 준다. 표시 기준과 공개 조건은 팀이 정한다. 성격이 비슷한 자동화 도구들 사이의 성능 비교는 장기 확장 방향이다. 첫 배포에서는 n8n 안에서 같은 업무·입력·환경으로 측정한 노드와 워크플로 버전을 비교한다.

## 2. 사전 검사와 두 가지 신청 흐름

| 경로 | 무엇을 받는가 | 처리와 결과 |
|---|---|---|
| 운영팀의 사전 검사 | 팀이 공개할 워크플로·패키지 버전, 가능하면 실제 이전 버전. 정상 업무 예시와 기대 조건 | 워커에서 검사한 뒤 공개 가능한 결과를 게시한다. 카탈로그에서 버전을 고르면 해당 시점의 결과, 변경 이력, 검사한 노드 버전을 볼 수 있게 한다. |
| 신청 ① 기존 워크플로 수정사항 검사 | 사용자가 관리하는 이전본·수정본. 기준이 이미 등록돼 있으면 해당 버전을 선택한다. | 같은 업무·정책·초기 상태로 비교하고 결과를 신청 건에 연결한다. 팀이 접수한 건의 진행 상태와 완료·부분 완료·실패 이유를 신청자가 확인하는 것이 목표다. |
| 신청 ② 카탈로그 원본을 내 용도로 수정 | 사용자가 실제 가져간 **정확한 카탈로그 버전**과 자신의 수정본 | 카탈로그의 최신 버전이 달라져도 선택한 버전을 기준으로 삼는다. 수정본의 검증 기록에서 원본으로 돌아갈 수 있게 하고, 공개 여부는 별도로 결정한다. |

두 신청 모두 운영팀이 접수하고, 어떤 조건을 검사했는지와 그 근거를 결과와 함께 신청자에게 돌려준다. 접수·결과 검토 중 어디에 운영자의 확인이 필요한지는 팀 의견을 받는다.

### 의도한 변경을 기록하는 예시

주문 저장 뒤 알림을 이메일에서 Slack으로 바꾼 사용자에게 “무엇을 바꿨고, 어떤 동작은 그대로여야 하나요?”라고 묻는 방안을 제안한다. 요청한 수신 채널 변경, 주문이 한 번 저장된다는 정상 조건, 알림에는 주문번호와 상태만 들어간다는 정책을 구별해 시험할 수 있다. 사용자가 허용할 수신자나 업무 정책까지 변경했다면 보고서에 달라진 조건을 적어야 이전 정책의 회귀와 새 정책에 대한 적합성을 구분할 수 있다.

### 비교할 이전본이 없는 첫 등록

단일 버전에서 실제로 수행한 검사와 그 범위를 기록하는 방안이다. 이후 버전이 생기면 그때 전후 비교를 연결한다. 현재 결과 DB는 이전·이후 버전을 모두 요구하고, 부모·자식 관계는 같은 워크플로 식별자 안에서만 연결한다. 게시 v2 이슈 역시 전후 버전 쌍을 요구한다. 단독 등록과 사용자 파생본을 표현할 데이터 계약은 수정이 필요하다. [결과 DB 스키마](https://github.com/serendipity-sec/flowdelta-app/blob/993326b7ba0db266d6c2db4e8c4be80404edf378/backend/migrations/versions/0001_public_results.sql) · [v2 게시 계약 이슈](https://github.com/serendipity-sec/platform/issues/126)

## 3. 배포할 서비스와 데이터가 이동하는 경로

| 구성 | 현재 구현 및 확인 범위 | 배포 목표와 남은 일 |
|---|---|---|
| 결과 웹 · Vercel | React·TypeScript·Vite로 검색·목록·상세를 구현했다. 표시하는 검증 기록은 합성 예시다. | 실제 카탈로그·버전별 이력을 조회 API에 연결한다. 신청·진행 상태·건별 결과 화면을 새로 만든다. |
| FastAPI · Vercel 배포 예정 | 저장소에 상태 확인 경로와 라우팅 설정이 있다. | 신청 접수·상태 반환, 인증된 공개 결과 게시·정정·철회, 목록·이력·상세 조회를 구현한다. 신청자 인증과 워커의 게시 인증은 용도가 다르다. |
| 작업 큐·로컬 검증 워커 | Python 워커가 등록된 주문 조회 사례를 Docker로 실행한다. | 비동기로 신청을 전달하고 신청 건과 엔진 실행 기록을 연결한다. 큐 제품과 전달 방식은 미결정이다. 팀이 사전 검사하는 경우에도 같은 엔진을 쓴다. |
| 로컬 게시 모듈·Neon 결과 DB | 공개 결과 테이블·버전 관계·읽기 뷰 마이그레이션이 있다. 팀은 DB를 띄웠다고 보고했다. | 워커가 허용된 결과와 근거만 골라 FastAPI에 보내고, API가 DB에 저장한다. 게시 모듈에는 결과 DB 접속 정보가 필요하지 않다. |
| 팀 공용 지식 DB·원본 자료 | 로컬 PostgreSQL·pgvector에 카드·임베딩과 일부 산출물을 저장한다. 일부 근거 원문은 파일로 관리한다. | 팀원이 함께 접근할 DB, 근거 원본 위치와 권한을 정한다. 공개 결과용 Neon을 선택한 것과 지식 DB의 운영 서버를 정하는 것은 별개다. |
| 외부 생성 모델 | 등록 시험 후보 선택이 열린 PR에 구현돼 있다. | B가 관련 카드와 A의 변경 요약을 바탕으로 OpenRouter의 저비용 GLM에 맞춤 시나리오를 요청하는 것이 이번 제안의 초기 방향이다. |

**신청 결과를 돌려주는 경로**는 웹 접수 → 큐 → 워커 → 신청 건별 상태·결과 조회다. **카탈로그에 공개하는 경로**는 사전 검사 또는 공개할 수 있는 결과 → 워커 게시 모듈 → FastAPI → Neon 공개 조회 뷰 → 웹이다. 개인 신청 결과는 기본 비공개로 시작하자는 제안이 나왔다. 실제 공개 범위, 제출 자료의 보관 위치·기한, 열람 권한은 합의 후 정한다. n8n에서 내보낸 JSON에는 자격 증명 이름·ID나 설정에 포함된 인증 헤더가 남을 수 있어, 접수한 원본과 외부 모델·공개 화면으로 내보낼 필드를 구분해야 한다. [n8n 내보내기 안내](https://docs.n8n.io/workflows/export-import/) · [엔진 결과 인계 이슈](https://github.com/serendipity-sec/platform/issues/122)

게시 모듈은 종료·중단된 검증 한 건의 대상 케이스들을 같은 키로 묶어 전송한다. FastAPI는 게시용 Bearer 토큰과 계약을 검증한 뒤 한 트랜잭션으로 저장한다. 설계상 최초 게시에는 `201`, 같은 키·같은 내용 재전송에는 `200`, 같은 키·다른 내용에는 `409`를 돌려준다. 정정 시에는 새 결과 게시와 기존 결과 철회를 함께 처리한다. 공개 조회는 게시된 목록·이력·상세만 제공하고 철회된 상세는 `404`로 처리한다. 원본 로그·입출력 본문·자격 정보는 공개 결과에서 제외한다. [게시 모듈](https://github.com/serendipity-sec/platform/issues/127) · [게시 API](https://github.com/serendipity-sec/flowdelta-app/issues/3) · [조회 API](https://github.com/serendipity-sec/flowdelta-app/issues/4)

## 4. A·B·C 엔진과 판정의 책임

| 단계 | 지금 되는 일 | 수정·신규 작업 |
|---|---|---|
| 입력 고정과 A 변경 분석 | 전후 원문과 해시, 업무·정책·환경·초기 상태를 묶는다. 노드를 대응시키고 변경 지점과 영향을 받을 수 있는 경로를 계산한다. | 단독 등록·사용자 파생본의 기준을 연결한다. 참조한 패키지 버전과 비교 조건을 보고서까지 전달한다. |
| B 검색과 시험 계획 | 일반 실행기는 로컬 카드로 등록 시험 계획을 만든다. 공유 벡터 검색 코드와 기본 실행기 연결 PR이 별도로 있다. | A의 변경·업무 맥락으로 팀 공용 카드에서 관련 보안 근거를 검색한다. GLM이 해당 수정의 시험 조건·입력·기대 결과·필요한 관측을 제안하면 C가 지원하는 형식과 범위인지 확인한다. |
| C 워크플로 검사 | 등록 주문 조회에서 전후 버전을 각각 분리된 환경·초기 상태로 실행하고 응답·서비스 이벤트·최종 상태를 수집한다. 일부 노드 코드에는 Semgrep 정적 규칙이 있다. | 두 번째 워크플로에도 서비스 설정·관측 항목·판정 규칙을 연결한다. 노드와 업무 전체의 성능 측정을 새로 설계한다. |
| 패키지 자체 검사 | 현재 정적 규칙은 워크플로 파일 안의 제한된 코드 패턴을 본다. | 커뮤니티·자체 제작 노드 패키지의 코드·의존성을 버전별로 검사한다. 워크플로 연결에서 관찰한 영향과 패키지 자체에서 확인한 근거를 각 대상에 남긴다. |
| 독립 판정과 보고 | 등록 주문에 선택적으로 적용하는 판정기가 있다. 일반 실행 요약의 `security_outcome`은 `null`이고 개별 규칙 판정은 별도 보고서에 남는다. | 시험을 제안한 AI와 독립적으로 서비스 기록·정책·증거 완전성을 확인한다. 보안, 정상 기능, 성능을 따로 표시하고 미지원·미실행·판단 불가를 보존한다. |

## 5. RAG 카드, 임베딩, OpenRouter를 어떻게 나눌까

**지식 카드**는 검색 결과를 실제 시험 조건으로 옮길 수 있게 하는 자료다. 카드에는 출처와 리비전·해시, 적용할 노드·버전·변경 조건, 확인할 정책, 기대하는 정상 동작과 필요한 관측 근거를 담는 방향이다. 알림 워크플로부터 다룬다면 수신처 변경, 전송 필드 추가, 노드 패키지 업데이트를 각각 설명하는 자료부터 채울 수 있다. 현재 코드에는 카드 초안 생성, 근거 확인, 사람이 검토한 카드의 승격·버전 관리가 있다. 대표 사례에 맞는 충분한 카드 수집·검토가 남았다. KB 검색용 자료와 엔진의 탐지·검색 성능을 평가할 정답은 구분해 관리한다. [카드 운영 코드와 절차](https://github.com/serendipity-sec/platform/blob/c1ef141a55a744e294ac6aca0448de2684fba90a/docs/KNOWLEDGE_OPERATIONS.md) · [KB·평가 자료 작업](https://github.com/serendipity-sec/docs/issues/67)

카드 본문을 임베딩해 색인하고, 실행 때 A의 변경 설명을 같은 프로필로 임베딩해 관련 카드를 검색한다. 현재 기본값은 Ollama의 `qwen3-embedding:0.6b`와 1,024차원이다. 모델 지문·차원·질의 지시문에 따라 프로필을 구별한다. 팀이 다른 모델을 고르면 해당 프로필로 카드 색인을 만들고, 과거 계획은 원래 카드·모델 버전으로 추적할 수 있어야 한다. DB를 공유해도 각 PC의 로컬 파일 경로까지 공유되지는 않으므로 카드 ID·버전·해시로 근거 원문을 다시 읽는 경로가 필요하다. [임베딩 프로필](https://github.com/serendipity-sec/platform/blob/c1ef141a55a744e294ac6aca0448de2684fba90a/docs/EMBEDDING.md) · [두 호스트 재현 과제](https://github.com/serendipity-sec/platform/issues/79)

| 같은 Qwen 0.6B로 먼저 비교할 후보 | 재사용 범위 | 결정 전에 비교할 점 |
|---|---|---|
| Neon Free의 팀 지식 DB + 로컬 Ollama | 기존 pgvector 색인·조회와 로컬 임베딩 코드를 사용한다. 양유상 개인안에서 먼저 검토할 후보다. | 무료 저장·연산 한도 안의 실제 카드·색인 크기, 마이그레이션·권한 호환성, 팀원 교외 접속, 임베딩 장비 가동 |
| 팀 장비의 PostgreSQL·pgvector + 로컬 Ollama | 기존 PostgreSQL 17·pgvector 0.8.1 Docker 구성을 재사용한다. | 전력·장비 가용 시간, 접속 경로, 백업·복구 운영 부담, 팀원이 다른 PC에서 같은 근거를 읽을 수 있는지 |

공식 가격표의 11월 20일 Free 표기는 프로젝트당 월 100 CU-hours와 저장 공간 1 GB다. 팀 사용량은 측정 전이다. 두 안을 같은 카드 묶음·한영 변경 설명으로 비교해 상위 5개에 필요한 카드가 들어오는 비율, 검색 시간, 저장량, 운영 부담을 볼 수 있다. BGE-M3는 비교 후보로 두고, 실제 팀 질의에서 차이가 있는지 확인한 뒤 운영 모델을 채운다. [Neon 가격표](https://neon.com/pricing) · [Neon pgvector 지원](https://neon.com/docs/extensions/pgvector) · [기존 Docker 구성](https://github.com/serendipity-sec/platform/blob/c1ef141a55a744e294ac6aca0448de2684fba90a/runtime/knowledge/compose.yaml)

**생성 모델**은 양유상이 팀이 함께 쓸 OpenRouter API 접근을 제공하고 저비용 GLM으로 시험 시나리오 생성·선택을 먼저 구현하는 방향이다. 임베딩 모델 선정과는 별개의 결정이다. 워커에서 키를 관리하고 사용 한도를 두는 방안이 제안됐다. 전달할 입력은 변경 요약과 필요한 카드 근거로 좁히고, 계획에는 사용한 카드·모델·설정과 실제 실행한 시험을 연결한다. 운영 GLM의 모델 ID, 예산 및 신청 데이터의 외부 전달 기준은 팀 논의가 남아 있다. [AI 계획 작업](https://github.com/serendipity-sec/platform/issues/121) · [OpenRouter 키와 한도](https://openrouter.ai/docs/api/reference/authentication)

## 6. 보고서에서 무엇을 읽을 수 있어야 하는가

사용자는 **보안**에서 검사한 정책과 실제 관측을, **정상 기능**에서 기대 업무 결과의 충족 여부를, **성능**에서 측정 환경·입력·반복 수와 결과를 본다. 예를 들어 “허용된 수신자에게 전달”, “주문 저장 완료”, “같은 입력으로 반복한 처리 시간과 실패율”은 각각 다른 질문의 답이다. 처리 시간을 비교할 때는 사용한 n8n·노드 버전, 같은 입력과 장비 조건, 외부 서비스를 대체했는지도 기록하자는 제안이다. 30회 반복 측정은 논의 중 나온 예시다. 채택할 지표, 반복 수, 검증 표시의 통과 기준은 공란이다.

11월 19일에는 로컬 n8n 2.42.6에서 등록 주문 조회 엔진이 낸 결과를 시험용으로 매핑해 격리된 PostgreSQL 18.7의 결과 스키마에 담고 공개 읽기 역할로 조회했다. 대상 목록·버전 쌍·검증 키 일부는 시험 매핑에서 보충했다. 아래 세 경우는 로컬 DB에서 표현한 사례이고, 운영 게시 API를 거치는 시험은 남아 있다. [당시 시험에 사용한 DB 스키마](https://github.com/serendipity-sec/flowdelta-app/blob/e0aeb0ee8008513d2522eb6e7005300ef37d3853/backend/migrations/versions/0001_public_results.sql) · [결과 화면의 완료 기준](https://github.com/serendipity-sec/flowdelta-app/issues/5)

| 로컬 사례 | 화면에 남길 사실 | 검증 전체의 보안 표시 |
|---|---|---|
| 정상 주문 조회 | 전후 각 1회 실행·수집·정리 완료. 정상 업무 검사는 각각 12/12 통과 | 미평가 |
| A 입력 실패 | 입력 조건 확인 실패. B·C는 미실행이고 비교 실행 ID가 없다. | 미평가 |
| C 자료 부분 수집 | 변경 후 HTTP 응답은 200이었으나 이벤트와 최종 상태 자료가 누락돼 부분 완료로 기록했다. 전후 각 회차의 결과를 따로 볼 수 있다. | 미평가 |

## 7. 팀이 검토할 확장과 첫 배포 확인 사례

- **AI 기반 흐름 해석**에서는 A가 제공하는 노드·간선·변경 경로를 읽어 새 수신자와 데이터 필드를 설명하거나, 빠진 정상 기능 검사를 제안하도록 할 수 있다. 팀이 판단할 것은 기존 규칙으로 놓치기 쉬운 사례, AI의 설명에 연결할 원본 위치, 실행 기록으로 확인할 수 있는 조건이다.
- **정적 검사 후보**인 n8n의 커뮤니티 노드 ESLint 규칙은 노드·자격 증명 정의 파일과 패키지 설정을 다룬다. 현재 워크플로 속 코드에 적용하는 제한된 Semgrep 규칙과 비교해 추가되는 범위를 확인한 뒤 도입 여부를 정한다. [n8n 노드 린터](https://github.com/n8n-io/n8n-docs/blob/main/docs/connect/create-nodes/test-your-node/node-linter.md)
- **동적 검사 후보** 중 n8n 저장소의 `NodeTestHarness`는 고정 워크플로 입력과 기대 출력 비교를 검토할 후보이고, WireMock은 합성 외부 서비스의 요청 기록을 확인할 후보다. 모의 요청이 도착했다는 증거와 실제 업무 상태가 변했다는 증거를 구별한다. 팀원이 다른 도구를 제안할 때는 어떤 검사 한 건을 개선하는지 함께 적으면 비교하기 쉽다. [n8n 테스트 코드](https://github.com/n8n-io/n8n/blob/e6b971535bc17e4c49c839d4b14112dda437d588/packages/core/nodes-testing/node-test-harness.ts) · [WireMock 요청 검증](https://wiremock.org/docs/verifying/)
- **카탈로그 탐색**과 관련해 11월 19일 면담에서는 대표 실제 워크플로 4~5개의 정상·문제 사례, 카테고리 탐색, 의심 노드의 상세 설명, 프로젝트 설명 메뉴 분리, 최근 분석 사례 노출이 제안됐다. 인기·위험도 집계 범위는 미정이다. Redis가 언급된 용도는 ‘핫 5’ 리더보드였다. [면담 기록](https://github.com/serendipity-sec/docs/pull/88/files)

**첫 배포 시연으로 제안한 흐름**은 ① 공개 워크플로 한 개의 두 버전과 포함된 커뮤니티 노드 한 버전을 사전 검사하고 ② 카탈로그에서 버전 이력과 근거를 조회한 뒤 ③ 사용자가 그중 한 버전을 골라 수정본을 신청하고 ④ 같은 기준에서 달라진 결과를 신청 화면에서 확인하는 것이다. 이와 별도로 등록 주문 한 건을 실제 게시·조회해 웹 연동을 먼저 확인할 수 있다. 대표 실제 사례는 추가 선정이 필요하다.

| 운영 임베딩 모델·실행 위치 | 기본 Qwen 0.6B를 출발점으로 비교한다. 공용 모델 서비스 또는 팀별 동일 프로필 사용 여부도 논의한다. | |
| 생성용 GLM의 세부 모델 ID와 비용 한도 | 초기 공급 경로는 OpenRouter, 생성 계열은 저비용 GLM이다. | |

| 신청자 인증·권한 | 공개 열람과 회원 신청을 구분한다. 기존 GitHub 조직 관리자 인증과의 관계는 미정이다. | |
| 작업 큐 제품·워커 전달 방식 | 비동기로 접수하고 워커가 처리하는 방향이다. | |
| 상시 워커 장비·운영 담당 | 로컬 워커를 사용한다. 503호 PC는 면담에서 제안된 후보다. | |
| 신청 원본·결과의 저장, 열람, 보존·삭제·백업 | 원본 로그는 로컬에 두고 게시 허용 필드를 선별한다. 사용자 신청 결과의 공개 정책은 별도 결정이 필요하다. | |
| 노드·워크플로 성능 지표와 버전별 검증 표시 기준 | 정상 기능·보안·성능을 구별해 보여 준다. | |
| 첫 공개 워크플로·노드 목록 | 대표 실제 사례 4~5개를 선정하자는 면담 의견이 있다. | |
