# 후보 1 — 기존 도구 직접 비교

확인일: **2026-09-20 KST**. 모든 아래 URL의 확인일은 이날이다. 실제 실행과 공식 문서상 기능을 구분한다. 설치·실행 난이도와 초보 가독성 평가는 이번 담당자의 판단이며 초보 사용자 실험 결과가 아니다.

**결론: “발견→이해→수정→재검증이 기존 도구에 없다”는 차별화 주장은 현재 근거로 성립하지 않는다.** ZAP·Semgrep·Ship Safe가 설명과 수정 방향을 실제로 제공했다. Ship Safe·Lovable에는 더 넓은 수정 흐름도 문서화돼 있다. 이번 실행에서 직접 확인한 개선 여지는 **코드의 사용 맥락에 맞는 수정 안내**와 **다른 회원의 접근 차단 + 정상 회원 기능 유지를 함께 확인하는 검증**이다. 이것이 경쟁 제품에 전혀 없는지는 아직 입증하지 못했다.

### 미실행 도구의 해석

Shannon은 CLI를 설치하고 실행했지만 제공자 설정이 없어 실제 침투 결과를 만들지 못했다. [오류 원문](evidence/shannon-preflight.stderr.log), [실행 명령·시간](evidence/shannon-preflight.run.json). 현재 공식 문서는 API 제공자 외에도 로컬 모델 구성을 설명한다. 따라서 “유료 키 없이는 절대 실행 불가”라고 단정하지 않는다. 로컬 모델을 Shannon에 연결한 실행은 이번에 하지 않았다. 외부 AI API 호출·과금은 하지 않았다.

Burp/Autorize는 이번 자동화 환경에서 GUI 설정과 확장 실행을 검증하지 못해 선택 항목을 미실행으로 남겼다. 설치 실패를 관찰한 것은 아니다. Autorize 공식 페이지는 Community/Professional 지원, 저권한 세션으로 요청 반복 및 enforcement 판정을 설명한다(확인 버전1.9.4). **따라서 권한 검증 자체가 빈 시장이라는 주장은 특히 피해야 한다.**

### 수정 안내의 맥락 문제: 직접 확인한 사례

Ship Safe는 `lib/insecurity.ts:41`의 MD5에 SHA-256/SHA-3 무결성 검사 사용을 설명하고, `createHash("md5")`를 `createHash("sha256")`로 바꾸라는 fix를 냈다. 그런데 로그인 코드34행은 바로 이 함수를 **비밀번호**에 사용한다. 빠른 SHA-256으로 교체하는 것만으로는 비밀번호 저장의 적절한 수정이 되지 않는다. [OWASP 비밀번호 저장 지침](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)은 salt와 느린 비밀번호용 함수를 요구한다.

이 판단은 **우리의 코드 맥락 분석**이다. Ship Safe 전체 또는 agent 모드의 한계를 입증한 결과가 아니다. 이번 `--no-ai` 정적 출력이 초보에게 그대로 적용되면 불충분한 수정으로 이어질 수 있다는 구체 사례다. 또 같은 로그인 SQL에 `Password Assignment` 시크릿 경고도 있지만, 해당 위치는 하드코딩 비밀번호가 아니라 SQL의 비밀번호 비교식이므로 확정 시크릿으로 세지 않았다.

Semgrep의 같은 SQL 경고는 Sequelize 매개변수화를 안내했다. ZAP SQLi solution은 JDBC/ADO 등 여러 기술의 일반 설명을 포함했다. 설명이 “있음”과 **내 파일에서 적용하고 성공을 판정할 수 있음**은 별개로 측정해야 한다.

| Burp+Autorize | 미실행 | 미실행 | 미실행 | 미실행; 권한별 반복 판정은 문서 확인 |

추가 조사: [Lovable Security](https://docs.lovable.dev/features/security), [Security view](https://docs.lovable.dev/features/security-view)는 검사·이슈 설명·수정 시도·재검사/오래된 결과 표시 흐름을 설명한다. **직접 계정에서 실행하지 않았으므로 문서 확인으로만 분류**한다. [VibeEval](https://vibe-eval.com/)도 발견했지만 외부 서비스 평가/업로드를 하지 않아 미실행이다. [Supabase RLS lint](https://supabase.com/docs/guides/database/database-linter)는 별도 PostgreSQL/RLS 환경의 후보이며 이번 Juice Shop 실험에 추가 실행하지 않았다.

## 6. 프로젝트 방향에 주는 판단

1. **유지할 가치:** 실제 HTTP로 남의 데이터에 접근하고, 수정 후 그 요청만 막히며 본인 요청은 성공하는 결과는 웹애플리케이션 보안 과목의 명확한 산출물이 된다.
2. **바꿀 차별화 문장:** “탐지 도구가 못 해주는 전체 흐름”보다 “초보가 자신의 회원·데이터 관계를 입력하면, 증거와 코드 맥락에 맞는 수정안을 이해하고 공격 차단과 정상 기능 유지를 확인하게 한다”가 이번 근거에 맞다. 시장 신규성은 아직 가설이다.
3. **다음 경쟁 비교의 합격 기준:** 동일 앱의 실제 취약점·안전 대조군을 고정하고, 초보 참가자의 수정 완료율/소요시간/잘못된 수정 수/정상 기능 회귀를 비교한다. Ship Safe agent·Lovable 수정 흐름·Autorize를 실제 사용해야 전체 흐름 차별화 검증이 완성된다.

이번 A는 성공 실행4개 구성(ZAP baseline·인증 active, Semgrep, Ship Safe)과 미실행 범위를 구분한 **1차 비교**다. 모든 경쟁 제품의 end-to-end 부재를 입증한 조사가 아니다. [B 논문·데이터셋](02-논문정독-데이터셋.md), [C 생성 앱·패치·23개 검증](../../../platform/experiments/vibe-app-baseline/README.md)과 함께 판단한다.
