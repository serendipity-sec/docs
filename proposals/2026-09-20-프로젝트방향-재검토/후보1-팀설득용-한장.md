# 후보 1 — AI로 만든 웹서비스, 공개 전 보안 검증

작성 2026-09-20 · 김민우 · 토요일 팀 회의 안건 · **제안이지 결정 아님**

> **한 문장**: "AI로 만든 내 웹사이트, 기능은 다 되는데 — 공개해도 될까?"
> 바이브코딩으로 만든 서비스를 등록하면 **취약점을 찾아서 → 초보가 이해할 말로 설명하고 →
> 고치는 법을 주고 → 고쳤는지 다시 확인해 주는** 웹서비스.

---

## 왜 이 주제인가 — 근거 4개

| | |
|---|---|
| **문제가 실측됐다** | 바이브코딩 앱 **9,041개 + 감사 200개: 91%가 취약, 65.8%가 Critical/High.** 최다 = broken access control · injection · 인증 실패 (arXiv 2606.23130, 2026-09) |
| **기능은 되는데 뚫린다** | 같은 논문이 확인. Lovable 앱 170개+ RLS 누락, 취약 엔드포인트 303개 (CSA 2026-04) |
| **AI 코드 자체가 취약** | 100+ LLM 테스트, OWASP Top 10 **45% 실패**, XSS 86% (Veracode) |
| **과목과 직결** | 대상이 웹앱 그 자체. 최다 취약 유형이 OWASP A01·CWE Top 25 #4(Missing Authorization)와 정확히 겹침 |

**팀 관심(AI)** — 충족. AI가 만든 코드가 대상이고, 검사·설명·수정 가이드에도 AI를 쓴다.
**빨리 시작** — 가능. 첫 검사 대상은 **우리가 직접 바이브코딩으로 만든 앱**이면 된다.

---

## 서비스 한 바퀴 (= 15주차 시연)

```
① 등록      내 웹앱 저장소 URL (+ 테스트 배포 URL, 테스트 계정 2개)
② 검사      정적(코드) + 동적(실제 요청) — 첫 학기는 3종에 집중
              · 다른 사용자 데이터 접근 (IDOR / broken access control)
              · 인증·세션 결함
              · 시크릿·설정 노출
③ 설명      "일반 사용자가 이 요청 하나로 다른 사람의 예약을 지울 수 있습니다"
              + 재현 요청 + 코드 몇 번째 줄 + 왜 AI가 이렇게 짰는지
④ 수정      패치 제안 (또는 AI 도구에 넣을 수정 프롬프트)
⑤ 재검증    같은 테스트 재실행 → 차단 확인 → 회귀 테스트로 저장
⑥ 리포트    "공개 준비도" — 무엇을 확인했고 무엇은 못 봤는지
```

**우와 포인트**: 시연에서 **실제로 남의 예약이 지워지는 걸 보여주고 → 고치고 → 같은 요청이 막히는 것**까지 3분 안에.

## 기존 도구와 뭐가 다른가 — 정직한 버전

| 있는 것 | 하는 일 | 우리가 다른 점 |
|---|---|---|
| **Shannon** (KeygraphHQ) | AI로 허가된 웹앱·API 자동 침투 | 전문가용. "찾았다"에서 끝 |
| **OWASP ZAP · Burp Autorize** | 스캔 / 권한 바꿔 재전송 | 결과 읽으려면 보안 지식 필요 |
| **Semgrep · Snyk** | 코드 정적 분석 | 취약점 목록. 초보는 뭘 고쳐야 할지 모름 |
| **우리** | | **바이브코딩한 사람이 발견→이해→수정→재검증을 혼자 끝내게 하는 흐름.** AI 코드 특유의 결함 패턴(논문의 8가지 실패 모드)에 맞춘 설명·수정 가이드. 회귀 테스트가 쌓임 |

→ "AI가 해킹해 줌"은 이미 있다. **우리 기여는 검사가 아니라 "고쳐서 공개까지" 가는 경험**이다.
이 차별화가 진짜인지는 **Shannon을 직접 써보고** 확인해야 한다 (미확인).

## 웹어플리케이션보안 과목 산출물 — 자연스럽게 나온다

| 제출물 | 이 주제에서 |
|---|---|
| 설계문서(6주) | 사용자·역할·API·DB + **우리 서비스 자체의 위협 모델** |
| 중간발표(9주) | 등록 → 3종 검사 → 설명 화면 시연 |
| 보안점검 리포트(12주) | **우리 서비스 자체**: 사용자 간 검사 결과 격리(IDOR), 검사 대상 URL로 인한 SSRF, 검사 작업 격리, 결과 화면 XSS, 테스트 계정 보관 |
| 소스·배포(13주) | + 수정 가이드 · 재검증 · 회귀 테스트 |
| 최종(15주) | 실제 바이브코딩 앱 N개에서 탐지율·오탐·**수정 완료율·소요시간** |

특히 **"남의 앱을 검사하는 서비스가 남의 앱을 안전하게 다루는가"** — 검사 대상 URL 처리(SSRF), 격리 실행, 테스트 계정 관리 — 가 우리 보안 설계의 핵심이 된다. 주제와 과목이 같은 문제를 본다.

## 평가 자료 — 확보 경로

- arXiv 2606.23130이 오픈소스 바이브코딩 앱 **9,041개**를 분석 — 목록 공개 여부 확인 (미확인)
- **직접 만든다**: Lovable·Claude Code·Cursor로 같은 스펙(예: 동아리 예약 서비스)을 여러 번 생성 → 취약 패턴 비교. **이게 곧 시연 대상**
- 정답 라벨: 팀이 수동 검증 + 논문 분류 체계
