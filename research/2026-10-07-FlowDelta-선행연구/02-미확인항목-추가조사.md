# FlowDelta 선행연구 — 미확인 항목 추가 조사

> 작성: 2026-10-07 · 담당: 준서 · 원 문서: FlowDelta 아키텍처와 닮은 선행연구·오픈소스·상용 제품 (Claude Docs)
> FlowDelta 기준: 업데이트된 스킬·n8n 워크플로를 **로컬에서 실행**해 이전 버전 대비 새로 생긴 행위·취약점을 찾는 방식 (차분 동적 분석, differential dynamic analysis)

## 요약

원 문서에서 "미확인"으로 남긴 6개 항목 중 **5개를 해결**했습니다. 핵심 결론은 다음과 같습니다.

1. **가장 가까운 선행연구 LifecycleGuard는 스킬을 실행하지 않습니다.** 이전·새 버전의 **지시문 임베딩 거리**만 비교합니다. 따라서 "스킬을 두 버전 모두 실행해 행위를 비교한다"는 FlowDelta의 차별점은 유지됩니다.
2. **두 버전을 실행해 비교하는 방식은 특허로 이미 존재합니다** (Trend Micro → VicOne, 2025 등록). 발표 때 "선행기술"로 먼저 언급하는 것이 안전합니다.
3. **상용 버전 비교 제품(Spectra Assure, Socket)은 모두 정적 분석입니다.** 실행 기반 버전 비교 제품은 이번 조사에서 확인되지 않았습니다.
4. **정적 버전 비교 연구가 2편 더 확인됐습니다** (diff-CodeQL, Amalfi). FlowDelta의 "코드 diff" 쪽 기준선(baseline)으로 쓸 수 있습니다.

## 1. LifecycleGuard — 실행 비교가 아니라 지시문 비교

**자료:** Badhe & Tiwari (Google), *Agent Skill Security: Threat Models, Attacks, Defenses, and Evaluation*, arXiv 2607.13987v1, 2026-07-15 — [원문](https://arxiv.org/html/2607.13987v1) · 신뢰도: **프리프린트**

**업데이트를 어떻게 검사하나 (단계별)**

1. 업데이트를 **새 스킬 등록과 똑같이** 다시 심사 절차(admission pipeline)에 넣습니다.
2. 게시자 출처(provenance)를 검증하고 패키지 import를 제한합니다. import 제한의 구체적 의미는 논문에 정의돼 있지 않습니다.
3. **이전 지시문과 새 지시문의 벡터 거리**를 재서, 기능이 크게 달라졌으면 표시합니다.

**결과 (업데이트 공격 실험)**

| 지표 | 값 |
| --- | --- |
| 악성 업데이트 탐지율 | 92.5% |
| 미탐률 | 7.5% (정교한 지시문 인젝션을 놓침) |
| **오탐률** | **37.0%** (정상적인 리팩터링도 걸림) |
| 정상 업데이트 수용률 | 63.0% |

**주의할 점**

- 앞서 2차 출처에서 본 "공격 성공률 100% → 23%"는 **업데이트 실험이 아닙니다.** 런타임 감시를 다룬 별도 실험의 수치입니다.
- 임베딩 모델, 거리 임계값, 업데이트 표본 수는 **논문에 공개돼 있지 않습니다.**
- 업데이트 실험에서는 샌드박스·런타임 감시를 평가하지 않았습니다.
- 실험은 SkillMCP의 실제 스킬 327개를 쓴 통제 환경이며, 실제 레지스트리는 아닙니다. 코드는 공개되지 않았습니다.

**FlowDelta에 주는 의미**

- 지시문 비교만으로는 **오탐률 37%**가 나옵니다. "지시문은 많이 바뀌었지만 행위는 같은" 정상 업데이트를 걸러 내지 못하기 때문입니다.
- FlowDelta처럼 **실제 행위를 비교하면 이 오탐을 줄일 수 있다**는 것이 우리 주장의 근거가 됩니다. 단, 이는 아직 검증 전인 가설입니다.
- 회의 대비 답변: "LifecycleGuard도 업데이트를 비교하는데 뭐가 다른가?" → "그 연구는 **글(지시문)**을 비교하고, 우리는 **실행 결과(행위)**를 비교한다. 그 연구의 한계로 보고된 오탐률 37%를 줄이는 것이 목표다."

## 2. Ohm et al. — 설치 중 아티팩트를 동적으로 관찰

**자료:** Ohm, Sykosch, Meier (University of Bonn, Fraunhofer FKIE), *Towards Detection of Software Supply Chain Attacks by Forensic Artifacts*, ARES 2020 부속 SSE 워크숍 — [ACM DL](https://dl.acm.org/doi/10.1145/3407023.3409183) · [ARES 2020 워크숍 목록](https://2020.ares-conference.eu/conference-2020/accepted-workshop-papers/index.html) · 신뢰도: **동료심사 (워크숍)**

**확인된 것**

- Amalfi 논문(ICSE 2022)은 이 연구를 "패키지 **설치 중** 생성되는 아티팩트를 관찰·측정하는 **동적 분석**으로 악성 패키지를 탐지"하는 방식으로 소개합니다 ([Amalfi 원문](https://arxiv.org/pdf/2202.13953)).
- 즉 FlowDelta의 ② 실행·기록 단계와 같은 계열입니다.

**여전히 미확인**

- 이전 버전과 아티팩트를 **비교**하는지는 확인하지 못했습니다.
- 접근 시도 결과: ACM DL·ResearchGate·Fraunhofer 저장소는 접근 차단(403·429)이었고, crossref API는 요청 제한(429)에 걸렸습니다. 학회 페이지에는 초록이 없습니다.
- 확인 방법 제안: 학교 도서관 계정으로 ACM DL에서 PDF를 받거나, [발표 영상](https://vimeo.com/444165227)을 보면 됩니다.

## 3. 버전 간 행위 변화 탐지 특허 — 출원인 확인

**자료:** US 12223045 B1, *Protecting customers against supply chain attacks by detecting a behavior change between versions of an application program* — [Google Patents](https://patents.google.com/patent/US12223045B1/en) · 신뢰도: **공식 (특허 문서)**

| 항목 | 내용 |
| --- | --- |
| 출원인 | Trend Micro (현재 권리자: **VicOne Corp**, Trend Micro 자회사로 차량 보안 전문) |
| 발명자 | Shih-Han Hsu, Wei-Jen Chang, Yao-Tang Chang, Yi-Li Cheng |
| 우선일·출원일 | 2022-08-24 |
| 등록일 | 2025-02-11 |

**방식 (단계별)**

1. 여러 버전의 애플리케이션을 통제된 환경(샌드박스)에서 실행해 시스템 활동을 기록합니다.
2. 활동을 벡터로 바꾸고 군집해 버전별 **행위 시그니처**를 만듭니다.
3. 버전 간 시그니처를 비교해, 정상 업데이트로 설명되지 않는 차이를 공급망 공격 의심으로 경고합니다.

**FlowDelta에 주는 의미**

- "두 버전을 실행해 행위를 비교한다"는 **아이디어 자체는 2022년에 이미 특허로 출원**됐습니다.
- 대상은 일반 애플리케이션이고, **스킬·n8n 워크플로·LLM 에이전트의 비결정성**은 다루지 않습니다. FlowDelta의 차별점은 여기서 찾아야 합니다.
- 캡스톤은 상업적 실시가 아니라 연구·교육 목적이므로 특허 침해 문제와는 별개입니다. 다만 발표에서 **선행기술로 먼저 언급**하는 것이 신뢰도에 유리합니다.

## 4·5. 상용 버전 비교 제품은 모두 정적 분석

| 제품 | 분석 방식 | 근거 |
| --- | --- | --- |
| ReversingLabs Spectra Assure | **정적만.** 분석 중 파일을 실행하지 않음. 추출한 데이터를 "능력(capabilities)"·"지표(indicators)"로 바꿔 행위를 추정 | [Spectra Assure 분석 개념](https://docs.secure.software/concepts/spectra-assure-analysis) |
| Socket | **정적만.** 오픈소스 패키지와 의존성을 정적으로 분석해 공급망 공격 징후 탐지 | [Socket for GitHub 문서](https://docs.socket.dev/docs/socket-for-github) |

**의미:** Spectra Assure가 버전 diff에서 보여 주는 "행위 변화"는 **실제 실행 관찰이 아니라 코드에서 추정한 능력의 변화**입니다. 이번 조사 범위에서 **실행 기반으로 버전을 비교하는 상용 제품은 확인되지 않았습니다** (위 특허 제외).

## 새로 찾은 자료: 정적 버전 비교 연구 2편

FlowDelta의 "코드 diff" 쪽 기준선이자, 정적 방식과 동적 방식을 비교 실험할 때 대조군으로 쓸 수 있습니다.

### diff-CodeQL — 버전 간 CodeQL 결과 차이만 보고

**자료:** Froh, Gobbi, Kinder (LMU München), *Differential Static Analysis for Detecting Malicious Updates to Open Source Packages*, SCORED '23 (ACM CCS 부속 워크숍), 2023-11-30 — [원문 PDF](https://www.plai.ifi.lmu.de/publications/scored23-diff-codeql.pdf) · 신뢰도: **동료심사 (워크숍)**

- **방식:** 네트워크 접근·프로세스 실행·파일 작업·난독화·메타데이터 변경·코드 생성 등 41개 CodeQL 행위 쿼리를 두 버전에 각각 돌리고, **새 버전에서만 새로 걸린 결과**만 점수로 합산합니다. 임계값(10)을 넘으면 경고하고, 원인 코드를 보여 주는 차분 보고서를 만듭니다.
- **결과:** 알려진 악성 버전이 있는 npm 패키지 9개의 악성 업데이트를 **모두 탐지**했습니다. 인기 패키지 25개의 6,361개 버전에서 오탐은 89건(**1.4%**)이었습니다.
- **FlowDelta와의 관계:** "두 버전 모두에 있는 위험은 빼고 새로 생긴 것만 본다"는 원칙이 같습니다. 단, 실행하지 않으므로 런타임에만 나타나는 행위(원격 다운로드 후 실행 등)는 보지 못합니다.

### Amalfi — 이전 버전 대비 변화를 특징으로 사용

**자료:** Sejfia & Schäfer, *Practical Automated Detection of Malicious npm Packages*, ICSE 2022 — [원문](https://arxiv.org/pdf/2202.13953) · 신뢰도: **동료심사**

- 원 문서에서 "버전 간 변경 특징을 쓰는지 미확인"이었던 항목입니다. **쓴다는 것을 확인**했습니다.
- 11개 특징 중 2개가 두 버전을 함께 보며, 이전 버전에 없던 API·능력이 새로 생겼는지를 계산합니다. 논문은 이전 버전에서 쓰지 않던 능력 3개가 새 버전에 나타난 사례를 예로 듭니다.

## FlowDelta 위치 정리 (갱신)

| 비교 대상 | 실행하지 않음 (정적) | 실행함 (동적) |
| --- | --- | --- |
| **한 버전만** | Cisco skill-scanner, SkillSpector 등 | USENIX '26, SkillDetonate, SandyClaw, OSCAR, Ohm et al.(설치 아티팩트) |
| **두 버전 비교** | Garrett (ICSE-NIER '19), Amalfi (ICSE '22), diff-CodeQL (SCORED '23), LifecycleGuard (지시문 임베딩), Spectra Assure, Socket | **US 12223045 특허 (일반 앱)** · **FlowDelta (스킬·n8n 워크플로)** |

**결론:** "두 버전 × 실행" 칸에서 스킬·워크플로를 대상으로 한 공개 연구·도구는 이번 조사에서도 찾지 못했습니다. FlowDelta가 주장할 수 있는 기여는 다음 두 가지입니다.

1. **대상의 차이:** LLM 에이전트가 해석해 실행하는 스킬·워크플로에 차분 동적 분석을 처음 적용합니다.
2. **비결정성 처리:** 같은 입력에도 매번 다르게 움직이는 에이전트 실행에서 노이즈를 빼고 진짜 행위 차이만 남기는 방법입니다 (Diffy식 노이즈 상쇄 참고).

**평가 설계 제안:** 같은 버전 쌍 데이터에 ① LifecycleGuard식 지시문 비교, ② diff-CodeQL식 정적 비교, ③ FlowDelta 행위 비교를 돌려 **오탐률을 나란히 비교**합니다. LifecycleGuard가 보고한 오탐률 37%가 좋은 기준점이 됩니다.
