## 먼저 읽을 결론

**확인함:** 현재 앱에는 계정·로그인·세션·작성자 필드가 없다. 블로그 글의 공개 조회뿐 아니라 생성·수정·삭제 API도 인증 없이 실행된다. 로컬에서 더미 글을 만든 뒤 다른 더미 HTTP 클라이언트가 수정·삭제했고, 원래 클라이언트의 재조회로 실제 변경과 삭제를 확인했다.

## 4. 사람이 흉내 낸 규칙 선언 화면

이 앱이 공개 인터넷에서 여러 방문자가 쓰는 블로그라는 가정을 먼저 선언했다. 이 가정 자체가 아직 지침에 없다는 점이 이번 실험의 핵심이다.

| ID | 사람이 선언한 규칙 | 지침에 명시? | 코드 강제 | 실제 검증 | 판정 |
|---|---|---|---|---|---|
| R1 | 발행된 블로그 글은 로그인 없이 읽을 수 있다 | 없음 | GET에 제한 없음 | A 표기 클라이언트 GET 200 | **현재 동작과 일치** |
| R2 | 승인된 작성자만 글을 생성할 수 있다 | 없음 | 주체 확인 없음 | 인증 없이 POST 201 | **강제되지 않음** |
| R3 | 저장 글에는 인증된 작성자/소유자 ID가 연결돼야 한다 | 없음 | 데이터 모델에 필드 없음 | 생성 응답에도 작성자 정보 없음 | **강제되지 않음** |
| R4 | 글은 작성자 또는 관리 권한만 수정할 수 있다 | 없음 | `_id`만으로 UPDATE | A 표기 PUT 200, B 재조회에서 A 내용 확인 | **강제되지 않음** |
| R5 | 글은 작성자 또는 관리 권한만 삭제할 수 있다 | 없음 | `_id`만으로 DELETE | A 표기 DELETE 200, B 재조회 404 | **강제되지 않음** |

**확인함:** 제안 규칙 5개 중 4개가 코드로 강제되지 않는다. 그중 R2·R4·R5는 HTTP로 관찰했고, R3는 데이터 모델과 응답에서 확인했다.

**중요한 한계:** 실제 계정 A·B를 만들 수 없었다. 대상에 회원가입·로그인·세션 기능이 없기 때문이다. A와 B는 쿠키 없는 서로 다른 더미 HTTP 클라이언트를 구분한 라벨이며, 보안 주체가 아니다. “A가 B의 소유 자원을 침범했다”보다 정확한 표현은 **“현재 앱은 소유 관계를 표현하지 않으며 임의의 별도 클라이언트가 같은 ID로 쓰기 작업을 수행할 수 있다”**이다.

관리자 기능과 역할 상승은 코드에 해당 개념이 없어 **미실행/해당 없음**으로 분류했다. 없는 관리자 기능을 만들어 결과 수에 넣지 않았다.

## 6. Semgrep 보조 결과

**확인함:** Semgrep CE 1.177.0 컨테이너를 `--network none`으로 실행했다. 대상 코드는 read-only, 결과 폴더만 write로 마운트했다. 고정된 community rules의 `javascript`, `typescript` 구성을 사용했다.

핵심 명령:

```text
semgrep scan --oss-only --jobs 2 --timeout 15
  --config /rules/javascript --config /rules/typescript
  --metrics off --disable-version-check --no-git-ignore
  --exclude node_modules --exclude .git --json /src
```

| 항목 | 결과 |
|---|---:|
| 선택된 규칙 | 212 |
| 실제 실행 규칙 | 201 |
| 검사 대상 | 62파일 |
| 파싱률 | 약 100% |
| 분석 오류 | 0 |
| 경고 | **0** |
| profile 총시간 | 230.306초 |

**확인함:** Semgrep은 R2–R5 중 0/4를 경고했다. 특히 `src/app/api/blog/[id]/route.ts`, `src/lib/db/blog.ts`도 검사 대상 목록에 포함됐다.

**해석:** 이는 이번 규칙셋·버전·구성에서 “사용자·소유자 개념이 없는 것”과 “누가 어떤 ID에 쓰기 가능한가”를 잡지 못했다는 결과다. Semgrep 전체 제품이 사용자 정의 규칙이나 다른 구성을 통해 이를 절대 검사할 수 없다는 뜻은 아니다. 또한 0건은 앱 전체가 안전하다는 뜻이 아니다.

## 7. 질문별 결론

### a. 코드로 강제되지 않은 규칙이 있는가? 몇 개인가?

**있다. 5개 제안 규칙 중 4개다.** 인증된 작성자만 생성(R2), 글과 작성자 연결(R3), 작성자/관리자만 수정(R4), 작성자/관리자만 삭제(R5)이 현재 코드로 강제되지 않는다. 단, 이 개수는 “공개 읽기 + 제한된 쓰기”라는 사람이 먼저 선언한 정책을 기준으로 한다.

### b. AGENTS.md/CLAUDE.md에 보안 규칙이 적혀 있었는가? 지켜진 것과 일치하는가?

**적혀 있지 않았다.** 두 파일은 Next.js 최신 문서 확인을 지시하고 서로를 연결한다. direction도 기능·저장·인코딩 목표만 제시한다. 따라서 “적힌 보안 규칙이 코드에서 깨졌다”는 전파 실패 사례는 아니다. 더 정확히는 **접근 정책이 선언되지 않았고 코드에도 사용자 관계 모델이 생기지 않은 사례**다.

### c. Semgrep이 그중 몇 개를 잡았는가?

**0/4개.** 전체 경고도 0개였다. 실제 HTTP에서는 무인증 생성·수정·삭제와 상태 변화가 확인됐다.

### d. 컨셉 v2가 이 프로젝트에서 유효한가?

**규칙 선언과 관계 검증 부분은 유효하다.** 정적 스캐너가 0건을 낸 코드에서, 사람이 먼저 “공개 읽기·제한된 쓰기·작성자 소유”를 선언하자 실제 HTTP로 검증 가능한 차이가 생겼다. 특히 규칙을 선언하지 않으면 현재의 완전 공개 쓰기가 의도인지 누락인지 도구도 결정할 수 없다는 점이 컨셉의 문제 정의와 맞는다.

**규칙 파일로 재교육하는 단계는 아직 미검증이다.** 무라이선스 대상 코드를 수정하지 않았고 AI에 수정 프롬프트를 넣어 재생성하지도 않았다. 따라서 v2 전체를 입증했다고 쓰지 않는다. 다음 통제 실험에서 동일 커밋의 별도 비배포 사본에 아래 규칙 파일을 입력하고, AI가 데이터 모델·서버 라우트·회귀 테스트까지 일관되게 바꾸는지 측정해야 한다.

제안 규칙 파일의 내용:

```markdown
## Security invariants for blog posts
- Published posts may be read without login.
- Creating a post requires an authenticated editor.
- Every post stores an immutable ownerId from the server-side session.
- PUT and DELETE require the authenticated owner or an explicit administrator role.
- Authorization is enforced in server routes and database filters; UI visibility is not authorization.
- Tests must prove: owner succeeds, another user gets 403, anonymous gets 401, and blocked requests do not change data.
```

제안 수정 순서: 인증/세션 주체 도입 → `ownerId` 저장 → 기존 글의 소유자 마이그레이션 정책 결정 → PUT/DELETE에서 `_id + ownerId`를 함께 필터링 → 관리자 예외가 필요할 때만 역할 추가 → A/B/무인증/정상 기능 회귀 테스트. 라이선스가 없으므로 이 보고서에서는 대상 코드 패치를 만들지 않는다.

### e. 취약점을 찾지 못했다면 그대로 보고했는가?

관계 규칙과 관련해 **확인 가능한 동작을 찾았다:** 무인증 POST/PUT/DELETE와 수정·삭제의 실제 반영이다. 다만 이것을 교수님의 의도와 무관하게 확정 취약점이라고 단정하지 않는다. Semgrep은 경고를 찾지 못했다는 결과도 그대로 기록했다.

## 8. 확인하지 못한 범위

- **미실행:** 외부 배포 서비스 검색·접속·스캔, 실제 MongoDB/실제 데이터, 실제 사용자 계정, 관리자 권한 상승.
- **미실행:** AI에 규칙 파일을 주고 수정시키는 단계, 수정 후 관계/회귀 재검증.
- **미실행:** 전체 공급망 취약점 감사, 부하·DoS, 브라우저 기반 XSS/CSRF, 운영 설정, MongoDB 자체 인증·네트워크 설정 평가.
- **미확인:** 현재 서비스가 공개 다중 사용자 블로그인지, 개인 로컬 도구인지, 의도적으로 모두에게 공동 편집을 허용하는지.
- **미확인:** 파일별 AI 생성 여부와 실제 생성 프롬프트·대화.

## 9. 교수님께 보고할 때 쓸 1페이지 요약

### 무엇을 왜 검사했는가

AI 지원 개발에서는 기능 요구가 구현돼도 “누가 누구의 데이터를 바꿀 수 있는가”가 지침에 없으면 접근 규칙이 코드에 생기지 않을 수 있다는 가설을 확인했다. arXiv 2606.23130의 감사 결과는 1,186개 취약점 중 Hidden security rules 658개(55.48%)를 보고한다. 이번에는 실제 Next.js 프로젝트의 고정 커밋을 로컬에서만 실행하고, 외부 서비스나 실제 데이터에는 접근하지 않았다. 관련 논문 수치와 분모는 [선행 조사](02-논문정독-데이터셋.md)에 정리돼 있다.

### 발견한 것

AGENTS.md와 CLAUDE.md는 Next.js 최신 문서 확인을 지시하지만 접근 정책은 담고 있지 않았다. direction.txt도 옛한글 입력·DB/파일 저장·학자용 서비스 목표를 설명하지만, 누가 글을 쓰고 고칠 수 있는지는 정하지 않았다. 코드에는 계정·세션·작성자 ID가 없다.

사람이 “발행 글은 공개 읽기, 쓰기는 승인된 작성자, 수정·삭제는 작성자 또는 관리자”라는 규칙을 먼저 선언했다. 그 기준으로 5개 규칙 중 4개가 코드로 강제되지 않았다. 로컬 테스트에서 무인증 글 생성 201, 별도 클라이언트의 수정 200과 재조회 변경 확인, 삭제 200과 재조회 404를 확인했다. Semgrep CE는 201개 규칙으로 62파일을 분석했지만 경고는 0개였다.

이 결과는 정적 분석이 “코드에 적힌 위험 패턴”을 찾는 것과, 서비스의 사용자·자원 관계가 의도와 맞는지 확인하는 일이 다르다는 사례다. 동시에 현재 공개 쓰기가 의도된 공동 편집인지 지침만으로는 결정할 수 없었다. 먼저 규칙을 선언하게 하는 화면이 필요한 이유도 여기에 있다.

### 제안하는 수정

정책을 먼저 확정한다. 공개 읽기는 유지하되 글 생성은 인증된 편집자로 제한하고, 글에 서버 세션의 `ownerId`를 저장하며, 수정·삭제 쿼리는 글 ID와 소유자를 함께 검사한다. 관리자 예외가 필요하면 명시적 역할로만 추가한다. 수정 뒤에는 소유자 성공, 다른 사용자 403, 무인증 401, 차단된 요청 뒤 데이터 불변, 정상 공개 읽기를 함께 재검증한다.

우리 캡스톤은 이 흐름을 “규칙 선언 → 사용자·자원·행위 관계 테스트 생성 → 실패 증거 → AI 수정 프롬프트/규칙 파일 → 공격 및 정상 기능 재검증”으로 구현할 수 있다. 이번 결과는 앞의 관계 검증까지 뒷받침한다. AI 재교육 효과는 후속 통제 실험이 필요하다.

### 확인하지 못한 범위

실제 배포 환경·계정·데이터에는 접근하지 않았다. 관리자 기능은 코드에 없어 검사하지 않았다. 현재 접근 정책의 최종 의도도 교수님 확인이 필요하다. 대상 라이선스가 없어 코드를 복사하거나 수정 패치를 만들지 않았다. AI가 어느 파일을 생성했는지도 단정하지 않는다.

### 추가로 관찰한 것

**1. `AGENTS.md`는 교수님이 쓴 글이 아니다.** 파일 자체가 이렇게 밝힌다:

> "This block is written and re-added by `next dev`"

즉 Next.js가 자동 생성한 도구용 지침이다. **규칙을 적을 자리(파일)는 프레임워크가 이미 만들어 주는데, 그 안이 도구 사용법으로만 채워져 있다.** 우리 컨셉 v2의 "규칙 파일로 AI를 가르친다"가 들어갈 빈자리가 문자 그대로 존재한다.

**2. `direction.txt`는 부실한 명세가 아니다.** 오히려 꼼꼼하다 — 가상 키보드, 옛자모 입력, 프린트, DB 저장까지 구체적이고, 심지어 **인코딩 검토를 따로 요청**한다("웹에서 활용될때 구체적으로 어떤 인코딩을 사용해야 하는지 검토해줘"). 보통은 언급하지 않는 기술적 세부까지 짚은 명세다.

그런데 같은 문서가 **"풀스택 웹서비스", "학자들이 활용할 수 있는 서비스"** 라는 다중 사용자 목표를 적으면서도, **누가 쓰고 고칠 수 있는지는 한 번도 말하지 않는다.**

→ 이것이 Hidden security rules의 교과서적 사례다. 명세가 허술해서가 아니라, **접근 규칙은 사람에게 너무 당연해서 글로 적히지 않기 때문**이다. arXiv 2606.23130이 1,186건 중 658건(55%)을 이 범주로 분류한 이유와 정확히 일치한다.

### 표현 정정 — IDOR이 아니다

보고서 본문이 이미 조심스럽게 쓰고 있지만 한 번 더 못 박는다. 이 앱에는 **계정 개념 자체가 없으므로** 이것은 "A가 B의 자원을 침범했다"(IDOR / broken access control)가 아니라 **"쓰기 작업에 인증이 없다"**(missing authentication)다. A·B는 쿠키 없는 별개 HTTP 클라이언트 라벨일 뿐 보안 주체가 아니다.

발표·상담에서 이 둘을 섞으면 안 된다. 다만 우리 제품 관점에서는 **R2~R5 모두 "선언된 규칙이 코드로 강제되지 않음"이라는 같은 형태**이므로 컨셉 검증에는 그대로 유효하다.

### 컨셉 v2에 주는 판정

| 단계 | 상태 |
|---|---|
| ① 규칙 선언 | **유효.** 지침에 없던 규칙 5개를 사람이 선언하자 검증 가능한 대상이 됨 |
| ② 관계 검증 | **유효.** 실제 HTTP로 4개 위반을 관찰, DB 상태 변화까지 대조 |
| ③ 정적 분석과의 빈 칸 | **입증.** Semgrep 201규칙·62파일·0건 vs 사람 선언 규칙 4건 위반 |
| ④ AI 재교육 (규칙 파일) | **미검증.** 무라이선스 대상이라 수정·재생성 안 함. 별도 통제 실험 필요 |

③이 이번 실험의 가장 큰 수확이다. "패턴 스캐너가 0건을 낸 코드에서 사람이 규칙을 선언하자 4건이 드러났다"는 문장을 **실제 제3자 프로젝트에서** 말할 수 있게 됐다.
