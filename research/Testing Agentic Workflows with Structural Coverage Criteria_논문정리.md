## 2. 핵심 문제

**최종 답변이나 업무 성공률만 평가하면, 선언한 에이전트 구성·도구 접근 규칙·제한·위임 관계를 실제로 시험했는지 알기 어렵다.**

예를 들어 고객지원 에이전트가 정상 답변을 했더라도, 결제 담당에게 위임하는 경로가 시험되었는지, 읽기 전용 에이전트의 쓰기 도구 제한이 공격 상황에서도 유지되는지는 별도 문제다. 이는 논문 취지를 설명하기 위한 예시이며 실제 벤치마크 사례로 확인한 내용은 아니다.

논문은 이 문제를 **시험 집합의 충분성(test-suite adequacy)** 관점에서 다룬다. 단순히 몇 개 입력을 실행했는지가 아니라, 명세에서 시험해야 할 구조를 얼마나 실제로 실행·관측했는지 확인한다. 기존 의미적 평가와 종단간 평가를 보완하는 층이다.

## 3. 제안 방법

공개 초록에서 확인되는 흐름은 다음과 같다.

1. 워크플로 명세를 **타입이 있는 조정 그래프(typed coordination graph)**로 표현한다.
2. 도달 가능한 에이전트, 허용된 도구 간선, 제한된 도구 간선, 위임 간선에서 **커버리지 의무(coverage obligations)**를 도출한다.
3. 커버리지에 따라 시험을 생성하고, **DSPy 기반 시나리오 실현**으로 의무를 자연어 시나리오에 연결한다.
4. 실행 시 **관측 증거(witness)**를 검사한다. 시나리오 문구가 그럴듯하다는 이유로 해당 구조를 시험했다고 인정하지 않는다.
5. 제한된 정제 예산 안에서 시나리오를 개선한다. 구체적 반복 방식과 종료 조건은 본문 미확인이다.

그래프가 “무엇을 시험해야 하는가”를 고정하고, DSPy가 “그 구조를 실행시키려면 어떤 자연어 상황을 제시할 것인가”를 담당한다. DSPy 사용이 자동으로 모든 의무 충족이나 보안 판정을 보장하는 것은 아니다.

## 4. 네 가지 구조적 시험 대상

아래 설명은 초록에 등장하는 대상의 실무적 해석이다. 논문의 정확한 기준 이름·기호·형식 정의를 대체하지 않는다.

| 대상 | 확인하려는 것 | 설명용 예시 |
|---|---|---|
| 도달 가능한 에이전트 | 시험이 관련 에이전트에 실제로 도달하는가 | 총괄 에이전트에서 결제 담당으로 진입 |
| 허용 도구 간선 | 허용된 에이전트–도구 관계가 실행되는가 | 결제 담당이 허용된 조회 도구 호출 |
| 제한 도구 간선 | 적대적 시나리오에서 제한된 호출 위반이 나타나는가 | 조회 전용 에이전트에 환불 실행을 유도 |
| 위임 간선 | 선언한 에이전트 간 위임이 실행되는가 | 총괄 → 결제 담당 위임 |

특히 제한 도구 의무에서는 **공격을 시도함, 금지 호출이 관측됨, 제한이 유지됨, 충분한 관측을 얻지 못함**을 구분해야 한다. 논문 초록은 제한 호출 위반 수를 보고하지만, 나머지 의무의 상세 분류는 공개하지 않는다.

이 커버리지는 구현 코드의 줄·분기 커버리지나 모든 가능한 전체 경로 커버리지와 같은 것으로 확인되지 않았다. 한 번 도구 관계를 실행했다고 그 도구의 모든 인수·권한·데이터 조건을 시험한 것도 아니다.

## 5. 구현과 저자 보고 결과

구현 대상은 **OpenAI Agents SDK 스타일의 워크플로**다. n8n, MCP, LangGraph 전반에 같은 구현이 적용되었다고 확인한 것은 아니다.

| 항목 | 초록에 보고된 값 | 해석 |
|---|---:|---|
| SDK에서 유래한 벤치마크 | 10개 | 특정 구성의 연구 평가 대상 |
| 도달 가능한 에이전트 | 49개 | 워크플로의 구조 규모 |
| 도구 | 47개 | 도구 수이며 호출 관계 수와 다름 |
| 구조적 의무 | 403개 | 시험 대상으로 도출된 의무 |
| 허용 도구 의무의 관측 증거 확보 | 54/75, 72.0% | 제한된 정제 예산에서 확보한 결과 |
| 위임 의무의 관측 증거 확보 | 36/48, 75.0% | 제한된 정제 예산에서 확보한 결과 |
| 제한 도구 호출 위반 유발 | 23/248, 약 9.3% | 적대적 제한 도구 기준에서 발견한 위반 |

백분율은 보고된 분수에서 계산했다. 실험을 독립적으로 재측정한 값이 아니다.

### 수치를 사용할 때 주의할 점

- **23/248은 일반 에이전트의 취약률이나 모든 공격의 성공률이 아니다.** 특정 벤치마크·기준·예산에서 제한 호출 위반을 관측한 비율이다.
- 나머지 225개를 모두 “차단 성공”이나 “안전”으로 분류할 근거는 초록에 없다. 자세한 관측·실패 분류가 필요하다.
- 허용 도구 21개와 위임 12개에서 증거를 확보하지 못했다고, 해당 기능이 고장났다고 단정할 수 없다. 생성 실패, 도달 조건, 실행 예산, 관측 방식 등을 본문에서 확인해야 한다.
- 75+48+248=371로, 총 403개와 32개 차이가 난다. 이 32개의 분류 및 결과는 초록에 설명되어 있지 않으므로 임의로 에이전트 커버리지 결과를 만들어 넣지 않는다.
- 전체 403개의 “총 커버리지”를 위의 서로 다른 결과들을 단순 합산해 계산하지 않는다. 허용·위임의 실행 증거와 제한 호출 위반은 의미가 다르다.
- 최종 답변 품질, 업무 정확도, 실제 정보 유출·외부 쓰기, 비용 대비 우수성은 위 수치로 입증되지 않는다.

## 6. FlowDelta와 겹치는 부분

첨부된 FlowDelta 아키텍처 제안 및 [기존 비교 문서](2026-10-07-FlowDelta-도구비교.md)를 기준으로 한 분석이다. FlowDelta 구현 완료나 실제 성능을 뜻하지 않는다.

| 관점 | 논문에서 확인한 접근 | FlowDelta 제안과의 관계 |
|---|---|---|
| 그래프 모델 | 에이전트·도구 접근·제한·위임 관계 | Graph 단계와 직접 겹치는 선행연구 |
| 시험 대상 도출 | 명세에서 구조적 의무 도출 | 그래프에서 시험 대상을 얻는 발상과 겹침 |
| 시나리오 생성 | 의무를 DSPy로 자연어 시나리오화 | 가설을 실행 가능한 시험으로 바꾸는 단계와 유사 |
| 실행 관측 | runtime witness 검사 | 단순 최종 답변보다 실행 증거를 확인한다는 점이 겹침 |
| 제한 위반 | 적대적 제한 도구 호출 유발 | 권한 위반 시험과 직접 관련 |
| 변경 비교 | 구조적 회귀 탐지를 동기로 언급 | 버전 diff에서 시험을 선택하는 구체적 구현은 초록만으로 미확인 |
| 외부 효과 판정 | 초록에 구체적 설명 없음 | FlowDelta의 독립 수신기·자원 상태 oracle과 동일하다고 확인할 수 없음 |

**“그래프에서 시험을 만들고 실행 증거로 권한 위반을 확인한다”는 포괄적 설명만으로 FlowDelta의 독창성을 주장하기 어렵다.** 이 논문은 직접 비교해야 할 선행연구다.

다만 논문 초록에서 설명하지 않는 기능을 “논문이 제공하지 않는다”라고 단정해서도 안 된다. 본문을 확보해 변경 기반 선택, oracle, 상태·데이터 모델을 비교해야 한다.

## 7. FlowDelta에 적용할 제안

이 절은 논문 결과가 아니라 **우리 설계에 대한 제안**이다.

### 7.1 가설 선택과 시험 충분성을 함께 기록하기

현재 FlowDelta는 변경 → 위험 가설 → TestPlan을 중심으로 한다. 여기에 구조적 의무 목록을 두면 검색 카드나 LLM이 선택하지 않은 시험 공백을 드러낼 수 있다.

- 변경에 연관된 에이전트·도구·위임·제한 관계를 명시한다.
- 어떤 관계에 시험 계획을 만들었는지 기록한다.
- 계획이 실제로 실행되었는지 기록한다.
- 실행이 목표 관계에 도달하고 필요한 증거를 남겼는지 기록한다.
- 위반 여부는 별도 oracle로 판정한다.

그래프를 그렸다는 사실, 시험을 생성했다는 사실, 관련 동작을 실행했다는 사실, 보안 위반을 증명했다는 사실을 서로 다른 항목으로 둔다.

### 7.2 변경 관련 커버리지를 별도로 보여주기

전체 구조 의무와 변경 관련 의무의 분모를 각각 고정해 보고한다. 알려진 경로, 제외한 관계, 접근 불가·분석 불가 관계도 함께 표시한다. 시험하기 쉬운 의무만 분모에 넣어 점수를 높이지 않는다.

보고서에는 단일 안전 점수보다 다음을 분리해 적는 편이 적절하다.

- 시험 의무 전체/선택 수.
- 시험 실행 수와 목표 관계 증거 확보 수.
- 정책 위반·차단·시도만 관측·미관측·판정 불가 수.
- 정상 업무 수행 결과.

제한 관계에서 위반이 발견되는 것은 좋은 커버리지 점수와 동일한 의미가 아니다. 도달·관측의 충분성과 시스템의 안전성을 분리한다.

### 7.3 도구 호출 증거와 실제 외부 효과 증거 연결하기

FlowDelta 예시의 비밀문서 조회 및 외부 전송에서는 다음 증거가 서로 다르다.

1. 관련 에이전트·도구 관계가 실행됨.
2. 전송 인수에 금지 수신자나 민감정보가 포함됨.
3. 도구가 요청을 거부하거나 수락함.
4. 독립 수신기에 실제 데이터가 도착하거나 자원 상태가 바뀜.

구조적 witness에 외부 효과 oracle을 연결하면 시험이 어디까지 도달했고 무엇을 입증했는지 설명할 수 있다. 단, 논문의 witness도 이 증거를 수집하는지 여부는 본문 확인 전에는 미확인이다.

### 7.4 비교 실험 후보

같은 워크플로 버전·모델·입력·실행 예산에서 무작위 시나리오, 구조 의무 기반 시나리오, 변경·위험 가설 기반 시나리오를 비교한다. 변경 관련 구조 도달률, 독립 oracle로 확인한 위반 수, 정상 업무 유지, 실행 비용을 측정한다.

이 비교로 검증할 주장은 “그래프를 사용한다”가 아니라 **변경 관련 위험을 제한된 예산에서 더 잘 시험하고, 결과를 더 구체적인 증거로 설명할 수 있는가**다. 실제 비교를 수행한 결과는 아직 없다.

## 8. 본문 확보 후 확인할 사항

- 네 기준의 정확한 정의와 포함 관계, 도달 가능성 분석 방법.
- 제한 도구 간선이 자연어 규칙인지 SDK의 실제 권한 강제인지.
- 금지 호출의 attempted/invoked/executed 구분과 witness 수집 위치.
- 10개 벤치마크의 구성 및 현실성을 뒷받침하는 근거.
- DSPy 설정, 모델, 반복·정제 예산, 비용, 난수·비결정성 처리.
- 403개 의무의 세부 분포 및 미관측 의무 처리.
- 대조군, 절제 실험, 통계 및 재현 자료.
- 구조적 회귀 탐지에 실제 변경 전후 실험이 포함되는지.
- 데이터 접근·외부 전송·상태 변화 및 독립 oracle의 모델링 여부.

## 9. 팀 공유용 요약

이 논문은 에이전트 워크플로를 타입이 있는 그래프로 표현하고, 도달 가능한 에이전트·허용 및 제한 도구 관계·위임 관계에서 시험 의무를 도출한다. DSPy로 실행 시나리오를 생성하고 실제 실행의 관측 증거로 구조가 시험되었는지 확인한다. 저자들은 OpenAI Agents SDK 스타일의 10개 벤치마크에서 허용 도구 의무 54/75, 위임 의무 36/48의 증거를 확보했고 제한 도구 의무 248개 중 23개에서 호출 위반을 유발했다고 보고한다. FlowDelta의 그래프 기반 시험 생성과 실행 증거 접근에 직접 겹치는 선행연구이며, 변경 관련 시험 선택과 독립 외부 효과 판정의 추가 가치는 별도 비교 실험이 필요하다. 현재 정리는 원문 접속 제한으로 공개 초록 재게시본에 기반한다.
