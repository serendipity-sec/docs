# 04. 기존 보안 도구 비교와 우리 플랫폼의 차별화 검증

조사 기준일: 2026-09-20  
질문: Cisco Scanner·Snyk 등 현재 도구를 사용해도 버전 변경, 구성 관계, 검토 근거를 충분히 연결하지 못하는가?

## 1. 결론

**현재 공개 자료만으로 기존 도구가 전반적으로 부족하다고 결론 낼 수 없다.** 보안 스캐너 외에도 잠금·서명·버전 고정·정책 통제·감사·증거 공유를 제공하는 제품이 있다. 우리 제안의 여러 기능은 이미 구현되어 있다.

따라서 프로젝트의 검증 대상은 “새로운 스캐너나 그래프가 필요한가”보다 구체적이어야 한다.

> 정해진 호스트에서 함께 사용하는 외부 구성의 변경을 검토할 때, 현재 사용할 수 있는 도구 조합보다 보안상 중요한 누락을 줄이고 정상 변경을 더 적은 부담으로 처리할 수 있는가?

이 질문에서 의미 있는 개선이 확인되면 제품의 추가 가치를 주장할 수 있다. 확인되지 않으면 기존 엔진의 사용 경험을 개선한 통합 구현으로 기여 범위를 표현하거나, 대상 과업을 바꾸어야 한다.

## 2. 비교 방법과 신뢰 수준

이번 비교는 **공식 문서·공개 소스·GitHub API에 대한 읽기 전용 조사**다. 설치·실행·탐지율 측정·상용 콘솔 사용은 하지 않았다.

- `문서 확인`: 공식 문서나 소스에 기능이 명시되어 있다. 실제 환경에서의 성공을 뜻하지 않는다.
- `범위 제한`: 특정 모드·호스트·설정·배포 유형에서 제공된다.
- `미확인`: 이번 조사로 확인하지 못했다. 기능이 없다는 뜻으로 사용하지 않는다.
- `과거 문서`: 계보와 기존 아이디어의 존재를 확인하는 데 사용하며, 최신 버전의 작동 보장으로 사용하지 않는다.

### 3.1 Cisco 스캐너에서 가져갈 것

Cisco Skill Scanner는 검사 범위의 불완전성과 오탐·미탐 가능성을 명시한다. 이는 제품을 사용할 때 결과를 어떻게 해석해야 하는지에 대한 근거이지, 다른 플랫폼이 더 좋다는 성능 증거는 아니다. 선택 분석기를 쓸 때는 실제로 실행한 엔진·규칙·입력 범위를 결과와 함께 남기는 구조가 필요하다. [R20](https://github.com/cisco-ai-defense/skill-scanner/blob/431cb58a5ac333bc0bb9aaa23f7c30ac628f59f8/README.md)

MCP Scanner의 미리 수집된 JSON 분석은 수집과 분석을 분리하는 구현 후보가 된다. 다만 JSON이 어떤 서버·시점에서 왔는지 확인하는 일은 입력의 출처 문제다. 코드 분석 기능이 있다는 것과 해당 서버의 모든 실행 동작을 검증했다는 것도 다른 주장이다. [R21](https://github.com/cisco-ai-defense/mcp-scanner/blob/9e47aabdf2017b82e78f3419f39a75f20b6f98fa/README.md)

### 3.2 Snyk 통합에서 확인할 조건

확인한 Agent Scan 문서는 분석에 필요한 서버 구성·도구 설명·skill content 등을 API로 보내며 전송 전에 비밀정보를 가린다고 설명한다. stdio 서버의 정보를 얻는 과정에서는 서버 실행이 발생할 수 있고 개별 동의 흐름을 제공한다. 제품 평가에서는 네트워크·실행 허용 조건을 같게 맞추고, API 분석을 끈 결과를 전체 제품 성능으로 발표하지 않아야 한다. [R22](https://github.com/snyk/agent-scan/blob/57fdd46e53ee833c63007c486477f17df4f65625/README.md)

**통합 제안:** 파서에는 도구 버전별 어댑터와 미지원 스키마 오류를 두고, 원본 응답을 비밀정보 처리 후 보존한다. 위험 이름이 바뀌거나 결과를 읽지 못하면 0건으로 처리하지 않는다. 공개 CLI와 상용 플랫폼의 기능·지원 조건도 따로 비교한다.

### 3.3 AgentShield에 대한 기존 비교를 갱신해야 한다

현재 README에는 여러 호스트 구성의 근거, 활성 구성과 예제·플러그인 manifest를 구분하는 `runtimeConfidence`, 정책 결과, 공급망 근거, SHA-256이 포함된 evidence pack, 검증·검토용 readback·여러 묶음의 집계가 설명되어 있다. 단순 baseline 외에도 정책 배포·공급망 설정 변경을 다룬다. **“기존 제품은 경고 목록만 내놓는다”는 설명은 부정확하다.** [R34](https://github.com/affaan-m/agentshield/blob/b0891303bdcd6037376a94263d45cfd2ff3dfb98/README.md)

이 기능들이 우리의 특정 검토 과업을 어느 수준까지 해결하는지는 미실행 상태다. 바로 그 이유로 강한 대조군에 포함해야 한다. README에 기능이 많다는 사실만으로 충분하다고 확정하지도 않고, 설치해 보지 않았다는 이유로 없는 기능처럼 취급하지도 않는다.

### 4.1 “검사하고 공유하는 플랫폼” 자체는 새로운 범주가 아니다

NVIDIA의 공개 trust pipeline은 검사, task 기반 평가, 설명 카드, 최종 디렉터리 서명을 구분한다. 검사 대상의 staged scope도 명시한다. Skill Card는 소유자·용도·의존성·위험·릴리스 근거를 연결한다. 따라서 “안전성 근거를 묶어 사용자가 판단하게 한다”는 전체 구상에서도 선행 체계가 존재한다. [R31](https://docs.nvidia.com/skills/agent-skill-trust-pipeline), [R33: Skill Card](https://docs.nvidia.com/skills/skill-cards)

이 사실은 프로젝트를 포기해야 한다는 뜻이 아니다. 다만 “최초의 보안 공유 플랫폼” 대신 **정해진 사용자·구성·검토 과업에서 확인한 개선**을 기여로 설정해야 한다. 서명·카드 형식이 이미 있으면 받아들이고 연결하는 것이 우선이다.

### 4.2 런타임 통제는 제품 이름만으로 판단하지 않는다

DefenseClaw의 capability matrix는 connector별 block·native ask·fail-closed 지원을 구분한다. native ask가 없는 connector의 흐름을 사용자 승인을 기다렸다 재개하는 기능과 동일하게 취급할 수 없다. “연동 지원”과 “특정 호스트·OS에서 강제 기능을 확인했다”도 다르다. [R29](https://github.com/cisco-ai-defense/defenseclaw/blob/85029e57e9094debd9366a7d5a9f7e6d5c3ef6fc/docs-site/content/docs/capability-matrix.mdx)

우리 플랫폼이 정적 검토만 제공한다면 runtime 차단까지 제공하는 대조군과 경쟁하는 모든 영역에서 더 안전하다고 주장할 수 없다. 먼저 도입·변경 검토라는 공통 과업을 비교하고, 실제 강제 효과는 별도의 평가로 분리해야 한다.

### 4.3 이전 세대의 기능도 차별성 주장에 반영한다

Invariant의 MCP-Scan 과거 문서는 tool hashing/pinning, cross-origin 문제 탐지, proxy에서 호출·응답 감시와 정책을 설명한다. 최신 Snyk 0.6의 정확한 기능·명령과 동일하다고 가정하지 않지만, **해시 기반 변경 감지나 여러 도구 사이의 문제 인식이 새 아이디어는 아니라는 근거**로 충분하다. [R35: 과거 공식 문서](https://invariantlabs-ai.github.io/docs/mcp-scan/)

## 5. 기능별로 다시 보면 어디가 이미 채워졌는가

|---|---|---|
| Skill·규칙 파일 보안 검사 | Cisco·NVIDIA·AgentShield·Snyk | 지원 범위·정확도·누락 처리의 개선 |

| 보안 보고서·검토 근거 공유 | SARIF, AgentShield evidence pack, NVIDIA Skill Card | 근거의 적용 범위를 더 정확히 전달하는 효과 |
| 사용자 승인·차단 | DefenseClaw, ToolHive 등의 정책 계층 | 지원 조건에서 보안·부담의 개선 |
| 관계 그래프 | SARIF의 그래프·흐름 표현, 각 플랫폼의 구성 구조 | 실제 관계 복원 정확도와 사용자 과업 성능 |

이 표의 마지막 열은 **확인된 차별성 목록이 아니라 앞으로 검증할 가설**이다.

## 6. SARIF와 공통 결과 모델: 재사용할 것과 새로 검증할 것

SARIF 2.1.0은 단순 경고 문자열 형식이 아니다. 공식 스키마에는 `versionControlProvenance`, `baselineState`, `graphs`, `codeFlows`, `graphTraversals` 같은 구조도 있다. “SARIF는 관계나 변경을 표현할 수 없다”는 주장은 맞지 않는다. [R36: OASIS 공식 스키마](https://github.com/oasis-tcs/sarif-spec/blob/main/sarif-2.1/schema/sarif-schema-2.1.0.json)

**설계 해석:** 표준이 표현 공간을 제공하는 것과 여러 엔진이 같은 의미·같은 대상 식별자로 채우는 것은 다른 문제다. 새로운 보고서 형식을 발명하기보다 다음 연결을 명시할 필요가 있다.

1. 어떤 원본 finding이 어떤 파일·구성요소·입력 digest에 해당하는가?
2. 해당 엔진이 실제로 실행됐는가, 일부 형식은 제외됐는가?
3. 서로 다른 severity와 confidence가 같은 의미인가?
4. 예외로 수용한 finding과 검사되지 않은 부분을 구분하는가?
5. 보고서를 받은 사람이 같은 설치본과 정책에 결정을 적용하는가?

원본 결과를 잃지 않는 얇은 어댑터가 우선이다. severity를 일괄 평균 내거나 여러 엔진의 같은 규칙을 독립 증거처럼 중복 계산하는 방식은 근거 없는 확신을 만들 수 있다.

## 7. 스캐너 불일치 연구가 실제로 말하는 것

*ClawHub Security Signals* v1은 67,453개 최신 공개 스킬 버전의 정제 자료에서 VirusTotal·정적 휴리스틱·SkillSpector의 신호를 비교했다. 표시된 스킬의 81.9%가 한 스캐너에서만 표시됐고 전체 스킬의 0.69%가 세 계열 모두에서 표시됐다고 보고한다. 분모가 다르므로 두 비율을 직접 비교하지 않는다. [R37: 논문](https://arxiv.org/html/2606.01494v1)

이 자료의 최종 판정은 registry의 자동화된 **silver label**이며 사람이 확정한 보안 정답이 아니다. 스캐너가 보는 입력·위험 종류도 다르다. 따라서 불일치를 곧바로 미탐률·오탐률로 해석하거나 다수결을 정답으로 삼을 수 없다. 최신 제품의 독립 성능 비교로도 사용할 수 없다. [R37](https://arxiv.org/html/2606.01494v1)

**프로젝트 해석:** 불일치한 근거를 나란히 보여 줄 이유는 있다. 그러나 “여러 엔진을 연결했으므로 정확도가 올랐다”는 별도 실험이 필요하다. OR 결합은 경고량을, AND 결합은 통과량을 늘릴 수 있으므로 정상 과업의 불필요한 거부와 중요한 누락을 함께 측정해야 한다.

기존 조사에 있는 특정 연구의 높은 우회율도 대상 스캐너 버전·설정·입력·실험 방식에 묶인 값이다. 이번 문서는 사고·공격 재현을 제외했으며 그 수치를 시장 전체나 현재 제품의 실패율로 재사용하지 않는다.

## 8. 실제 도입 비용도 비교해야 한다

| 항목 | 문헌에서 확인되는 차이 | 우리 비교에서 통제할 내용 |
|---|---|---|
| 외부 전송 | 로컬 분석과 API·LLM 분석이 섞여 있음 | 소스·메타데이터 전송 범위, 사내 자료 사용 가능 조건 |
| 검사 전 실행 | 로컬 파일 분석과 MCP 서버 기동·연결은 다름 | 결과 수집과 분석 분리, 동일한 입력 접근권한 |
| 엔진 옵션 | 선택적 semantic 분석·API·규칙 설정 | 활성화한 엔진을 명시하고 미실행을 0건으로 세지 않기 |
| 출력 안정성 | 표준 결과와 실험적 CLI 응답이 공존 | 버전별 어댑터, 원본 보존, 파싱 실패 상태 |
| 유지보수 | 기본 브랜치와 릴리스·의존 도구가 달라질 수 있음 | 커밋·버전·규칙·API·모델 식별과 재검증 비용 |
| 플랫폼 적용 | 호스트·connector·운영체제별 지원 차이 | 지원되지 않는 조합을 제품 전체 결함으로 세지 않기 |
| 운영 통합 | 프로필·인가·감사·승인 기능이 이미 있는 제품도 있음 | 단일 스캐너 외에 강한 통합 대조군 포함 |

라이선스 표시는 코드 재사용 검토의 시작점이다. 실제 채택 전에는 선택 릴리스의 LICENSE·NOTICE와 사용하는 서비스 조건을 함께 확인하고 저장소에 기록한다. 이번 조사에서는 서비스를 계약하거나 API 키를 등록하지 않았다.

## 9. 가설을 검증하는 비교 과업

아래 표는 **미실행 비교 설계**다. 실제 악성 코드를 배포하거나 외부 서버를 공격하는 절차가 아니다. 검토용 고정 자료와 무해한 합성 설정으로 입력·정답·평가 기준을 명확하게 만든다.

| 과업 | 사례 구성 | 기존 도구에 공정하게 제공할 것 | 우리 제안이 실패하는 조건 |
|---|---|---|---|
| 설치본 동일성 | 원본과 동일한 구성 / 로컬 수정 구성 | 잠금 파일·서명·현재 디렉터리 정보 | 기존 검증과 차이가 없거나 수정본을 동일하다고 표시 |
| 변경 검토 | 설명만 변경 / 명시적 접근 범위 변경 / 범위 축소 | baseline·Git diff·정책·같은 스캔 결과 | 문구 변경을 과도하게 위험으로 표시하거나 중요한 변경 누락 |
| 근거 연결 | 두 엔진이 다른 범위를 검사한 보고서 | 원본 보고서·지원 범위·버전 | 불일치를 잘못된 다수결로 통합 |
| 부분 실패 | 필수 엔진 오류·미지원 형식·만료 보고서 | 명확한 실행 상태 | 오류나 미검사를 “안전”으로 처리 |
| 구성 관계 | 명시적으로 연결된 도구 / 함께 설치만 된 도구 | 동일한 설정·참조 자료 | 실제 연결 없이 확정적인 데이터 흐름을 만들어냄 |
| 검토 인계 | 다른 사람이 내린 조건부 승인 | 기존 evidence pack·카드·정책 문서 | 조건을 더 자주 오해하거나 기존 보고서보다 오래 걸림 |

도구별로 `지원`, `지원되지만 설정 필요`, `자료 부족`, `지원 범위 밖`을 기록하고 실제 증거 파일을 남긴다. 미지원 과업을 0점으로 합산해 제품 전체 순위를 만들기보다 **공통 범위 성능**과 **추가 범위**를 따로 보고한다.

## 10. 대조군은 세 단계로 구성하기

**기본 검토:** 사용자가 현재 이용하는 원문·Git diff·패키지 정보. 이것만 이긴다고 새로운 플랫폼의 필요성이 입증되는 것은 아니다.

**강한 도구 조합:** 선택한 호스트에서 현실적으로 쓸 수 있는 스캐너, baseline, evidence pack 또는 카탈로그·정책 기능. 설치·교육 시간을 포함한 실제 도입 비용도 기록한다.

**우리 플랫폼:** 동일 엔진·동일 입력을 쓰는 상태에서 관계 연결·변경 요약·검토 이력의 추가 효과를 본다. 새 분석 규칙을 넣는 경우에는 UI 효과와 탐지 효과를 분리한다.

특히 AgentShield의 증거 묶음, NVIDIA의 카드·서명, Docker의 고정 배포물과 같은 강한 기존 기능을 대조군에서 빼면 우리에게 유리한 비교가 된다. 사용할 수 없는 상용 기능은 제한 이유를 기록하고, 공개 도구만 비교한 결론으로 범위를 좁힌다.

## 11. 이번 학기의 구현 범위 제안

### 재사용 우선

- 기존 스캐너의 원본 finding과 표준 출력.
- Git·패키지 digest·현재 잠금·서명 정보.
- 사용 호스트가 제공하는 권한 정책과 감사 정보.
- 기존 evidence pack·카드가 제공하는 증거 링크.

### 검증할 추가 구현

- 지원하는 설정에서 원본·설치본·검사·승인 대상을 일관되게 연결하기.
- 고정한 이전 구성과 현재 구성의 의미 있는 차이를 근거 위치와 함께 보여 주기.
- 미실행·미지원·해석 불가를 유지하면서 다음 검토 행동을 안내하기.
- 검토자가 다른 사람에게 동일한 조건을 전달하고 재검토할 수 있게 하기.

### 첫 단계에서 보류

- 모든 자연어·코드의 실제 능력을 자동으로 완전 추론하는 엔진.
- 자체 범용 sandbox·모든 호스트용 runtime gateway.
- 모든 기존 제품보다 높은 탐지율을 전제한 마케팅.
- 단일 “안전 점수”로 서로 다른 정책과 위험을 대체하는 방식.

이 범위는 확정 요구사항이 아니라, 현재 근거와 팀 규모에 비추어 제안하는 실증 범위다.

## 12. 추진·전환 판단

| 검증 결과 | 판단 |
|---|---|
| 강한 기존 도구에서도 반복적인 누락·근거 연결 부담이 남고 우리 구현이 개선한다. | 해당 과업을 핵심 가치로 삼아 진행 |
| 보안 성능은 같고 검토 시간이 줄어든다. | 보안 검토 지원·운영 효율 개선으로 기여를 한정 |
| 속도는 빨라지지만 위험한 승인도 증가한다. | 출시 근거로 삼지 않고 판단 표시·강제 조건을 수정 |
| 기존 도구가 같은 과업을 비슷한 비용으로 해결한다. | 통합 교육·배포 지원으로 전환하거나 다른 과업 탐색 |
| 원격·동적 구성이 대부분이라 정적 자료만으로 판단할 수 없다. | 범위를 줄이거나 기존 실행 통제 체계와 연동하는 방향 검토 |

현 단계의 차별화 문장은 다음 정도가 적절하다.

> 기존 보안 도구와 배포 검증 체계를 활용하되, 개발팀이 실제 사용하는 혼합 구성의 도입·변경 검토에서 대상 동일성, 근거 적용 범위, 승인 조건을 함께 추적하는 방법을 구현하고 비교 평가한다.

“기존 도구가 하지 못한다”와 “우리 방법이 더 낫다”는 실험 전에는 포함하지 않는다.
