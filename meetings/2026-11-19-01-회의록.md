# 지도교수 면담: 프론트 시안 피드백과 실제 사례·서비스 완성도 점검

- **일시**: 2026-11-19

## 안건별 논의 내용

### 1. 캡스톤 경진대회 신청서
신청서는 작성 중이라고 보고함. 교수는 계획만 있는 상태로는 1차 통과가 어렵다고 함. 이 정도 성능으로 완성됐다는 모습을 (가상이라도) 담아 제출하고, 채택되면 최종 데모 때까지 실제로 완성해서 보여 줄 수 있게 빨리 준비하라고 강조함.

### 2. 프론트 시안 공유와 피드백
**시안 내용**: 랜딩 페이지를 공유함. 라이트/다크 모드를 지원하고, 워크플로우 이름으로 검색하면 해당 페이지로 이동하며, 처음 쓰는 사람을 위한 검색 예시와 간단한 설명이 있음. 상세 페이지에는 검증 횟수, 케이스별 결과, 변경 노드와 변경점, 수립한 계획, 검증 로그를 보여 줄 예정임. 현재는 목(mock) 데이터이고 API는 아직 연결되지 않았음.

**교수 피드백**:
- 개념 설명은 별도 메뉴("프로젝트 설명")로 빼고, 메인에는 많이 쓰이는 워크플로우를 사용량이나 위험도 기준으로 보여 줄 것(예: "최근 분석 핫 5")
- 처음 쓰는 사람은 워크플로우 이름을 직접 입력하기 어려우니 분야별 카테고리로 이름을 보여 주고 클릭해서 검색할 수 있게 할 것
- 의심(!) 표시를 클릭하면 해당 노드의 의심·오류 내용이 팝업으로 나오게 할 것
- 실제 사례가 없어 이 화면만으로는 보안 검사가 왜 필요한지 느껴지지 않음

### 3. 실제 워크플로우 분석 사례 부재
실제 워크플로우를 검사한 결과는 아직 없다고 답함. 교수는 사람들이 많이 쓰는 유명 워크플로우 4~5개(예: AI로 영화·음악을 만드는 워크플로우)를 골라 정상 사례와 문제 사례를 분석하고, 그 결과를 메인에 보여 주라고 함. 문제가 있는 워크플로우는 어디에 어떤 문제가 있는지 구체적으로 드러나야 함. 데이터셋은 민호가 준비하기로 했으며 진행 상황은 다시 확인하기로 함.

### 4. 사용자 검증 요청 기능
팀은 일반 사용자가 검증을 요청하는 것은 원래 목적이 아니었다고 설명함. 캡스톤 지원비가 클라우드에 적용되지 않아 무료로 운영 가능한 구조로 짜 두었다는 점도 언급함. 교수는 보여 주기만 하는 사이트로는 부족하다고 지적함. 회원 가입한 사용자가 아직 분석되지 않은 워크플로우를 신청하면, 음식 주문처럼 큐에 넣고 워커가 알아서 분석한 뒤 완료되면 보여 주는 구조여야 한다고 함. 팀은 신청 창구를 추가하는 것은 어렵지 않다고 답함.

### 5. 검사 방식에 대한 설명 부족
교수는 어떤 검사를 하는지, LLM을 어떻게 활용하는지, FlowDelta(변경 전후에 같은 입력을 넣어 차이를 보는 방식)로 무엇이 드러나는지 설명을 들은 적이 없다고 지적함. 수정된 워크플로우의 원본성 검증(전자서명, 버전 관리, 지문)도 물었고, 팀은 해시로 따로 관리하는 것으로 안다고 답함.

팀이 설명한 A/B/C 구조와 현황은 다음과 같음.
- **A**: 무엇이 변경됐는지 파악
- **B**: 변경된 곳에서 어떤 실험을 할지 결정. 임베딩해 둔 카드에서 로컬 LLM이 추천 문서를 찾고, 그 문서를 바탕으로 실험 계획을 세움
- **C**: 결정된 실험을 버전별로 돌려 검증
- **현황**: B에서 C로 넘기는 단계까지 연결됨. 예시로 등록한 n8n 워크플로우 2~3개는 결과까지 나옴. 다만 어떤 검증을 할지 정의한 카드가 많이 부족해서 카드 보강이 필요하고, 이후 데이터셋에 모인 버전들로 테스트를 돌릴 계획임

### 6. 실행·배포 구조
- **검증 실행**: 로컬에서 워커를 실행하고, 결과는 별도로 뚫어 둔 API로 DB에 저장함. LLM은 로컬 LLM이나 상용 API 중 하나를 쓸 예정임.
- **DB·API**: DB는 이미 띄워 두었고, 데이터만 들어가면 API를 연결하면 됨. 머지만 되면 메인에 반영될 상태라고 함.
- **배포**: 프론트는 Vercel로 배포되어 있음(Windows 환경에서는 글꼴이 깨짐). 백엔드도 Vercel로 올릴 예정임.
- **핫 5 기능**: Redis 리더보드 같은 것이 필요하므로, 우선 몇 개를 보여 주는 수준으로 진행함.
- **워커 장비**: 교수가 민우가 가져다 놓은 503 컴퓨터를 워커로 운영하라고 제안함.

### 7. 기타
- Terraform과 n8n의 차이를 설명함. Terraform은 클라우드 인프라를 코드로 구축하는 도구이고, n8n은 AI를 활용한 작업 연결에 가까움. 교수는 AI 요소를 연결해 구축할 때의 보안 문제와 관련된 주제를 몇 개 정해 보라고 함.
- HTML로 만든 발표 자료도 최종 모습 없이 연구 계획에 가깝다는 지적이 있었음. 이후 팀별 발표는 온라인으로 진행함.

## 결정사항
- 검증을 빨리 돌려 결과를 DB에 적재하고, 그 데이터로 API를 연결한 뒤 프론트를 수정한다.
- 교수 피드백 중 서버 없이 가능한 프론트 개선부터 먼저 처리한다.
- 경진대회 신청서는 계획이 아니라 완성된 서비스의 모습으로 작성해 제출한다.
