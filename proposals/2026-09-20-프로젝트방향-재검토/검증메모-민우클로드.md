# 재검토 세션 검증 메모

작성 2026-09-20 · Claude Code(민우님 세션) · GPT 재검토 세션의 주장 3건을 1차 자료로 확인한 결과

> GPT와의 대화 기록과 후보 3개를 읽고, **판단이 바뀔 만한 주장 3개**만 골라 원본으로 확인했다.
> 결론: GPT 방향은 대체로 타당하다. 다만 **후보 2는 이미 민우님이 한 것**이고,
> **SkilLock은 GPT가 말한 것보다 훨씬 좁다**. 두 사실이 후보 순위를 바꾼다.

---

## 검증 1 — SkilLock: "capability diff는 이미 있다"는 절반만 맞다

GPT: "SkilLock이 capability 변경 비교·승인 이력·PR 검사를 이미 제공하므로 '이런 도구는 없다'는 유지 불가."

**확인 결과 (github.com/skills-lock/skil-lock, SPEC.md 원문):**

| 항목 | 실제 |
|---|---|
| 성숙도 | ★6, fork 0, Go 단일 바이너리, Apache-2.0, 2026-05 생성, v0.2.5 |
| 하는 일 | `SKILL.md`를 파싱해 shell 명령·네트워크 호스트·파일 경로·allowed-tools를 `skills.lock`에 고정, PR에서 capability 델타를 보여주고 CI 차단 |
| **입력 범위** | **`SKILL.md`만.** CLAUDE.md·AGENTS.md·`.mcp.json`·hooks·플러그인 **안 읽음** |
| **호스트** | **claude·codex만.** Cursor·Copilot·MCP는 "Planned" |
| **코드 분석** | shell 스크립트만 파싱. **`.py`·`.js`는 해시만** |
| **MCP·교차 참조** | v0.1 미지원(명시된 future work) |
| **웹 UI·팀 검토·다중 스캐너 통합** | **없음.** CI/CLI 전용 |

**판정**: GPT가 맞다 — "capability diff 도구가 아예 없다"는 이제 못 쓴다. **틀린 전제는 폐기한다.**
그러나 SkilLock은 **가장 좁은 조각**(SKILL.md, 2개 호스트, CI 게이트)만 차지한다.
Red Hat 논문·SkilLock 둘 다 **CI 개발자용 CLI**다. 우리가 원래 그리던
"규칙·스킬·MCP·플러그인을 아우르는 팀 검토 **웹 플랫폼**"과는 층이 다르다.

→ 이건 기존 주제를 **죽이지 않지만**, 차별화를 "capability diff를 최초로 한다"가 아니라
"CLI가 아닌 **팀 검토 웹 흐름**, SKILL.md를 넘는 **여러 입력**"으로 옮겨야 한다는 뜻이다.
그런데 그 차별화는 점점 방어하기 빡빡해진다. **기존 주제의 매력이 이번 검증으로 더 줄었다.**

## 검증 2 — ★ 후보 2(PII)는 민우님이 이미 한 캡스톤이다

GPT: "후보 2는 PII 탐지·비식별화가 이미 많이 다뤄졌을 가능성이 우려."

**확인 결과 — GPT가 몰랐던 사실:**

- `github.com/vmaca123/LLM-KOREAN-GUARDRAIL-PROJECT` (2026-03)
- `C:/My-AI-Security-Project/` + `korean_pii_guardrail_v0_2/` + `PII/layer_0~4`
- **캡스톤 연구보고서**: 『한국어 LLM 게이트웨이 환경에서 다계층 PII 가드레일의 취약성 분석 및
  정규화 기반 방어 계층 설계』, 지도교수 임정묵, 2026-04
  — Presidio·Bedrock·Lakera 3계층 + GPT-4o-mini LLM-judge 4계층 스택을 **이미 구축·평가**함

**판정**: 후보 2는 "이미 많이 다뤄진" 정도가 아니라 **민우님 본인의 직전 작업**이다.
같은 과 캡스톤에서 반복하면 자기표절 우려 + 새로움 0. **후보 2는 탈락 권장.**
(단, 그 경험은 자산이다 — 후보 1·3에서 "민감정보가 외부로 나가는 경로"를 다룰 때 재활용 가능.)

## 검증 3 — 후보 1(바이브 코딩 보안)은 근거가 압도적이다

민우님: "책에서 AI로 만든 코드가 기능은 100% 되는데 보안은 뚫려 있단 내용을 본 적 있다."
→ 그 기억이 맞다. 2026년에 이걸 정면으로 잰 자료가 쏟아졌다.

| 근거 | 수치 | 출처 |
|---|---|---|
| **바이브코딩 앱 실측** | **9,041개 앱 + 200개 배포본 감사. 91%가 취약점 1개+, 65.8%가 Critical/High.** 최다 유형 = **broken access control · injection · 인증 실패** | arXiv 2606.23130 (Deng et al., 2026-09-14) |
| AI 생성 코드 OWASP 실패율 | **45%.** XSS 86%, 로그 인젝션 88% 취약 | Veracode (100+ LLM) |
| AI 코드 CVE | 확인 74건(추정 400~700), 3월에만 35건 | CSA 연구노트 (2026-04-04) |
| Lovable 앱 | RLS 누락 170개+, 취약 엔드포인트 303개, 분석 대상의 10.3% | CSA / OX Security |
| 결정타 | **"기능은 되는데(functional) 뚫려 있다"** = 논문이 직접 확인 | arXiv 2606.23130 |

**판정**: 후보 1은 이 세션에서 **근거가 가장 강하고, 공감이 즉각적이고, 과목 적합성이 직결**된다.
- 공감: "AI로 만든 내 사이트, 기능은 되는데 공개해도 되나?" — 설명이 필요 없다
- 과목: 대상이 **웹앱 그 자체**다. 웹앱 보안 과목에 억지로 맞출 필요가 없다
- 최다 취약 유형(broken access control = IDOR, injection, XSS)이 CWE Top 25·OWASP와 정확히 겹친다

**단, 차별화 숙제**: AI 웹앱 자동 보안 검증은 이미 있다(Shannon 등). 그래서 후보 1의 기여는
"AI가 해킹해 줌"이 아니라 **"바이브코딩한 초보가 발견→이해→수정→재검증까지 끝내게 하는 흐름"**
이어야 한다. 여기가 우리 웹앱이 들어갈 자리다.

## 종합 판단 — Claude 의견

GPT의 큰 방향(사고·시장 근거는 충분, 이제 "누가 왜 쓰는가"가 관건)에 동의한다. 여기에 검증 2건을 더하면:

| 후보 | 이번 검증 후 | 한 줄 |
|---|---|---|
| 기존 AI 공급망 검사·공유 | ↓ 약화 | SkilLock·Red Hat이 좁은 조각을 이미 채움. 차별화가 "웹·팀·다입력"으로 밀렸고 방어가 빡빡 |
| **후보 1 바이브코딩 보안 검증** | **↑ 최상** | 근거·공감·과목적합 3박자. 민우님도 아는 문제. 차별화는 "수정까지 끝내는 흐름" |
| 후보 2 PII AI 문서작업 | ✗ 탈락 권장 | 민우님 직전 캡스톤과 중복 |
| 후보 3 AI 작업 실행 전 확인 | → 유지 | 흥미롭지만 공감에 설명 필요, 승인 기능은 LangChain 등 기존. 후보 1의 대안 |

**개인 추천**: 후보 1을 1순위 후보로, 후보 3을 대안으로. 후보 2는 접는다. 기존 주제는 3순위로 내린다.
단, 이건 **민우님이 팀에 가져갈 재료**지 결정이 아니다. 팀이 AI를 원하는데 후보 1도 AI다 — 접점이 있다.

**결정 방법(GPT 제안에 동의)**: 보고서 더 모으지 말고, 후보 1·3을
"문제 발생 → 우리 도구로 원인 확인 → 조치 후 달라짐" 30초 시연으로 만들어
대상 사용자(AI로 웹 만들어본 학생) 몇 명에게 보여주고 **"내 것도 검사돼요?"가 나오는 쪽**을 고른다.

## 정직하게 남기는 것

- SkilLock·Shannon·Presidio·Autorize·LangChain HITL의 **실제 기능은 공식 문서로만 확인**했다. 설치·성능 비교는 안 했다.
- 후보 1의 차별화(수정까지 끝내는 흐름)가 Shannon 등과 정말 다른지는 **직접 확인 필요**.
- arXiv 2606.23130의 세부 비율(IDOR/RLS 개별 %)은 초록 수준만 확인. 본문 미열람.
- 이 메모는 **민우님 세션의 판단**이다. 팀 합의도, 9/15 회의 결정 변경도 아니다.
