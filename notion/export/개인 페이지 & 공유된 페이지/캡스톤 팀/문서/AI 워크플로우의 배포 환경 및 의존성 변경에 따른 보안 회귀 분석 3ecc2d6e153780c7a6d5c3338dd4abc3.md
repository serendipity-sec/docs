    여기서 **보안 회귀**는 업데이트나 환경 변경 때문에 이전에는 없던 위험이 새로 생기는 것을 뜻해. 프로젝트의 중심 질문은 다음으로 잡자.
    
    > **“이 AI 워크플로우를 업데이트하거나 다른 환경으로 옮겼을 때, 어떤 데이터 접근·외부 전송·실행 권한이 새로 생기며, 기존 보안 검토를 그대로 인정해도 되는가?”**
    > 
    
    아래는 이를 연구와 구현 양쪽에서 구체화한 프로젝트 제안이야. 수치로 제시한 범위와 성능은 **이미 달성된 결과가 아니라 프로젝트의 설계 목표**야.

    # 2. 기존 기능과 무엇이 다른가?
    
    새로운 파일 형식이나 위험 노드 목록을 만드는 데 연구의 중심을 두면 안 돼.
    
    현재 n8n에는 워크플로우와 의존성 정보를 담는 **`.n8np` 패키지 형식**이 있고, 노드 종류·버전, 자격증명 참조, 변수, 하위 워크플로우 등의 요구사항을 표현한다. 다만 패키지 기능은 문서상 Preview 상태야. 따라서 의존성 목록 자체를 발명하는 것이 아니라, 기존 입력을 분석에 활용하는 쪽이 맞아. [n8n Docs](https://docs.n8n.io/build/manage-workflows/n8n-packages/package-format)
    
    n8n의 Workflow Reviews는 특정 버전의 노드·연결을 검토하지만, 자격증명·변수·설정·하위 워크플로우는 그 검토 범위에 포함하지 않는다. **워크플로우 파일의 승인과 실제 배포 구성의 검증 사이에 차이가 있다**는 출발점은 공식 문서로 뒷받침돼. [docs.n8n.io](https://docs.n8n.io/build/manage-workflows/workflow-reviews)
    
    또한 위험한 도구 조합을 분석하는 Toxic Flow Analysis와, 에이전트 코드·설정·권한 위험을 함께 분석하는 Agent Audit도 이미 존재해. 그러므로 “에이전트에 데이터 흐름 분석을 처음 적용했다”는 식의 주장은 피해야 해. [Invariant Labs](https://invariantlabs.ai/blog/toxic-flow-analysis)
    
    **FlowDelta의 연구 기여 후보는 다음 세 가지를 결합하는 데 둬.**
    
    | 기여 후보 | 구체적인 내용 |
    | --- | --- |
    | **에이전트 특화 분석** | 데이터가 이동하는 경로와, 외부 입력이 도구 선택·실행 인자에 영향을 미치는 경로를 구분 |
    | **배포 구성의 보안 변경 분석** | 상위 JSON이 같아도 하위 워크플로우·계정 권한·변수 변경으로 위험이 달라지는지 분석 |
    | **변경 중심 벤치마크** | 위험한 변경뿐 아니라 정상 변경, 분석 불가 변경까지 포함한 재현 가능한 평가 자료 |
    
    이 조합의 학술적 차별성은 관련 연구와 비교해서 검증해야 해. **지금 단계에서는 ‘연구 기여 후보’이지, 최초성이나 논문 채택을 보장할 수 있는 상태는 아니야.**

    # 3. 위협 모델을 명확하게 고정하자
    
    ## 보호할 대상
    
    핵심 자산은 **민감정보, 외부 전송 권한, 업무 시스템 변경 권한, 기존 보안 검토의 신뢰성**이야.
    
    공격자 유형을 지나치게 늘리지 말고, 다음 두 가지를 중심으로 잡는 것을 추천해.
    
    | 공격자 | 변경하거나 통제할 수 있는 것 | 프로젝트가 분석할 위험 |
    | --- | --- | --- |
    | **악성 또는 침해된 공급자** | 배포되는 워크플로우, 제공된 하위 워크플로우, 프롬프트·도구 설정 | 업데이트를 통해 새로운 전송 경로나 실행 권한을 도입 |
    | **외부 콘텐츠 공격자** | 이메일, 웹훅 입력, 문서·도구 응답 등 | 이미 구성된 에이전트의 도구 사용을 공격자에게 유리하게 유도 |
    
    두 번째 공격자는 공급망 공격자와 동일하지 않아. 다만 **공급망 변경이 외부 콘텐츠 공격자에게 새로운 공격 경로를 열어주는지**를 분석하는 데 필요해.
    
    예를 들어 처음에는 외부 이메일을 요약만 하던 에이전트에, 업데이트로 사내 문서 검색과 외부 발송 도구가 추가되는 경우야.
    
    ## 신뢰할 것과 신뢰하지 않을 것
    
    **보안 정책은 워크플로우 제공자가 아니라 도입 조직이 정의한다**고 가정하자. 공급자가 워크플로우와 함께 넣어준 “이 노드는 안전함” 같은 설명을 분석의 사실로 받아들이면 안 돼.
    
    환경 정보도 출처를 구분해야 해.
    
    **운영자 선언**, **수집기가 관측한 사실**, **분석기가 추론한 결과**는 서로 다른 증거야. 이를 하나의 “확인됨”으로 섞지 않는 것이 중요해.
    
    반대로 다음은 핵심 보장 범위에서 제외하자.
    
    **n8n 자체의 미공개 취약점, 운영체제 탈취, 임의 원격 MCP 서버 내부 행동의 완전한 검증, 모델 가중치의 백도어, 악의적인 최상위 관리자.**
    
    이 경계가 있어야 무엇을 탐지하지 못했는지 정직하게 설명할 수 있어.

    # 4. 입력과 지원 범위를 이렇게 정하자
    
    ## 4.1 입력은 파일 하나가 아니라 ‘분석 묶음’
    
    FlowDelta가 분석할 입력은 다음 네 부분으로 구성해.
    
    | 입력 | 포함할 정보 | 주의점 |
    | --- | --- | --- |
    | **워크플로우 묶음** | 상위 워크플로우, 제공된 하위·오류 처리 워크플로우 | 참조된 파일이 없으면 분석 불가로 남김 |
    | **구성요소 정보** | 노드 종류·버전, 커뮤니티 패키지 식별자·해시, 모델·도구 설정 | 식별자가 있다는 사실과 구현을 검증했다는 사실은 다름 |
    | **환경 스냅샷** | 자격증명 연결 관계, 지원 범위 내 권한, 변수, 허용된 목적지 | 실제 비밀키·토큰은 보고서에 저장하지 않음 |
    | **조직 보안 정책** | 민감정보 출발점, 허용 수신자·리소스, 승인 요구사항 | 워크플로우 공급자가 변경할 수 없는 별도 입력 |
    
    n8n의 일반 JSON 내보내기에는 자격증명 이름과 ID가 포함되지만, 그것만으로 실제 계정 권한을 알 수는 없어. HTTP Request 노드에 인증 헤더가 남을 수도 있으므로 입력 파일 자체의 민감정보 처리도 필요해. [n8n Docs](https://docs.n8n.io/build/manage-workflows/export-and-import)
    
    또 패키지를 가져올 때 n8n은 자격증명과 일부 하위 워크플로우 참조를 대상 환경에 맞게 연결한다. 따라서 **원본 패키지를 검사한 결과와, 실제로 어느 계정·워크플로우에 연결됐는지를 함께 봐야 한다**는 요구가 생겨. [n8n Docs](https://docs.n8n.io/build/manage-workflows/n8n-packages/how-import-works)
    
    ## 4.2 모든 n8n 노드를 지원하지 않는다
    
    지원 규모는 **약 20개 안팎의 노드 유형과, 그 안의 명시된 동작·버전 조합**을 목표로 잡자.
    
    “Gmail 노드 지원”처럼 넓게 쓰지 말고, “특정 버전의 메시지 조회·발송 동작 지원”처럼 지원 계약을 정의하는 거야.
    
    | 영역 | 우선 지원 대상 |
    | --- | --- |
    | 입력 | Manual Trigger, Webhook, 제한된 이메일 입력 |
    | 데이터 접근 | HTTP Request, Gmail 조회, 제한된 PostgreSQL 조회 |
    | 변환·분기 | Edit Fields, If, Switch, Merge, Loop Over Items |
    | 코드 | 제한된 JavaScript 표현식과 Code 노드 부분집합 |
    | AI | AI Agent, 채팅 모델 설정, 모델이 채우는 도구 인자 |
    | 도구·출력 | HTTP 전송, 이메일 발송, Slack 메시지, Call n8n Workflow Tool |
    | 의존성 | Execute Sub-workflow, 제공된 하위 워크플로우 |
    | 승인 | 명시적으로 모델링한 n8n 도구 승인 구성 |
    
    실험 대상 n8n 릴리스와 노드 구현은 **태그·커밋·컨테이너 digest로 고정**하자. 지원하지 않는 버전에서 조용히 같은 의미라고 가정하면 안 돼.
    
    MCP는 핵심 범위에서 **연결 설정, 노출 도구 목록, 제공된 도구 메타데이터 스냅샷**까지만 다루는 것이 적절해. 원격 구현까지 분석하는 별도 연구를 붙이지는 말자.
    
    ## 4.3 환경 수집은 좁게, 실제로 구현한다
    
    환경 정보를 전부 사람이 적게 하면 시연이 인위적이고, 모든 SaaS의 실제 권한을 수집하려고 하면 범위가 폭발해.
    
    따라서 **공통 환경 스키마 + 실제 수집기 한 종류**를 추천해. 예를 들어 실험용 PostgreSQL에서 연결 계정과 지정 테이블의 접근 가능 여부를 확인하는 수집기를 구현하는 거야.
    
    이때도 “PostgreSQL의 모든 유효 권한을 완전히 분석한다”고 주장하지 말고, **지정한 리소스·동작·세션 조건에서 확인한 사실**로 한정해.
    
    다른 서비스는 운영자 선언 또는 모의 서비스의 권한 모델을 사용하되, 보고서에서 그 차이를 표시하자.

    # 5. 핵심 분석 엔진
    
    이 프로젝트에서 가장 많은 연구적 깊이를 넣을 부분이야.
    
    ## 5.1 워크플로우를 보안 분석용 중간 표현으로 변환한다
    
    JSON을 직접 순회하면서 규칙을 적용하는 구조 대신, **중간 표현인 IR**을 만들자.
    
    IR에는 최소한 다음 관계를 따로 표현해야 해.
    
    | 관계 | 의미 |
    | --- | --- |
    | **실행 관계** | 어떤 조건에서 다음 노드가 실행되는가 |
    | **데이터 관계** | 어느 출력 필드가 어느 입력·인자로 전달되는가 |
    | **도구 호출 관계** | 에이전트가 어떤 도구를 호출할 수 있는가 |
    | **의존성 관계** | 어떤 하위 워크플로우·설정·패키지에 의존하는가 |
    | **권한 관계** | 해당 동작이 어떤 계정과 리소스 권한으로 수행되는가 |
    
    이 구분은 중요해. **화면에 선이 연결되어 있다는 사실이 곧 특정 필드가 전달된다는 뜻은 아니고, 도구 연결이 곧 반드시 실행된다는 뜻도 아니야.**
    
    n8n에는 이전 노드 참조와 데이터 항목 연결 기능이 있으며, 분할·병합에 따라 항목의 대응 관계가 달라질 수 있어. 따라서 단순한 노드 연결 그래프만으로는 데이터의 출처를 충분히 표현하지 못해. [n8n Docs](https://docs.n8n.io/build/work-with-data/reference-data/link-data-items/how-items-link-through-workflows)
    
    구현에서는 노드별로 **입력 필드, 출력 필드, 외부 효과, 권한 요구사항을 요약한 의미 모델**을 작성하고, 작은 실행 테스트로 그 모델을 확인하도록 하자.
    
    ## 5.2 민감도와 신뢰도를 독립적으로 추적한다
    
    데이터에 붙이는 표시는 최소 두 축이 필요해.
    
    **민감도:** 공개 / 내부 / 기밀 / 미확인
    
    **신뢰도:** 신뢰된 입력 / 외부 비신뢰 입력 / 미확인
    
    예를 들어 공개 웹페이지는 민감하지 않지만 비신뢰 입력일 수 있어. 반대로 사내 계약서는 기밀이지만 그 안의 텍스트를 에이전트의 실행 지시로 신뢰해서는 안 될 수도 있어.
    
    각 값에 대해 **출처, 민감도, 신뢰도, 가능한 값의 범위**를 함께 추적하자. 가능한 값의 범위는 처음부터 복잡할 필요 없이 **상수, 유한한 후보 집합, 미확인** 정도로 시작할 수 있어.
    
    필드 단위로 추적해야 다음을 구분할 수 있어.
    
    > 고객 레코드 전체를 외부로 보내는 경우와, 공개 가능한 상태 코드 하나만 보내는 경우.
    > 
    
    단, “요약”, “인코딩”, “형식 변환”을 했다는 이유만으로 민감도 표시를 지우면 안 돼. **민감도 해제는 별도로 검토한 변환 계약이 있을 때만 인정**하는 설계가 좋아.
    
    ## 5.3 에이전트의 ‘판단 영향’을 별도로 분석한다
    
    이 부분이 일반 자동화 검사와 가장 차별화되는 지점이야.
    
    n8n에서는 모델이 도구 인자를 채울 수 있고, 그 값은 작업의 문맥과 다른 연결 도구의 정보에서 영향을 받을 수 있다. 따라서 수신자·URL·리소스 식별자를 모델이 결정하는 설정은 일반적인 고정값과 다르게 다뤄야 해. [n8n Docs](https://docs.n8n.io/build/integrate-ai/ai-examples/use-ai-for-parameters)
    
    FlowDelta는 다음 두 경로를 구분해야 해.
    
    **내용 전달 경로:**
    
    사내 문서 내용이 이메일 본문으로 전달될 수 있는가?
    
    **판단 영향 경로:**
    
    외부 이메일 내용이 발송 도구의 수신자 선택에 영향을 줄 수 있는가?
    
    에이전트에 대해서는 “모델이 실제로 반드시 이렇게 행동한다”고 예측하지 말자. 대신 **연결된 도구, 접근 가능한 정보, 모델 결정 인자를 바탕으로 가능한 행동을 보수적으로 요약**하는 거야.
    
    따라서 결과도 다음처럼 표현해야 해.
    
    > “외부 입력이 수신자 선택에 영향을 줄 수 있고, 동일 에이전트가 기밀 문서와 발송 도구에 접근할 수 있습니다.”
    > 
    
    이것은 **위험 구조의 발견**이지, 프롬프트 인젝션 성공을 입증한 결과는 아니야.
    
    ## 5.4 제한된 표현식·분기 분석을 구현한다
    
    지원할 JavaScript 부분집합을 명시하자.
    
    **필드 참조, 상수, 문자열 결합, 객체 구성, 단순 조건식**은 분석하고, 임의 함수 호출·동적 코드 실행·복잡한 외부 모듈은 미확인으로 처리하는 식이야.
    
    분기에서는 상수 비교나 유한한 후보 집합처럼 확인 가능한 조건을 활용해, 실행될 수 없는 경로를 일부 제거하자.
    
    반복과 재귀 호출은 무조건 펼치기보다 **요약과 고정점 계산**을 사용하고, 지원 범위를 넘어서는 경우 분석 불확실성을 기록해.
    
    여기서 목표는 전체 JavaScript 검증기가 아니야. **지원하는 부분집합의 의미를 정확하게 정의하고, 지원하지 않는 부분을 숨기지 않는 분석기**야.
    
    ## 5.5 승인 단계가 정말 보호하는지 확인한다
    
    승인 노드가 존재한다는 이유만으로 보호된 경로라고 판단하면 안 돼.
    
    분석할 질문은 다음이야.
    
    **위험한 동작으로 가는 모든 지원 경로가 승인 단계를 통과하는가? 승인된 대상·인자와 실행되는 대상·인자가 일치하는가? 실패·분기·하위 워크플로우 경로에서 우회할 수 있는가?**
    
    n8n 자체에도 특정 도구 호출을 멈추고, 사람이 도구와 인자를 확인한 뒤 승인·거부하도록 하는 기능이 있다. FlowDelta는 승인 기능을 새로 만드는 것보다 **그 보호가 해당 동작에 실제로 연결돼 있는지를 검토하는 역할**을 맡는 게 좋아. [n8n Docs](https://docs.n8n.io/build/integrate-ai/ai-examples/human-in-the-loop-for-tools)
    
    이름이 “승인 확인”인 노드나, 프롬프트 안의 “반드시 승인받아라”라는 문장은 검증된 승인 통제로 인정하지 않도록 하자.

    # 6. 보안 의미를 기준으로 변경을 비교한다
    
    분석 엔진의 결과를 다음처럼 정의할 수 있어.
    
    \[
    \operatorname{Analyze}(B,E,P)=(F,V,U)
    \]
    
    여기서 **B**는 워크플로우·의존성 묶음, **E**는 환경 스냅샷, **P**는 보안 정책이야.
    
    출력 **F**는 분석된 데이터 흐름·실행 능력, **V**는 정책 위반 또는 위험 후보, **U**는 미확인 사항이야.
    
    이전과 이후를 비교할 때는 경고 개수만 비교하지 말고 다음을 구분하자.
    
    | 변경 유형 | 예시 | 기본 처리 |
    | --- | --- | --- |
    | **새로운 정책 위반** | 기밀정보가 허용되지 않은 수신자에게 전달될 경로 추가 | 차단 또는 명시적 검토 |
    | **실행 능력 확대** | 고정 수신자를 모델 결정 값으로 변경 | 영향 분석과 재검토 |
    | **보호 약화** | 승인 우회 경로 추가 | 보호 조건 위반 보고 |
    | **분석 가능성 저하** | 분석 가능한 하위 워크플로우를 미확인 원격 호출로 교체 | 기존 검토 결과 재사용 금지 |
    | **정상적인 변경** | 참조를 유지한 이름 변경, 허용된 데이터 처리 개선 | 불필요한 보안 경고 억제 |
    
    **경고가 줄었다고 안전해졌다고 판단해서는 안 돼.** 분석 가능한 노드를 미확인 코드로 교체하면 경고가 줄어들 수도 있기 때문이야.
    
    ## 변경 대응은 두 가지 해시를 분리해서 처리한다
    
    **원본 산출물 해시**는 정확히 어떤 파일을 검사했는지를 식별하는 데 사용해.
    
    **보안 의미 비교용 표현**은 실행에 영향을 주지 않는 화면 배치 변경 등을 구분하는 데 사용해.
    
    이 둘을 혼합하면 안 돼. 특히 노드 이름은 표현식에서 참조될 수 있으므로, 무조건 비교에서 제외하면 위험해. 이름을 정규화하려면 관련 참조도 함께 해석해야 해.
    
    또 노드 ID가 바뀐 경우에는 구조와 동작을 이용해 대응시킬 수 있지만, **대응이 모호하면 동일하다고 단정하지 않는 것**이 중요해.
    
    ## 검토 결과는 환경과 함께 묶는다
    
    검토 결과에는 최소한 다음이 포함돼야 해.
    
    **검사한 산출물, 의존성, 대상 환경 연결 정보, 정책 버전, 분석기·노드 의미 모델 버전, 미확인 사항, 증거 출처.**
    
    서명은 필요하면 기존 서명 도구와 연동하고, 새로운 암호 프로토콜은 만들지 말자.
    
    CI에서는 이 결과를 바탕으로 배포를 거부할 수 있지만, **별도 편집 화면이나 관리자 경로로 우회할 수 있는 환경까지 통제한다고 주장하면 안 돼.** 배포 통제 시연은 관리된 실험 환경에서 수행하고, 실제 운영에서는 통제 범위를 명시해야 해.

    # 7. 대표 시연은 이렇게 구성하자
    
    ## 시나리오: 외부 문의를 읽는 내부 업무 지원 에이전트
    
    기본 구성은 다음과 같아.
    
    **외부 문의 수신 → AI Agent → 사내 문서 조회 → 내부 지원 메일함으로 요약 발송**
    
    조직 정책은 “기밀 문서는 지정된 내부 수신자에게만 전달하며, 해당 발송은 검증된 승인 경로를 거친다”로 정의하자.
    
    그다음 **동일한 정상 구성에서 서로 독립적인 변경 사례**를 만든다.
    
    | 변경 사례 | 기대하는 분석 |
    | --- | --- |
    | 고정된 내부 수신자를 모델이 결정하도록 변경 | 목적지에 대한 판단 영향이 새로 생김 |
    | 상위 워크플로우는 그대로 두고 발송용 하위 워크플로우 수정 | 의존성 내부에서 전송 경로가 추가됨 |
    | 연결 계정의 접근 가능 리소스 확대 | 이전에 접근할 수 없던 민감정보 경로가 열릴 가능성 |
    | 승인 경로를 거치지 않는 분기 추가 | 보호 조건 우회 |
    | 노드 배치·설명을 바꾸되 동작과 참조는 유지 | 보안 회귀 경고 없음 |
    | 제공된 하위 워크플로우를 미확인 동적 참조로 교체 | ‘안전’이 아니라 ‘검증 불가’로 전환 |
    
    보고서는 다음처럼 읽혀야 해.
    
    > **재검토 필요: 발송 대상에 대한 모델의 결정 범위가 확대됨**
    > 
    > 
    > 변경 위치: 발송 도구의 수신자 설정
    > 
    > 이전: 지정된 내부 수신자
    > 
    > 이후: 에이전트가 결정하는 값
    > 
    > 관련 근거: 외부 문의가 에이전트 문맥에 포함되며, 같은 에이전트가 기밀 문서 조회 도구를 사용할 수 있음
    > 
    > 보호 상태: 해당 발송 경로를 포괄하는 수신자 제한을 확인하지 못함
    > 
    > 판단 수준: 가능한 위험 경로. 실제 모델의 공격 수행 여부는 별도 실행 실험이 필요함
    > 
    
    **위험을 일으킨 변경과 판단의 한계를 함께 설명하는 것**이 핵심이야.

    # 8. 구현 구조와 기술 선택
    
    분석기는 **로컬 실행을 기본값**으로 하고, 분석 중에 워크플로우 코드나 낯선 MCP 서버를 실행하지 않도록 설계하자.
    
    | 구성요소 | 책임 | 제안 구현 |
    | --- | --- | --- |
    | 입력 어댑터 | JSON·지원 패키지 형식 파싱, 참조 수집 | TypeScript, 스키마 검증 |
    | 의미 모델 계층 | 노드·동작·버전별 데이터 전달 및 효과 정의 | 버전 관리되는 노드 계약 |
    | 분석 엔진 | 필드·판단 영향 분석, 분기·하위 호출 요약 | 그래프와 워크리스트 기반 엔진 |
    | 변경 분석기 | 이전·이후 대응, 새 위험과 보호 약화 식별 | 구조 비교 및 분석 결과 비교 |
    | 환경 수집기 | 명시적으로 허용된 대상의 메타데이터 수집 | 코어와 분리된 수집 명령 |
    | 보고·연동 | CLI, JSON, SARIF, 검토용 HTML | 동일한 구조화 결과를 여러 형식으로 출력 |
    | 실험 러너 | 격리된 n8n 실행, 모의 서비스, 결과 관측 | 별도 VM 또는 통제된 실행 환경 |
    | 평가 도구 | 정답 대조, 통계, 비교 실험 | Python 기반 평가 스크립트 |
    
    대형 그래프 데이터베이스나 별도 SaaS 백엔드는 필수로 두지 말자. **분석 엔진 자체가 독립 라이브러리로 동작해야 연구·테스트·CI 연동이 쉬워져.**
    
    CLI의 목표 인터페이스는 다음처럼 단순하게 설계할 수 있어. 아래는 **구현할 인터페이스의 예시**이지, 현재 존재하는 명령은 아니야.
    
    ```
    flowdelta analyze ./bundle --env environment.json --policy policy.yaml
    flowdelta compare ./before ./after --env-before env-old.json --env-after env-new.json --policy policy.yaml
    flowdelta verify ./bundle --report review.json
    ```
    
    보안 도구 자체의 방어도 구현 범위에 넣어야 해. **압축 해제 경로 탈출, 과도한 중첩·파일 크기, 파서 자원 고갈, 보고서 HTML 삽입, 로그의 비밀정보 노출**을 테스트하자.
    
    실행 실험은 정적 분석 프로세스와 분리해야 해. n8n 공식 문서도 작업 실행기의 격리와 강화 설정을 별도로 다루고 있으므로, 컨테이너를 썼다는 사실만으로 충분한 격리라고 간주하지 않는 게 맞아. [n8n Docs](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/harden-task-runners)

    # 9. 데이터셋을 프로젝트의 주요 결과물로 만든다
    
    분석기만큼 중요한 결과물이 **FlowDeltaBench라는 변경 중심 벤치마크**야.
    
    ## 9.1 제안 규모
    
    | 구성 | 목표 규모 | 목적 |
    | --- | --- | --- |
    | 공개 워크플로우 구조 코퍼스 | 중복 계열 제거 후 약 200개 | 현실적인 노드·표현식·의존성 분포와 분석 범위 확인 |
    | 정답을 검토한 기준 워크플로우 | 약 80개 | 정책과 환경이 명확한 기준 사례 |
    | 변경 쌍 | 약 480쌍 | 기준 사례마다 위험 변경 3개, 정상 변경 3개 |
    | 미확인·경계 사례 | 약 40개 | 동적 참조, 지원하지 않는 코드, 누락 의존성 처리 |
    | 실행 재현 사례 | 약 40쌍 | 정적 결과와 실제 실행의 관계 확인 |
    
    공개 워크플로우는 **정상이라고 가정하지도, 무단으로 실행하지도 않아야 해.** 출처·라이선스·수집 버전·수정 내역을 기록하고, 재배포 가능한 범위만 공개하자.
    
    이 숫자들은 목표야. 변경을 넣었다고 자동으로 위험 사례가 되는 것은 아니므로, 실제로 정책 위반이 성립하지 않는 변형은 정답을 수정하거나 제외해야 해.
    
    ## 9.2 정상 변경을 어렵게 만들어야 한다
    
    음성 사례를 노드 위치 변경만으로 채우면 평가가 약해져.
    
    **동작을 유지한 하위 워크플로우 분리, 참조를 보존한 이름 변경, 이미 허용된 목적지 사이의 변경, 불필요한 민감 필드 제거, 동등한 분기 재구성**도 넣자.
    
    그래야 “많이 바뀌면 위험하다고 경고하는 분석기”와 실제 보안 의미를 이해하는 분석기를 구분할 수 있어.
    
    ## 9.3 정답은 분석기의 출력과 독립적으로 만든다
    
    각 사례에는 **보안 정책, 공격자 통제 범위, 위반 위치, 성립 조건, 근거 또는 실행 증거**를 붙이자.
    
    두 명이 독립적으로 검토하고 의견이 다른 사례는 조정해. 모호한 사례는 억지로 안전·위험 중 하나에 넣지 말고 별도로 관리해야 해.
    
    개발·검증·최종 평가 분리는 **워크플로우 원본 계열 단위**로 해야 해. 같은 원본에서 만든 변형들이 서로 다른 분할에 들어가면 구조를 외운 효과가 섞일 수 있어.
    
    ## 9.4 실행 재현은 무엇을 증명하는지 구분한다
    
    모의 메일함·문서 저장소·전송 서버와 합성 데이터를 사용하자. 유출 여부는 지정한 테스트 데이터가 모의 수신 지점에 도착했는지 등으로 판정할 수 있어.
    
    여기서 두 종류의 실험을 구분해야 해.
    
    **도구 호출을 고정한 재현:** 해당 위험 동작이 구성상 가능한지 확인.
    
    **실제 모델을 사용하는 재현:** 특정 모델·공격 입력·설정에서 그 행동이 유도되는지 확인.
    
    전자가 성공했다고 “실제 프롬프트 인젝션 성공률”로 발표하면 안 돼. 반대로 모델 실험에서 공격이 실패했다고 구조적 위험이 없다고 결론 내려서도 안 돼.
    
    AgentDojo도 에이전트의 정상 작업 수행과 공격·방어를 함께 평가하는 환경을 제공하므로, 이 평가 원칙은 참고할 가치가 있어. 다만 그 데이터셋을 n8n 변경 분석의 정답으로 그대로 대체할 수는 없어. [arXiv](https://arxiv.org/abs/2406.13352)

    # 10. 실험 질문과 성공 기준
    
    ## 반드시 비교해야 하는 기준선
    
    | 기준선 | 비교 이유 |
    | --- | --- |
    | **위험 노드·설정 규칙 검사** | 단순 검사보다 무엇을 추가로 발견하는가 |
    | **일반 JSON 변경 + 규칙 검사** | 구조적 변경 탐지만으로 충분한가 |
    | **전체 재분석 후 경고 차집합** | 별도 보안 변경 분석의 실질적 가치가 있는가 |
    | **노드 단위 단일 흐름 분석** | 필드 구분과 에이전트 판단 영향 구분이 도움이 되는가 |
    
    특히 **‘전체 재분석 후 경고 차집합’은 빼면 안 돼.** 이 기준선과 비교하지 않으면 기존 분석기를 두 번 돌린 것과 무엇이 다른지 설명하기 어려워.
    
    n8n 기본 감사와 비교한다면, 양쪽이 공통으로 검사할 수 있는 항목만 비교하자. 기본 감사는 자격증명 사용 상태, SQL 표현식, 파일 접근, 위험 노드, 인스턴스 설정 등을 다루므로 전체 목적이 FlowDelta와 같지는 않아. [n8n Docs](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/run-security-audits)
    
    ## 연구 질문
    
    **RQ1.** 필드 단위 분석과 에이전트 판단 영향 분석이 단순 노드 그래프보다 정확한가?
    
    **RQ2.** 환경·하위 의존성을 포함하면 상위 워크플로우만 분석할 때 놓치는 위험 변경을 발견하는가?
    
    **RQ3.** 변경 영향 중심의 재분석이 전체 재분석과 같은 결과를 유지하면서 분석량과 검토 부담을 줄이는가?
    
    세 번째에서는 **정확도가 더 높아야 한다고 요구하는 것이 아니라, 같은 의미 모델에서 결과가 일치해야 한다**는 점이 중요해.
    
    ## 제안하는 정량 목표
    
    | 지표 | 설계 목표 |
    | --- | --- |
    | 지원 범위 내 위험 변경 정밀도 | 90% 이상 |
    | 지원 범위 내 위험 변경 재현율 | 85% 이상 |
    | 정상 변경 쌍의 오탐률 | 5% 이하 |
    | 미확인 사례 처리 | 미확인을 무경고 정상 결과로 처리하지 않음 |
    | 분석 결과 설명 | 모든 경고에 규칙·위치·근거 경로·가정 포함 |
    | 성능 | 명시한 시험 장비에서 총 100노드 수준 사례의 정적 분석 P95 10초 이하 |
    
    이 목표를 위해 지원 범위를 사후에 유리하게 바꾸면 안 돼. **지원·미지원 비율, 전체 코퍼스 결과, 지원 범위 내 결과를 함께 보고**해야 해.
    
    정밀도와 재현율 외에도 **얼마나 많은 입력을 끝까지 분석하지 못했는지**가 중요한 결과야. 미확인이 많은 분석기는 일부 사례에서 정확하더라도 실용성이 낮을 수 있어.
    
    구성요소 제거 실험도 넣자. 환경 정보, 하위 워크플로우 분석, 필드 구분, 판단 영향 구분을 각각 제거해서 **어느 설계가 실제 개선을 만들었는지** 확인하는 거야.

    # 11. 4명 역할 분담
    
    프런트엔드 한 명, 백엔드 한 명처럼 나누기보다 **각자 연구적으로 의미 있는 모듈을 소유하도록** 나누는 것이 좋아.
    
    | 담당 | 주 책임 | 독립적으로 남길 결과물 |
    | --- | --- | --- |
    | **A: 실행 의미·IR** | n8n 입력 어댑터, 노드 의미 모델, 표현식·항목 연결, 하위 호출 해석 | IR 명세, 노드 계약 라이브러리, 의미 모델 검증 테스트 |
    | **B: 보안 분석 엔진** | 민감도·신뢰도 추적, 판단 영향, 분기·승인 분석, 정책 판정 | 분석 알고리즘, 지원 부분집합 명세, 정확성 논증 |
    | **C: 변경·환경 검증** | 버전 대응, 환경 스냅샷, 보안 의미 비교, 검토 결과 결합, CI | 변경 분석기, 환경 수집기, 검토 결과 형식과 배포 검증 |
    | **D: 벤치마크·실행 검증** | 코퍼스·변형 생성, 모의 서비스, 실행 재현, 기준선·통계 | FlowDeltaBench, 재현 러너, 비교 실험 |
    
    D를 단순 테스트 담당으로 두면 안 돼. **변경 벤치마크와 실행 판정 체계도 주요 연구 결과물**이야.
    
    정답 검토는 네 명이 교차 수행하고, 각자 만든 의미 모델을 다른 사람이 검증하게 하자. 보고서 UI는 구조화된 결과를 보여주는 얇은 계층으로 유지해 특정 인원이 UI에만 묶이지 않도록 하는 편이 좋아.

    # 12. 최종 범위와 완료 조건
    
    ## 반드시 완성할 것
    
    핵심 결과물은 **분석 엔진, 보안 변경 분석기, 환경 스키마와 수집기 한 종류, CLI·검토 보고서, 변경 벤치마크, 격리된 재현 환경**이야.
    
    여기에 위협 모델, 지원 범위, 실패 사례를 포함한 기술 보고서를 묶으면 하나의 완결된 보안 연구 프로젝트가 돼.
    
    ## 확장 후보로 남길 것
    
    **추가 SaaS 권한 수집기, 추가 n8n 릴리스 지원, MCP 메타데이터 변경 비교의 정교화, 검토자 대상 사용성 실험**은 확장 후보로 두자.
    
    반대로 **다중 워크플로우 플랫폼 지원, 범용 JavaScript 분석, 모든 MCP 구현 검사, 상용 런타임 방화벽, 자체 LLM 학습, 대형 SaaS 관리 화면**은 핵심 범위에서 빼는 것을 추천해.
    
    ## 프로젝트가 완성됐다고 말할 수 있는 상태
    
    최종적으로 다음 장면이 재현되어야 해.
    
    > 사용자가 워크플로우 업데이트와 대상 환경 정보를 제공한다.
    > 
    > 
    > FlowDelta가 새로운 위험과 그 원인이 된 변경을 찾아낸다.
    > 
    > 검토자는 어느 경로가 문제이며 무엇을 확인하지 못했는지 이해한다.
    > 
    > 수정 후 같은 분석을 다시 수행하면 위험이 해소되었는지 확인할 수 있다.
    > 
    > 이 결과의 정확성과 한계가 독립된 데이터셋·기준선·실행 실험으로 뒷받침된다.
    > 
    
    **이 프로젝트의 중심은 ‘AI 보안 점수를 매기는 도구’가 아니라, ‘워크플로우의 어떤 변경이 어떤 보안 가정을 깨뜨렸는지 근거를 제시하는 도구’야.** 그 한 가지를 깊이 있게 구현하는 것이 4인 연구팀의 역량을 가장 잘 드러내는 방향이라고 판단해.
