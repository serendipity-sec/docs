# 후보 1 컨셉 v2 — "AI가 만든 앱이 내가 의도한 대로 동작하는가"

작성 2026-09-20 · 김민우 · A·B·C 실험 결과를 반영한 컨셉 발전안 · 제안

> v1(한 장)은 "발견→이해→수정→재검증 흐름"을 팔았고, 실험(A)에서 그 흐름은 기존 도구에도 있다고 나왔다.
> v2는 **AI 코딩의 구조적 약점 하나**에 제품을 세운다: **AI는 당신 머릿속의 규칙을 모른다.**

---

## 1. 논지 — 의도와 구현 사이의 틈

바이브코딩 앱 취약점 1,186건을 원인별로 나눈 논문(Deng 외, 2026-09)의 8가지 실패 모드 중 상위 4개:

| 실패 모드 | 건수 | 뜻 |
|---|---:|---|
| **Hidden security rules** | **658 (55%)** | 사용자가 말하지 않은 암묵적 규칙을 AI가 몰랐다 ("예약은 작성자만 수정" 같은 것) |
| Demo-oriented design | 174 | 시연이 되게 만드는 데 최적화 |
| Incomplete change propagation | 110 | 한 곳에만 보호를 넣고 다른 경로엔 안 넣음 |
| Function-fix side effects | 100 | 기능 고치다 방어를 약화 |

**절반 이상이 "규칙을 몰라서"다.** 사용자는 "회원가입·예약·취소 되게 해줘"라고 시켰지, "다른 사람 예약은 못 건드리게"라고는 안 한다. 그건 사람에겐 너무 당연해서 말을 안 하고, AI는 안 들은 건 안 한다.

C 실험이 정확히 이걸 재현했다 — 기능만 요구한 예약 앱에서 **A가 B의 예약을 조회·변경·취소**, 무인증 관리자 조회, 평문 비밀번호.

기존 스캐너(ZAP·Semgrep·Ship Safe)가 A에서 소유권 문제를 **하나도 못 잡은 이유도 같다** — 스캐너도 "A와 B가 다른 사람이어야 한다"는 규칙을 모른다. 코드 패턴만 본다.

**→ 제품의 일은 단 하나: 사용자 머릿속의 규칙을 꺼내서, 앱이 그 규칙대로 도는지 실제 요청으로 확인하고, 안 맞으면 AI에게 다시 가르친다.**

## 2. 사용자 경험 — 화면 6개

가상 사용자: **지영**, 동아리 총무. Lovable로 시설 예약 앱을 만들었다. 잘 돌아간다. 공개하기 전에 불안하다.

### ① 등록
저장소 URL 또는 zip. (첫 학기: FastAPI/Express + SQLite — C에서 쓴 조합. 우리가 컨테이너로 띄운다.)

### ② 규칙 선언 — **이 화면이 제품이다**
AI가 코드를 읽고 초안을 뽑아준다. 지영은 맞는지만 확인한다.

```
발견한 역할:   회원 · 관리자
발견한 자원:   예약 · 회원정보
규칙 초안:
  ☑ 예약은 만든 회원만 조회·수정·취소할 수 있다
  ☑ 관리자만 전체 예약을 볼 수 있다
  ☑ 로그인하지 않으면 예약 기능을 쓸 수 없다
  ☐ (추가) ...
```
지영이 한 번도 AI에게 말하지 않았던 규칙이 **여기서 처음 글이 된다.** 이게 "Hidden security rules"를 드러내는 순간이다.

### ③ 검사
규칙마다 테스트 계정 2개(A·B)를 만들어 실제 요청을 보낸다. "A가 B의 예약을 GET/PUT/DELETE", "무인증으로", "일반회원이 관리자 경로로".
시크릿·취약 라이브러리·XSS 같은 패턴 문제는 **ZAP·Semgrep을 붙여서** 처리한다. 우리가 만들지 않는다.

### ④ 결과 — 경고 목록이 아니라 이야기
```
✗ 규칙 1 위반 — "예약은 만든 회원만"
   민수(회원 A)가 지영(회원 B)의 예약 #2를 취소했습니다.
   요청:  DELETE /reservations/2   (A의 세션으로)
   응답:  200 → 예약 상태가 CANCELLED로 바뀜
   원인:  app.py 157행 — 예약 ID만 보고 삭제. 누구 것인지 확인 안 함
   AI가 왜: 화면에서 "내 예약"만 보이니 서버에서도 내 것일 거라 가정 (추정)
```
심각도 점수 대신 **누가 무엇을 할 수 있었나**. 브라우저 화면 캡처도 같이(시연용).

### ⑤ 수정 — 바이브코더답게, 프롬프트로
세 가지를 준다. 지영은 코드를 안 고친다. AI에게 다시 시킨다.

1. **수정 프롬프트** — "당신의 AI 도구에 그대로 붙여넣으세요":
   > 예약 조회·수정·취소 API에서 요청한 회원의 ID와 예약의 user_id가 다르면 403을 반환하도록 고쳐줘. 관리자(is_admin)는 예외. 기존 기능은 그대로 유지해.
2. **패치** — 직접 볼 사람용 (C의 security-fix.patch가 이 형태)
3. **★ 프로젝트 보안 규칙 파일** — `CLAUDE.md` / `AGENTS.md`에 붙일 조각:
   > 이 프로젝트에서 예약은 작성자와 관리자만 접근한다. 모든 예약 API는 소유권을 서버에서 확인한다. 비밀번호는 평문 저장 금지.
   → **다음에 기능을 추가할 때 AI가 같은 실수를 안 하게 한다.** 한 번 고치는 게 아니라 가르친다.

### ⑥ 재검증 → 공개 준비도
같은 규칙 테스트 재실행. **A→B는 403, B 본인은 200** (C에서 23항목 통과한 그 대조). 규칙별 통과/실패/미검사 + "우리가 못 본 것"을 적은 리포트.

## 3. "우와" 장면 3개 (발표 순서)

| # | 장면 | 왜 먹히나 |
|---|---|---|
| 1 | 브라우저에서 A로 로그인 → B의 예약이 **눈앞에서 사라진다** | curl이 아니라 화면. 보안 모르는 사람도 안다 |
| 2 | 지영이 우리 프롬프트를 Lovable에 붙여넣음 → 30초 뒤 재검사 → **초록** | "코드 못 고치는 사람이 고쳤다" |
| 3 | 규칙 파일을 넣고 **새 기능**(예: 예약 시간 변경)을 AI에게 시킴 → 처음부터 소유권 검사가 들어가 있다 | 재발 방지. 논문 §7이 규칙 지시로 취약 54→25/210 감소를 실측 — 우리는 그걸 제품 안에서 보여준다 |

3번이 최종발표의 클라이맥스다. 중간발표는 1·2까지.

## 4. 기존 조사와 어떻게 이어지나 — 버린 게 아니다

| 기존 조사 | v2에서의 자리 |
|---|---|
| AGENTS.md·CLAUDE.md 표준화(저장소 6만+) | **⑤-3 규칙 파일**의 출력 형식. 우리가 조사한 그 표준에 쓴다 |
| Rules File Backdoor(ENISA), Check Point CVE | "규칙 파일은 힘이 세다"의 반대 방향 근거 — 같은 메커니즘을 방어에 씀 |
| capability(무엇을 할 수 있는가) | 규칙 = "누가 무엇에 무엇을 할 수 있는가". 대상이 스킬에서 **앱의 사용자**로 바뀌었을 뿐 같은 질문 |
| 스캐너 불일치·우회 연구 | "패턴 스캐너는 못 잡는 게 있다"의 근거 → ③에서 ZAP·Semgrep은 붙이되 의존하지 않는 이유 |

발표 도입부 문장이 자연스럽게 나온다: *"저희는 AI 에이전트가 읽는 설정 파일의 보안을 조사했습니다. 그러다 반대 질문을 만났습니다 — AI가 만든 결과물은 안전한가."*

## 5. 만든다 / 안 만든다 (첫 학기)

| 만든다 | 안 만든다 |
|---|---|
| 규칙 초안 추출 (LLM 보조 + 사용자 확인) | 범용 취약점 스캐너 (ZAP·Semgrep 연동) |
| 관계 기반 테스트 생성·실행 (2계정, 소유권·인증·관리자) | XSS·SQLi·CSRF 자체 탐지 |
| 이야기형 결과 + 코드 위치 | 자동 패치 적용 (제안만) |
| 수정 프롬프트 · 패치 · 규칙 파일 3종 출력 | 프론트엔드 취약점 |
| 재검증 + 회귀 저장 + 준비도 리포트 | 실서비스 URL 스캔 (저장소/zip만, 컨테이너 격리) |
| 지원: FastAPI · Express + SQLite | 다른 프레임워크·DB |

## 6. 평가 — 세 질문

| 질문 | 방법 | 지표 |
|---|---|---|
| 규칙 테스트가 소유권 문제를 잡는가 | 우리가 생성한 앱 N개(모델 3종 × 회차) + 안전 대조 앱 | 규칙별 탐지율·오탐, 대조군 오탐 0 확인 |
| 초보가 혼자 고치는가 | 초보 6~10명, ZAP 보고서만 vs 우리 흐름 | **수정 완료율 · 시간 · 틀린 수정 수 · 기능 회귀** (B의 지표) |
| 규칙 파일이 재발을 막는가 | 규칙 파일 있/없이 같은 기능 추가 재생성 | 취약 발생률 (Deng §7 방식 재현) |

## 8. 아직 답 없는 것 — 5주차 설계에서 결정

- **남의 앱을 안전하게 띄우기**: 컨테이너, 네트워크 차단, 자원 제한. 이게 우리 서비스 자체 보안 점검(12주)의 핵심이 된다
- **규칙 초안을 LLM이 뽑으면 틀릴 수 있다**: 사용자 확인 단계가 필수인 이유. 오탐률 측정 필요
- **테스트 계정 자동 생성**: 가입 API 형태가 앱마다 다름. 첫 학기는 "가입 엔드포인트를 알려달라"로
- **Autorize·Shannon 실측 비교**: 아직 안 돌렸다. ②·⑤가 진짜 다른지는 이걸로 확인
- **C 원본이 기능부터 깨졌던 문제**: 상용 도구(Lovable·Claude Code)로 재생성해 "기능은 되는데 규칙은 모른다"를 확인해야 시연 문장이 성립
